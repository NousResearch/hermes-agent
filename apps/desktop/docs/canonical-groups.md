# Gateway-owned group chats in Desktop

There is one kind of new group chat: a **gateway group chat** (the gateway owns its log and runs its turns, with Desktop open or closed; `canonical-group*` in `src/plugins/hermes-bots/`), whether its bots are on one computer or several. A **classic group chat** (Desktop runs its rounds; `group-*`) is only an older record already on disk: it keeps its history and composer, but Desktop never creates a new one.

The Bots roster lists the selected connection/profile's gateway rooms as ordinary Group Chat rows beside legacy renderer rooms. The list keeps itself current (a poll, every socket or source change, and right after a create or disband here); a failed read keeps the last good list and never shows transport text. Opening a room binds and captures that exact authority; changing the foreground profile does not retarget its controls.

## Which group chats are gateway group chats

One classifier, `groupExecutionMode`, reads `groups.capabilities`. The gateway (`hermes_agent/gateway/session_group_controls.py`) answers directly or through the server used by remote connections (`hermes_agent/tui_gateway/methods_groups.py`); a standalone server may instead own its own group chats.

- **Gateway group chats:** an answer with `driver: true`, from either surface. Both run their own group chat driver, so these group chats keep working while Desktop is closed. An answer without a running driver is unavailable (below), but a group chat Desktop has already bound (opened from the gateway list, or earlier in this session) still opens and says its group driver is unavailable.
- **Classic group chats through the migration gate:** only a server that reports no group chat driver and owns no group chats (`driver: false`, `persistent_process: false`), as on `main`. Desktop runs those group chats itself; no other capability answer makes the gate fall back to it. A group chat already routed to a Desktop-driven workspace does not enter this gate.
- Anything else is unavailable, and the gate says why and offers **Retry**: a server without the group surface (`-32601`) or with an answer Desktop can't read is too old for group chats (update Hermes on that computer and reconnect); an answer whose driver isn't running asks to restart or update Hermes there; a transport error, or a socket that isn't open, could not reach the gateway.

A gateway group chat offers a control only when the answer's `methods` lists its method: Stop (`groups.stop`), Discard (`groups.discard`), Retry (`groups.retry`), Allow and Deny (`groups.approve`), file upload and download, including pasted or dropped files and inline image previews (`groups.attachment.upload`, `groups.attachment.download`), Rename (`groups.rename`) and Disband (`groups.disband`). Current standalone servers support attachments. A standalone-owned group chat does not advertise `groups.discard`; when a gateway owns the group chat, the standalone server forwards its group chat methods and advertises the methods the owner offers. Older standalone servers without attachment methods still hide upload and disable **Download**. For a group chat on the foreground connection, the list holds for one opening of that gateway socket: an update restarts the gateway, so when the socket reopens the list is read again, and a reply that started before the socket changed is dropped. Until a read for the current opening succeeds none of these controls is offered, and a failed read is tried again every two seconds while the group chat is visible; a successful answer without a method list keeps them all. A group chat on another connection retains its own list until reopened; changes to the foreground socket do not invalidate it.

New group chat retains the union picker, device badges and `seatableGroupBots` rules. `groupCreationEngine` is the single decision point and only ever plans a gateway-owned group chat: same-connection members use `gateway`; a mixed selection uses `gateway-peer` when its owner and every lender meet the requirements below. Otherwise the plan is `unavailable` with the missing piece and the computer it is on (`owner_update_required` for a gateway too old to run group chats, `peer_owner_unavailable` for an owner that cannot seat peers, a lender's `room_link` refusal, an unreachable lender, a changed installation, a missing route); the dialog says it in words, keeps the draft, disables Create and offers Retry. Nothing falls back to a Desktop-driven group chat, on any gateway. Pending checks disable Create. A selection of bots all on one other connection keeps the switch-connection guidance. The complete plan is read again before creation. If capabilities changed, the displayed plan refreshes and the person presses Create again to accept the new choice.

Gateway records extend the existing `engine` field with `{kind: 'gateway', connectionId, profile, roomId}`. This local owner record survives storage, hydration, membership edits and rename; name reopening checks its complete identity before accepting a cached binding. A canonical key opens its own connection, profile and group chat ID. Other Desktops discover gateway-owned group chats through `groups.list`; these owner records are not published through the ui_meta mirror. A mirrored Desktop group chat with a conflicting identity leaves the local gateway record unchanged. Creation never adopts a record by name: a collision gets a free local name without changing the other group chat. Confirmed Disband retires the matching local owner record so its name can be reused. Losing a peer never changes the engine. Existing Desktop-driven group chats (`engine: 'desktop'`, or an unmarked older record whose members span connections) are not converted: they keep their history and composer, and a membership edit keeps them Desktop-driven. No edit makes a group chat Desktop-driven that was not already.

## Including bots on other gateways

Desktop creates the group chat on its owner, invites each peer on its own gateway, then registers the pinned catalog, endpoint and grant on the owner. Grants remain transient in Desktop. New group chat retains one creation ID and wire payload while retrying an unchanged name and bot selection after an uncertain result, and says in the dialog that trying again is safe. Acknowledgement or refusal ends the intent. A changed selection or a newly opened dialog starts a new intent. Once created, a gateway-owned group chat is never replaced by a courier fallback: interrupted setup leaves the same group chat with an unjoined member. A member without a stored route shows **not joined**, **Retry**, and **Start new group chat without X** (a separate group chat; Disband of the original is requested only after every replacement bot has joined). A stored route marked `unavailable` instead shows **offline**: the last attempt could not reach its computer, and the next message to it tries again. A stored route with expired access shows **access expired**. Retry for a stored route appears only when this Desktop has a matching connection to that computer; starting a new group chat without the member stays available when at least two members remain. These banners and buttons share the message column’s width and margins. Disband waits for every member’s confirmed Stop and revokes peer access at each member gateway before ending the original. After an uncertain registration reply, Desktop reads the new group chat’s own state once. A ready member counts as a confirmed first join; an already registered route does not prove renewed access. If that read cannot confirm joining, Desktop says so, keeps both group chats and gives no instruction to use a Retry that might not be there. Confirmed join failures name the bot and keep both group chats without requesting Disband; use Retry in the new group chat if offered, then Disband the original when ready. If Disband is refused, Desktop explains why and keeps both group chats; Disband can be tried later. Start new group chat without X keeps one creation ID and payload in memory for that original and removed bot while its create reply is uncertain. Pressing it again while creation is uncertain resends the same request. A late completion can clear only its own current intent, including across view remounts. Acknowledgement or refusal ends the intent; using the action again afterwards deliberately creates another group chat. The new group chat has an ordinary owner record and its own Retry. The uncertain intent survives socket reconnects, capability refreshes and closing the original view in this window. It is never saved to disk or shared between windows, and restarting Desktop loses it. New group chat also retains its draft and uncertain intent through a socket reconnect while its dialog remains open. Closing and reopening that dialog deliberately starts a fresh draft and intent; check the gateway’s group chat list first if the earlier create may have succeeded. This is separate from the driver's preparation-stall Retry. Retry finds a connection matching the pinned installation and catalog; ordinary failures never revoke a working scope. Connection kind (SSH, URL or otherwise) is not an eligibility rule; advertised capabilities are.

Invitations allow dispatch for one day and request a 30-day renewal horizon only when advertised. While a group chat is open, Desktop re-seats joined peers after 20 hours or on the first open after restart; only an acknowledged registration makes renewed access fresh. Failed or unconfirmed renewals retry after five minutes, and a newly loaded connection retries immediately. A Send is journaled before waiting up to 45 seconds for renewal, and Stop still holds that Send back. The owner can renew on dispatch only while the current grant remains dispatch-valid. There is no Desktop background renewal loop: after more than a day idle, open the group chat with a reachable lender or use Retry. Re-seating does not revoke earlier grants; they expire or are covered by the gateway's scope revocation.

These owner/lender rules apply to the canonical gateway (`hermes gateway run`), including when `hermes serve` forwards Desktop’s group calls to it. The home must report `driver: true`, `persistent_process: true` and `groups.peer.register` in `groups.capabilities.methods`; it does not need its own `room_link.enabled`. Each member must route consistently to one profile its gateway serves (any served profile, not only `default`; a named profile that inherits the gateway’s `room_link_url` is reached at its `/p/<profile>` mirror). That gateway must report `room_link.enabled: true` and list `groups.peer.invite` in `methods`, with a compatible text-only persistent catalog, matching installation identity and an advertised endpoint reachable from the owner (see [the Bot Mode guide](../../../website/docs/user-guide/bot-mode.md#bots-from-another-gateway-in-a-gateway-owned-group-chat)). Standalone `hermes serve` answering for its own group chats derives `persistent_process` from its lending catalog and skips API-server and endpoint checks for `room_link`; clients should not use it as a home for gateway-owned group chats.

Approvals from bots on another gateway use the same pending-action cards. The home accepts `once` or `deny` and answers the exact observed prompt using the lender’s run generation.

A classic group chat that reaches `GroupExecutionGate` on a gateway connection is first looked up by name in `groups.list`; a match opens that gateway group chat. Otherwise the gate says what happened, why, what to do and what happens to the earlier messages. These rules apply to group chats that reach the gate, not to group chats already routed to a Desktop-driven workspace.

- Bots that can form a gateway group on this connection: the gate offers **Start new group**, a fresh gateway group chat with the same bots that keeps working when Desktop is closed. Earlier messages are not copied into it.
- Bots on other connections, or on several (some here, some elsewhere): the gate names those connections and says to switch to the connection where the bots run and start a group there, or to start a new group chat with bots from this connection.
- Bots here that cannot form a gateway group as they are (two to six bots, distinct profiles and handles, `@all` and `@everyone` reserved): the gate gives the reason and says to start a new group chat and choose its bots.
- A failed lookup offers **Retry**.

Under the gate, a classic group chat's earlier messages stay readable, read only and inert, like gateway group chat history below: no `MEDIA:` path, Markdown image, file link or directive card resolves, rich fences show their source, and only an explicit web link to a public host opens, on a click. They stay on this Desktop.

## The group chat workspace

The gateway owns the log and the work. Desktop polls `groups.state` and `groups.log` every two seconds while the group chat is visible. It reads the log after the last event it showed, and from the start again when the group chat's `authority_epoch` changes.

- **Status:** the native group chat header keeps per-member live chips (tool, elapsed time and outcome), the transcript keeps its typing rows and threaded replies, and the composer keeps the round strip. Beside the roster, the group chat summarizes what it waits on: a blocked group chat (a stopped task that is still settling is not a block), approvals, and other pending actions. A gateway whose driver is down sends no driver status; the group chat then says its group driver is unavailable. A failed member never hides the others' live work.
- **Send** uses the native prepared-submission journal: one unresolved intent per group chat, shared by every Desktop window and written with compare-and-set. The entry counts the requests that may have posted its intent: one more is written before each request leaves, one less when the gateway proves that request posted nothing. Both gateway surfaces give that proof by marking a refusal `admitted: false` (on `4001`, `4111`, `4123` or `5112`), and only for a refusal raised before the user event commits or a Send no driver or worker could take; a code or reason alone proves nothing. Main already returns the committed event when preparing the group chat fails afterwards, and its driver reports persistent preparation failure with Retry; this PR preserves that recovery. At zero the words come back for editing, and the journal keeps them until a Send replaces them, so a group chat closed meanwhile shows them again when it reopens. Any other outcome (an unmarked refusal, a timeout, an unconfirmed reply) keeps the intent for **Retry**, which resends the same `event_id`; the gateway recognizes it, so it is never posted twice. A Send is delivered only by a receipt whose `client_event_id` is this intent's (and `accepted: true` when present); a failed journal cleanup after that receipt is retried before this window's next Send. When another window holds the group chat's intent, Send sends that one first and puts this window's words and reply thread back afterwards; a refused intent handed back for editing keeps its own thread; an intent another window finished with is neither resent nor offered as a new message. If the journal cannot be read, Send stays locked and **Try loading again** reads it again without writing.
- **Stop** (`groups.stop`) remains a header icon shown while the group chat works, a Send is in flight or Stop is still settling. It has its own pending state, so it works while a Send is in flight. It keeps one `cancel_id` until the gateway returns its cancellation count. That count can include turns still stopping and excludes deferred turns whose Stop is unconfirmed, so it can be zero. The notice and history say Stop was requested; unconfirmed turns stay visible with the actions the gateway offers. The footer also says Stop requested until the gateway reports no live work, pending actions or unfinished task counts. Only then can it say Stopped. Stop also covers a Send in flight: one not yet sent is held back with its words kept; one on the wire is fenced again under a fresh `cancel_id` once it settles, unless the gateway proved it posted nothing. The next Send waits until the last Stop fence finishes.
- **Retry, Discard and approvals** come only from `driver_status.pending_actions` and send the exact member, task, generation and request identity. The native pending-action cards keep their bot names and avatars. An approval shows its description and its command; only the choices the gateway offered appear, and **Allow once** needs this exact request with a real command, or with the description a synthetic tool label stands for (a plugin approval rule sends `<tool> (plugin approval rule)`, as in the chat approval card). Discard asks first: side effects are not undone. A deferred turn on another local profile offers only Retry; Discard for a local member is limited to an indeterminate turn. Every deferred peer turn can offer Discard, with or without a saved run receipt; Desktop follows the offered action without inspecting receipts. Discard never starts the turn: the member confirms that its admission key is closed (settling it immediately) or that its existing run has stopped. A `session_busy` refusal keeps the turn and asks the person to try Discard again when the member’s computer is answering. A `peer_unreachable` refusal keeps it and asks them to reconnect the member’s computer, unless `error.data.detail` says the member is too old to confirm it never started; that refusal asks them to update Hermes on that computer, then try Discard again.
- **Attachments** upload with `groups.attachment.upload` and download with `groups.attachment.download`.
- **Rename** (`groups.rename`) sends the trimmed new name from the group chat header. **Disband** (`groups.disband`) asks through a confirmation dialog, which stays open with the error when the gateway refuses; if a member gateway is unreachable or still stopping, the group chat and its owner record stay available for another attempt. A `member_home_unknown` refusal asks to restore the missing bot profile in `hosted_rooms.profiles` on the computer running the group chat, so its Stop can be confirmed before retrying Disband. Older gateways and unknown reasons keep the existing fallback. A Stop-pending refusal says the bots have not all confirmed they stopped; try Disband again once they have, or use Retry or Discard on a waiting turn if offered in the group chat. Typed refusals also explain a Disband that needs another attempt (including one still in progress or waiting on late grants), a member that needs an update to remove access, or an owner that must be started or reconnected. The `peer_unreachable` and `peer_revoke_unsupported` refusals arise during revocation, after acknowledged Stop, so their messages also say that work was stopped. Other refusals do not make that claim. An unconfirmed Disband explains that a bot’s computer may be asleep or offline and asks the person to retry once it is back. Only a matching tombstone confirms it ended; then Desktop leaves the group chat, drops it from the sidebar and its bindings, and says it was disbanded.

For a deferred peer turn, Discard uses the member's non-admitting close operation
when the home has no run receipt; an older or unreachable member keeps the turn.
A closed key survives restart for the issuer's maximum status lifetime after
closing. Retry after a lost close reply confirms the closure and cancels the same
attempt. After the closed key expires, an explicit Retry under newly granted
access can start a turn still deferred at home. With a run receipt, Discard waits
for confirmed Stop as before.

Disband retains scoped grants handed in during deletion as durable holds and
revokes them before committing the tombstone. A late grant triggers another pass,
up to three passes before a retryable refusal. An unreachable member keeps the
group chat and its unrevoked holds. Grants received after the tombstone become
ordinary owed revokes. Capacity failures preserve earlier holds.

History shows messages and notices for failed, cancelled and deferred turns (a deferred turn names its reason, such as `member_unavailable`), a stop, the work limit (`room.activity` with status `bounded`), the group chat's end and lost ownership; Other events feed the member chips, handoffs and round strip without adding raw transport rows. Your own messages read as **You**. Group chat text may come from another machine: its `MEDIA:` paths, Markdown images, file links and directive cards stay inert, rich code fences (`listing`, `mermaid`, `svg`) show their source, and an explicit web link to a public host (not loopback, link-local or a private network) opens only on a click.

Read timeouts explain that the gateway may be waiting for a bot’s computer and offer Refresh, without showing raw request text. Errors stay visible, and no failed gateway group chat action falls back to Desktop-run execution. Membership editing is not offered.

## Contract tests

`canonical-group-contract-test-utils.ts` wraps each canonical group test's request double and, after each test, checks every `groups.*` request it captured against the generated gateway contract (`apps/shared/src/gateway-contract.openrpc.json`, the gateway's own `x-canonical-methods` entry before the shared one): a method the gateway does not list, an unknown parameter or a missing required one fails the test. The `groups.capabilities` fixtures for both surfaces are data, checked against the same contract when they load. `canonical-groups-contract.test.ts` covers the check itself.
