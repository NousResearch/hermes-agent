The problem with AI-generated PRs on a solo portfolio

When Claude Code is writing 70 percent of your diffs, the bottleneck stops being generation and starts being review. A solo dev with four repos hits a wall that a team never sees: there is no second pair of eyes. You wrote the prompt. The agent wrote the code. You are now the reviewer of your own instructions, which is a famously bad arrangement.

The first version of my workflow was "read the diff, hope I notice the schema drift." That worked for two weeks. Then I shipped a Convex schema mismatch that the agent introduced in 30 seconds and I spent two hours debugging. The issue was not that the model was careless. The issue was that review needs different context than generation. The generating agent had the feature in its head. The reviewing agent, if it existed, needed the repo's conventions, the test suite, and the specific places this app breaks when you touch them.

So I built a Hermes sub-agent that does PR review as a separate pass. Hermes is my personal AI infrastructure, the orchestrator I run locally on WSL Ubuntu. It already manages the agentic loops I use for feature work. The PR review loop is just another sub-agent with a different system prompt, different tools, and a strictly read-only posture.

The point of this article is the mechanism, not the hype. I will show you the config, the prompt skeleton, and the three failure modes that made me rebuild it twice.

How the Hermes PR review loop works

The core idea is separation of context. The agent that writes the feature should not be the agent that reviews the PR. They share the repo but not the conversation.

Hermes runs the review as a three-stage loop:

  1. Gather. A read-only sub-agent diffs the current branch against main, loads the repo's CONTEXT.md file, and pulls the relevant test files.
  2. Evaluate. The same sub-agent runs the test suite, checks the diff against the conventions in CONTEXT.md, and looks for the three failure classes I have learned to care about: schema drift, silent type changes, and unhandled async edges.
  3. Report. The sub-agent posts a structured review back to the terminal and optionally writes a REVIEW.md file in the repo root. It never edits code. It never commits. Read-only is enforced at the tool level, not the prompt level.

The enforcement matters. Early on I tried to do review with the same agent that wrote the feature, just by asking it to "review your own work." That is like asking a student to grade their own exam. The model will find the bugs it already knew about and miss the ones it introduced. A separate sub-agent with no memory of the writing session catches different things.

Here is the Hermes config that wires this up. I keep one per repo because each app has different conventions.

# hermes.review.yml — Plenishd
agent:
  name: plenishd-reviewer
  model: claude-sonnet-4-6
  read_only: true
  tools:
    - git_diff
    - git_log
    - read_file
    - run_tests
    - search_code
  forbidden:
    - write_file
    - git_commit
    - git_push

context:
  conventions: ./CONTEXT.md
  test_command: npx convex dev --once && npm test
  hotspots:
    - convex/schema.ts
    - convex/baskets.ts
    - app/supermarket/tesco.ts
    - app/supermarket/aldi.ts
    - app/supermarket/sainsburys.ts

review_checks:
  - schema_drift
  - silent_type_change
  - unhandled_async_edge
  - convention_violation
  - test_coverage_gap

The hotspots list is the bit I wish someone had told me to add on day one. These are the files where, historically, this specific app breaks. For Plenishd it is the supermarket adapter files, because each UK supermarket has different basket-fill quirks. For MatchdayMaestro it is the prediction engine. The review agent reads these files in full even if the diff does not touch them, because a change in one file can break a contract another file depends on.

The prompt skeleton, and why each line is there

The system prompt is short on purpose. Long review prompts make the model chatty and vague. Short prompts with explicit structure make it specific.

You are a read-only PR reviewer for {repo_name}.

You will be given a git diff and the repo's CONTEXT.md.
Your job is to find problems the author would miss.

Do not rewrite code. Do not suggest style changes.
Report only:

1. SCHEMA DRIFT — does this change the shape of data in a way
   that breaks existing callers? Cite the file and line.
2. SILENT TYPE CHANGES — has a function signature changed
   return type or argument shape without updating callers?
3. UNHANDLED ASYNC EDGES — is there a promise that can reject
   with no catch, or a race between two writes?
4. CONVENTION VIOLATION — does this break a rule in CONTEXT.md?
   Quote the rule and quote the violation.
5. TEST COVERAGE GAP — is there a new code path with no test?

For each finding, output:
  SEVERITY: blocker | warning | nit
  FILE: path:line
  EVIDENCE: the specific code or contract that is broken
  SUGGESTION: one sentence, not a rewrite

If you find nothing, say "CLEAN" and stop.
Do not pad the report.

The "do not rewrite code" line is load-bearing. Without it, the reviewer drifts into rewriting the diff, which defeats the point. I want findings, not patches. Patches come from the feature agent in a second pass, after I have read the review and decided what to fix.

The "if you find nothing, say CLEAN and stop" line is the one that saved me from the worst failure mode: the model inventing problems to seem useful. A reviewer that always finds something is a reviewer that is lying some of the time. Giving it permission to say clean makes the non-clean findings more trustworthy.
