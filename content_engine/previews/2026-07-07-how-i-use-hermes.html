The problem: agentic speed without review is just faster slop

Claude Code on its own is fast. Point it at a feature, give it context, and it produces a diff. The issue is that a diff is not a ship. A diff is a proposal. When you're running multiple panes in tmux, one agent writing a feature on Plenishd's basket-fill logic, another writing tests for MatchdayMaestro's prediction engine, the changes land fast. But nobody has checked whether the Convex schema migration is backwards-compatible, whether the Expo navigation stack still resolves, or whether the sub-agent's test file actually tests the right thing.

The trap is that agentic output feels done. It looks like shipped code. It has tests. It has comments. It compiles. But "it compiles" is the lowest bar in software, and an AI that writes code in 30 seconds can write a schema mismatch in 30 seconds too. I've spent hours debugging issues that an AI created in minutes because I skipped review in the name of velocity.

The fix isn't slower coding. It's a review layer that moves at agentic speed but applies human-grade scrutiny. That's what Hermes does in my setup.

What Hermes actually is in this workflow

Hermes is my custom deployment for personal AI infrastructure. I run it as a local orchestrator on WSL Ubuntu. It's not a model. It's a routing and orchestration layer that sits between me and the Anthropic API, managing context, retries, sub-agent dispatch, and now, PR review.

The key architectural decision: Hermes treats every code change as a pull request, even when I'm the only person on the repo. Every change goes through the same pipeline:

  1. Diff generation — Claude Code produces the change in a feature branch
  2. Static analysis — Hermes runs the diff through structured checks
  3. Agentic review — a separate Claude Code instance reviews the diff as a PR, with no context about why the change was made, only what changed
  4. Human gate — I read the review, approve or reject, merge or iterate

The critical part is step 3. The reviewing agent has no context about the feature's intent. It only sees the diff, the existing code, and the test output. This is deliberate. The agent that wrote the code is biased toward its own solution. A fresh agent with no priors catches things the writer agent rationalises away.

The pipeline in practice: a worked example

Here's a real scenario from last week. I was working on Plenishd's multi-store split optimisation, the feature that compares basket prices across UK supermarkets. Claude Code generated the change in a feature branch. Here's what Hermes did with it.

Step 1: Diff capture

Hermes captures the git diff and writes it to a structured context file:

# Hermes captures the diff and metadata
git diff main...feature/multi-store-split > /tmp/hermes/pr_diff.patch
git log main..feature/multi-store-split --oneline > /tmp/hermes/pr_commits.txt

The diff file becomes the primary context for the review agent. The commit log gives it a sense of how the change evolved, which matters because a single squashed diff can hide intermediate mistakes that a multi-commit history reveals.

Step 2: Static analysis pass

Before any agent touches the diff, Hermes runs deterministic checks. These are cheap, fast, and catch the obvious stuff:

# Hermes static analysis config
checks = [
    "tsc --noEmit",           # TypeScript type check
    "eslint --max-warnings 0", # Lint with zero tolerance
    "convex dev --typecheck",  # Convex schema validation
    "expo export --dry-run",   # Expo build validation
]

If any of these fail, Hermes halts the pipeline and returns the error to the writing agent. No review needed. The change isn't ready. This saves the review agent's context window for actual logic issues, not missing semicolons.

Step 3: Agentic review

This is where the pipeline earns its keep. Hermes dispatches a fresh Claude Code instance with a specific prompt structure:

You are reviewing a pull request. You did not write this code.
You have no context about the feature's intent beyond what
the diff and tests tell you.

Review for:
1. Schema compatibility — will this Convex migration break
   existing queries?
2. Edge cases — what inputs break this function?
3. Test coverage — do the tests actually test the change,
   or do they test something adjacent?
4. State management — does this introduce race conditions
   in the React Native navigation stack?

Be specific. Cite line numbers. If you flag an issue,
explain why it matters, not just that it exists.

The prompt is intentionally narrow. A general "review this code" prompt produces vague feedback. A structured prompt with specific categories produces actionable findings.

Step 4: The human gate

Hermes returns the review as a structured report. I read it. If the review flags issues, I send them back to the writing agent with the specific feedback. If the review is clean, I merge.

The human gate is non-negotiable. Hermes can run steps 1 through 3 autonomously, but step 4 is mine. Not because the AI can't make good judgements, but because the consequences of a bad merge land on my users, my app store reviews, and my weekend. The AI doesn't bear that cost. I do.
