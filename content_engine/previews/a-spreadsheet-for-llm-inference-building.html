A spreadsheet for LLM inference: building an economics calculator that actually changes procurement decisions

Most teams running agents in production cannot answer a basic question: what does one request actually cost us, end to end? I built a small calculator framework to force the answer into the open, and the numbers it produced have already stopped two procurement decisions in their tracks. This is the practitioner log of what I built, why it works, and where the model quietly lies to you.

The adoption-economics gap

The 2026 numbers on agent adoption are striking. 79% of organisations report some form of AI agent adoption, yet only 34% say they have full implementation, 59% are spending over GBP 750K per year, and just 29% report significant results. That gap between spend and outcomes is not a model problem, it is an economics problem. Nobody is doing the per-request maths honestly, so procurement defaults to "more GPUs" or "switch provider" when the real lever is usually somewhere else entirely.

I have been on three of these calls this year. The pattern is consistent: the room agrees on a target, picks a model, signs a contract, and then six months later nobody can produce a defensible cost-per-task number. The Inference Economics Calculator Framework is my attempt to fix that, at least for my own work, and at least for the conversations I am in the room for.

What the framework is, and where it came from

The idea is not original. It is a synthesis of cost-modelling patterns from the vLLM and TGI repositories, plus a handful of spreadsheets that the open-source inference community has been quietly maintaining on the side. What I added was a fixed shape: a small set of input variables, a deterministic calculation, and a one-page output that a non-engineer can read without translation.

The input variables are deliberately boring:

  • Model size in parameters
  • KV cache size per token
  • Cost per GPU-hour on your actual contract
  • Expected input tokens per request
  • Expected output tokens per request
  • Target queries per second
  • Acceptable p99 latency
  • Prompt cache hit rate

The output is a per-request cost, a monthly run-rate at target QPS, a hardware count, and a break-even price against the equivalent SaaS API. There is no machine learning in it. There is no agentic loop. It is a calculator with opinions.

The mechanism, in plain arithmetic

Per-token cost on a self-hosted stack is dominated by three things: GPU cost, tokens per second per GPU, and the ratio of output to input tokens. Everything else is noise unless you are running at scale.

The core formula, expressed in code, looks like this:

def cost_per_request(input_tokens, output_tokens,
                     tokens_per_sec_per_gpu, gpu_hour_cost):
    seconds = (input_tokens + output_tokens) / tokens_per_sec_per_gpu
    return seconds / 3600 * gpu_hour_cost

A worked example, using illustrative defaults for a 70B-parameter model on H100s: roughly USD 2.50 per GPU-hour, around 800 tokens per second per GPU at sensible batching, and a typical request of 2,000 input tokens and 500 output tokens. The arithmetic gives a per-request cost of about USD 0.0022. At a sustained 10 QPS, that is roughly USD 0.022 per second, or close to USD 58,000 per month if you pack the GPU well. The same request against a typical SaaS API in mid-2026 pricing lands somewhere around USD 0.01 to USD 0.02 per call, so self-hosting only beats the API once you are running above 5 to 10 QPS consistently. Below that, you are paying a premium for control you are not using.

The framework computes this in a single pass, then layers on the prompt cache and batching multipliers. It is small enough to read in one sitting and reproducible enough that two engineers get the same answer.

The variables that actually move the answer

The single biggest lever is output tokens. Output is roughly three to four times more expensive per token than input on most stacks because autoregressive decoding is memory-bandwidth bound. Halving the output halves your cost more aggressively than doubling the input. Most teams optimise the wrong one. They compress prompts. They should be constraining completions.

The second lever is the prompt cache hit rate. A 30% cache hit on a 2,000-token system prompt with vLLM prefix caching cuts effective input cost by 30% with zero model work. This is the easiest win in the whole stack and almost nobody tracks it in production. The calculator exposes it as a first-class input because it is a first-class number.

The third lever is batch size. Going from batch 1 to batch 8 on a 70B model can improve tokens-per-second-per-GPU by a factor of three to four, because the matrix multiplies become compute-bound rather than memory-bound. The framework exposes a batch-utilisation factor because it is the difference between a cost model that matches reality and one that does not.

Latency, contrary to popular belief, is rarely a procurement variable. It is a constraint. You either meet it or you do not, and if you do not, the only fix is more GPUs or a smaller model, not better maths.

Hype vs reality: what the framework will not do for you

I want to be candid about the limits, because the inference-economics conversation online is dominated by people selling GPUs or people selling API credits.

First, the framework assumes you know your real input and output token distributions. You almost certainly do not. The first run of the calculator against your actual traffic will be off by a factor of two to five. Treat the output as a direction, not a number.

Second, the tokens-per-second-per-GPU figure is hardware, model, and serving-stack specific. The values I used above are reasonable midpoints for a 70B on H100 with vLLM at batch 4 to 8. They are not facts. Run your own benchmark on your own hardware before you trust any number, including mine.

Third, self-hosting has a fixed cost floor that the spreadsheet does not capture: an engineer to keep it running. At 1 to 2 QPS, that floor is the entire bill. The calculator will tell you self-hosting is cheaper than the API, and it will be wrong, because it does not price the on-call rotation or the eval pipeline.

Fourth, the framework has nothing to say about quality. A cheaper model that answers wrong is not cheaper. Run your evaluation separately, then feed the result back in as a constraint rather than a free variable.

How to apply this

If you want to use this kind of calculator inside your own procurement process, here is the order I would do it in.

  1. Pull two weeks of production traffic. Count the actual distribution of input and output token lengths, not the averages your dashboard shows.
  2. Pick the three models you are seriously considering. Get a real tokens-per-second-per-GPU number for each on your actual hardware, with your actual serving stack, at a realistic batch size.
  3. Fill the calculator in for each, with three scenarios: low QPS, median QPS, and 2x median QPS.
  4. Compute the break-even against your current API spend, including any commitment discounts or credits that are about to expire.
  5. Add the line items the spreadsheet will not show: one SRE, observability, eval pipeline, and a 30% buffer for incidents.
  6. Take the result to procurement. Be prepared to discover that your current API contract is subsidised by credits that disappear at renewal.

What I'd try next

The next thing I want to add is a token-distribution sampler, so the calculator can run Monte Carlo over a week's worth of real traffic instead of just the median. That is the missing piece: per-request cost is a distribution, not a number, and procurement decisions made on medians tend to regret themselves at month three.

After that, a multi-region model. The cheap region and the cheap region with data-residency constraints are not the same region, and the framework currently does not help you see that trade. For a team whose agents touch EU or UK customer data, this matters more than the GPU line item.

Last, integration with the broader research pipeline. I already have a discovery and scoring flow for evaluating infrastructure providers, and the calculator should sit one step upstream of the procurement decision, feeding numbers into the same review process that the Kensei strategic lenses use for everything else. A single artefact that says: at this quality threshold, this model, on this hardware, at this QPS, in this region, costs this much. That is the procurement document that should exist. Right now it does not, in any tool I have found.
