Compact cron failure messages and bare repo repair after git gc

Cron jobs that manage git repositories fail in two ways: loudly, with pages of stack trace nobody reads, or silently, with nothing at all. This is the story of a small fix, 82 lines added across 3 files, that made cron failures actionable and added a repair step for bare repositories after git gc. The commit message is mundane. The patterns inside it are not.

The economics of cron failure messages

When a cron job fails, the message it produces is the only diagnostic you get. The problem is that most cron jobs either dump everything (stdout, stderr, full tracebacks) or nothing. Both extremes waste the operator's attention.

The durable pattern here is one that surfaces repeatedly in diagnostic localization work for code repair: the value of a failure signal is not in identifying that something went wrong, but in providing the minimal context needed to act on it. A repair agent that receives a file path without diagnostic reasoning has to re-derive the problem from scratch. A human reading a cron email faces the same issue. A 200-line log dump tells you something broke. A three-line structured message tells you what broke, where, and what to do about it.

The economics are simple. Cron failures are infrequent enough that you never build a tolerance for parsing them, but frequent enough that ignoring them eventually costs you. Compact, structured messages get acted on in the minute between meetings. Verbose ones get archived until something breaks downstream.

What compact failure messages look like in practice

The fix I shipped restructured cron failure output into a predictable format. Instead of the default behaviour, which mails the entire stderr, each failure now produces a message with three fields: the job name, the specific failure point, and the exit code.

# Before: cron mails everything, you read everything
0 3 * * * /opt/scripts/sync-bare-repos.sh 2>&1

# After: structured failure, compact output
0 3 * * * /opt/scripts/sync-bare-repos.sh || \
  printf '[%s] job=%s step=%s exit=%s\n' \
    "$(date -u +%FT%TZ)" "sync-bare-repos" "${FAILED_STEP}" "$?"

The key decision was what to include and what to cut. I kept the timestamp in UTC because cron logs use local time and the offset is never obvious. I kept the step name because this script has several stages (fetch, gc, fsck) and knowing which one failed saves a round trip to the server. I cut the full traceback because if you need it, you can re-run the script manually.

This is the same trade-off that diagnostic localization frameworks address: enough context to act, not so much that the signal is buried. The decision rule I use is that a failure message should let you decide between three actions without reading anything else: retry now, investigate later, or ignore safely.

Bare repository repair after git gc

The second part of the fix addresses a real operational problem with bare repositories. Bare repos, the kind you use as remotes on a server, are just git object stores without a working tree. They are efficient and simple until they are not.

The pattern is this: git gc compacts loose objects into packfiles. On a bare repo, there is no working tree to detect problems. A packfile that was partially written, or objects that were pruned because they appeared unreachable, do not surface until someone tries to clone or fetch. The repo looks fine. git fsck may report no errors. But a checkout of a specific commit fails with "object not found."

I am not claiming this happens every time or even frequently. The conditions are specific: interrupted gc, concurrent access during repack, or disk pressure during the write. But when it does happen, the failure mode is confusing because the repository reports as healthy until you actually use it.

The fix adds a repair step to the cron job that runs after gc:

repair_bare_repo() {
  local repo="$1"
  # Verify every ref points to objects that exist
  if ! git --git-dir="$repo" rev-list --all --objects >/dev/null 2>&1; then
    echo "step=repair action=fetch-objects repo=$repo"
    git --git-dir="$repo" fetch origin --prune '+refs/*:refs/*' 2>/dev/null
  fi
  # Re-run fsck after repair
  git --git-dir="$repo" fsck --full >/dev/null 2>&1 || \
    echo "step=repair action=manual-intervention repo=$repo"
}

The repair logic is straightforward. rev-list --all --objects walks every reachable object. If that fails, something is missing. The repair is to fetch from the upstream, which restores missing objects. If fsck still fails after that, the script flags it for manual intervention rather than trying increasingly aggressive fixes.

Why rev-list and not just fsck

The choice of git rev-list --all --objects as the verification command was deliberate. git fsck checks structural integrity: are the object files valid, are the refs consistent. It does not necessarily walk every reachable object in a way that catches every missing one. rev-list --all --objects forces git to traverse the full object graph, which surfaces any missing object that a clone or checkout would also hit.

The trade-off is cost. On a large repository, rev-list --all --objects is more expensive than fsck alone. For the repos this cron job manages, the traversal takes under two seconds. For a repository with millions of objects, you would want to run this less frequently or only after gc, which is exactly what this script does.

I considered using git gc --verify instead, but that option does not exist as a standalone. gc does run a verification internally, but only after it has already rewritten packfiles, which is the operation that can introduce the problem in the first place. Running verification after gc, using a different command than gc itself, gives you an independent check.

Honest reality check

The hype around automated repository maintenance is that git gc and git maintenance are set-and-forget. In practice, bare repos on servers that serve as remotes for multiple developers need monitoring. The repair step in this fix exists because the assumption that gc always produces a clean repository is optimistic.

What this fix does not solve: concurrent gc runs from multiple cron jobs, which is a configuration error but one that is easy to make if you have multiple scripts touching the same repo. The repair step also assumes the upstream is available and has the missing objects. If the bare repo is the canonical source and it has lost objects, fetching from origin will not help.

The compact failure messages are the more generally useful part of this fix. The repair step is specific to a setup where bare repos are mirrors with an upstream to fetch from. If your bare repo is the primary, the repair strategy would be different: restore from backup, or use git unpack-objects from a recent bundle.

The 82 lines added are mostly the repair function and the message formatting. It is not a large change. The value is in the discipline of making failures actionable rather than noisy, and in not trusting gc to always produce a clean result.

How to apply this

  1. Audit your cron jobs that touch git repositories. Check what happens when they fail. If the failure output is more than 10 lines or less than 1 line, restructure it.
  1. Format failure messages with a fixed schema: timestamp, job name, failed step, exit code. This lets you grep failures and spot patterns.
  1. If you run git gc on bare repos in cron, add a verification step after gc using git rev-list --all --objects. This catches missing objects that fsck alone may not surface.
  1. For repair, fetch from upstream if the repo is a mirror. If it is a primary, ensure you have a backup or bundle strategy.
  1. Run the verification only after gc, not on every cron invocation. The cost of rev-list --all --objects is small per run but unnecessary if nothing has changed.
  1. Test the failure path manually. Stop a gc mid-run, check whether your verification catches it. If it does not, your repair step is dead code.

What I'd try next

The compact message format could be extended to cover partial failures, where the script continues after one repo fails but reports all failures at the end. Right now, the script exits on the first failure, which is conservative but means you only learn about one problem per run.

I would also explore using git maintenance as a replacement for the manual gc invocation, since it is designed for scheduled background use. The limitation is that git maintenance does not easily compose with custom pre and post hooks, which is why the current script calls gc directly and runs verification after. A wrapper that runs maintenance and then verifies would be the clean path if maintenance ever supports custom post-run hooks.

Finally, the diagnostic localization pattern, giving enough context to act without re-deriving the problem, applies beyond cron messages. The same principle could shape error output in CLI tools, CI pipelines, and agent-based systems where the consumer of the error is not the person who produced it.
