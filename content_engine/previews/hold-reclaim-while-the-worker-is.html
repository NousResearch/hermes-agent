Hold reclaim while the worker is still alive: a kanban fix

When a task sits on a kanban board in "in progress" for too long, the natural instinct is to reclaim it: pull it back into the queue so another worker can pick it up. That instinct is correct when the original worker has died. It is destructive when the worker is still alive and simply taking longer than expected. This is the story of a three-file, three-commit fix that taught me something general about coordination systems.

The problem: premature reclaim under the Hermes Kanban layer

The Hermes Kanban coordination layer is the mechanism I use to orchestrate work across specialised Hermes profiles. Each profile is a worker with a specific role. The kanban board tracks which task each worker has claimed, and a supervision loop periodically checks whether tasks are stuck.

The bug was straightforward in hindsight. A task would be claimed by a worker, the worker would begin processing, and the supervisor would see the task sitting in "in progress" past its expected duration. The supervisor would then reclaim the task, moving it back to "ready" so another worker could pick it up. But the original worker was still alive, still running, still consuming resources for a task it no longer owned.

This produced the classic distributed systems failure mode of duplicate execution. Two workers processing the same task. Side effects fired twice. Emails sent twice. Files written with conflicting names. The kanban layer was doing its job on paper but creating chaos underneath.

The diff tells the story: +257/-1, 3 files, 3 commits. Two hundred and fifty-seven lines added to fix what was, at its core, a one-line conceptual error. The one deleted line was the unconditional reclaim. The 257 added lines were the machinery to make reclaim conditional on worker liveness.

The mechanism: heartbeat-gated reclaim

The concept that fixed this is not new. It appears in work-stealing schedulers, in distributed task queues like Celery and Sidekiq, and in lease-based systems like etcd's election primitives. The idea is simple: before reclaiming a task, check whether the worker that claimed it is still alive.

In practice this means the worker must emit a heartbeat. Not a full status report, not a progress update, just a timestamped proof of life. The supervisor, before reclaiming, reads that heartbeat and compares it to a timeout threshold. If the heartbeat is fresh, the task stays put. If the heartbeat is stale, the worker is presumed dead and the task is reclaimed.

The key implementation detail is what counts as "fresh." Too short a timeout and you reclaim tasks from slow-but-alive workers, recreating the duplicate execution problem. Too long and dead workers leave tasks stranded for unacceptable periods. I settled on a timeout that is three times the heartbeat interval. If the worker heartbeats every 10 seconds, the reclaim threshold is 30 seconds. This gives the worker a comfortable margin for garbage collection pauses, network jitter, or slow I/O without triggering false reclaims.

def should_reclaim(task, now):
    if task.worker_id is None:
        return False  # nothing to reclaim
    
    last_heartbeat = heartbeat_store.get(task.worker_id)
    if last_heartbeat is None:
        return True  # worker never heartbeated, treat as dead
    
    age = now - last_heartbeat
    return age > RECLAIM_TIMEOUT

This is the entire decision. The complexity in the 257 lines comes from the plumbing: registering workers, storing heartbeats, cleaning up stale worker registrations, and making the heartbeat emission cheap enough that it does not slow down the actual work.

What I built: a liveness layer over the existing kanban

The fix was implemented across three files. The first file handles worker registration. When a Hermes profile picks up a task from the kanban, it registers itself with a worker ID, a process handle, and a heartbeat channel. The second file is the heartbeat store itself, a simple key-value mapping from worker ID to last-seen timestamp. The third file modifies the supervisor's reclaim logic to consult the heartbeat store before pulling a task back.

The design choice that mattered most was keeping the heartbeat store separate from the kanban board itself. The kanban tracks task state. The heartbeat store tracks worker state. These are different concerns and conflating them would have made the kanban layer harder to reason about. A task can be "in progress" on the kanban while its worker is simultaneously "dead" in the heartbeat store. That combination is what triggers reclaim. Keeping them separate means I can inspect each independently when debugging.

class WorkerRegistry:
    def register(self, worker_id, process_handle):
        self.workers[worker_id] = {
            "process": process_handle,
            "last_heartbeat": time.monotonic(),
        }
    
    def heartbeat(self, worker_id):
        if worker_id in self.workers:
            self.workers[worker_id]["last_heartbeat"] = time.monotonic()
    
    def is_alive(self, worker_id, now, timeout=RECLAIM_TIMEOUT):
        worker = self.workers.get(worker_id)
        if worker is None:
            return False
        return (now - worker["last_heartbeat"]) < timeout

The heartbeat itself is emitted from a background thread inside each worker profile. It fires every 10 seconds, writes a single timestamp to the store, and returns. It does not block the worker's main processing loop. If the worker is stuck in a long API call, the heartbeat thread keeps running independently. The only scenario where the heartbeat stops is if the worker process itself has crashed or been killed, which is exactly the case where reclaim should happen.

The reality check: heartbeat systems are harder than they look

Here is where I push back on the clean narrative above. Heartbeat-gated reclaim is a well-known pattern, and the implementation is conceptually simple. But the edge cases will eat your time.

The first edge case is the stuck-but-alive worker. A worker can be alive in the process sense, heartbeating faithfully, while being completely stuck in a deadlock or an infinite retry loop. The heartbeat says "I am alive" but the task is not progressing. My current system does not distinguish between "alive and working" and "alive and stuck." This is a known limitation. The fix would be to include task progress in the heartbeat payload, but that raises the question of what counts as progress for a task that is waiting on a slow external API call. I have not solved this and I am not sure it is worth solving yet.

The second edge case is the graceful shutdown problem. When a worker finishes a task and shuts down cleanly, it deregisters itself. But if the worker is killed with SIGKILL, no deregistration happens. The heartbeat store retains a stale entry. This is harmless for correctness, because the stale heartbeat will eventually time out and the worker will be marked dead. But it means the heartbeat store grows over time with entries for workers that no longer exist. I added a periodic cleanup that removes entries older than ten times the reclaim timeout, which is aggressive enough to keep the store bounded without removing entries for workers that are merely slow.

The third edge case is clock skew. I used time.monotonic() for the heartbeat timestamps, which avoids wall-clock jumps but means the heartbeat store and the supervisor must run on the same machine. For my current single-host deployment this is fine. If I ever distribute across multiple machines, I will need to switch to a shared time source or use a distributed heartbeat service like Redis with TTL keys. That is a problem for another day.

The honest summary: the fix works, the duplicate executions have stopped, and the kanban layer now correctly distinguishes between "task is stuck because the worker is slow" and "task is stuck because the worker is dead." But it took 257 lines to get there, and the remaining edge cases around stuck-but-alive workers are real and unsolved.

How to apply this

If you are building a task coordination layer, here is the decision rule: never reclaim a task without first checking whether the worker that claimed it is still alive. The check does not need to be sophisticated. A periodic heartbeat with a timeout threshold of three times the heartbeat interval is sufficient for most cases.

The concrete steps:

  1. Give each worker a unique ID when it starts.
  2. Have the worker emit a heartbeat to a shared store every N seconds, where N is short relative to your expected task duration.
  3. In your supervisor's reclaim loop, check the heartbeat before reclaiming. If the heartbeat is fresher than your timeout threshold, leave the task alone.
  4. Keep the heartbeat store separate from your task state store. They are different concerns.
  5. Add a cleanup job for stale worker registrations. Workers that crash without deregistering leave orphan entries.
  6. Use a monotonic clock if everything runs on one machine. Use a shared store with TTL if you are distributed.
  7. Accept that this does not solve the stuck-but-alive problem. That requires progress reporting, which is a separate and harder design question.

What I'd try next

The next thing I would try is adding a lightweight progress signal to the heartbeat. Not a full progress report, just a hash of the last action the worker took. If the hash has not changed across three consecutive heartbeats, the supervisor can flag the task as "alive but stalled" and surface it for manual inspection rather than automatically reclaiming it. This would close the gap between "dead worker" and "stuck worker" without the complexity of a full progress tracking system. I would also want to test the system under a real failure scenario, not just the simulated ones, by killing a worker process mid-task and observing whether the reclaim fires at the right time with no duplicate execution. That test is more convincing than any amount of code review.
