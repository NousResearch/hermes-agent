The Problem: Why AI Workflows Are Harder Than They Look

Every AI feature I’ve shipped follows the same pattern. The model integration takes a week. Everything around it — data prep, context engineering, error handling, monitoring — takes months. The model is the engine. The context is the entire vehicle.

The real bottleneck isn’t model capability. It’s orchestration. You need to chain multiple calls: retrieve context, format it, call the model, parse the output, validate it, fall back if it fails, log everything. Do that once and it’s fine. Do it across three features in two apps and you’re drowning in boilerplate.

I hit this wall building Plenishd’s recipe search. The idea was simple: let users describe what they have in the fridge and get a recipe. The first prototype took an afternoon. The production version took three months. The difference was everything that happens before and after the model call — ingredient normalisation, dietary filters, response formatting, latency budgets, hallucination guardrails.

That’s where Hermes came in.

What Hermes Does (and Doesn’t Do)

Hermes is an open-source tool for building and running AI agents. It’s not a model provider. It’s not a vector database. It’s an orchestration layer that lets you define workflows as code — chains of LLM calls, tool use, conditional logic, and observability.

What I like about it: it doesn’t abstract away the complexity. You still write the prompts. You still define the context. You still handle errors. But you do it in a structured way that’s testable, versionable, and reusable across projects.

What it doesn’t do: it won’t fix bad data. It won’t write your system prompts. It won’t tell you when your retrieval strategy is wrong. It’s a tool for the 80% of work that isn’t the model — and that’s exactly where most AI features fail.

Here’s a simplified example of what a Hermes workflow looks like for a recipe search:

from hermes import Workflow, step, tool

@step
def parse_user_input(input_text: str) -> dict:
    # Extract ingredients, dietary preferences, meal type
    return {"ingredients": ["chicken", "broccoli", "rice"], "diet": "gluten-free"}

@step
def retrieve_recipes(parsed: dict) -> list:
    # Query vector DB with ingredient embeddings
    return vector_db.search(parsed["ingredients"], top_k=5)

@step
def filter_by_diet(recipes: list, diet: str) -> list:
    return [r for r in recipes if diet in r["tags"]]

@step
def generate_response(recipes: list) -> str:
    prompt = f"Given these recipes: {recipes}, write a friendly response..."
    return llm.call(prompt)

workflow = Workflow(steps=[parse_user_input, retrieve_recipes, filter_by_diet, generate_response])
result = workflow.run("I have chicken and broccoli, need gluten-free")

This is deliberately simple. The real value comes when you add error handling, retries, logging, and monitoring — all built into Hermes’ runtime.

A Worked Example: Plenishd’s Recipe Search

Let me walk through the actual pipeline I built for Plenishd. The goal: take a user’s voice input (“I’ve got chicken, broccoli, and some rice — what can I make?”) and return a recipe card with ingredients, steps, and dietary notes.

Step 1: Input parsing. Hermes calls a small LLM (Claude Haiku) to extract structured data from the free-text input. I use a system prompt that defines the schema: ingredients list, dietary flags, meal type. This step costs pennies and runs in under a second.

Step 2: Ingredient normalisation. Raw ingredient names are messy. “Chicken breast” vs. “chicken” vs. “boneless skinless chicken breast”. I use a lightweight embedding lookup to map to a canonical set. This is a tool call in Hermes — a function that queries a local SQLite database of ingredient synonyms.

Step 3: Vector search. The normalised ingredients become a query vector. I search a Pinecone index of 10,000 recipes. Hermes handles the API call and returns the top 5 results.

Step 4: Dietary filter. A simple rule-based step — no LLM needed. Hermes supports conditional branching: if the user said “gluten-free”, filter out recipes with wheat. This step is a pure Python function.

Step 5: Response generation. The filtered recipes are passed to a larger model (Claude Sonnet) with a prompt that includes the user’s original input, the matched recipes, and formatting instructions. The output is a structured JSON that the frontend renders.

Step 6: Validation. Before returning to the user, Hermes runs a validation step that checks for hallucinated ingredients, missing steps, and response length. If validation fails, it retries with a stricter prompt.

The entire workflow is defined in a single Python file, version-controlled, and deployed as a serverless function. When I change one step — say, switch from Pinecone to Supabase vector search — I only change that step’s implementation. The rest of the pipeline stays the same.
