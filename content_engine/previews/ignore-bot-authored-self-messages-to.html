Ignore bot-authored self-messages to stop self-ingestion: a telegram fix

When you wire a Telegram bot into an LLM pipeline, the bot's own outgoing replies get delivered back to it as incoming updates. Left unfiltered, the model reads its own output, reacts to it, and spirals into a feedback loop that burns tokens and produces nonsense. The fix is small and durable: drop any message where the author is the bot itself, before it reaches the reasoning layer.

The problem: bots that eat their own output

Telegram's update model is straightforward in principle but quietly hostile in practice. When your bot sends a message to a chat it is a member of, that message appears in the conversation history. If your ingestion pipeline reads recent messages from the chat and feeds them into a context window, the bot's own replies are included. The model then sees its prior response as if a user had sent it, and responds again. Each iteration compounds: the bot replies to its reply to its reply, drifting further from anything useful.

This is not a hypothetical. It happens the moment you connect a polling or webhook-based reader to a group chat where the bot has send permissions, which is the default configuration for most bot setups. The symptom is usually a sudden burst of messages from the bot, each one slightly more deranged than the last, until a rate limit or a human intervenes.

The underlying mechanism is worth naming precisely. The loop has three stages: the bot emits a message, the ingestion layer collects it as part of the chat history, and the model generates a new message in response. Break any one stage and the loop stops. The cleanest place to break it is stage two, at the ingestion boundary, because you preserve the full chat history for human readers while preventing the model from reacting to its own voice.

The mechanism: author filtering at the ingestion boundary

The fix that landed in PR #11905 adds 86 lines across 2 files and 2 commits. The net-add nature of the change tells you something about the architecture: this was not a rewrite or a refactor. It was a guard inserted at the point where raw Telegram updates are converted into internal message representations.

The core logic is simple to express. Every Telegram message update carries a from field identifying the sender. Every bot knows its own user ID, which it receives during the getMe call at startup. The filter is a single comparison: if message.from.id == bot_user_id, skip the message.

def should_ingest(update, bot_user_id):
    if update.message is None:
        return False
    if update.message.from_user is None:
        return False
    if update.message.from_user.id == bot_user_id:
        return False
    return True

This is not clever code. It is boring, defensive, and exactly the right shape for a problem that recurs across every chat platform integration. The reason it works is that Telegram guarantees the from field on message updates, so the check is reliable. You are not guessing at heuristics or parsing message text for self-referential patterns. You are using a field the protocol provides for exactly this purpose.

What this looks like in a real pipeline

In a typical setup, you have a polling loop or webhook handler that receives updates, transforms them into an internal format, and pushes them into a queue or context builder. The self-message filter belongs in the transform step, after parsing but before enrichment.

async def handle_update(update, bot_user_id):
    if not should_ingest(update, bot_user_id):
        return  # silently drop, do not log as error

    internal_msg = {
        "chat_id": update.message.chat.id,
        "text": update.message.text,
        "sender_id": update.message.from_user.id,
        "sender_name": update.message.from_user.full_name,
        "timestamp": update.message.date.isoformat(),
    }
    await context_builder.add(internal_msg)

The key design decision is where to place the filter relative to other processing. Put it too late, after enrichment or after the message has been added to the context window, and you have already paid the cost of processing. Put it too early, before you have parsed the update into a usable structure, and you risk missing edge cases where the from field is nested differently across update types.

The right position is immediately after you have a parsed message object and before you do anything expensive with it. This is the ingestion boundary: the line between "raw protocol data" and "something my system reasons about."

Why this keeps happening across platforms

The self-ingestion problem is not unique to Telegram. It appears in Discord bots, Slack integrations, Matrix bridges, and any system where a bot both reads from and writes to the same channel. The reason it recurs is that most platform SDKs do not warn you about it. The from field is there in the API response, but nothing in the documentation says "by the way, your own messages will come back to you and you need to filter them."

The pattern is durable enough to abstract. For any chat platform integration, you need three things at startup:

  1. The bot's own identifier, obtained from the platform's identity endpoint.
  2. A filter function that compares incoming message sender IDs against that identifier.
  3. A placement decision: where in the pipeline the filter runs.

For Telegram, the identity endpoint is getMe. For Discord, it is the user field on the ready event. For Slack, it is the auth.test endpoint. The shape of the filter is identical in all three. What changes is the field name and the ID format.

The reality check: what the hype misses

The PR is 86 lines of additions across 2 files. That sounds trivial, and the core logic is. But the reason this class of bug ships to production is not that the fix is hard to write. It is that the failure mode is invisible during development.

When you test a bot in a private chat with yourself, the bot sends a reply and you, the human, send the next message. The loop never triggers because you are driving the conversation. The self-ingestion bug only appears in group chats or in scenarios where the bot is triggered by message arrival rather than by an explicit command. By the time you notice it, the bot has already sent dozens of messages and possibly hit a rate limit.

The second thing the small diff hides is the cost of the loop when it does trigger. Each iteration sends a message to an LLM endpoint. If you are paying per token, a self-ingestion loop that runs for 30 seconds before you kill it can cost more than a full day of legitimate usage. The 86-line fix is cheap. The absence of the fix is not.

There is also a subtler failure mode that the basic author filter does not catch. If your bot is a member of a group and another bot in the same group sends messages, your bot will ingest those. If the other bot is also LLM-powered and also lacks a self-filter, the two bots will talk to each other indefinitely. The author filter stops your bot from eating its own output, but it does not stop your bot from eating another bot's output. For that, you need either a broader filter (drop all messages from accounts flagged as bots) or a rate limiter on ingestion. Neither is in the scope of this PR, and neither should be, because they introduce trade-offs about what conversations the bot is allowed to participate in.

How to apply this

If you are building or maintaining a Telegram bot integration, here is the concrete checklist:

  1. Call getMe at startup and store the bot's user ID.
  2. In your update handler, after parsing the message but before any enrichment or context building, compare message.from_user.id against the stored bot user ID.
  3. If they match, return early. Do not log this as an error or warning. It is expected behaviour, not a fault.
  4. Test in a group chat, not just a private chat. Send a message, let the bot reply, and verify the bot does not reply again to its own reply.
  5. If you have multiple bots in the same group, consider an additional filter on the is_bot flag of the sender, but make this configurable. Some legitimate use cases involve bots responding to other bots.

The decision rule is simple: filter at the ingestion boundary, not at the model prompt construction stage. Filtering at prompt construction means the message has already entered your system, been enriched, and potentially triggered side effects. Filtering at ingestion means it never existed as far as your pipeline is concerned.

What I'd try next

The author filter solves the immediate self-ingestion problem, but the broader question of loop prevention in multi-agent chat systems is still open. The next thing worth exploring is a generalised ingestion policy: a configurable layer that decides which messages enter the context window based on sender type, message age, conversation depth, and rate. The 86-line fix is the minimal viable version of that policy. A full policy engine would let you express rules like "ingest bot messages only if the last human message is less than 5 minutes old" or "cap ingestion at 20 messages per minute per chat." That is a larger piece of work, but it is the natural next step once you have seen how quietly the feedback loop can start and how quickly it can run up a bill.
