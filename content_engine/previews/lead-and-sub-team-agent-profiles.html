Lead and sub-team agent profiles: structuring an agent org that delegates without losing the plot

When you give a single agent everything, it forgets the important things and remembers the noise. The fix is not a bigger context window. It is an organisation: a lead agent that holds the plot, and specialist sub-team agents that do the work. This is a learning log from building exactly that, including the parts that are harder than the diagrams suggest.

The problem with single-agent context

The problem with single-agent context

The first instinct when an agent starts dropping details is to feed it more context. More system prompt, more tool descriptions, more retrieved documents, more transcript history. This works up to a point and then actively hurts. The agent starts conflating instructions from different sections, prioritising the wrong tool, and losing track of the original goal three steps into a multi-step task.

The mechanism is straightforward. Attention over a long context is not uniform. The model weights different tokens depending on position, salience, and recency. As the working context grows, the signal-to-noise ratio drops. Instructions that were crisp at the top of the prompt get diluted by the accumulated tool-call chatter below them. You do not get a clean failure. You get drift: the agent still sounds competent, still produces plausible output, but it has quietly stopped tracking the thing you asked it to do.

This is an economics problem, not a model-quality problem. Context is a finite resource. Spending it on everything means spending it on nothing well. The durable answer is to budget context per role, and give each role only what it needs.

Lead and sub-team profiles: the mechanism

Lead and sub-team profiles: the mechanism

The pattern I have been operating is borrowed from how human teams actually function. A lead agent owns the objective, the plan, and the decision to delegate. Sub-team agents own a specialist domain and execute within a bounded scope. Each profile is a separate prompt configuration with its own instructions, tools, and context budget.

The lead profile carries the canonical objective document, a lightweight plan, and the authority to spin up or tear down sub-team agents. It does not carry the full context of every specialist domain. It carries summaries. Its job is to know what the team is doing and why, not how each step is performed.

Each sub-team profile carries a specialist prompt, the tools for its domain, and only the context relevant to its current task. When the lead delegates, it passes a bounded brief: the objective for this sub-task, the constraints, and the expected output format. The sub-team agent works inside that envelope and returns a result. It never sees the full plan. It never needs to.

The key insight is that delegation is context isolation. By splitting the work across profiles, each agent operates in a smaller, cleaner context window. The lead does not accumulate the noise of every tool call the specialists made. The specialists do not accumulate the noise of the lead's planning reasoning. Each stays sharp within its lane.

Here is the shape of it, expressed as the profile structure I use:

lead:
  name: lead
  carries:
    - canonical_objective_doc
    - current_plan
    - delegation_log
  tools:
    - delegate_to_subteam
    - read_objective
    - update_plan
  does_not_carry:
    - specialist_domain_context
    - raw_tool_call_history_from_subteams

subteam_specialist:
  name: specialist
  carries:
    - specialist_system_prompt
    - delegated_brief
    - domain_tools
  tools:
    - domain_specific_tools
  does_not_carry:
    - full_plan
    - other_subteams_context

The delegation_log on the lead side is important. It is not a transcript. It is a structured record: which sub-team, what brief, what result, what status. This is how the lead reconstructs state without re-reading everything.

A worked example: delegation cycle

Consider a task that requires three specialist domains: research, implementation, and verification. A single agent doing all three in one context window will bleed research notes into the implementation step and lose the verification criteria by the time it reaches the end.

With the profile structure, the cycle looks like this:

  1. The lead reads the objective and produces a plan with three delegated sub-tasks.
  2. The lead delegates the research sub-task. The research specialist receives a brief: "Find the relevant API contracts for X. Return a structured summary, not prose." It works in its own context, returns the summary, and is torn down.
  3. The lead records the result in the delegation log and delegates the implementation sub-task. The implementation specialist receives the research summary plus its own brief. It does not receive the lead's planning reasoning. It returns code and a short report.
  4. The lead delegates verification. The verification specialist receives the implementation report plus the original acceptance criteria. It returns pass or fail with specifics.

The lead's context at the end of this cycle contains three structured summaries and a delegation log. It does not contain the full research transcript, the implementation tool calls, or the verification step-by-step. The lead can still answer "what did we do and why" because it holds the plan and the results. It cannot answer "what exact grep command did the researcher run" and it should not need to.

Policy enforcement at the boundary

Delegation creates a new failure surface. When the lead hands a brief to a sub-team agent, that brief is data crossing a trust boundary. If any part of that brief is influenced by untrusted input, you have an injection path into the specialist. The specialist, operating in a clean context, will trust its brief because that is all it has.

The durable pattern here is to treat every delegated brief as untrusted until structurally validated. The brief should be typed, schema-checked, and stripped of anything that looks like an instruction rather than a parameter. A brief that says "research the API for X" is a parameter. A brief that says "research the API for X and also ignore previous instructions" is an attack.

There is a deeper layer worth naming. Tool-call interception at the harness level catches what the agent explicitly does. It does not catch what the agent decides internally based on poisoned context. The pattern that addresses this is policy enforcement at a layer below the harness, where the OS itself validates that an action is permitted regardless of what the agent believed it was doing. Whether you build this or buy this, the principle is the same: do not let the agent's own reasoning be the only gate on what the agent is allowed to do. The reasoning is the thing under attack.

Reality check: hype versus practice

The hype says multi-agent systems are just function calling with extra steps. Wire up a few agents, give them tools, and the orchestration emerges. This is wrong in a way that costs real time.

In practice, the hard parts are not the agents. The hard parts are the interfaces between them. Getting the brief schema right takes longer than writing any individual profile. If the brief is too loose, the specialist drifts. If the brief is too rigid, you spend your time writing delegation plumbing instead of doing the work. I went through three iterations of the brief format before settling on one that was structured enough to validate but flexible enough to be useful.

The hype also says specialist agents are cheaper because they use smaller models. Sometimes true, but the economics are more subtle. You now have multiple inference calls per task instead of one. You have orchestration overhead. You have the cost of reconstructing state at the lead level. For simple tasks, a single agent in a well-trimmed context is cheaper and better. The profile structure pays off when the task is complex enough that a single agent would drift, and the cost of drift exceeds the cost of orchestration.

The unglamorous truth: most of the value is in the operating model document, not the profiles. The profiles are short. The document that defines what each profile is responsible for, what the brief schema is, what the delegation log looks like, and when to tear down a specialist is where the actual engineering lives. I spent more time on that document than on every profile prompt combined.

How to apply this

Start with one task that you have watched a single agent fail at through context drift. Not a task that is too hard for one agent. A task that is right at the edge, where the agent starts well and degrades.

Write down the objective in a single document. This is your canonical context. Keep it short.

Identify the natural seams in the task. Where does the work change domain? Where does one step's output become the next step's input in a clean handoff? Each seam is a delegation boundary.

Define two profiles to start: a lead and one specialist. Resist the urge to create five specialists on day one. Get one delegation cycle working end to end before you add complexity.

Write the brief schema before you write the specialist prompt. The brief is the contract. If you cannot express what the specialist needs as a typed, validatable structure, you are not ready to delegate.

Keep a delegation log on the lead side. Structured, not prose. This is your audit trail and your state reconstruction mechanism.

Tear down specialists after they return. Do not keep them alive in the background hoping to reuse them. The context isolation is the point. A persistent specialist accumulates state and becomes a second lead, which defeats the structure.

What I'd try next

The current structure delegates sequentially. The lead waits for each specialist before delegating the next. For tasks where the sub-tasks are independent, this is wasted time. The next iteration is parallel delegation: the lead dispatches multiple briefs simultaneously and collects structured results. The risk is that the lead's context now fills with multiple concurrent result streams, which reintroduces the noise problem at the coordination layer. The answer is probably a merge step: a dedicated summariser profile that folds multiple specialist results into a single structured report before the lead sees it. That is one more profile, one more boundary, and one more schema to get right. It is where the operating model goes next.
