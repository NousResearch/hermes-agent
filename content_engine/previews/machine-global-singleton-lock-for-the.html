Machine-global singleton lock for the embedded dispatcher: a kanban fix

When you embed a task dispatcher directly into your application process rather than running it as a standalone service, you inherit a subtle but destructive problem: if two instances of the process start on the same machine, both dispatchers wake up, both pull from the same kanban board, and both try to execute the same tasks. The fix is older than most of the tooling around it. A file lock, held for the lifetime of the process, is the cheapest correct guard you can put in front of an embedded dispatcher.

The problem: multiple dispatchers on one machine

The kanban coordination layer I work with runs Hermes profiles as orchestrated workers. Each profile picks up tasks from a shared board, processes them, and moves them through columns. The dispatcher is the component that scans the board, assigns work, and triggers profile execution. It is embedded, meaning it lives inside the same process as the rest of the application rather than running as a separate daemon you manage with systemd or supervisord.

This is convenient until it is not. The convenience is that you do not maintain a separate service, a separate health check, a separate restart policy. The dispatcher starts when your process starts and stops when it stops. The problem is that "your process" might start more than once on the same machine. A crash recovery script might relaunch it while the old process is still shutting down. A deployment might overlap old and new instances briefly. A developer might run it manually while a scheduled instance is already active.

When two dispatchers run against the same kanban board, the failure mode is not a crash. It is worse. Both dispatchers see a task in the "ready" column. Both assign it to a profile. Both execute it. You get duplicate work, corrupted shared state, duplicate calendar events, duplicate messages sent to external services. The system appears to work fine until you notice the duplicates, and by then the damage is done.

The constraint is specific: you need exactly one dispatcher per machine, not one dispatcher globally. If you have three machines, you want three dispatchers, each owning its local set of profiles and tasks. A distributed lock across all machines would be wrong here. You want a machine-local singleton guard.

The mechanism: file locks as process-scoped singletons

The pattern that solves this is a machine-global singleton lock using the operating system's file locking primitives. On Linux and macOS, that means flock. On Windows, LockFileEx. The idea is simple: before the dispatcher starts, it tries to acquire an exclusive lock on a well-known file. If it succeeds, it runs. If the lock is already held by another process, it either exits or runs without the dispatcher enabled.

What makes file locks suitable for this purpose is their lifecycle semantics. The lock is tied to the file descriptor, which is tied to the process. When the process exits, for any reason, including a crash or a kill signal, the operating system releases the lock. You do not need explicit cleanup code. You do not need a heartbeat or a lease renewal. The OS handles it.

The non-blocking variant is important here. You do not want the second instance to wait for the lock. You want it to fail fast and either exit or continue without dispatcher mode. Blocking would mean the second instance hangs silently, which is harder to debug than a clean exit with a log line.

Here is the pattern in its essential form:

import fcntl
import sys
from pathlib import Path

lock_path = Path("/tmp/hermes_dispatcher.lock")
lock_file = lock_path.open("w")

try:
    fcntl.flock(lock_file.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)
except BlockingIOError:
    print("Another dispatcher is already running on this machine.", file=sys.stderr)
    sys.exit(1)

# Write the current PID for diagnostics
lock_file.write(str(os.getpid()))
lock_file.flush()

# Dispatcher starts here. Lock is held until the process exits.

The LOCK_EX | LOCK_NB combination means: try to get an exclusive lock, do not block if it is taken, raise an error instead. The BlockingIOError catch is your fast-fail path. The lock is released automatically when the process exits, whether cleanly or through a crash.

What I built: wiring the guard into the kanban dispatcher

I applied this pattern to the Hermes Kanban coordination layer, which orchestrates specialised profiles. The dispatcher component scans the kanban board, assigns tasks to profiles like the Research Lead and General Assistant, and triggers their execution. Before this fix, nothing prevented two instances from running simultaneously.

The change adds a lock acquisition step early in the dispatcher initialisation. Before the dispatcher creates its task scanner, before it reads the board state, before it assigns anything to any profile, it tries to acquire the lock. If it fails, it logs a clear message and the process continues without the dispatcher active. The rest of the application still works. You can still interact with profiles manually. You just do not get a second dispatcher competing for board tasks.

The lock file lives at a predictable path. I write the PID of the holding process into the file for diagnostics. When debugging, you can check which process holds the lock with lsof or fuser on the lock file path. This matters more than you would expect. When something goes wrong and the dispatcher is not running, the first question is always "is the lock held by a stale process?" Being able to answer that in five seconds instead of twenty minutes of guessing is worth the few lines of code.

The change itself was small. The signal that prompted this work was a kanban fix touching three files across four commits, adding roughly a hundred lines. That ratio tells you something: the concept is compact, but the wiring, the error handling, the logging, the configuration, and the tests add up. The lock acquisition itself is five lines. Everything around it is what makes it production-ready.

The reality check: what is harder than it looks

The hype around file locks is that they are trivially simple. The reality is that the edge cases will bite you if you do not think about them.

The first edge case is lock file location. Using /tmp is tempting and usually fine, but /tmp can be cleared on reboot, and on some systems it is subject to size limits or cleanup policies. Using a directory your application owns, perhaps alongside its data directory, is more predictable. The path needs to be consistent across all instances or the lock is useless.

The second edge case is what happens when the lock file is deleted while the lock is held. On most systems, deleting the lock file does not release the lock because the lock is associated with the file descriptor, not the file path. But if another process creates a new file at the same path, it can acquire a lock on the new file, and now you have two processes thinking they hold the lock. The fix is to never delete the lock file. Create it once, and let it persist. It contains only a PID string and costs nothing.

The third edge case is network filesystems. If your lock file lives on NFS or a similar network filesystem, file lock semantics may not behave as you expect. Different filesystems implement advisory locks differently, and some configurations silently succeed without actually providing mutual exclusion. The safe rule is to keep lock files on local storage only. If your application runs in a container, the lock file should be on a local volume, not a shared mount.

The fourth edge case is graceful shutdown. When the process exits normally, the lock is released. When it is killed with SIGKILL, the lock is also released, because the OS closes all file descriptors. But if the process is stuck in an uninterruptible state, perhaps waiting on a network call to a dead service, the lock stays held. Your monitoring needs to catch this. The lock being held does not mean the dispatcher is healthy. It means the process is alive. Those are different things.

Finally, there is the question of what the second instance should do when it cannot get the lock. Exiting is the simplest option. But in some deployments, you want the process to stay up for other functions while the dispatcher stays dormant. That is the approach I took: the application continues, the dispatcher does not start, and a log line explains why. This is more resilient than a hard exit and makes deployment overlap less disruptive.

How to apply this

If you are running an embedded dispatcher or any singleton process on a machine, here are the concrete steps:

  1. Choose a lock file path on local storage. Use a directory your application owns. Never a network mount.
  1. Open the file in write mode. Do not delete it if it already exists. Create it if it does not.
  1. Attempt flock with LOCK_EX | LOCK_NB (or the equivalent on your platform). Catch the would-block error.
  1. On success, write your PID to the file for diagnostics. Flush the write.
  1. On failure, log a clear message with the PID of the holding process if you can read it. Then either exit or continue without the dispatcher.
  1. Do not write explicit unlock code. Rely on process exit to release the lock. This is more reliable than trying to handle every shutdown path manually.
  1. Add a health check that distinguishes between "process is alive" and "dispatcher is actively scanning the board." The lock tells you the first. It does not tell you the second.
  1. Document the lock file path in your operations runbook. When someone asks why the dispatcher is not running, this is the first thing they should check.

What I'd try next

The singleton lock solves the "one dispatcher per machine" problem. It does not solve the "which machine should run the dispatcher" problem. In a multi-machine deployment, you still need a way to decide which machine activates its dispatcher. Currently, the answer is simple: every machine tries, and the lock ensures only one per machine wins. But if you want exactly one dispatcher across all machines, you need a different primitive, something like a lease in a distributed store.

I would not reach for that unless the pain demands it. Distributed locks introduce network partitions, clock skew, and lease renewal complexity. The file lock is locally correct and operationally simple. For the kanban coordination layer running on a single machine or a small set of machines where one per machine is acceptable, it is the right tool.

The next thing I would try is adding a stale-lock detector. A background thread that periodically checks whether the PID in the lock file corresponds to a running process. If the process has died but the lock was somehow not released (which should not happen with flock, but defensive programming is cheap), the detector can log a warning. It cannot safely steal the lock, because the conditions that cause a stale lock are the same conditions that make it unsafe to assume the lock is actually stale. But it can alert a human to investigate.

That is the shape of this work. Small, durable patterns that solve real coordination problems without introducing distributed systems complexity you do not need. The file lock is one of the oldest tools in the Unix toolbox. It is still here because it works.
