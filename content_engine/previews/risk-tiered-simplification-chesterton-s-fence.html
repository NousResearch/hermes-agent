Risk-tiered simplification: Chesterton's Fence, slop detection, and not deleting the wrong thing

Automated code simplification is easy to get wrong in a way that is expensive to notice. The dangerous simplifications are not the ones that break tests, because tests catch those immediately. The dangerous ones are guards that exist for a silent failure mode, a condition that rarely triggers but matters when it does. This is a learning log about building a simplify-code feature that applies risk tiers, respects Chesterton's Fence, and tries to detect when a simplification has introduced slop or a silent failure path.

The problem: simplification that removes guards

Most "simplify this code" tooling, whether a linter autofix or an LLM prompt, optimises for reducing lines and cyclomatic complexity. That is a reasonable proxy for readability most of the time. But it has a failure mode that anyone who has maintained production code will recognise: a guard clause that looks redundant because the condition "can never happen" gets removed, and six months later a silent failure occurs in exactly the case the guard was written for.

The pattern is old enough to have a name. Chesterton's Fence: do not remove a fence until you know why it was put up. In code, the fence is often a null check, a type narrowing, a defensive early return, or a comment-annotated workaround. They look like noise. They are not noise.

The question I wanted to answer: can you build a simplification pass that is aggressive on genuinely redundant code but conservative on guards, and can you detect when you have guessed wrong?

The mechanism: risk tiers as a first-class concept

The core idea is to stop treating simplification as a single operation. Instead, classify every proposed change into a risk tier before applying it. The tiers I landed on, after iterating, are:

  • Tier 0: Pure formatting and dead branch removal. Code that is provably unreachable, or formatting normalisation. Apply automatically.
  • Tier 1: Structural simplification with preserved semantics. Collapsing nested conditionals, extracting a helper, replacing a loop with a comprehension. The behaviour is provably equivalent. Apply with test verification.
  • Tier 2: Guard removal or condition narrowing. Anything that removes a defensive check, narrows a type, or eliminates an early return. This is the Chesterton's Fence tier. Do not apply automatically. Surface for review, and require a justification.
  • Tier 3: Behavioural change. Anything that changes observable behaviour. Reject by default in a simplification pass; this is a refactor, not a simplification.

The important property is that Tier 2 exists at all. Most tooling either applies everything or applies nothing. The intermediate position, "I think this is safe but I am not sure why this guard exists," is where the value is.

Here is a sketch of the classification logic, simplified to illustrate the concept:

def classify_change(change):
    if change.removes_dead_code or change.is_formatting:
        return Tier.T0

    if change.removes_guard_or_early_return:
        return Tier.T2

    if change.changes_observable_behavior:
        return Tier.T3

    return Tier.T1

The real classification is messier than this, but the shape is right: guard removal is its own category, separated from structural simplification.

Slop and silent failure detection

The second half of the feature is a check on the output, not the input. After a simplification pass runs, you want to detect two things:

Slop is code that compiles and passes tests but is semantically looser than the original. The classic example: replacing an explicit error path with a generic catch, or replacing a typed narrow with a wider type. The code works, but it has lost specificity.

Silent failure is when a code path that previously threw or logged now does nothing. The guard that returned an error on a missing field is gone, so the code proceeds with a default and produces a wrong result quietly.

The detection approach I used is to compare the observable effect surface before and after. Concretely, for each function that was modified:

  1. Identify the set of conditions under which the function could produce an error, log a warning, or return a sentinel value.
  2. After simplification, compute the same set.
  3. If the post-simplification set is a strict subset of the pre-simplification set, flag it. A simplification that reduces error paths is the signature of a removed guard.
def detect_silent_failure(before, after):
    before_error_conditions = before.error_conditions()
    after_error_conditions = after.error_conditions()

    removed = before_error_conditions - after_error_conditions
    if removed:
        return Flag(
            severity="review",
            reason=f"Simplification removed error path: {removed}",
        )
    return None

This is conservative by design. It flags any reduction in error surface, including legitimate ones. The point is not to block all of them; the point is to make the reviewer aware that a fence may have been removed.

What I built: the simplify-code feature

The feature is a simplify-code command that takes a file or directory, runs a simplification pass, and produces a diff grouped by risk tier. Tier 0 and Tier 1 changes are applied directly. Tier 2 changes are written as comments in the diff, with the original guard preserved and a note explaining why it was flagged. Tier 3 changes are rejected entirely.

The output for a Tier 2 flag looks something like this:

// RISK-TIER-2: Removed guard on `user.email == null`
// Original: if (user.email == null) return ValidationError("email required")
// Reason: Guard removal detected. This guard may exist for a
//         silent failure mode. Review before accepting.
// Justification required: [ ]

The reviewer has to fill in the justification before the change can be merged. This is the Chesterton's Fence enforcement mechanism: you can remove the guard, but you have to say why it was put up first.

The slop detection runs as a post-pass. After the simplification diff is generated, the tool checks whether any function's error surface has shrunk. If it has, the diff is annotated with a warning, and the Tier 2 flag is upgraded to require explicit acknowledgement.

The economics of this matter. The feature is small, a handful of files, and the classification logic is the bulk of it. The value is not in the code volume; it is in forcing a decision at the right point. A simplification pass that removes a guard without telling you is worse than no simplification pass at all, because it introduces a regression that is invisible until it matters.

Reality check: hype versus practice

The hype version of automated simplification is that you point a tool at a codebase and it makes everything cleaner with no risk. The practice is that simplification is a judgement call, and the tool's job is to surface the judgement, not to make it for you.

Things that are harder than they look:

Classifying Tier 2 correctly is genuinely difficult. A guard that checks if (x == null) before a database write is obviously load-bearing. A guard that checks if (x.status != "pending") before an update is less obvious, and whether it is redundant depends on the state machine elsewhere in the codebase. The classifier uses heuristics, not a full semantic model, and it both over-flags and under-flags. Over-flagging is fine; it produces noise but no harm. Under-flagging is the real risk, and there is no cheap solution to it.

Slop detection has false negatives. The error-surface comparison catches guards that produce errors or logs. It does not catch a simplification that replaces a specific error message with a generic one, or that changes the timing of when an error is raised. These are slop, but they are not detectable by this method. The detection is a lower bound on slop, not a complete check.

The justification field is the weakest link. The tool requires a justification for Tier 2 changes, but it cannot evaluate the quality of the justification. "Not needed" is a valid string. The enforcement is procedural, not semantic. It works in a team culture where reviewers actually read justifications. It does not work as a gate on its own.

Test coverage is the real safety net. The risk tiers reduce the frequency of bad simplifications, but the thing that actually catches a removed guard is a test that exercises the condition the guard was protecting. If that test does not exist, no tier system will save you. The feature is a complement to test coverage, not a substitute.

How to apply this

If you are building or configuring code simplification tooling, the decision rules I would recommend:

  1. Separate guard removal from structural simplification. Do not treat them as the same operation. If your tool does not distinguish them, add a post-pass that at least annotates which changes touch error paths or early returns.
  1. Require a justification for any change that reduces the error surface. The justification does not need to be long, but it needs to exist and it needs to be reviewed by a human.
  1. Run slop detection as a diff annotation, not a gate. A gate that blocks all error-surface reductions will produce too many false positives and people will disable it. An annotation that says "this change removes 2 error paths" is useful information that a reviewer can use.
  1. Default to Tier 0 and Tier 1 only in automated runs. Save Tier 2 for interactive sessions where a human is in the loop. Automated CI simplification that includes Tier 2 will eventually remove a guard that matters.
  1. Check whether a guard was added in response to a past incident before removing it. If your version control history or incident log references the condition the guard checks, that is a strong signal to leave it alone. This is the operational version of Chesterton's Fence: the fence was put up because something got through it.

What I'd try next

The classifier currently uses syntactic heuristics. The next step is to make it slightly less syntactic: for each guard, look at the git blame and the commit message that introduced it. If the commit message references a bug fix, an incident, or a specific failure mode, that guard gets an automatic Tier 2 classification with the commit message as context for the reviewer. This does not require any semantic understanding of the code; it just requires correlating the guard with the reason it was written.

The slop detection could also be extended to compare log output, not just error paths. A simplification that removes a log statement is often fine, but it is sometimes the only observable signal for a condition that is now silent. Comparing the log surface before and after would catch a class of slop that the error-surface check misses.

Finally, I want to track the outcomes. For each Tier 2 flag, record whether the reviewer accepted or rejected the simplification, and whether any subsequent incident was traced back to a guard removal. Over time, this builds a dataset of which heuristic classifications are accurate and which are noise, and the classifier can be tuned accordingly. The feature is only useful if the flags are trustworthy, and trustworthiness is something you measure, not something you assume.
