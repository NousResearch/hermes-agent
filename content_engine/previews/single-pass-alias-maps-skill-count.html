Single-pass alias maps, skill-count caching, and event-loop offload: making profile listing fast

When you ask an agent system "what specialist profiles exist and what can each one do?", the answer should be instant. It rarely is. I spent a morning refactoring the list_profiles path in KENSEI and the lesson that stuck was not about any single trick but about layering three small optimisations that compound.

The hot path nobody profiles

In KENSEI, profiles are the specialist personas the agent can route to. Each profile has a canonical name, a set of aliases, and a skill manifest. When the orchestrator needs to decide which specialist to hand a task to, it calls list_profiles. That call returns every profile, its aliases resolved to canonical names, and a per-profile skill count that the router uses as a rough capability signal.

The problem: this call happens on every routing decision. It is not cached at the call site. It walks every profile directory, reads each manifest, builds an alias-to-canonical map, and counts skills. In a system with a dozen profiles this is fine. When you start adding profiles for different domains, the latency creeps up, and because the call is on the hot path, the creep compounds with every user turn.

The commit that addressed this bundled three changes. Each is independently useful. Together they change the character of the function from "slow and repeated" to "fast and cached".

The mechanism: one pass, not three

The first change is the simplest and the most generalisable. The original list_profiles did something like this:

# Before: three passes through the profiles list
names = [p.name for p in profiles]
aliases = {}
for p in profiles:
    for alias in p.aliases:
        aliases[alias] = p.name
skill_counts = {p.name: len(p.skills) for p in profiles}

Three iterations over the same list. The refactored version does it in one:

# After: single pass
alias_map = {}
skill_counts = {}
for p in profiles:
    alias_map[p.name] = p.name
    for alias in p.aliases:
        alias_map[alias] = p.name
    skill_counts[p.name] = len(p.skills)

The performance difference on a small list is negligible. The point is not the speedup on a dozen items. The point is that this pattern scales: as profiles grow, you have one pass instead of three, and the alias map includes the canonical name mapped to itself, which simplifies downstream lookups. You never need to check "is this already canonical?" separately because the canonical name is in the map.

This is the kind of change that code review would flag as premature optimisation if the list were small and static. The reason it is not premature here is that the list is neither small nor static in the intended deployment, and the function sits on the hot path.

The skill-count cache: memoisation with a clear invalidation boundary

The second change caches the skill counts. Counting skills requires reading each profile's manifest, which is a file read or a parsed JSON object. Doing this on every list_profiles call is wasteful when the skill manifest changes rarely.

The cache is straightforward:

_skill_count_cache = {}

def get_skill_count(profile_name, profile):
    if profile_name not in _skill_count_cache:
        _skill_count_cache[profile_name] = len(profile.skills)
    return _skill_count_cache[profile_name]

The hard part is not the cache. The hard part is invalidation. When does the cache go stale?

The answer in KENSEI: when a profile's skill manifest is written. The profile management code already had a write_manifest function that is the single entry point for skill changes. Adding a cache invalidation line there means the cache is correct without needing a global invalidation or a TTL guess.

def write_manifest(profile_name, manifest):
    # ... existing write logic ...
    _skill_count_cache.pop(profile_name, None)

This is the pattern I want to highlight: the cache is only safe if the invalidation boundary matches the mutation boundary. If skills could be modified by any other code path, the cache would be a bug. The discipline of routing all mutations through one function makes the cache cheap and correct. Without that discipline, no caching strategy saves you from staleness.

Event-loop offload: the async trap hiding in plain sight

The third change is the one that had the largest effect in practice. The list_profiles function was async, but the work it did was synchronous: file reads, JSON parsing, dictionary construction. In Python's asyncio, synchronous work inside an async function blocks the event loop. Every other coroutine waiting on the loop stalls until list_profiles finishes.

The fix is to move the blocking work to a thread pool:

import asyncio

async def list_profiles():
    return await asyncio.get_event_loop().run_in_executor(
        None, _list_profiles_sync
    )

def _list_profiles_sync():
    # the actual file reads, parsing, map building
    ...

This is not free. Thread pool execution has overhead, and for very fast operations the context switch costs more than the blocking. The threshold depends on the workload. For list_profiles, the file reads and JSON parsing sit well above that threshold once you have more than a handful of profiles.

The trade-off: you are now using a thread from the default executor. Python's default pool size is min(32, os.cpu_count() + 4). If many async paths start offloading to threads simultaneously, you can exhaust the pool. This is fine for list_profiles because it is called rarely relative to the volume of LLM calls, but it is worth knowing before you start offloading everything in sight.

Reality check: what the hype gets wrong

The temptation with this kind of work is to claim a dramatic speedup. "Cut latency in half" or "10x faster" are the kind of numbers that get attention. They are also the kind of numbers that are meaningless without context: faster than what? Under what load? With how many profiles? On what hardware?

The honest framing: these three changes move list_profiles from "does redundant work on every call and blocks the event loop while doing it" to "does the work once, caches what is stable, and does not block other coroutines". The improvement is real but it is not a single number. It depends on profile count, skill manifest size, and what else is running on the event loop concurrently.

What I will say concretely: the single-pass alias map is the change I would make first if I were starting over. It is the simplest, the most obviously correct, and it carries no invalidation concerns. The cache is second: useful but only safe because the mutation boundary is clean. The event-loop offload is third: highest impact but also the one with the most subtle failure modes if the thread pool comes under pressure.

One thing the optimisation literature does not emphasise enough: the biggest win was not any of these three changes. It was realising that list_profiles was on the hot path at all. Adding a call-site cache in the orchestrator, a one-line @lru_cache on the routing function's profile lookup, would have delivered most of the benefit without touching the function internals. I made the internal changes because they make the function better regardless of call-site caching, but if you are triaging performance and you only have time for one fix, cache at the call site first.

How to apply this

  1. Find your hot path. Use a simple timer or profiler around the function that gets called on every turn. In KENSEI this was list_profiles in the routing path.
  1. Before optimising the function, check whether you can cache at the call site. A @lru_cache or a manual dict cache on the caller side is often the highest-leverage change for the least effort.
  1. If you do optimise the function itself, start with algorithmic changes. Collapsing multiple passes into one is the cheapest win and the easiest to verify.
  1. Add caches only where the invalidation boundary is clear. If you cannot point to the single function that mutates the cached data, do not cache. You are trading correctness for speed and you will lose.
  1. Offload to a thread pool only for genuinely blocking work. Measure before and after. If the function completes in under a millisecond, the offload overhead is probably not worth it.
  1. The mutation boundary is the foundation. If all writes go through one function, caching is safe and cheap. If writes are scattered, no amount of caching will save you from staleness bugs.

What I'd try next

The natural next step is a manifest-level cache, not just a skill-count cache. If the entire parsed manifest is cached and invalidated on write_manifest, the list_profiles path becomes a pure dictionary lookup with no file I/O at all. The risk is memory: caching full manifests for every profile uses more memory than caching counts. For KENSEI's profile count, which sits in the low double digits, this is negligible. For a system with thousands of profiles, it would need a different strategy, perhaps an LRU eviction policy.

I would also like to move the alias map construction to build time rather than runtime. If profiles are registered through a single register_profile function, the alias map can be built incrementally as profiles are added, and list_profiles just returns the pre-built map. This eliminates the pass entirely. The trade-off is that the map lives in memory for the lifetime of the process, which is fine for a long-running agent but wasteful for a short-lived CLI invocation.

The last thing I want to explore is whether the event-loop offload is necessary at all once the manifest cache is in place. If list_profiles becomes a set of dict lookups, it is fast enough to run synchronously on the loop without blocking anything meaningful. The offload might be removed, simplifying the code and freeing thread pool capacity. Sometimes the best optimisation is the one you can delete after the real fix lands.
