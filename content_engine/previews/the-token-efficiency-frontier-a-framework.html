The Token-Efficiency Frontier: A Framework for PMs Who Actually Ship AI Features

Every product team building on top of large language models eventually hits the same wall. Someone asks, in a planning meeting, "Why is this so expensive?" and the room goes quiet. The honest answer is that the team has been optimising the wrong thing. They have been counting tokens as if more tokens meant more value, or treating cost as a constraint to bolt on after the fact. Neither works. What works is the Token-Efficiency Frontier Framework: a way of mapping the trade-off between what you spend and what you get, so that every decision about model, context, and prompt lands somewhere defensible.

This post walks through the framework from first principles, applies it to a real system I run (a multi-service agent stack with chat, command centre, and content pipeline components), and ends with a decision rule you can reuse on Monday morning.

The problem with naive token thinking

The default mental model in most AI product teams goes like this: tokens are fuel, more context is better, and the right thing to do is maximise useful output per dollar. It sounds reasonable. It is also a category error.

Tokens are not fuel. Fuel has a roughly linear relationship with motion. Tokens have a non-linear relationship with capability. Stuffing a 200k context window does not give you a 2x better answer than a 100k window, and a 4x more expensive model does not give you a 4x better answer than the cheap one. The relationship is closer to a diminishing returns curve, and the curve has a knee, and the knee is different for every task.

The second mistake is treating cost as a single number. In a real system, you have at least three costs running in parallel: the model tokens (which you pay the API for), the latency budget (which you pay in user patience), and the engineering surface area (which you pay in maintenance). A "cheap" prompt that requires three retries, a fallback chain, and a custom evaluation harness is not cheap.

The third mistake is treating the frontier as a line. It is a region. For any given task, there is a set of configurations (model, context size, prompt style, retrieval depth, tool count) that achieve a target quality at the lowest cost, and another set that achieve the highest quality at any cost. The region between them is the frontier. Outside the frontier, you are spending tokens you do not need to, or accepting quality you should not.

What the frontier actually looks like

Imagine a graph with quality on the y-axis and total cost on the x-axis. Each point on the graph is a configuration: a specific model, a specific prompt template, a specific context window, a specific set of tools enabled. Plot enough of them and you get a cloud. The upper-left edge of that cloud is the frontier. Configurations on the frontier are Pareto-optimal: you cannot improve quality without raising cost, and you cannot lower cost without sacrificing quality. Configurations inside the cloud are dominated: there is another configuration that is both cheaper and better.

The job of the PM is not to find a single "best" point. The job is to know which point on the frontier you are operating at, and to know when the task has moved you to a different frontier altogether.

Tasks have frontiers. Summarisation has one frontier. Multi-step agentic reasoning has another. Code generation has a third. A configuration that is frontier-optimal for one task is often dominated for another. The mistake teams make is shipping a single configuration across all tasks, which is equivalent to drawing one point on the graph and calling it done.

The three axes that define your position

Every configuration lives at the intersection of three axes. Knowing them lets you reason about movement.

The first axis is model tier. This is the obvious one, and the one teams over-optimise. The cheap model is not always cheaper in total once you account for the longer prompts it needs and the extra retries it triggers. The expensive model is not always better once you account for the fact that you are using it for tasks the cheap model handles fine.

The second axis is context composition. This is the one PMs have the most leverage over. A 4k context of carefully chosen, task-specific material will outperform a 128k context of loosely relevant background almost every time. The composition includes: system prompt length, number of retrieved documents, tool definitions, conversation history, and any injected user state. Every one of these is a place to spend or save.

The third axis is interaction shape. Single-shot prompt, multi-turn conversation, agent loop with tool calls, plan-then-execute pattern. The shape determines how many model calls happen, how much state is carried, and how error-prone the whole thing is. A well-designed agent loop on a cheap model can be both cheaper and more reliable than a single expensive call to a powerful model, because the loop allows decomposition, validation, and early termination.

A worked example: a triage agent on a multi-service stack

Here is a real configuration I have been tuning, stripped of identifying detail. The stack has a chat service, a dashboard API exposing sessions, skills, memory, config, cron, conductor, swarm, profiles, kanban, approvals and a terminal proxy, and a self-hosted content scheduler. There is also a Google Workspace integration across three Gmail accounts, with token refresh currently manual and a 7-day expiry in test mode.

The naive configuration: load the entire system state (every session, every skill, every profile, every kanban column) into a single prompt, hand it to the most capable model, ask it to triage. Tokens: roughly 180k per call. Cost per triage: high. Latency: painful. Quality: surprisingly mediocre, because the model drowns in irrelevant context and the relevant signals are buried.

A frontier configuration: use the dashboard API to fetch only the sessions flagged as needing review, summarise each into a 200-token capsule, and pass those capsules plus a tight triage rubric to a mid-tier model. Tokens per call: around 12k. Cost: roughly 15x lower. Latency: about 4x faster. Quality: higher, because the model is not wasting attention on noise and the rubric is forcing a structured output.

The move was not "use a worse model". The move was changing the context composition and the interaction shape. The model tier barely moved. The same lesson applies to the Gmail integration: pulling all three mailboxes into context for every query is dominated by routing the query to the right mailbox first and pulling only what is needed.

The trade-offs nobody warns you about

The frontier has a few features that bite teams who do not see them coming.

The first is that frontier configurations are task-specific. A triage prompt is not a summarisation prompt is not a planning prompt. If you ship one configuration, you are operating on the wrong frontier for most of your tasks, and you are paying for the privilege.

The second is that the frontier moves. New models shift it. New tools shift it. New retrieval methods shift it. A configuration that was frontier-optimal six months ago is now dominated. You need a mechanism for re-evaluating, not a one-time exercise.

The third is that some points on the frontier are operationally fragile. The configuration that is cheapest in tokens might depend on a tool call that fails 8% of the time, which means retries, which means the actual cost is higher than the modelled cost. PMs need to include failure rates in the cost calculation, not just nominal API spend.

The fourth is the testing trap. It is easy to benchmark on a small, hand-picked set of examples and conclude you have found the frontier. You have found the frontier for those examples. Real traffic looks different. The only honest way to find the frontier is to measure on real traffic, with a representative sample, and to revisit the measurement regularly.

How to apply this framework

Step one: pick the three or four tasks that account for the bulk of your token spend. Do not start with the long tail. Start where the money is.

Step two: for each task, define a quality metric you can measure cheaply. This might be a rubric score, a human-rated sample, an automated check on output structure, or a downstream business metric. Without a metric, the frontier is a guess.

Step three: enumerate the configurations you are willing to consider. Vary model tier, context composition, and interaction shape independently where you can. A reasonable starting grid is 2 models x 3 context sizes x 2 interaction shapes, giving 12 configurations per task.

Step four: run each configuration on a representative sample and plot the result. The frontier will be visible. If it is not visible, your configurations are too similar or your quality metric has too much noise.

Step five: pick the point on the frontier that matches your constraints. A user-facing feature with a tight latency budget sits in a different place than a back-office batch job that runs overnight.

Step six: instrument the production configuration so you can detect when the frontier has moved. Track cost per call, quality on a sampled basis, and failure rates. Review quarterly.

What I'd try next

I am going to build a small internal tool that runs this exercise automatically for the highest-spend tasks in my stack. The tool takes a task description, a quality metric, and a grid of configurations, and produces a frontier plot with the current production point highlighted. The first version will be ugly. The point is to make the framework executable, not just intellectually satisfying.

I am also going to retire one assumption I have been carrying: that the most capable model is the right default for "hard" tasks. In my own stack, the hard tasks are the ones where context composition matters most, and a mid-tier model with a tight context has, in two out of three cases I have measured, beaten the top-tier model with a loose context. The framework would have caught this earlier. I am catching it now.

Reflection

Most AI product decisions are made in the dark, with cost measured at the end of the month and quality measured by vibes. The Token-Efficiency Frontier Framework is a way of bringing light to that process without pretending it is a science. The frontier is real, the trade-offs are real, and the points on the frontier are reachable, but only if you measure them rather than assume them. The most useful thing this framework has done for me is change the question. I no longer ask "which model should I use". I ask "which point on which frontier am I operating at, and is it the right one for this task". That question has a defensible answer. The old one almost never did.
