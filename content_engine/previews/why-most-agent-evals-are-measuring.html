Why most agent evals are measuring the wrong thing

Most agent evaluation frameworks score whether the model called the right function. That is the easy part. The hard part, and the part that actually breaks in production, is whether the agent acted on the right entity: the right customer record, the right Slack thread, the right repository branch. Tool selection is a solved measurement problem. Entity binding is not measured at all, and the gap between the two is where agents silently fail in ways that are expensive, hard to detect, and structurally invisible to the eval harness you probably already have.

The measurement gap

The measurement gap

The standard agent eval pipeline looks something like this: you define a set of tasks, each with an expected tool call sequence, and you score the agent on whether it produced the right calls in the right order. If the task is "send a message to Alice about the Q3 report," the eval checks whether the agent called send_message. It might check whether the message body mentions Q3. It rarely checks whether the recipient field resolved to Alice and not Alex.

This is not a hypothetical concern. It is the dominant failure mode in multi-entity environments. An agent operating across a CRM, a messaging platform, and a document store has to bind each action to a specific entity identifier. The model might perfectly understand that it needs to use send_message, perfectly compose the body, and send it to the wrong person because it conflated two contacts with similar names, or picked the first result from a fuzzy search, or carried over an entity reference from a previous turn in the conversation.

Signal: The eval says "tool call correct, task passed." The audit log says "message sent to wrong recipient." Both are right. They are measuring different things.

The core problem is that tool selection is a classification problem with a small, closed label set. Entity binding is a retrieval problem over an open, often ambiguous, and context-dependent set. Evaluating one does not evaluate the other. They are structurally independent failure modes, and most eval frameworks treat the former as a proxy for the latter.

Tool selection vs entity binding

Tool selection vs entity binding

Tool selection is the question "which function should I call?" The answer space is the tool registry, typically a few dozen entries. The model has the schema, the description, and the parameter types. Modern models get this right almost all the time in controlled settings. When they do not, the error is obvious: the agent called delete_record instead of update_record, and your eval catches it immediately.

Entity binding is the question "which specific instance of the external thing should this parameter resolve to?" The answer space is the entire state of the external system: every user, every document, every channel, every order. This space is unbounded, changes over time, and is frequently ambiguous. Two customers named "Alex Chen" in the CRM. Two Slack channels called #engineering. Two branches named feature-auth. The model has to resolve a natural language reference to a specific identifier, and the resolution depends on context that may or may not be in the prompt.

The mechanism of failure is straightforward. The agent receives a request like "follow up with the vendor about the delayed shipment." It correctly identifies that it should use send_email. It searches the contact database for "vendor" and gets back 14 results. It picks one. Maybe it picks the right one. Maybe it picks the one from the last shipment, not this one. Maybe it picks the primary vendor contact, but the delayed shipment was handled by a secondary contact. The tool call is correct. The entity binding is wrong. The eval, if it only checks tool selection, passes the run.

Signal: Entity binding failures are silent because the agent does everything it was asked to do at the API level. The error only manifests in the world, not in the call log.

Why standard evals miss entity errors

There are three structural reasons standard eval frameworks do not catch entity binding failures.

First, evals typically run against synthetic or frozen environments where entity ambiguity is minimised by design. The test fixture has one user named Alice, one document titled "Q3 Report," one channel called #engineering. In production, there are five Alices, two Q3 reports, and three engineering channels. The eval environment does not reproduce the ambiguity that causes the failure.

Second, evals check outputs, not side effects. If the agent calls send_message(recipient="alice@corp.com", body="..."), the eval sees a well-formed API call with a plausible-looking recipient. It does not check whether alice@corp.com is the Alice the user meant. To do that, the eval would need to maintain a mapping from natural language references to canonical entity identifiers, and check the agent's resolution against that mapping. Almost no eval framework does this.

Third, evals are often scored by an LLM judge that reads the conversation transcript and decides whether the task was completed. The judge sees the agent say "I've sent the message to Alice" and marks the task as complete. The judge does not have access to the external system state to verify which Alice received the message. The judge is evaluating the narrative, not the world state.

Signal: The eval environment, the scoring method, and the judge's information access are all structured to measure what the agent said it did, not what the agent actually did to which entity.

The cost asymmetry of wrong-entity actions

Wrong-tool errors are loud. If the agent calls delete_database instead of read_database, the system breaks immediately and someone notices. The error is caught, the bug is filed, the fix is shipped.

Wrong-entity errors are quiet. The agent sends the message to the wrong Alex Chen. The message is professional, well-formatted, and on-topic. The wrong Alex does not reply, or replies with confusion that gets lost, or takes an action based on information that was not meant for them. The error propagates. By the time anyone notices, the audit trail points to a "successful" agent run.

The cost asymmetry is severe. A wrong-tool error costs you a failed task and a debugging session. A wrong-entity error costs you a data leak, a compliance violation, a broken customer relationship, or a financial transaction against the wrong account. The eval framework that only catches the former is optimising for the cheap failure and ignoring the expensive one.

In regulated environments, this is not just a cost problem. It is a liability problem. If your agent sends customer A's order details to customer B, you have a GDPR breach. Your eval said the agent passed. The regulator does not care about your eval. They care about which entity received which data.

What a correct eval looks like

A correct agent eval for entity binding has three components that standard frameworks lack.

Entity-grounded task definitions. Each task specifies not just the expected tool call but the expected entity resolution. "Send a message to Alice Chen (user_id: usr_8f3a) about the Q3 report (doc_id: doc_22b1)." The eval checks whether the agent's API call resolved to usr_8f3a and doc_22b1, not just whether it called send_message.

Ambiguous environments. The eval fixture must contain entity collisions: multiple users with the same name, multiple documents with similar titles, multiple channels with overlapping purposes. If the fixture has one Alice, you are not testing entity binding. You are testing tool selection in a trivially unambiguous world.

Side-effect verification. The eval must check the state of the external system after the agent run, not just the API call log. Did the message arrive in the right user's inbox? Did the file get written to the right directory? Did the PR get opened against the right branch? This requires the eval harness to have read access to the external system, which most do not.

Signal: The minimum viable entity eval is: (1) a task with a canonical entity resolution, (2) an environment with deliberate ambiguity, (3) a post-run check of external system state against the canonical resolution. Without all three, you are not measuring entity binding.

The same blind spot in coding agent guidance

The entity binding problem has a parallel in the coding agent space that is equally under-measured. When engineers write guidance files for coding agents (AGENTS.md, CLAUDE.md, or similar), they include navigation hints, test commands, coding conventions, and architectural notes. The assumption is that this guidance helps. Whether it actually helps is rarely tested.

The durable pattern here is the same: the eval measures whether the agent followed the guidance, not whether the guidance improved the outcome. An agent that runs the test command specified in the guidance file is scored as "following instructions." But the question that matters is whether the guidance caused the agent to produce a correct fix faster, or whether it caused the agent to fix the right file, or whether it introduced a bias toward a particular subsystem that was wrong for this specific task.

The right approach is systematic: treat each guidance unit as an intervention and measure its effect on task outcomes. Does the test command hint reduce iterations to a passing fix? Does the navigation hint reduce the number of files the agent reads before finding the right one? Does the coding convention reduce the rate of style-related review failures? If you cannot measure the effect, you do not know whether the guidance helps or harms.

This is the same structural error as the tool-selection eval. You are measuring compliance with an instruction rather than improvement of an outcome. The instruction-following metric is easy to collect and almost useless for deciding whether to keep the guidance.

Trade-offs in building entity-aware evals

Building an entity-aware eval is expensive. You need to maintain entity fixtures, keep them ambiguous in realistic ways, and verify side effects after every run. The cost scales with the number of entity types your agent touches. For an agent that operates on users, documents, and channels, you need three separate fixture systems, each with collision sets and canonical resolutions.

The honest trade-off is this: entity-aware evals are hard to build and slow to run, but they catch the failures that matter. Tool-selection evals are easy to build and fast to run, but they catch failures that are already rare and cheap. If your agent operates in a single-entity environment (one user, one repo, one document), the entity binding risk is low and the investment is not justified. If your agent operates across multiple entities of the same type, the investment is mandatory.

A reasonable decision rule: if your agent's actions are parameterised by entity IDs that come from search or resolution rather than direct user specification, you need entity-aware evals. If the user always provides the exact ID, you do not. Most production agents fall into the first category. Most eval frameworks assume the second.

How to apply this

  1. Audit your existing evals for entity checks. For each task in your eval set, ask: does the expected outcome specify a canonical entity ID, or just a tool call? If only a tool call, the task is not testing entity binding. Flag it.
  1. Introduce collision sets into your eval fixtures. For each entity type your agent touches, add at least two entities with near-identical natural language descriptions. Two users with the same first name. Two documents with overlapping titles. Two channels with similar purposes. If the agent resolves correctly in the presence of collisions, you have a real signal.
  1. Add post-run state verification. After each agent run, query the external system to check which entity was actually affected. Compare against the canonical resolution in the task definition. This is the only way to catch silent wrong-entity actions.
  1. Score entity binding separately from tool selection. Report two metrics: tool selection accuracy and entity binding accuracy. They are independent. A high tool selection accuracy with a low entity binding accuracy tells you exactly where to invest: better entity resolution, not better tool descriptions.
  1. Test your guidance, not just compliance with it. For each guidance unit in your agent's context file, run a controlled comparison: the same task with and without the guidance. Measure outcome quality, not instruction-following rate. If the guidance does not improve outcomes, remove it. It is consuming context window for no benefit.

What I'd try next

Build a minimal entity binding eval for a single agent workflow, one that operates on two entity types with deliberate collisions. Run it against your current model and measure the gap between tool selection accuracy and entity binding accuracy. If the gap is large, which it likely will be, the next investment is not a better model or better tool descriptions. It is a better entity resolution step: explicit disambiguation prompts, confirmation before acting on ambiguous references, and structured entity search that returns candidates with enough metadata for the model to distinguish them. The model is not going to solve entity binding by itself. The eval has to measure it first, and the system has to be designed around it.
