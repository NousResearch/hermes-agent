## 1. 产品摘要

AgentOps 完整自愈平台是一套独立于 Hermes Gateway 和业务 Agent 的本地控制面。它持续登记运行对象、采集技术与业务信号、把重复信号聚合为事故、生成可审计的修复计划，并按风险等级执行确定性修复、隔离代码修复、灰度验证和自动回滚。

平台不是“每天运行一次 LLM 日志总结”，也不是允许 Agent 无限制修改生产环境。确定性检测、已审核 Runbook 和回滚能力必须在模型不可用时继续工作；生产数据、业务规则、Prompt 和高风险发布默认需要人工批准。

## 2. 背景与问题

Hermes 当前已经具备日志、Doctor、Cron、Curator、插件、Dashboard 和 Kanban 等能力，但它们尚未形成统一事故闭环。此前几轮实际修复暴露出以下问题：

1. 模型适配问题：Codex Responses 流解析异常、工具 Schema 兼容、凭证状态传递和按轮 Reasoning 路由。
2. 运行稳定性问题：Gateway 重复启动、飞书断连、MCP 周期性连接失败、API 调用与压缩失败。
3. 用户体验问题：内部重试和辅助任务警告暴露给用户、后台任务把大段日志注入会话、异常时可能无有效回复。
4. 检查“假绿”：任务进程退出码为 0，但预期业务能力实际不可用，例如已知 MCP 故障被静默处理后仍显示 Cron 成功。
5. 业务质量问题：明确指定原书却生成其他书、dry-run 绕过生产主链、R1/R2/R3 规则未真实执行、压缩失败产物被误用、写回来源与记录隔离不足。
6. 发布基线问题：当前工作目录存在用户未提交修改，并且与上游有较大差异，无法安全地在实时目录中自动改代码和发布。
7. 控制器重叠问题：现有多个 Profile、Gateway、watchdog、Cron 和独立 agentops 运行面，若没有唯一控制权，可能发生重复重启、重复告警和相互修复。

因此，核心产品问题不是“缺少一个 Review Prompt”，而是缺少统一的目标登记、事故状态、权限策略、验证证据和发布回滚体系。

## 3. 产品愿景

让每一次已经发生并确认的问题，都能至少沉淀为以下资产之一：

- 一个确定性探针；
- 一条事故指纹和关联规则；
- 一个回归测试；
- 一个业务黄金用例；
- 一个带前置条件、验证和回滚的 Runbook；
- 一条发布健康门禁。

平台最终形成闭环：

```text
发现 → 聚合 → 诊断 → 计划 → 授权 → 修复 → 验证 → 灰度 → 观察 → 解决/回滚 → 资产沉淀
```

## 4. 目标与非目标

### 4.1 产品目标

**G-01 主动发现：** 在用户反馈前发现重复故障、业务假绿和体验回归。

**G-02 统一沉淀：** 用稳定指纹把同类信号聚合成事故，保存证据、根因、修复和验证历史。

**G-03 安全自愈：** 对白名单内、确定性、可逆的运维问题自动修复。

**G-04 受控代码修复：** 在隔离 worktree 中复现、搜索上游、补回归测试和生成补丁，不直接修改实时部署目录。

**G-05 可验证发布：** 只有不可变版本才可进入灰度；健康门禁失败时自动回滚。

**G-06 业务质量保护：** 将 Book Workflow 等关键流程的业务不变量做成版本化 Review Pack。

**G-07 单一控制权：** 全部写操作由唯一控制面编排，现有 watchdog 和 agentops 只能成为采集器或被迁移、停用。

### 4.2 非目标

- 不在第一版建设多机分布式 SaaS、Postgres 集群或消息队列。
- 不把 LLM 判断当作唯一故障检测依据。
- 不允许 Agent 无审批修改生产数据、业务规则或 Prompt。
- 不重新实现 Hermes 主聊天界面。
- 不替代现有日志、Cron、Doctor、Kanban；只通过适配器复用它们。
- 不承诺修复所有未知问题；未知问题首先生成高质量事故与修复建议。
- 不在部署基线未清理前开放代码自动发布。

## 5. 用户与职责

### 5.1 Molly：平台所有者

- 查看 Fleet 健康和事故摘要。
- 审批高风险 ActionPlan。
- 设置维护窗口、自动权限和 Kill Switch。
- 决定业务 Review Pack 的最终不变量。

### 5.2 Luna：实施与修复执行者

- 按阶段规格实现平台。
- 对 R2/R3/R4 事故提交可审阅的修复产物。
- 不得绕过 Policy Engine、审批收据或发布门禁。

### 5.3 Codex：设计与代码审阅者

- 审阅阶段规格、权限边界、接口、测试、迁移和回滚。
- 验证事故复现、修复证据和灰度结果。
- 对门禁给出通过、驳回或限范围通过结论。

### 5.4 Hermes Agent / Gateway：被管理对象

- 通过只读探针和桥接插件提供状态。
- 不拥有全局自愈控制权。
- Gateway 故障不得导致控制面同时失效。

## 6. 核心产品原则

1. **独立控制面：** `agentopsd` 必须是独立进程、独立虚拟环境和独立状态库。
2. **确定性优先：** 规则、探针和 Runbook 优先于 LLM 推断。
3. **严重度不等于权限：** P0 决定响应速度，R0-R4 决定允许采取的动作。
4. **默认拒绝：** 未登记动作、目标或执行器一律不可自动运行。
5. **证据先于结论：** 事故解决必须有技术、行为或业务验证证据。
6. **不可变发布：** 只有清洁、可追溯、可回滚的构建可部署。
7. **最小爆炸半径：** 自动动作按目标加锁、限制次数并逐 Profile 灰度。
8. **模型可失效：** 模型不可用时采集、已知事故识别、R1 Runbook 和回滚仍可运行。
9. **不信任被监控内容：** 日志、用户输入和工具输出都可能包含 Prompt Injection，只作为数据，不作为控制指令。
10. **一次问题，一项资产：** 已解决事故必须转化为检测、测试、Runbook 或明确的“不自动化”决定。

## 7. 产品范围

### 7.1 第一阶段纳管对象

- Hermes `default` Profile。
- Hermes `feishu3`、`feishu4`、`feishu5`、`newbot` Profile。
- 对应 Gateway launchd 服务和日志。
- Hermes Cron Job 及其业务结果。
- Hermes 代码仓库、部署 SHA 和 dirty 状态。
- AIVault MCP 等已登记外部依赖。
- Book Workflow。

`hermes-ai-native` 和 OpenClaw 在完成控制器职责盘点后，可作为只读 Target 接入；在唯一控制权确定前，不授予写权限。

### 7.2 Review Pack

第一版提供五类 Review Pack：

1. `runtime-core`：进程、单实例、端口、锁、日志、磁盘、SQLite、连接。
2. `model-and-tools`：文本回复、Tool call、Schema、流式响应、Reasoning、辅助模型、降级。
3. `experience`：无回复、重复回复、内部错误暴露、延迟、后台通知噪声。
4. `code-health`：部署 SHA、dirty 状态、上游差异、关联测试和依赖健康。
5. `book-workflow`：书籍身份、入口一致性、R1/R2/R3、产物质量、来源、隔离、写回验证。

## 8. 功能需求

### 8.1 Fleet 与版本登记

**FR-001** 平台必须登记 Target 的类型、稳定 ID、Profile、风险级别、运行位置、负责人和维护窗口。

**FR-002** 每个运行 Target 必须关联代码版本、配置指纹和部署时间；无法追溯时状态为 `unmanaged`，禁止 R2/R3。

**FR-003** 平台必须识别同一服务的多个活跃实例，并区分合法多实例与重复启动。

**FR-004** 平台必须显示现有 watchdog、Cron 和控制器的职责与写权限，避免控制权重叠。

### 8.2 采集与探针

**FR-010** 日志采集必须使用文件身份与 offset 游标增量读取，支持轮转和截断恢复。

**FR-011** 同一底层错误在 `agent.log`、`errors.log` 和 `gateway.log` 重复出现时，不得重复计为独立事故。

**FR-012** Cron 健康必须同时包含执行状态和业务断言；退出码为 0 不能单独判定健康。

**FR-013** 平台必须支持本地进程、launchd、HTTP、MCP、SQLite、Git 和业务合成探针。

**FR-014** 探针必须有超时、预算和速率限制，不得因检查本身拖垮目标。

**FR-015** 所有采集内容在持久化前必须经过脱敏。

### 8.3 事故管理

**FR-020** Signal 必须通过稳定 fingerprint 关联到 Incident。

**FR-021** Incident 必须记录首次/最近发生时间、计数、影响范围、严重度、置信度、证据和状态历史。

**FR-022** 平台必须支持新建、分流、抑制、合并、拆分、重开和解决事故。

**FR-023** 同一事故在观察窗口内复发时必须重开，而不是新建无关事故。

**FR-024** 告警必须按事故聚合，避免逐日志通知。

**FR-025** 用户反馈可关联最近会话上下文形成候选事故，但不得因一条用户输入直接触发写操作。

### 8.4 诊断与计划

**FR-030** 已知 fingerprint 首先匹配已审核 Runbook。

**FR-031** 未知事故可调用 Review Agent 生成根因假设、复现步骤、修复方案、验证方案和回滚方案。

**FR-032** LLM 输出必须解析为受约束的 ActionPlan，不得把自然语言直接交给 Shell。

**FR-033** 代码事故必须先搜索当前代码与上游历史，避免重复发明已有修复。

**FR-034** 每个 ActionPlan 必须标注风险等级、允许目标、最大改动范围、所需审批和有效期。

### 8.5 修复与审批

**FR-040** 仅 R1 白名单动作允许无人工审批执行。

**FR-041** R2 允许在隔离 worktree 中生成代码、测试和补丁，但默认不得部署。

**FR-042** R3 仅对不可变部署版本开放，并必须经过灰度和自动回滚门禁。

**FR-043** R4 数据、业务规则、Prompt 和正式写回必须人工批准。

**FR-044** 审批必须绑定 ActionPlan 内容哈希、目标、范围和过期时间；计划变化后审批失效。

**FR-045** 每个 Target 同一时刻最多存在一个写执行 Lease。

**FR-046** 自动动作必须具备前置条件、幂等键、超时、重试预算、验证和回滚。

**FR-047** 平台必须提供全局、按 Target 和按动作类型的 Kill Switch。

### 8.6 验证、灰度与回滚

**FR-050** 验证必须区分技术、行为、业务和观察窗口四层。

**FR-051** 修复命令成功不等于事故解决；只有必需验证通过才可进入 `observing`。

**FR-052** 发布顺序必须支持 `sandbox → shadow → 非关键 Profile → 扩大范围 → 关键 Profile`。

**FR-053** 任一强制健康门禁失败必须停止扩容，并按策略自动回滚或等待人工处置。

**FR-054** 回滚必须在开放自动发布前做真实演练。

### 8.7 Dashboard、报告和审计

**FR-060** Dashboard 必须显示 Fleet、Incident、Evidence、Repair、Verification、Deployment、Runbook、Review Pack 和 Safety。

**FR-061** Dashboard 是 Hermes 现有 Dashboard 的辅助插件，不得实现第二套聊天界面。

**FR-062** 平台必须生成每日摘要和每周趋势，包含新增、复发、已解决、自动修复、回滚和待审批事项。

**FR-063** 每个状态变化、审批和执行动作必须产生不可变审计记录。

**FR-064** 报告不得包含明文密钥、Token、Cookie 或未经脱敏的用户内容。

## 9. 核心用户流程

### 9.1 已知运行故障自动修复

1. 进程探针发现已登记 Gateway 不健康。
2. Incident Engine 合并相邻日志和进程 Signal。
3. Policy Engine 匹配已审核的“单实例安全重启”Runbook。
4. 执行器确认目标、PID 归属、旧进程状态和重试预算。
5. 取得 Target Lease，执行一次重启。
6. 运行连接探针和合成消息验证。
7. 进入观察窗口；稳定后解决，否则回滚或熔断并通知。

### 9.2 未知代码问题

1. 错误指纹持续超过阈值，生成 Incident。
2. Review Agent 关联堆栈、最近变更、历史事故和上游记录。
3. 代码执行器创建隔离 worktree 并复现失败。
4. Luna 或代码 Agent 补回归测试和最小修复。
5. 平台保存 diff、测试和风险证据，状态为 `awaiting_approval`。
6. 未获得 R3 审批和不可变发布基线前，流程停止在此处。

### 9.3 业务假绿

1. Cron 执行返回 0，但 AIVault 语义查询合成断言失败。
2. 平台创建业务能力事故，而不是 Cron 进程事故。
3. 若属于外部依赖波动，按退避策略重试并抑制重复通知。
4. 若持续失败，生成根因和修复计划；不把“脚本无输出”视为恢复。
5. 只有业务断言重新通过并经过观察窗口，事故才解决。

### 9.4 Book Workflow 质量回归

1. Review Pack 使用脱敏黄金输入执行 dry-run。
2. 检测到指定书籍身份、三链一致性或来源不变量失败。
3. 平台阻止相关版本进入灰度，并保存输入、输出、规则版本和差异。
4. Prompt 或业务规则修复进入 R4 审批。
5. 基线样本、对照样本和回归样本全部通过后才可恢复发布资格。

## 10. 严重度与服务目标

| 级别 | 定义 | 首次发现目标 | 通知策略 |
|---|---|---:|---|
| P0 | 数据安全、广泛不可用、失控写操作 | 5 分钟内 | 立即通知，持续更新但去重 |
| P1 | 关键 Profile 或核心能力持续不可用 | 15 分钟内 | 立即通知，30 分钟摘要 |
| P2 | 局部退化、有降级路径 | 60 分钟内 | 事故创建后通知 |
| P3 | 趋势、维护和低风险质量问题 | 24 小时内 | 每日摘要 |

P0/P1 的目标是检测与通知，不表示可绕过风险权限。

## 11. 成功指标

平台进入 R1 自动修复前必须达到：

- 被纳管 Target 资产覆盖率 100%。
- 被纳管运行版本可追溯率 100%；不可追溯对象明确标记并禁止 R2/R3。
- 已知历史故障对应探针、测试或 Runbook 覆盖率 100%。
- 经过至少连续 7 天只读观察。
- 已标注事故集合上的聚合准确率不低于 90%。
- 故障注入中的 P0/P1 漏报率为 0。
- 自动动作前置条件、验证、回滚和审计覆盖率 100%。
- 明文凭证落库测试通过率 100%。
- 控制面在所有 Gateway 和模型不可用时仍能采集、匹配已知事故并执行允许的回滚。

平台进入 R3 灰度发布前还必须达到：

- 部署版本清洁且不可变。
- 自动发布不触碰用户 dirty worktree。
- Shadow 和非关键 Profile 灰度门禁通过。
- 至少完成一次失败灰度的自动回滚演练。
- 所有发布均能定位源码 SHA、配置指纹、审批和验证证据。

## 13. 依赖与约束

- macOS launchd 是当前宿主上的服务管理器。
- 初期存储采用独立 SQLite WAL，不引入外部数据库。
- 控制 API 只监听 Unix Domain Socket 或 localhost，并要求本地认证。
- Hermes 状态路径必须遵守 Profile-aware 路径规则；AgentOps 全局状态根由控制面配置明确指定。
- 现有用户修改不得被覆盖、清理或纳入平台提交。
- 现有 watchdog、Cron 和 agentops 在写权限迁移前保持原状；迁移必须有职责对照和回滚计划。
- Feishu 操作如进入后续实施，优先使用确定性 CLI、官方 API 或 Connector，UI 自动化只作受限回退。

## 14. 产品风险

| 风险 | 产品控制 |
|---|---|
| 误报导致告警疲劳 | 事故聚合、观察期、抑制规则、每日摘要 |
| 误修扩大故障 | 默认拒绝、白名单、Lease、灰度、熔断、回滚 |
| 模型被日志注入 | 日志视为不可信数据、结构化 ActionPlan、策略二次授权 |
| 多控制器互相干扰 | 单一写控制面、职责登记、目标 Lease |
| dirty 目录被覆盖 | R2/R3 前置基线、隔离 worktree、不可变构建 |
| 业务质量被“技术成功”掩盖 | 业务断言和黄金用例作为强制门禁 |
| 敏感数据进入事故库 | 入库前脱敏、引用代替复制、保留期和访问控制 |

## 15. 验收定义

该产品被视为完整交付，必须同时满足：

1. G0-G7 全部门禁有审阅证据。
2. 当前五个 Hermes Profile 均被登记并有独立健康视图。
3. 本文第 2 节列出的历史问题均被映射到具体探针、测试、Runbook 或人工审批策略。
4. 模型、单个 Gateway、所有 Gateway 分别失效时，平台行为符合降级设计。
5. 自动 R1、隔离 R2、灰度 R3 和人工 R4 权限不可互相绕过。
6. 任意自动动作可从审计记录复原“谁、何时、基于什么证据、对哪个版本做了什么、如何验证、是否回滚”。
7. 用户通过全局 Kill Switch 能在一个操作内阻止新的写执行，且不影响只读采集和证据保存。
