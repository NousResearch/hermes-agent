# Hermes Evidence Fabric v1 Design

## Status and scope

This design covers the first durable Hermes Evidence Fabric layer only:
`ResearchRun`, `EvidenceRecord`, `ClaimRecord`, `ClaimEvidenceLink`,
provenance, validation, persistence, and a small runtime/service surface.

It does not add Query Graph, Skeptic, Verifier, reliability/trust scoring,
Knowledge Hub UI or adapter code, Obsidian/NotebookLM write-back, embeddings,
semantic contradiction detection, or local-model support. Existing browser
isolation, Knowledge Hub v1, Desktop UI, HUD, memory, session, delegation,
and grounded-citation behavior remain outside this change unless a concrete
compatibility seam is required.

## Current Hermes infrastructure

The authoritative checkout is `C:\Users\curti\.hermes\hermes-agent`.
Evidence Fabric will reuse:

- `SessionDB` and its profile-aware `state.db` path resolution;
- the existing SQLite `SCHEMA_SQL`/schema-version reconciliation and migration
  mechanism;
- foreign-key enforcement, WAL mode, bounded read pooling, and the existing
  `BEGIN IMMEDIATE` write transaction/retry path;
- `hermes_home_key()` as the existing stable storage-scope identity;
- existing file/artifact conventions where a raw source body is too large for
  ordinary metadata rows; and
- the existing self-registering tool registry and non-core toolset pattern.

Evidence Fabric is a distinct domain layer, not a session-memory extension.
The domain service/repository owns its DTOs, validation, lifecycle rules, and
queries; it calls the existing state-store transaction primitives without
making Evidence Fabric consumers understand session tables or chat messages.

## Alternatives considered

### A. Extend Hermes core persistence directly — chosen

Add dedicated Evidence Fabric tables and a focused domain repository/service
alongside the existing `SessionDB` infrastructure. This gives remote gateways
the same durable authority, reuses the already-proven SQLite concurrency and
migration behavior, and avoids a second database or process. The domain
boundary prevents evidence from becoming generic memory while keeping the
storage implementation small.

### B. Gateway-side plugin/service using existing storage primitives

This would keep most code at the gateway edge and could expose a service-gated
tool cleanly, but a plugin-owned persistence layer would make the authority
dependent on gateway/plugin loading and complicate migrations and non-gateway
execution. It is useful as a future adapter surface, not as v1 authority.

### C. Standalone research database/service — rejected for v1

This would isolate the domain strongly, but duplicates profile routing,
backup, migration, locking, and remote lifecycle machinery already present in
Hermes. It also creates synchronization and failure modes between session and
research stores without a v1 requirement that justifies them.

## Authority and placement

The authoritative state lives in the Hermes runtime's profile-scoped
`state.db`, where CLI, gateway, remote gateway execution, and delegated agents
already resolve Hermes state. Desktop is a later read/API consumer and does not
own factual research state.

The implementation will use a focused `research`/Evidence Fabric domain
module and repository methods over `SessionDB`. It will not store authoritative
records in process-global dictionaries, conversation context, Desktop state,
or model-generated JSON.

## Data model

All IDs are generated by the service as opaque, stable UUID-style identifiers.
All timestamps are UTC, serialized in the repository's existing canonical
timestamp format. JSON metadata is opaque structured metadata and is never
interpreted as instructions.

### ResearchRun

Fields:

- `id`
- `objective` (non-empty)
- `owner_scope_key` (immutable `hermes_home_key()` value for the active
  profile-scoped runtime store)
- `owner_profile` (diagnostic/provenance metadata, not the sole authority key)
- `owner_connection_id` (optional opaque connection/source identity supplied by
  a remote gateway when available)
- `status`: `OPEN`, `COMPLETED`, `CANCELLED`, or `FAILED`
- `metadata`, `created_at`, `updated_at`

`owner_scope_key` is the exact v1 access boundary. A caller may read or mutate
a run only when its resolved Hermes home scope matches the stored key. The
profile name and connection ID are retained for auditability and routing, but
cannot grant access by themselves. A remote gateway therefore has authority
only in the profile/home scope under which it executes; an explicit future
sharing/participant model is out of scope.

Lifecycle transitions are deterministic: `OPEN` may move once to any terminal
state; terminal states cannot be reopened or changed. A terminal run graph is
read-only in v1: adding evidence or claims, adding links, and changing claim
status are all rejected after `COMPLETED`, `CANCELLED`, or `FAILED`. The
status check is performed inside the same write transaction as every graph
mutation so concurrent close/write races resolve deterministically.

### EvidenceRecord

Fields:

- `id`, `research_run_id`
- `source_type` as a validated extensible string with v1 values `WEB_SEARCH`,
  `WEB_PAGE`, `DOCUMENT`, `FILE`, `NOTE`, `NOTEBOOKLM`, `OBSIDIAN`,
  `HERMES_MEMORY`, and `OTHER`
- `retrieval_method` as a separate validated extensible string with v1 values
  `DIRECT_HTTP`, `BROWSER`, `BROWSER_VISION`, `API`, `MCP`, `FILE_READ`,
  `NOTEBOOKLM`, `OBSIDIAN`, `HERMES_INTERNAL`, and `OTHER`
- `source_uri` and normalized `canonical_uri` where URI semantics apply
- `title`, `publisher_or_origin`, `published_at`, `retrieved_at`
- `content_hash` (lowercase SHA-256 hex computed by the service; for text the
  exact basis is Unicode NFC text encoded as UTF-8, and for binary/document
  content it is the exact retrieved bytes; no whitespace, newline, query, or
  semantic normalization is applied)
- `raw_reference` (bounded reference to an artifact/file or other reconstructable
  source locator; raw bodies are not automatically placed in ordinary rows)
- `relevant_passages` as structured locators/excerpts
- `created_by_agent`, `created_by_profile`, optional provider/model metadata
- `derived_from_evidence_id` (nullable self-referencing foreign key)
- `untrusted_external_content` boolean
- `created_at`

The original source remains a first-class record. A derived summary is a new
evidence row whose `derived_from_evidence_id` points to the original, and the
original `source_uri`/`raw_reference`/hash remain untouched. The self-FK is
implemented as a composite foreign key over
`(derived_from_evidence_id, research_run_id)` to a unique matching pair on
EvidenceRecord, so a derived record cannot point across runs. This is
preferred over a separate provenance table in v1 because the required
provenance relation is a single parent chain; a later genealogy model can
replace or extend it without changing the original source row.

### ClaimRecord

Fields:

- `id`, `research_run_id`, non-empty `text`
- `status`: `UNVERIFIED`, `SUPPORTED`, `PARTIALLY_SUPPORTED`,
  `CONTRADICTED`, or `UNRESOLVED`
- `created_by_agent`, `created_by_profile`, `updated_by_agent`,
  `updated_by_profile`, `metadata`
- `created_at`, `updated_at`

No confidence/probability is accepted or persisted as a reliability result.

### ClaimEvidenceLink

Fields:

- `claim_id`, `evidence_id`, `research_run_id`
- `relation`: `SUPPORTS`, `CONTRADICTS`, or `CONTEXT`
- optional passage/reference locator
- `created_by_agent`, `created_by_profile`
- `created_at`

The explicit `research_run_id` plus composite foreign keys enforce that claim,
evidence, and link all belong to the same run. Multiple links are allowed,
including simultaneous support and contradiction. Links do not automatically
change claim status; status changes use explicit deterministic service calls.

## Deduplication, versioning, and source change

The database, not only the service, enforces exact identity with partial unique
indexes:

- `UNIQUE(research_run_id, canonical_uri, content_hash) WHERE canonical_uri
  IS NOT NULL`; and
- `UNIQUE(research_run_id, raw_reference, content_hash) WHERE canonical_uri
  IS NULL AND raw_reference IS NOT NULL`.

The service computes the hash from the retrieved source content and rejects a
caller-supplied hash that does not match. A concurrent duplicate insert handles
the SQLite uniqueness conflict by re-reading and returning the committed
existing evidence identity; it never creates a second row or overwrites the
winner. The schema also has a unique `(id, research_run_id)` key so composite
same-run foreign keys are enforceable.

Canonical URI normalization is deliberately conservative and deterministic.
The service parses an absolute URI, lowercases only the scheme and hostname,
removes a fragment, removes the default port for the scheme, ensures an empty
path is `/`, and preserves path bytes, query parameter order/duplicates, and
query casing. It does not heuristically remove tracking parameters, reorder
queries, follow redirects, or infer equivalence between different URLs.

For records with a canonical URI, the service treats
`(research_run_id, canonical_uri, content_hash)` as the exact retrieval
identity. Repeating the same source and normalized content in the same run
returns the existing evidence identity or an explicit duplicate result; it
does not create meaningless duplicate rows.

The same canonical URI with a different valid content hash creates a new
EvidenceRecord. Earlier versions remain immutable and queryable, with their own
retrieval timestamps and provenance. No semantic duplicate or contradiction
detection is attempted. Evidence without a URI is deduplicated only when an
explicit stable raw reference and content hash make exact identity possible;
otherwise it is a distinct retrieval.

Claim status changes and link creation retain runtime-owned mutation identity:
`set_claim_status` writes `updated_by_agent`/`updated_by_profile`, and every
ClaimEvidenceLink writes `created_by_agent`/`created_by_profile`. These values
come from the authorized runtime scope, not arbitrary model-provided fields.

## Deletion and retention

There is no public hard-delete operation in v1. Runs and their evidence,
claims, links, and provenance are retained after completion, cancellation, or
failure so the research history remains auditable. Closing a run changes only
its lifecycle status and `updated_at`.

The schema uses foreign keys and safe cascade behavior only as an integrity
guard for a future administrative purge; v1 APIs never invoke that purge.
Any future retention/deletion feature must be an explicit, scope-authorized,
transactional operation that removes a whole run graph and its owned raw
artifacts together, or fails without partial deletion.

## Service and model-facing API

The domain service exposes controlled methods, not SQL or arbitrary mutation:

- `create_research_run`, `get_research_run`, `list_research_runs`,
  `complete_research_run`/terminal transition;
- `add_evidence`, `get_evidence`, `list_evidence`;
- `create_claim`, `get_claim`, `list_claims`;
- `link_evidence_to_claim`; and
- `set_claim_status`.

Each method receives/resolves an authorized runtime scope and validates all
IDs, enum values, timestamps, hashes, URI fields, text, and run compatibility
before entering the write transaction. Invalid IDs and cross-scope/run
references fail loudly.

If model-facing exposure is needed by the existing delegation path, it will be
one compact, non-core `research_fabric` tool in the existing research/service
toolset. Its operation enum dispatches only the service methods above and is
available only when a valid runtime scope and authorized run context exist.
Delegated agents use this interface; they never receive SQL, a database path,
or arbitrary update capability. If current tool wiring cannot provide a safe
run context, the service API remains the v1 surface and model exposure is
deferred rather than weakening authorization.

## Concurrency and transactions

All mutations use the existing `SessionDB` write seam (`BEGIN IMMEDIATE`, WAL
busy retry/backoff, commit/rollback behavior, and bounded lock patience).
Foreign keys are enabled on every connection. A single logical mutation,
including link creation and its run-scope checks, is one transaction. Reads
use the existing deterministic/WAL read path. IDs are generated independently
for each record, so concurrent agents can add evidence and claims without
lost updates; a failed transaction rolls back only its own work.

## Migration strategy

The Evidence Fabric tables and indexes are added through Hermes' existing
schema source and version reconciliation, with a monotonic schema-version
bump. The migration is additive, idempotent, and does not rewrite or delete
unrelated session/memory/delegation data. Tests will cover a fresh database,
upgrade from the previous schema, repeated startup, and preservation of
existing tables/rows.

## Grounded-citation compatibility

The existing grounded-citation and citation-validation system is not rewritten
or duplicated. Evidence Fabric stores compatible source URI and passage
locators and provides a narrow future import/adapter boundary so a validated
grounded citation can become an EvidenceRecord while retaining its original
citation metadata. v1 does not automatically import citations or change their
current behavior.

## Security and trust boundary

Externally sourced text is stored and returned as data and marked
`untrusted_external_content`; no service method interprets it as Hermes
instructions. Validation is deterministic and bounded. Raw references are
validated as references, not executed. No arbitrary SQL, filesystem database
path, model-controlled schema mutation, fabricated reliability score, or local
inference lifecycle is introduced.

## Verification required before implementation completion

The implementation plan must include failing-first tests for run lifecycle and
scope isolation, evidence hashing/deduplication/versioning/provenance, claim
links and statuses, FK integrity, malformed input, untrusted content,
concurrent writers, close/reopen persistence, fresh/upgrade/idempotent
migrations, delegation/service authorization, grounded-citation compatibility,
and relevant existing memory/session/delegation/citation regressions. Final
verification must include targeted tests, concurrency tests, migration tests,
static/type checks, broader relevant regressions, adversarial mechanical
search, and final diff inspection. Knowledge Hub, Desktop, browser isolation,
and unrelated worktree changes must remain untouched.
