# 招聘邮箱整理流程

当用户要求 `/offer` 读取招聘通知、更新秋招进度，或定期检查招聘邮箱时，读取并遵循本参考文件。

## 需要用户提供的信息

根据任务需要收集：

- 邮箱服务商或邮箱类型，例如 Gmail、Outlook、QQ 邮箱、163 邮箱或学校邮箱；
- 登录邮箱地址；
- 可选的公司名称、岗位名称、关键词或日期范围，用来缩小搜索范围；
- 如果需要定期检查：每天检查的时间，以及是否只在记录发生变化时通知。

登录邮箱地址只用于确认需要访问的账户。密码、多因素认证、验证码和 CAPTCHA 必须由用户在浏览器中自行完成，不能让用户把这些信息发到聊天中，也不能保存。

## 浏览器处理流程

1. 使用用户指定的浏览器入口；如果用户没有指定，使用当前可用的默认浏览器入口。
2. 打开用户所用邮箱服务商的官方网页。
3. 如果需要登录，请用户在浏览器中完成登录；确认邮箱页面已准备好后再继续。
4. 使用公司名称、招聘关键词、邮件主题或发件人搜索近期邮件，优先查看上次检查之后的新邮件或未读邮件。
5. 只读取识别求职进度所需的可见邮件元数据和正文，不读取无关邮件。
6. 将每封相关邮件整理成：日期、公司、岗位、当前状态、下一步和备注。能够确认时尽量保留邮件中显示的原始状态。
7. 合并同一公司同一岗位的重复通知。后续的拒信、测评、面试或 Offer 通知覆盖早期的“申请已收到”通知。
8. 更新桌面上的 `application-tracker.html`，然后报告发生变化的记录和文件保存路径。

## 邮件信号与状态映射

| 邮件信号 | 进度表状态 |
| --- | --- |
| 已收到申请、申请已提交 | 已投递 |
| 测评邀请、在线笔试、在线测试 | 测评中 |
| 简历筛选、评估进行中 | 筛选中 |
| 面试邀请 | 面试，可进一步写明一面、二面或 HR 面 |
| Offer、录用成功、入职邀请 | Offer |
| 拒绝、未通过、流程终止 | 拒绝/已结束 |

不能从普通自动回执推断出面试、Offer 或拒绝。邮件没有明确进入下一阶段时，使用“已投递”或“待确认”。

## 定期检查

当用户要求每天检查招聘邮箱时：

- 使用 Codex 的自动化能力创建或更新任务，不要手写 cron、RRULE 或原始自动化指令；
- 优先复用当前任务中已经存在的同类自动化，避免重复创建；
- 在自动化任务说明中写入邮箱服务商、登录邮箱、桌面进度表路径、搜索范围以及更新和通知规则；
- 绝对不要把密码、验证码、恢复码或 MFA 信息写入自动化任务；
- 用户没有指定时间时，先询问每天检查的时间，再创建任务；
- 每次只检查新的招聘相关邮件，更新进度表；没有变化时报告“无新增进度”。

## 隐私边界

- 不把邮件正文全文复制进公开简历、skill、README 或 GitHub 仓库；
- 进度表只保留公司、岗位、状态、下一步和必要备注；
- 申请编号只有在用户明确要求时才保留，密码和验证码永不保留；
- 如果邮件内容不足以确认状态，标记为“待确认”，不要替用户做过度推断。
