# Audit: Deep Dive — 29/05/26

## Current state

Friday deep dive picked the most significant findings from the week: orphan gateway processes, stale DB backups, and script deadwood.

### Finding 1: Orphan Gateway Worker Processes (750MB RAM waste)

**What:** 11 `hermes_cli.main gateway run --replace` worker PIDs (769030-769040) from a gateway launch at 09:03. The gateway was replaced by systemd at 12:30 (PID 879813), but the old worker threads were never cleaned up. Each has PPID=1 (adopted by init) and maintains an active Discord TLS connection.

**Impact:** 750MB wasted RAM on a 7.7GB system already using 2.3GB swap. This is 10% of total RAM consumed by ghost processes that may be sending duplicate messages to Discord.

**Root cause:** Hermes gateway replacement does not kill all worker threads from the replaced gateway instance. Related to upstream bug #15275 (MCP orphans from interactive sessions).

**Task:** t_7b4c65f4 (CLASS B — needs architectural decision on cleanup strategy)

### Finding 2: Corrupt Kanban DB Backups (213MB)

**What:** 1,015 `.corrupt.*.bak` files in `/home/kensei/.hermes/kanban/boards/ops/.archive-20260526/` — remnants of the May 26 multi-gateway concurrent-write corruption incident. The DB was rebuilt but auto-generated backups were never cleaned up.

**Impact:** 213MB of dead data in a directory that should be <1MB.

**Task:** t_024add87 (CLASS A — routine cleanup)

The current hermes-chat session at 14:00 spawned a second generation of MCP processes (PID 1037258-1037282). These are normal for the interactive session and will clean up when it exits. Not a new issue — just noting the pattern.

System swap at 57% with 750MB of ghost gateway workers and 690MB Java (Elasticsearch for Temporal). The ghost workers are the biggest actionable waste. If killed, swap usage should drop significantly.
