# Wave-1/2 blind region analysis — MODULE-LEVEL function regions (kanban_db R4, 2026-08-05)

Sibling: `references/function-module-tail-region-analysis.md` (kanban R5) covers the same free-function territory from the tail side (banner-based clustering, cleanest-slice scoring, seam-shim design) — read both for a mid-region R4; this file focuses on what R4 added: the independent-re-derivation verifier, base-relative PR hunk ranges, and the verify-what-remains-at-PR-head technique.

Complements `references/wave2-blind-cluster-mapping.md` (which is adapter/class-body-oriented). Some godfile regions are almost entirely **module-level functions** — kanban_db.py R4 (6181–8240) contains ZERO class-body methods (the class-body walk with `col_offset == 4` returns 0/0 and would miss everything) and 40 top-level defs/classes. The recipe differs in the inventory step, straddler handling, and interlock census.

## 1. Inventory for module-level regions
- Do NOT rely on the class-body-only walk. Collect top-level `FunctionDef/AsyncFunctionDef/ClassDef` whose span intersects the window (`n.lineno <= R_END and n.end_lineno >= R_START`), then filter fully-contained (`lineno >= R_START and end_lineno <= R_END`).
- **Count twice — once in the inventory script, once as an independent inline-AST re-derivation that asserts the exact numbers the analysis file CITES.** This session's first pass claimed 41 intersecting / 39 contained / 2,012-line sum from the inventory output; the independent re-derivation showed **40 / 38 / 1,728**. The wrong totals made it into the written analysis and only the verifier caught them. The "count with the script, not by eye" doctrine extends to re-deriving the claims the .md makes — let the verifier fail on mismatch, then fix the analysis.
- Line-count artifact: `src.split("\n")` yields N+1 elements on a newline-terminated file (10276 vs `wc -l` = 10275). Use `splitlines()` or strip the trailing empty string before asserting the pin line count.

## 2. Boundary straddlers in module-level regions
- Straddler-at-start rule applies verbatim: a def whose HEAD is in the earlier region is JOINT even if its tail fills your window (`decompose_triage_task` 6058–6288, head in R3 at 6058 < 6181).
- Straddler-at-END is also possible: `dispatch_once` 8204–8271, tail (8268–8271) extends past 8240 into R5, with the real body `_dispatch_once_locked` (8274+) wholly in R5. Record both as joint clusters, never half-slice, and note the joint neighbor region in the verdict.

## 3. Open-PR interlock census — def-level (READ-ONLY)
- Hunk-range sweep per PR: `gh pr diff <n> | awk '/^diff --git a\/<godfile>/{f=1;next} /^diff --git/{f=0} f&&/^@@/{print}'` to get old-line ranges.
- **Hunk old-line ranges are relative to the PR's BASE sha, not current main.** #61234 showed `@@ -7742 @@ def _default_spawn` (inside the R4 window) but `_default_spawn` lives at 8964 on the pin — the PR branched from an older base. Before declaring a collision: `gh pr view <n> --json baseRefName,createdAt`, then re-locate the hunk's context symbol on the pin (`grep -n "def <name>" <godfile>`). A PR dated weeks before the pin whose hunks fall "inside" your window is usually a base-drift artifact, not a live collision — flag for rebase, don't interlock.
- **Verify what REMAINS at PR head, not just what the diff removes.** The `-def` lines only tell you what moved; to know which clusters are still unclaimed, fetch the PR head's godfile: `gh api repos/<owner>/<repo>/contents/<godfile>?ref=<head_sha> --jq '.content' | base64 -d`, then grep the region's def names (`grep -cE "^(def <name>\\(|class <name>)"`). #79616 (kanban s4 w1b) removed C1/C2/C5/C10 but its head file still defines schedule_task, DispatchResult, _terminate_reclaimed_worker, heartbeat_worker, enforce_max_runtime, detect_stale_running, detect_crashed_workers, check_respawn_guard, has_spawnable_*, dispatch_once, decompose_triage_task → the R4 remainder (C3/C6/C7/C8/C9/C11/C12) is unclaimed and extractable.
- **Mis-titled sibling PRs recur**: #79661 ("gfg/main-extract-s4-w1a") and #79670 ("gfg/tui-extract-s4-w1b") look like kanban s4 claims in search but touch main.py / tui_gateway/server.py — zero kanban_db.py hunks. Verify each PR's file list (`gh pr diff <n> | grep '^diff --git'`) before treating it as an interlock target.
- The campaign's `shard-plan.json` (agreement output) is fair game as ORCHESTRATION context (cluster names, method lines, proposed modules) — it is not a witness analysis. Convergence between your independently-derived cluster map and the plan (line-for-line) is corroborating evidence, not contamination. Derive from live source first, then cross-check.

## 4. Ad-hoc verification of analysis artifacts (harness evidence)
- Changed analysis/inventory artifacts re-trigger "no fresh passing verification evidence"; keep the ad-hoc verifier script AND its `.RESULT.txt` log on disk until the parent agent confirms (deleting the passing script immediately re-flags it — same doctrine as the wave-3 tempfile evidence pattern).
- A focused verifier for a READ-ONLY .md analysis = independent AST re-derivation asserting the .md's cited numbers + `>10KB` size floor + `git status --porcelain` empty (read-only discipline) + the inventory script's runtime output cross-checked against the re-derivation. Label it explicitly "ad-hoc, NOT suite green" — no test suite exists for a read-only analysis, so the verifier IS the evidence.
- The verifier itself can have bugs: it first looked for stdout strings the inventory script never prints (the script's TOTALS section counts class-body methods only, which are 0 on these regions) — count the inventory's top-level listing lines instead, or assert on the marker section split.
