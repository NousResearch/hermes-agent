# 更新とアンインストール

## 更新

実行中のインストールに合った更新方法を選んでください。

| インストール | 更新方法 |
|---|---|
| 管理されたソースチェックアウト | `hermes update`、またはソースからビルドしたデスクトップの更新ハンドオフ。 |
| Windows サイドロード MSIX | デスクトップの Update コントロールと Windows App Installer。 |
| Microsoft Store パッケージ | Microsoft Store の更新。 |
| macOS バンドルアプリ | `electron-updater` を通じたデスクトップの Update コントロール。 |
| Docker イメージ | 選んだイメージを pull し、同じデータマウントでコンテナを再作成します。 |
| Nix | flake/プロファイルを更新してリビルドします。 |
| Termux APT | `pkg update` の後に `pkg upgrade hermes-agent`。 |

`hermes update` はパッケージが所有するアプリケーションファイルを書き換えません。PM が管理するのは
依存関係であって、アプリケーションの配布ではありません: `hermes pm update` はメンテナー向けの
ピン更新コマンドであり、アプリケーションの代替アップデーターではありません。

管理されたソースインストールの場合:

```bash
hermes update
```

公式リポジトリのソースチェックアウトは **stable** チャネルを追跡します: 最新の公開済み
`vX.Y.Z` GitHub リリース（ドラフト、プレリリース、canary タグは決して対象になりません）を、
その正確なコミットでチェックアウトします。`hermes update` とデスクトップの更新ボタンは、
リリースからリリースへのみ移動し、コミット単位では移動しません。フォークやミラーは引き続き
その `main` ブランチを追跡します。更新は PM を通じて依存関係を準備し、設定の変更と
プロセス再起動の結果を報告します。

```bash
hermes update --set-channel main     # follow every commit on main instead
hermes update --set-channel stable   # back to releases only
hermes update --channel main         # one run against main; nothing is saved
```

この選択は `config.yaml` の `update.installs` の下にインストールごとに保存されます。
チャネルを一度も選んでいないインストールは前方にのみ移動します: すでに最新リリースより新しい
チェックアウト（例えば、このデフォルトの導入前に `main` を追跡していたもの）は、より新しい
リリースが出るまでそのまま残ります。`--set-channel stable` を実行すると、チェックアウトは
たとえそれが古くても正確なリリースコミットにピン留めされます。デスクトップはその移動を
リリースへのロールバックと呼び、`hermes update --check` は新しい更新を通知する代わりに、
チェックアウトの方が新しいと表示します。

インストーラー（`install.sh`、`install.ps1`、Hermes-Setup）も、新規インストールを最新の
stable リリースに配置します。チャネルを一度も選んでいないインストールの上で再実行すると、
そのリリースがチェックアウトの子孫である場合にのみ、そのリリースに移動します。それ以外の
チェックアウト（`main` を追っていたもの、またはすでにリリースより先にあるもの）はそのまま残り、
その移動は `hermes update` が判断します: チェックアウトがすでに使っているセッションストアより
古いリリースは拒否されます。`main` 以外のチャネルを選んだインストールの上で再実行した場合、
チェックアウトはそのまま残ります: 移動させるのは `hermes update` だけです。
代わりに `main` の先端をインストールするには、`--channel main` を渡します（`install.ps1` では
`-Channel main`、または `irm | iex` のワンライナーの前に `HERMES_INSTALL_CHANNEL=main` を
設定します）。インストーラーはその選択を `hermes update --set-channel main` と同じように
保存します。明示的な `--commit` のピンは引き続き適用されます。
Windows Store、MSIX、バンドルされたデスクトップのインストールは影響を受けません。それらの
チャネルはパッケージに組み込まれています（下記参照）。

### バンドルされたデスクトップの更新

Windows では、サイドロードアプリは登録された App Installer のソースを確認します。適用時は、
アプリが所有するバックエンドを停止する前に `.appinstaller` 記述子をダウンロードし、
そのローカルファイルを開いてから終了し、Windows がパッケージを置き換えます。
切り離された待機プロセスが、パッケージのバージョンが変わった後に自動的な再起動を試みます。
待機プロセスの登録に失敗した場合は、手動で開き直すよう警告が表示されます。

macOS では、適用時に ZIP の更新をダウンロードし、Squirrel.Mac が署名されたアプリを
受け入れるのを待ってからバックエンドを停止します。インストールと再起動を要求するのは
その適用フローだけです。通常の終了では、保留中のダウンロードはインストールされません。
ダウンロードや検証に失敗した場合、バックエンドは実行されたままになります。

Store パッケージは、どちらのサイドロードフィードでもなく Store を使います。壊れている、
または利用できない更新チェックを「すでに最新」と解釈してはいけません。
アプリケーションとそのバンドルされたベースランタイムは一緒に更新され、ユーザーデータは
パッケージの外に残ります。[デスクトップのインストール](/docs/user-guide/desktop#install) を参照してください。

stable と canary のデスクトップバンドルは別々のアプリケーションです。canary をインストールしても、
MSIX を使う Windows を含め、stable は置き換えられません。各アプリケーションは独自の
デスクトップ状態を保持し、ビルドに組み込まれたチャネル内で更新されます。
チャネルの変更とは、設定を変えることではなく、もう一方のアプリケーションをインストールすることです。
canary のアイコンは黄色の背景（ダークモードでは濃い黄色）で、その CLI
コマンドは `hermes-canary` です。

単発のコミットバンドルは、どちらのリリースチャネルとも、他のコミットバンドルとも別のものです。
その赤いアイコンには短いビルド SHA が表示され、これは `hermes-<short-sha>` CLI コマンドにも
使われます。これらは `hermes update` や `hermes update --check` を含め、更新を確認も
インストールもしません。次のように説明されます:

> This build doesn't get updates. Ask the developer who gave it to you for a new build.

別々のアプリケーションでも、同じ Hermes ホームの下にある Hermes のプロファイル、設定、
セッションは共有されます。1 つのプロファイルに対して異なるビルドを実行することは、
スキーマの分離ではありません: 新しいビルドは、古いビルドが読めない形に保存データを
変更することがあります。テストの前に共有データをバックアップしてください。デスクトップと
スタンドアロンの CLI は、別の稼働中のインストールが同じプロファイルを使っている場合に
警告しますが、これは助言であってロックではありません。デスクトップの更新後の通知は
アプリケーションごとにスコープされるため、canary を起動しても stable の保留中の通知が
消費されることはありません。`hermes://` URL スキームは共有されたままで、最後に登録した
アプリケーションがリンクを処理します。

:::tip
`hermes update` は新しい設定オプションを自動的に検出し、追加するように促します。そのプロンプトをスキップした場合は、手動で `hermes config check` を実行して不足しているオプションを確認し、`hermes config migrate` で対話的に追加できます。
:::

### 受動的な更新通知

ピン留めされたインストールや非対話型のインストールでは、CLI の受動的なバージョン確認とバナーの更新チェックを無効にできます。

```bash
hermes config set updates.check false
```

これにより、キャッシュされた更新通知と、受動的な更新チェックのネットワークリクエストの両方が抑制されます。デフォルトは `true` です。明示的な `hermes update --check` と `hermes update` は引き続き動作します。この設定はデスクトップアプリケーションのアップデーターを制御しません。

### 更新中に何が起こるか {#what-happens-during-an-update}

受け入れられたソースチェックアウトに対して、`hermes update` は次のフェーズを実行します。

1. **更新前スナップショット** — Hermes は、すべてのプロファイルについて選択された状態ファイルを、そのプロファイルの `state-snapshots/` ディレクトリに保存します。これにはペアリングデータ、cron ジョブ、`config.yaml`、`.env`、`auth.json` が含まれます。自動のクイックスナップショットは、1 GiB を超える個々のファイルをスキップします。`updates.pre_update_backup` で `quick`、`full`、`off` を選択します。完全なアーカイブは [バックアップの除外対象](../reference/faq.md#hermes-backup-vs-hermes-profile-export) を使います。復元には [スナップショットとロールバック](../user-guide/checkpoints-and-rollback.md) を使います。クイックスナップショットが復元するのは状態ファイルであり、アプリケーションのコードではありません。スナップショットはベストエフォートです: 失敗した場合、更新は `⚠ Pre-update snapshot FAILED` という警告を表示して続行し、レシートには `pre_update_backup` が失敗したステップとして記録されます（意図的な `off`/`--no-backup` の場合は、代わりにその理由とともにレシートのスキップに記録されます）。
2. **コードの更新** — 設定されたソースブランチまたは stable リリースタグを適用し、サブモジュールを更新します。Linux と macOS では、このインストールから実行されているすべてのゲートウェイが、チェックアウトへの最初の変更の直前に一時停止されます（[更新中のゲートウェイのダウンタイム](#gateway-downtime-during-an-update) を参照）。適用するものがない更新や、チェックアウトを変更する前に失敗した更新では、何も停止されません。
3. **移動前後の構文検証 + 自動ロールバック** — チェックアウトを移動する前に、Hermes は対象が `pyproject.toml` に列挙している起動ファイル（`[tool.hermes] update-startup-files`: すべての `hermes` 呼び出しが起動時にインポートするファイル）をコンパイルし、いずれかが欠けているかパースに失敗した場合は更新を拒否します。pull の後にも再度チェックします。いずれかが失敗した場合（例: 取り残されたマージコンフリクトのマーカー、誤って切り詰められたファイル、リファクタリングで落とされたファイル）、Hermes はシェルが起動可能な状態を保てるようインストールをロールバックします: チェックアウトを pull 前に実行していたコミットにリセットする（`git reset --hard <pre-pull-sha>`）か、更新が detached なチェックアウトや待機中のフィーチャーブランチから切り替えていた場合は、`git checkout --detach <sha>` / `git checkout <branch>` でそこに戻ります（再びチェックアウトできないブランチは、同じコミットで detached の状態に復元されます）。アップストリームの修正が入ったら `hermes update` を再実行してください。そのリストが存在する前のリリースは、実行中のアップデーター自身のリストに照らしてチェックされ、存在しないファイルはスキップされます。
4. **依存関係の準備** — PM は必要なツールをプロビジョニングし、新しいロック、既存の extras、有効なプラグインの要件から完全な Python 環境を準備します。選択を公開する前にその環境を検証します。プラグインが更新を失敗させることはありません。新しいコアにもう適合しないプラグインは、それを有効にしているすべてのプロファイルで `plugins.enabled` から `plugins.disabled` に移されます。メモリプロバイダーは `memory.provider` の選択を保持します。プラグインが無効になっている間、Hermes は組み込みのメモリを使い、そのことを起動時、`hermes memory status`、`hermes doctor` で伝えます。これに該当するのは、Hermes の Python を除外する `requires-python`、この Hermes がサポートするより新しい `manifest_version`、そしてリゾルバーがコアや設定順で先にあるプラグインと一緒に解決できないと証明した依存関係、または自身のビルドに失敗した依存関係です。ダウンロードやネットワークの失敗は 1 回リトライされ、再度失敗すると無効化されます。更新は `⚠ Disabled plugin '<name>' in <home>: <reason>` を表示し、レシートの警告と、そのプロファイルの設定の `plugins.disabled_by_update` の下に記録して、続行します。ダウンロードの失敗で無効化されたプラグインは次の更新でリトライされます。リゾルバーや自身のビルドに拒否されたものは、プラグインまたは Hermes の依存関係が変わった最初の更新でリトライされます。リトライは有効なプラグインのビルドが終わった後に実行され、適合した時点で（メモリプロバイダーも含めて）再び有効になります。例えば、プラグインが互換性のあるリリースを出した後や、Hermes が壊れた原因を修正した後です。リトライされたプラグインが有効なプラグインを押しのけることはありません。プロバイダーのみの記録は、`memory.provider` がまだそれを指している間だけリトライされます。早めに再び有効にするには `hermes plugins enable <name>` を実行します。オフのままにするには `hermes plugins disable <name>` を実行すると、リトライが止まります。この動作以前の更新では、プラグインが `plugins.enabled` と `plugins.disabled` の両方に記載され、どこにも読み込まれない状態になることがありました。`hermes doctor` はその状態を報告し、`hermes plugins enable <name>` または `hermes plugins disable <name>` で解消できます。実行中のバージョンが満たさない `requires_hermes` の範囲や、`hermes-agent` に対するプラグインの要件によってプラグインが無効化されることはありません。リリースタグのないソースチェックアウトは古いリリースのように見えることがあるためです。そのプラグインは代わりに今回は見送られ（`⚠ Left plugin '<name>' … out of this update`）、有効なまま残り、Hermes が受け入れ可能なバージョンを報告すると復帰します。設定を読み取れないセカンダリプロファイルも、設定が修正されるまで同じように見送られます。このステップを失敗させるのは、単独でビルドできないコアだけです。
5. **設定のマイグレーション** — お使いのバージョン以降に追加された新しい設定オプションを検出し、設定するように促します
6. **デスクトップのリビルド（ステージしてから入れ替え）** — Hermes Desktop アプリがこのチェックアウトからビルドされていた場合、GUI が新しいコードと一致するようにリビルドされます。リビルドは `apps/desktop/release/` の隣にある一時的なステージングディレクトリにパックされ、ステージされたアプリを検証してから、以前のビルドの上にリネームされます（Windows では、リアルタイムスキャナーが一時的に `release/win-unpacked` を掴んでいる場合、短いリトライを数回行ってやり過ごします）。どの時点でリビルドが失敗しても — Electron のダウンロードの破損、依存関係の欠落、ディスクの空き不足 — 以前のアプリはそのまま起動可能な状態で残ります。更新は `⚠` の行を表示し、残りのステップ（設定のマイグレーション、ゲートウェイの再起動）を終えて、レシートに `build` のフォローアップを記録して終了コード 0 で終了します。次回の起動、`hermes update`、または `hermes desktop --build-only --force-build` がリビルドをリトライします。macOS では、リビルドされたバンドルがその後、古い `/Applications/Hermes.app` または `~/Applications/Hermes.app` の上に（`ditto` で、署名を保ったまま）コピーされるため、Finder と Dock が起動するコピーがバックエンドと一致します。インストール済みのコピーが実行中の場合はそのままにされ、更新はそれを終了してから再度 `hermes update` を実行するよう伝えます。以前の更新がインストールしたコピーがその後削除されていた場合（ゴミ箱へのドラッグを含む）、更新は必要ならリビルドし、元に戻してそのことを伝えるため、Finder、Dock、Spotlight が再び Hermes を見つけられます。`hermes uninstall` はアプリを完全に削除します。Windows では、リビルド対象の Desktop アプリの内部から更新が完了する場合（アプリが起動時に中断された更新を完了させる場合）、リビルドは通知とともにスキップされます: Windows は実行中のアプリのファイルをロックし、アプリを停止すると更新も一緒に終了してしまうためです。更新の残りは完了します。リビルドして開き直すには、Hermes Desktop を終了してターミナルから `hermes desktop` を実行するか、**Settings → About** の **Update now** を使ってください。
7. **ゲートウェイの自動再起動**: どのゲートウェイも起動する前に、更新は、更新後のインストールともう一致しない各プロファイルのゲートウェイのサービス定義（systemd ユニット、停止中の launchd ジョブの plist、Windows のランチャースクリプト）を書き換えます。Linux と macOS では、更新のために一時停止されたゲートウェイは、依存関係が準備されそれらの定義が書き換えられた時点で、製品のビルドの前に再び起動されます。Windows ではビルドの後に再起動されます。その他の実行中のゲートウェイは、更新の完了後にリフレッシュされます。サービスとして管理されているゲートウェイ（Linux では systemd、macOS では launchd）は、サービスマネージャーを通じて再起動されます。手動のゲートウェイは、Hermes がその PID をプロファイルに対応付けられる場合に再起動されます。手動で起動した `hermes serve` / `hermes dashboard` のバックエンドは異なります: アップデーターはそれらを実行したままにし、所有者に再起動を求めます。[手動バックエンドの再起動リマインダー](#manual-backend-restart-reminders) を参照してください。実行中の Desktop アプリが所有するバックエンドは、引き続きアプリの責任です。
8. **マルチプレックスへの移行（複数プロファイルのインストール）** — フリートが新しいコードで検証されると、まだ **プロファイルごとに 1 つのゲートウェイ** を実行している 2 つ以上のプロファイルを持つインストールは、何も妨げるものがなければ、単一のマルチプレックスされたデフォルトゲートウェイにまとめられます（`hermes gateway migrate --multiplex --yes` と同じ）。妨げとなるもの（2 つのプロファイルで共有されたボットトークン、`/p/<profile>/` のイングレスなしにポートをバインドするセカンダリプロファイル）がある場合、更新はそれらとその修正方法を表示し、何も変更しません。単一プロファイルのインストールに手が加えられることはありません。[プロファイルごとのゲートウェイからの移行](/docs/user-guide/multi-profile-gateways#migrating-from-per-profile-gateways) を参照してください。

### 更新中のゲートウェイのダウンタイム {#gateway-downtime-during-an-update}

Linux と macOS では、`hermes update` はこのインストールから実行されているすべてのゲートウェイを、チェックアウトを最初に変更する直前に停止し、依存関係が準備された時点で（数分かかることがある Web UI、TUI、Desktop のビルドの前に）、まさにその集合を新しいコードで再び起動します。その間、ボットはオフラインになります: 通常は git の更新と依存関係の同期の時間です。以前は、git がファイルを書き換えている間もゲートウェイが古いコードで動き続け、その間に遅延インポートしたモジュールは新しいコードから読み込まれていました。

- 更新は、一時停止したものを示す 1 行（`⏸ Paused for the update: hermes-gateway.service`）と、復帰したときの 1 行（`▶ Restarted paused gateway(s): …`）を表示します。
- systemd ユニットと launchd エージェントは systemd/launchd を通じて停止・起動されるため、サービスマネージャーが更新の途中で古いコードのまま再起動することはありません。手動で起動したゲートウェイ（`hermes gateway run`）はドレインされた後、同じコマンドラインと Hermes ホームからバックグラウンドで再び起動されます。その出力はターミナルではなく、そのホームの `logs/gateway-update-resume.log` に送られます。
- チャットからの `/update` は一時停止を乗り切ります: 更新がゲートウェイ自身の systemd ユニット内で実行される場合、まず自分自身を独自のスコープに移動させます。ゲートウェイが一時停止している間に尋ねられたプロンプトは、中継できるゲートウェイがないため、即座にデフォルト値が採用されます。
- 一時停止した集合は、最初の停止の前に Hermes ホームに記録されます。更新が kill された場合、次の `hermes` コマンド（または `hermes update`）がまさにそれらのゲートウェイを再び起動します。チェックアウトを一度も変更しなかった失敗した更新は、それらを古いコードで再起動します。チェックアウトが移動した後に依存関係の同期が失敗した場合は、起動時に依存関係が同期された時点で再起動されます。
- アップデーターがスーパーバイザーを通じて停止できないゲートウェイ（s6 やカスタムの systemd ユニット、`--external-supervisor`、この更新を開始した launchd ジョブ）は、以前と同様に実行されたまま残され、更新後にリフレッシュされます。
- `--no-gateway-restart` は何も停止しません。ゲートウェイの管理はあなたが行います。
- 一時停止が更新を妨げることはありません。ゲートウェイを一覧表示、記録、停止できない場合は、停止したものを再起動してそのことを伝え、更新は一時停止が存在する前と同じように続行します: ゲートウェイは入れ替えの間も動き続け、その後に再起動されます。

Windows はもともと更新の前にゲートウェイを一時停止しており（依存関係の同期が置き換えるファイルをロックするため）、更新の完了後、ビルドの後に再起動します。

### ゲートウェイが所有するセッションランタイムへのアップグレード {#upgrading-to-the-gateway-owned-session-runtime}

このリリースから、ホストごとに 1 つのゲートウェイがすべてのローカルセッション（CLI、TUI、Desktop、
API、ACP、cron、Bot Chat）を所有します。既存のインストールが最初の更新で目にすること:

- **`cron.bot_chat_delivery_timeout_seconds` は廃止されました。** Bot Chat の配信は
  対象プロファイルの実行中のゲートウェイに受け入れられ、レシートによって追跡されます。cron 側に
  タイムアウトさせるターンはもう残っていません。設定マイグレーション v51 は、1 回限りの注記とともに
  このキーを削除します（バージョンのない `config.yaml` からも）。ゲートウェイが実行されていない場合、
  その実行は `delivery_failed` として記録され、自動的に再配信されることはありません。
- **レガシーな Bot Chat の保留レコード**（廃止された `hermes chat` 配信レーンが残した
  `cron/bot_chat_pending/*.json`）は、以降のスケジューラーのティックで、それ自身の ID のまま
  対象の稼働中のオーナーに引き渡されます。`claimed` のレコードは不確かな CLI のターンであったため、
  再送信されることはありません。レコードは証拠として最終ステータスとともに保持されます。
- **切り替えの再起動で中断された作業は決して再実行されません。** 最初のゲートウェイの
  起動時、ターンの途中（`started`）だった入力と、実行中だったマネージドワーカーは
  `unknown` になり、その後ろにキューされた入力は待機します。セッションを確認してから、
  `hermes chat`（または Desktop/TUI の同等の操作）で `/discard <admission_id>` を使うか、
  スクリプトから `hermes sessions discard <session> --yes` を使って確認応答してください。そうすると後続の入力が実行されます。ゲートウェイがクレームしたものの完了しなかった cron の配信も同様に
  `unknown` としてフェンスされ、`delivery_failed` として記録されます。
- **新しいゲートウェイが `state.db` に書き込んだ後のロールバックはサポートされません。**
  [古いリリースへのロールバック](#rolling-back-to-an-older-release) を参照してください。

### 古いリリースへのロールバック {#rolling-back-to-an-older-release}

古いリリースは、ゲートウェイランタイムが書き込んだ `state.db` 上では実行できません。それを行い得る
各箇所は、履歴を破損させる代わりに拒否します:

- **`hermes update`** は、いずれかのプロファイルの `state.db` がゲートウェイランタイムの履歴を
  保持している間、ゲートウェイランタイムより前の対象（`--branch`、チャネルの切り替え、ピン留めされた
  リリース）を拒否します。チェックアウトに触れる前に停止し、影響を受けるストアと戻る方法を
  一覧表示します。
- **アップグレードされたストア上で実行された古いリリース**（古いタグの手動の `git checkout`）は、
  ゲートウェイランタイムの履歴を持つセッションを削除もプルーニングもできません。`hermes sessions delete`
  と `prune` は `Refused to delete a session that has gateway runtime history` で停止します。
  古いリリースは依然としてこれをトレースバックの中に表示し、`prune` はバッチ全体を
  ロールバックします。
- **実行中のゲートウェイ** は、そのチェックアウトがそのようなリリースに戻されると、
  約 30 秒以内に自身を停止し、古いリリースが自分のゲートウェイを起動できるようにします。

それでも戻したい場合は、アップグレードされたデータベース上で古いリリースを実行するのではなく、
更新前の状態を復元してください:

1. `hermes gateway stop`
2. 古いリリースをチェックアウトします。
3. 最新の更新前スナップショット（`/snapshot restore <id>`）、または
   `hermes update --backup` で取得した完全バックアップ（`hermes import <backup.zip>`）を復元します。クイックスナップショットは
   1 GiB を超える `state.db` をスキップします。大きなストアには完全バックアップが必要です。

更新後に作成されたセッションとメッセージは、そのスナップショットには含まれません。

### ゲートウェイの再起動に時間がかかることがある理由

再起動はドレイン優先です: 実行中のゲートウェイは新しいターンを拒否し、進行中の作業（チャットのターン、cron ジョブ、API の実行）が終わるのを待ってから終了します。長時間実行のジョブが途中で打ち切られないよう、待機時間は `agent.restart_after_turn_timeout`（デフォルト 30 分）で上限が設けられています。その待機の間、アップデーターは 30 秒ごとに、ゲートウェイがまだ何を待っているかを表示します — 例:

```
  → hermes-gateway: draining (up to 1875s)...
  ⏳ still draining — 1560s left before the forced restart
     waiting on 1 active work unit(s):
       • cron job 6ba19dab68df (nightly-scout) in external worker pid 573597, running 6m40s
     finish or kill the work above to release the drain now; agent.restart_after_turn_timeout in config.yaml caps this wait
```

チャットのターンはセッションキー、モデル、現在のツールを表示し、cron ジョブはジョブ ID、名前、それを実行しているプロセス（systemd のインストールでは外部の再起動安全なワーカー、それ以外ではゲートウェイ自身）を表示します。ゲートウェイがドレインしている間、`hermes gateway status` も同じ作業単位を一覧表示します。待機をやめるには、一覧の作業を終わらせるか kill するか、`config.yaml` の `agent.restart_after_turn_timeout` を下げてください（`0` にすると即座に強制ドレインに入ります）。

固まった作業が再起動を引き留めることはありません: `agent.gateway_timeout` を超えてアイドル状態のチャットのターンや、スケジューラーの進行中許容時間（`max(2 × the job's interval, cron.inflight_max_minutes)`、デフォルト 30 分）より古い cron の実行は待機から除外され、代わりに再起動によって中断されます。

ゲートウェイより長く生き続ける作業も再起動を引き留めません: 独自の systemd スコープ（`systemd-run --user --scope`、systemd のインストールでは通常のケース）のワーカーにすでに引き渡された cron の実行は、ゲートウェイが停止しても実行を続け、その結果は次に起動するゲートウェイによって永続キューから配信されます — そのため、再起動は上限いっぱいまで待つことなく進みます。独自のスコープを得られなかったワーカー（到達可能なユーザーの D-Bus セッションがない。`cron.require_restart_safe_scope` を参照）はゲートウェイの cgroup に残り、再起動によって途中で kill されてしまうため、引き続き待機されます。

### Windows のアップデーターファイルの欠落

メンテナンスされているアップデータースクリプトが欠落している場合（例えばウイルス対策ソフトによる隔離の後）、レガシーな更新フォワーダーはハンドオフの成功を報告する代わりに失敗します。リトライする前に、インストールを修復し、セキュリティソフトの隔離レポートを確認してください。ウイルス対策の保護を無効にしないでください。成功を報告する前に、メンテナンスされているアップデーターは、CLI のインポート、Windows 実行ファイルのヘッダー、ASAR ヘッダーとパッケージ化されたメインエントリ、ローカルモジュールのエントリを持つ読み取り可能なレンダラー HTML、初期モジュールファイル、現在のビルドスタンプを確認します。これらは成果物の最小限のチェックであり、完全な依存関係の監査や、アプリケーション/バックエンドの起動テストではありません。Python の欠落は、Desktop の終了を待つ前に報告されます。依存関係の修復は引き続き更新の一部として実行できます。Electron は、そのレイアウトが存在する場合、バックエンドを停止する前にメンテナンスされているハンドオフの前提条件を確認します。本物のレガシーなフラットのアップデーターレイアウトは引き続きサポートされるため、欠落したアップデーターファイルがすべてバックエンドの終了前に検出されるわけではありません。

Windows では、パッケージングの間に開き直された Desktop は、ステージされたビルドが昇格される直前に再び停止されます。このクリーンアップは、そのチェックアウトの Desktop リリースツリー内の実行ファイルに限定されており、関係のないインストールは停止されません。それでもロックが残っている場合、リネームのエラーを回避するのではなく、ステージされたビルドの昇格が失敗します。

### fetch が `not a git repository` で失敗する

インストールの `.git` フォルダーは残っているものの、git がそれを受け付けなくなった場合 — `HEAD` の消失や空の `HEAD`、または存在しないフォルダーを指す `.git` ファイル — `hermes update` は "This Hermes checkout's git data is damaged" で停止します。kill された更新、書き込み途中のクラッシュ、`.git` に触れる同期ツールやウイルス対策ツールによって、このような状態になることがあります。そのようなチェックアウトでは、どの更新も fetch できません。更新が一時停止したゲートウェイは、何も書き込まれていないため、変更されていないコードで再び起動されます。

修復するにはインストーラーを再実行してください。インストーラーは破損したチェックアウトを `hermes-agent.broken-<timestamp>` として脇に移動し（何も削除されません）、新しく clone します。設定、セッション、その他のデータはチェックアウトの外にあるため保持されます。エラーにはお使いのチェックアウト用の正確なコマンドが表示されます。デフォルトの場所の場合は次のとおりです:

- Linux / macOS / WSL2: `curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash`
- Windows（PowerShell）: `iex (irm https://hermes-agent.nousresearch.com/install.ps1)`

別の場所にインストールしたチェックアウトでは、表示されたコマンドのとおり、そのディレクトリを再度渡す必要があります（Linux/macOS では `bash -s -- --dir <path>`、Windows では `-InstallDir <path>`）。指定しないと、インストーラーは代わりにデフォルトの場所を修復します。

Hermes が再び動作するようになったら、`.broken-*` フォルダーは削除して構いません。

### fetch が `should_include_obj should only be called on existing objects` で失敗する

Git 2.53 以降では、パーシャルクローンのパックファイルの一部に `.promisor` マーカーがない場合、
fetch 中にクラッシュすることがあります。これは、フィルター付きの fetch によって完全なクローンや
シャロークローンがパーシャルクローンになった場合や、マーカーが失われた場合に起こります。`hermes update` はそれらのパックにマークを付けて fetch を 1 回リトライし、
インストーラーの再実行も fetch の前にマークを付けます。その修正より前のアップデーターを持つインストールは
その修正自体を fetch できません: インストーラーを再実行するか、（Hermes を閉じた状態で）手動でパックにマークを付けてから再度更新してください。

チェックアウトは Hermes ホーム（`~/.hermes`、または設定されている場合は `HERMES_HOME`。
Windows では `HERMES_HOME` が設定されていない限り `%LOCALAPPDATA%\hermes`）の下の `hermes-agent` です。

```bash
# macOS / Linux
repo="${HERMES_HOME:-$HOME/.hermes}/hermes-agent"
for p in "$repo"/.git/objects/pack/pack-*.pack; do [ -e "${p%.pack}.promisor" ] || : > "${p%.pack}.promisor"; done
```

```powershell
# Windows
$repo = Join-Path ($(if ($env:HERMES_HOME) { $env:HERMES_HOME } else { "$env:LOCALAPPDATA\hermes" })) 'hermes-agent'
Get-ChildItem "$repo\.git\objects\pack\pack-*.pack" | ForEach-Object {
  $m = [IO.Path]::ChangeExtension($_.FullName, '.promisor')
  if (-not (Test-Path -LiteralPath $m)) { New-Item -ItemType File -Path $m | Out-Null }
}
```

チェックアウトはパーシャルクローンのままです。クラッシュを回避するために `remote.origin.promisor` / `partialclonefilter` を
削除しないでください: リリースタグや更新のバックアップからしか到達できないオブジェクトは一度もダウンロードされていないため、
パーシャルでないチェックアウトはその後 `git gc` が `bad tree object` で失敗します。すでに削除してしまった場合は、
欠けているオブジェクトを fetch し、何も残っていないことを確認してから、自動クリーンアップを再び有効にしてください:

```bash
git -C "$repo" rev-list --objects --missing=print --all | grep '^?' | cut -c2- | git -C "$repo" fetch -q --no-tags --stdin origin
git -C "$repo" rev-list --objects --missing=error --all >/dev/null && echo complete
```

```powershell
git -C $repo rev-list --objects --missing=print --all | Where-Object { $_.StartsWith('?') } | ForEach-Object { $_.Substring(1) } | git -C $repo fetch -q --no-tags --stdin origin
git -C $repo rev-list --objects --missing=error --all | Out-Null; $LASTEXITCODE   # 0 = complete
```

### パーシャルクローンで `.git` が増え続ける

インストーラーのチェックアウトは blobless のパーシャルクローンです: すべてのコミットとディレクトリの一覧はローカルにあり、
git はファイルの内容をオンデマンドでダウンロードし、オンデマンドのダウンロードはそれぞれ独自の小さなパックとして書き込まれます。
2026 年 9 月下旬のインストーラーは、代わりに treeless（`--filter=tree:0`）のクローンを作成していました。git は
欠けているツリーを要求するとき、すでにどれを持っているかを伝えないため、treeless のチェックアウトはチェックアウトや
パスでフィルターした履歴の走査のたびに、ディレクトリの完全なスナップショットを再びダウンロードしていました。`hermes update`
はそのようなチェックアウトを 1 回だけ変換します。これは新しいコードを pull した後、依存関係の作業の前の
最初のステップです: 1 回の `git fetch --refetch --filter=blob:none` ですべてのコミットとツリー（約
120 MB）を取得し、以降の更新ではそれらの再ダウンロードが止まります。そのようなチェックアウトの上でインストーラーを再実行しても、
同じように変換されます。その fetch が失敗した場合、更新は警告を表示して続行し、
次回に変換をリトライします。

変換が存在する前にビルドされた Hermes Desktop は、数分ごとにパスでフィルターした履歴の走査を実行するため、
treeless のチェックアウトではディスクをパックファイルで埋め尽くすことがあり（ある報告では 434 GB に達しました）、
更新が失敗した後も続いていました。すでにそうなってしまった場合の復旧方法:

1. Hermes Desktop を終了し、残っている `git rev-list`、`git maintenance`、
   `git commit-graph` のプロセスを終了させます。アプリを終了してもそれらは止まりません。
2. ディスクが完全にいっぱいの場合は、放棄された転送ファイルを削除して空きを確保します:
   `rm -f "$repo"/.git/objects/pack/tmp_pack_*`（Windows: `.git\objects\pack` の
   `tmp_pack_*` を削除）。各更新も、git のプロセスが実行されていなければ自動的にそれらを削除します。
3. `hermes update` を実行します。まずチェックアウトを変換し、その後、下記のとおり今回と以降の
   更新でパックの山を整理していきます。

`hermes update` 自体が起動できない場合、手動での変換は次のとおりです:

```bash
git -C "$repo" fetch --refetch --filter=blob:none origin
git -C "$repo" config remote.origin.partialclonefilter blob:none
```

`hermes update` と `hermes update --check` は、そのチェックアウトで `maintenance.commit-graph.enabled`、`gc.writeCommitGraph`、`fetch.writeCommitGraph` を `false` に設定します。グラフがまだ把握していないコミットに対して commit-graph を書き込むと、それらのツリーをすべてダウンロードしてしまうためです。これらの設定は変更せず、`gc.auto` もデフォルトのままにしておいてください。そうすれば git 自身の自動 gc が引き続きパックをまとめられます。

commit-graph がないとバージョンを調べるたびに履歴全体をたどることになるため、Hermes は commit-graph を自分で最新に保ちます。`hermes update` のたび（新しいコードが配置された後）と `hermes -w` の起動のたびに、グラフが存在しないか 1 日以上古い場合は、`git commit-graph write --reachable --split --no-changed-paths` でバックグラウンド更新します（最大で 6 時間に 1 回）。このコマンドはコミットだけを読み、ツリーは一切ダウンロードしません。アップデートはこの処理の完了を待たず、10 分経っても実行中の書き込みは停止されます（まず終了を要求するので、git は自分のロックを削除します）。失敗または停止した書き込みは `logs/agent.log` に記録されます。リンクされた worktree やサブモジュールのチェックアウトでは、オブジェクトを共有しているリポジトリのグラフが更新されます。リポジトリ自身、グローバル、またはシステムの git 設定で `core.commitGraph=false` になっているリポジトリには、グラフは作成されません。強制終了された git が残した `commit-graph.lock` や `multi-pack-index.lock` は、`index.lock` と同じ古いロックの掃除処理によって、10 分以上経過していて、どの形態の git プロセス（`git`、`git-commit-graph`、`git.exe` など）も動いていない場合に削除されます。Hermes が実行中のプロセスを一覧できない場合、ロックは削除されません。`hermes -w` を起動したリポジトリでは、これらのオブジェクトストアのロックだけが掃除され、`index.lock` や `HEAD.lock` は決して削除されません。

また、`hermes update` は毎回最大 60 秒をかけて、前回のアップデートが中断したところからこれらのパックを整理します。すべてのオブジェクトが別のパックにも格納されているパックを削除し、残りのパックが 50 個を超えている間は最も小さいものから統合します。ローカルに保存されたものが失われることはなく、GitHub が引き続きそれを提供しているかどうかにも依存しません。強制終了された `git fetch` が `.keep` ファイルで固定したまま残したパックも対象になります（git 自身の repack はこれらに触れません）。代わりに手動で一度にすべてをまとめるには、Hermes を閉じた状態で次を実行します（大きなチェックアウトでは完全な repack となり、何分もかかることがあります）:

```bash
git -C "$repo" -c gc.writeCommitGraph=false gc --auto
```

### デフォルト以外のブランチに対する更新: `--branch`

`--branch NAME` は、選択されたチャネルの代わりにブランチの先端に対して更新する、
1 回限りのオーバーライドです:

```bash
hermes update --branch release-candidate
hermes update --check --branch experimental   # preview behindness only
```

ローカルのチェックアウトが別のブランチにある場合、Hermes はコミットされていない作業を自動的に stash し、HEAD を対象のブランチに切り替えてから pull します。ローカルに存在しないブランチは `origin/<name>` から自動的に追跡されます（`git checkout -B <name> origin/<name>`）。どこにも存在しないブランチはきれいに失敗します — stash した変更は終了前に復元されるため、おかしな状態で取り残されることはありません。`main` 専用のフォークとアップストリームの同期ロジックは、`main` 以外のブランチでは自動的にスキップされます。

### フィーチャーブランチに置かれたままのチェックアウト

ソースチェックアウトが（ツールやワークツリーの実験、手動のチェックアウトによって）フィーチャーブランチに置かれたままになっている場合、作業ツリーがクリーンであれば、`hermes update` は自動的にそれを更新対象に戻します:

- **ブランチが完全にマージ済み**（すべてのコミットがすでに `origin/main` に含まれている — `git cherry` が未マージのものを報告しない）: 更新はそのことを伝え — `Checkout was parked on '<branch>' (fully merged) — switched back to main` — その後は `main` に留まります。
- **ブランチに未マージのコミットがある** がツリーはクリーン: 更新を進められるよう、それでも `main` に切り替えます — これは、スキップを解決する手段を持たない非対話型の呼び出し元（デスクトップの更新ボタン、ゲートウェイの `/update`、cron）が頼りにしている動作です。あなたのコミットには手が付けられません: `git checkout` がコミット済みの作業を破棄することはなく、更新はブランチ名とコミット数、後で作業を再開するための `git checkout <branch>` コマンドを示す目立つ通知を表示します。

カスタムブランチ（main の上で維持しているローカルパッチ）を *意図的に* 運用している場合は、`config.yaml` で `updates.parked_branch_strategy: update_in_place` を設定してください。すると更新は、ブランチから切り替える代わりに `origin/main` をそのブランチ **に** マージします — チェックアウトは移動せず、コミットは残り、実行中のコードが前進します。可能であれば fast-forward し、分岐している場合は `pre-update-<stamp>` の安全タグの背後で本当のマージを行い、コンフリクト時はきれいに停止します（何も変更されません）。`hermes update --switch-branch` は 1 回の実行に限り切り替えのパスに戻します — 更新によるマージコミットを溜めたくない深いフィーチャーブランチで便利です。

置かれたままのブランチに **コミットされていない変更** がある（ツリーが汚れている）場合、Hermes はそれに **触れません**。コードの更新は、更新が成功したふりをする代わりに、ブランチ名、`origin/main` からどれだけ遅れているか、解決するための正確なコマンドを示す目立つ警告とともに **SKIPPED** とマークされます。完了行には常に実際のブランチと HEAD が表示される（`✓ Update complete! [main @ 30fcf9580]`）ため、ずれが一目で分かります。自動切り替えを完全に無効にするには、`config.yaml` で `updates.auto_switch_parked_branch: false` を設定します（スキップの警告は引き続き表示されます）。

### 対象ブランチ上のローカルコミット

更新対象（`main`）に直接作成したコミットは、アップストリームが進むと fast-forward を妨げ、チェックアウトはそれをアップストリームの force-push と区別できないため、更新は `main` を `origin/main` にリセットします。リセットの前に、古い HEAD を `refs/hermes-update-backups/diverged-main-<stamp>-<sha>` として保存し、その ref と、ブランチから外れるコミット数を表示します。`git log origin/main..<ref>` でそれらを一覧表示でき、`git branch <name> <ref>` または `git cherry-pick` で取り戻せます。既存のチェックアウトの上でインストーラー（`install.sh` / `install.ps1`。デスクトップのブートストラップが実行するもの）を再実行しても、同じ ref が書き込まれます。`hermes update` がそれを書き込むたびに、種類ごとに最新の 10 個を保持し、30 日より古いものを削除します。更新をまたいでパッチを維持するには、代わりに `updates.parked_branch_strategy: update_in_place` を使ったカスタムブランチ上に置いてください。

### 非対話型の更新でのローカルの変更

ターミナルで `hermes update` を実行すると、Hermes はコミットされていないソースツリーの変更を stash し、pull してから、それらを復元するかどうかを **尋ねます** — これまでとまったく同じです。対話型の更新では何も変わりません。

自動 stash が対象にするのは *ソースツリー* の変更だけです。git チェックアウトのルートが `$HERMES_HOME` でもある **フラットなインストール**（例えば `HERMES_INSTALL_DIR=$HERMES_HOME` で作成したインストールや、古いインストーラーが作成したもの）では、プロファイルの実行時状態（`state.db` とその WAL/SHM サイドカー、`state-snapshots/`、`backups/`、`sessions/`、`cron/jobs.json`、`cron/*.db` ストア、`config.yaml`、`auth.json`、`memories/`、ロック/pid ファイル、…）が、追跡されていないファイルとしてチェックアウト内に存在します。これらのパスは git で無視されているため、自動 stash がそれらに触れることはなく、実行中のゲートウェイは更新の間もデータベースを保持します。フラットなインストールのルートに他の追跡されていないファイルを置いている場合は、チェックアウトの外に移動するか、`.git/info/exclude` に追加してください。追跡されておらず無視もされていないものは、ソースの編集と同様に自動 stash に取り込まれます。

更新が **ターミナルなしで** 実行される場合 — デスクトップ/チャットアプリの "Update" ボタンや、ゲートウェイがトリガーした更新から — 答えるべきプロンプトはありません。stash した変更をどうするかは、`updates.non_interactive_local_changes` の設定で決まります:

```yaml
# ~/.hermes/config.yaml
updates:
  non_interactive_local_changes: stash   # default: keep + auto-restore
  # non_interactive_local_changes: discard  # throw local source edits away
```

- `stash`（デフォルト） — 自動 stash し、pull してから、更新されたコードの上に変更を自動的に復元します。何も失われません。復元でコンフリクトが発生した場合は、手動で回復できるよう git stash に保持されます。
- `discard` — 自動 stash し、pull の後にその stash を破棄するため、更新は常にクリーンなツリーに着地します。Hermes のソースへのローカルな編集を保持するつもりがまったくないマシンでのみ使ってください。これは stash の drop であり（`git reset --hard` + `git clean -fd` ではありません）、`node_modules`、`venv`、ビルド出力のような無視されたパスに触れることはありません。

デスクトップアプリでは、これは **Settings → Advanced → In-App Update Local Changes** です。

**デスクトップの更新は決して自動復元しません。** デスクトップのアップデーターは `hermes update --keep-stash` を呼び出します: 更新を進められるようローカルのソースの編集は引き続き stash されますが、その後再適用は **されません** — それらは `git stash` に置かれたままになり、更新ログにはそれらを取り戻すための正確な `git stash apply <ref>` コマンドが表示されます。これにより、ローカルの編集がデスクトップの更新をまたいで黙って持ち越され、更新したばかりのインストールを壊すことを防ぎます。（破棄を選択している場合は、`non_interactive_local_changes: discard` が引き続き優先されます。）置かれたままの変更を手動で復元するには:

```bash
cd ~/.hermes/hermes-agent   # or your install root
git stash list --format='%gd %H %s'   # find the hermes-update-autostash entry
git stash apply stash@{0}
```

対話的にも同じ再適用しない動作にしたい場合は、ターミナルの `hermes update` にも `--keep-stash` を渡せます。

### プレビューのみ: `hermes update --check`

`hermes update --check` は、コードの適用、依存関係のインストール、ゲートウェイの再起動を行わずに、
チェックアウトを選択されたチャネルの対象（デフォルトでは最新の stable リリース、main チャネルでは `origin/main`）と
比較します。比較では Git のメタデータを fetch することがあり、ファイルシステムへの書き込みがゼロであることを約束するものではありません。
パッケージが所有するインストールは、外部の更新方法を報告します。

### フリートのプレビュー: `hermes update --plan`

複数のプロファイルやサービスを実行しているマシンを更新する前に、`hermes update --plan` を実行してください。インストールの種類、プロファイルをまたいで実行中の Hermes サービス、それらのスーパーバイザーと実行中のコードのバージョン、各サービスの再起動の仕組みを表示します。手動で起動した `hermes serve` / `hermes dashboard` のバックエンドは記録されたバインドエンドポイントとともに表示されますが、再起動はその所有者に委ねられます。アップデーターがそれらを停止したり再起動したりすることはありません。イメージやパッケージで管理されているインストールは、代わりに外部の更新コマンドを報告します。プランは読み取り専用で、稼働中のフリートでも安全です。

同じインベントリはすべての実際の更新のレシート（`~/.hermes/logs/update_receipts/`）に埋め込まれるため、更新の後で、アップデーターが見たものと行ったことを比較できます。

### 更新レシートとフリートのバージョンチェック

すべての `hermes update` の実行は、機械可読なレシートを `~/.hermes/logs/update_receipts/` に書き込みます（最新 20 件を保持し、`latest.json` は常に最新のものを指します）: 更新前のフリートのプラン、実行された各ステップ、スキップされたものとその理由、ゲートウェイの再起動の結果、最終的なフリートのバージョンマトリクスです。SQLite ランタイムの修復はそのステップの 1 つです（`sqlite_runtime_repair`）: 失敗した修復は実際の理由（例えば `uv sync` のエラー）と SQLite のバージョンの組を記録し、延期された、または該当しない修復はその理由とともにスキップに記録されます。再起動フェーズの後、アップデーターは稼働中の各ゲートウェイの実行中のコードを更新されたばかりのチェックアウトと比較し、プロファイルごとのマトリクスを表示します — まだ更新前のコードを提供しているゲートウェイは、正確な再起動コマンドとともに目立つように報告され、レシートに `gateway_restart` のフォローアップとして記録されます。コードはすでに配置されているため、更新は引き続き終了コード 0 で終了し、フリートが新しいコードを提供するまで以降のすべてのコマンドが警告するため、バージョンが混在したフリートが黙って健全とみなされることはありません。`--plan` とフリートのチェックはどちらも、利用可能な場合はローカルの制御ソケット（プロファイルのデータディレクトリにある `gateway.sock`、Windows では名前付きパイプ）を通じて実行中の各ゲートウェイに直接問い合わせるため、バージョンとスーパーバイザーの情報はゲートウェイ自身から得られます。古いバージョンのゲートウェイは、以前と同様に状態ファイルを通じて引き続き発見されます。

マルチプレックスされたデフォルトゲートウェイは複数のプロファイルを提供する 1 つのプロセスであるため、マトリクスには 1 回だけ表示され、その `served_profiles` レコードにあるすべてのプロファイルを保証します。同じカバレッジによって、"A previous `hermes update` pulled new code but did not restart running gateways" というヒントも解消されます: そのゲートウェイ（または手動の `git pull` の後では、更新が再起動したすべてのゲートウェイ）が現在のコードを実行すれば、`hermes gateway restart` で十分です — ヒントは、次の `hermes update` が新しいレシートを書き込むのをもう待ちません。どのゲートウェイに再起動の義務があるかを記録する前に終了した更新（またはそれを一度も記録しなかった古いアップデーター）が残した再起動の義務も同様です: すべての稼働中のゲートウェイが現在のチェックアウトを実行すれば、義務は解消され、ヒントは止まります。ゲートウェイをまったく実行していないホスト（Desktop アプリのみ）では、きれいに停止せずに消えたゲートウェイを持つプロファイルがなく、実行中のすべてのバックエンドが独自のスーパーバイザーによって再起動されるか独自のリマインダーを持っていれば、義務は解消されます。その義務は、プロファイル横断のランデブーディレクトリ（`$HERMES_GATEWAY_LOCK_DIR`、なければ `$XDG_STATE_HOME/hermes/gateway-locks`）に `host-update-restart-<install key>.json` としてホストごとに 1 回記録されます（インストールごとに 1 つなので、同じユーザーの 2 つ目の Hermes チェックアウトは独自のものを保持します。古いリリースのキーなしの `host-update-restart.json` は尊重され、独自の記録を持たないインストールによってのみクリアされるため、まだそのリリースにある別のチェックアウトは自身の負債を保持します）。そのため、すべてのプロファイルの CLI が同じものを参照します: `hermes -p coder update` と `hermes -p writer update` は、共有のマルチプレックスされたゲートウェイを、それぞれ 1 回ずつではなく、両者の間で 1 回だけ再起動します。古いプロファイルごとのアップデーターが残した義務（1 つのプロファイルの Hermes ホームにある `fleet_restart_pending`）も、引き続き読み取られクリアされます。更新前のプランでゲートウェイが 1 つも見つからなかった更新は何も負わず、痕跡も残しません。Desktop、systemd、launchd が監督するバックエンドはそのスーパーバイザーによって再起動され、この解消を妨げることはありません。義務を開いたままにするのは、リマインダーを保存できなかった手動のバックエンドだけです。

### 手動バックエンドの再起動リマインダー {#manual-backend-restart-reminders}

更新の後、手動で起動した各バックエンドの所有者に、`hermes serve` または `hermes dashboard` を再起動するよう依頼してください。SSH バックエンドの場合は Desktop を再接続します。ゲートウェイを再起動するだけでは、これらのプロセスはリフレッシュされません。

検証済みの稼働中のバックエンドについて、アップデーターはその再起動を `deferred` として記録する前にリマインダーを保存します。これにより、残りのチェックが通れば更新を完了できます。プロセスの識別情報が不明な場合は、新たな延期の対象になりません。

リマインダーは、ローテーションする更新レシートとは別に、アクティブな Hermes ホームの下の `serve_restart_pending/` に保存されます。各リマインダーは PID と作成時刻でプロセスを識別します。起動時の警告は、そのプロセスが生きている間、または生存状態が不明な間はリマインダーを保持し、まさにそのプロセスが消えたと確認されたときにのみ削除します。後の更新や正常なゲートウェイがそれを削除することはありません。

保存に失敗した場合、Hermes は警告し、保存されなかった義務を後のレシートに持ち越してリトライします。ストレージの権限と空き容量を確認し、指示どおりにバックエンドを再起動してください。リマインダーとレシートの両方のストレージが失敗した場合、永続的な保持は保証できません。

### ゲートウェイ内部からの自動更新: `--no-gateway-restart`

ゲートウェイ *によって* 起動された更新（cron ジョブ、Desktop のアップデーター、ゲートウェイプロセスの子である任意の自動化）は、
自身によるフリートの再起動を乗り切れません: ゲートウェイは
`SIGUSR1` でドレインし、その後 systemd の `KillMode=mixed` が cgroup に残っているものを、アップデーターも含めてすべて kill します。`hermes update --no-gateway-restart` は完全なパイプライン（pull、依存関係、
Node ワークスペース、Web UI、メンテナンス）を実行し、再起動とフリートの検証だけをスキップします。Linux
と macOS では、チェックアウトが変わる前の一時停止もスキップするため、何も停止されません。
保留中の再起動のマーカーは保持されるため、次回の CLI の起動で警告が表示され、次の通常の `hermes update`
（または `hermes gateway restart`）がフリートを追いつかせます。別の再起動ステップと組み合わせてください。例えば
更新ジョブの 10〜15 分後のタイマーです。レシートは延期を記録します。延期だけが原因で古くなった
フリートによって、更新が `partial` になることはありません。

### 中断されたゲートウェイの再起動

以前の更新がコードを pull したもののフリートの再起動を終えなかった場合、次の `hermes update` は、チェックアウトがすでに最新であってもリトライします。空のプロセススキャンは回復を証明しません: 失敗した systemd ユニットやインストール済みの launchd ジョブは、稼働中の PID を持たないことがあります。発見や再起動が失敗した場合、または要求されたサービスがアクティブであることを検証できない場合、マーカーは保留のままです: 更新は引き続き終了コード 0 で終了し（新しいコードは配置されています）、`⚠` の行とレシートの `gateway_restart` のフォローアップを表示し、すべての CLI の起動で負っている再起動について警告し、次の `hermes update` がそれをリトライします。表示されたコマンドで影響を受けたサービスを回復するか、`hermes update` を再実行してください。

失敗した過去のレシートだけでは、ゲートウェイがまだ古いことの証明にはなりません。起動時とゲートウェイのステータスの警告、そして更新の追いつき処理は、そのレシートに記録されたすべてのゲートウェイプロファイルについて、現在のチェックアウト上の稼働中の後継を確認します。手動のゲートウェイの再起動によって、過去の結果を書き換えることなく、レシートのみの助言を解消できます。手動バックエンドの義務は、まずそれぞれのリマインダーに移される必要があります。

保留中の再起動マーカーは、それ自身の更新前のランタイムインベントリと対象のコミットを記録します。回復はそのインベントリを確認し、古いレシートのインベントリを確認することはありません。解消には、空でない検証済みの現在のフリート、記録されたすべてのゲートウェイプロファイルについて対象のコミットにある後継、そして特定された手動バックエンドの義務の処理の成功が必要です。まだ生きている、または生存状態が不明な手動バックエンドには保存されたリマインダーが必要です。終了が確認されたプロセスにはリマインダーは不要です。ゲートウェイの欠落、サポートされていないランタイム、リマインダーの書き込みの失敗は、マーカーを保留のままにします。

インベントリのないレガシーなマーカーや、不正な形式またはサポートされていないインベントリは、起動時や追いつき処理の調整によって自動的にクリアできません。見えているすべてのゲートウェイを再起動するだけでは、その更新が何を負っていたかを確定するのに十分ではありません。警告は、後の更新が独自のインベントリを含む新しいマーカーとともに完了し、正常に解消されるまで残ります。

### 更新前の完全バックアップ: `--backup`

重要度の高いプロファイル（本番環境のゲートウェイ、チーム共有のインストール）では、pull の前に `HERMES_HOME`（設定、認証、セッション、スキル、ペアリング）の完全バックアップを取得するように選択できます。

```bash
hermes update --backup
```

または、すべての実行でこれをデフォルトにすることもできます。

```yaml
# ~/.hermes/config.yaml
updates:
  pre_update_backup: full
```

`updates.pre_update_backup` には 3 つのモードがあります:

- `quick` は前述の選択された状態ファイルを保存します。これがデフォルトです。
- `full` は [バックアップの除外対象](../reference/faq.md#hermes-backup-vs-hermes-profile-export) を適用した zip アーカイブを追加します。大きなデータディレクトリでは数分かかることがあります。
- `off` は更新前のバックアップを無効にします。`--no-backup` は 1 回の実行に限りこのモードを選択します。

レガシーな真偽値も引き続きサポートされます: `true` は `full`、`false` は `off` を意味します。

:::tip 新しいマシンに移行する場合は?
更新のバックアップは、その場での更新を保護するものです。セットアップ全体を別のハードウェアに移行する場合は、代わりに `hermes backup` + `hermes import` を使ってください — [Hermes を別のマシンにエクスポートする](../reference/faq.md#exporting-hermes-to-another-machine) と [`hermes backup` vs `hermes profile export`](../reference/faq.md#hermes-backup-vs-hermes-profile-export) を参照してください。
:::

### Windows のプロセスの所有権と依存関係の変更

Windows では、プロセスの実行中、実行ファイルやネイティブ拡張のファイルが開いたままになることがあります。
そのため PM は、インポート済みのライブラリをその場で置き換えるのではなく、依存関係の世代を
別に準備します。実行中のプロセスは、再起動するまで現在のインポートを保持します。

特定のプロセスとインストールに対するブロッカーの診断に従ってください。Python や Hermes という
名前のプロセスをすべて kill しないでください。ソースの更新と MSIX パッケージの
置き換えでは、所有者と終了の要件が異なります。

パーサーは Windows との互換性のために `--force` と `--force-venv` を保持しています。これらは
通常の更新手順ではなく、OS のファイルロックを回避できることを保証するものでもありません。失敗した更新をリトライする前に、
`hermes update --plan`、更新ログ、`hermes pm status` を確認してください。

### 推奨される更新後の検証

ソースの更新の後は、次の診断を実行してください。バンドルされたアプリの場合は、パッケージ内で
Git コマンドを使う代わりに、その About ページとバックエンドのヘルスを使ってください。

1. `git status --short` — ツリーが想定外に変更されている場合は、続行する前に確認してください
2. `hermes doctor` — 設定、依存関係、サービスの状態をチェックします
3. `hermes --version` — バージョンが想定どおりに上がったことを確認します
4. ゲートウェイを使用している場合: `hermes gateway status`
5. `hermes pm status` — 依存関係の準備と、失敗したステップを確認します。

:::warning 更新後の作業ツリーが汚れている場合
`hermes update` の後に `git status --short` が想定外の変更を表示する場合は、続行する前に停止して確認してください。これは通常、ローカルの変更が更新されたコードの上に再適用されたか、依存関係のステップがロックファイルを更新したことを意味します。
:::

### 更新の途中でターミナルが切断された場合

`hermes update` は、ターミナルの予期しない切断から自身を保護します。

- 更新は `SIGHUP` を無視するため、SSH セッションやターミナルウィンドウを閉じても、インストールの途中で終了させてしまうことはなくなりました。`pip` と `git` の子プロセスもこの保護を継承するため、接続が切断されても Python 環境がインストール途中の状態で残ることはありません。
- 更新の実行中、すべての出力は `~/.hermes/logs/update.log` にミラーリングされます。ターミナルが消えた場合は、再接続してログを確認し、更新が完了したか、ゲートウェイの再起動が成功したかを確認できます。

```bash
tail -f ~/.hermes/logs/update.log
```

- `Ctrl-C`（SIGINT）とシステムシャットダウン（SIGTERM）は引き続き尊重されます。これらは意図的なキャンセルであり、事故ではないためです。新しいコードが配置された後の `Ctrl-C` は終了コード 130 で終了し、そのことを伝えます: 残りのステップ（依存関係、ビルド、ゲートウェイの再起動）は保留となり、次回の起動または `hermes update` がそれらを完了させます。

ターミナルの切断に耐えるために `hermes update` を `screen` や `tmux` でラップする必要はなくなりました。

### 更新や起動が推測せずに拒否する場合

続行すると更新途中のチェックアウトや古いコードで動くゲートウェイが残る可能性があるため、いくつかの状況では続行せずにメッセージを表示して停止します:

- **別の起動が中断された更新を修復している。** git がチェックアウトを移動している間に更新が kill された場合、次の `hermes` の起動がまずチェックアウトを元に戻します。同時に始まった起動（CLI の隣で再起動するゲートウェイや Desktop のバックエンド）は順番に処理されます。別の起動の修復を 10 秒以上待った起動は、ステータス 1 で終了します: `hermes: another Hermes launch is finishing an interrupted 'hermes update'; launch again in a moment.` もう一方が終わったら再度起動してください。その時点で Hermes Desktop が起動したバックエンドは起動失敗として表示されますが、開き直せば十分です。
- **Windows での git の失敗 → ZIP フォールバック。** Windows では、`hermes update` 中の git のエラーは、git がまだチェックアウトに触れていない場合にのみ、リリースの ZIP のダウンロードにフォールバックします: 更新開始時と同じコミットとブランチで、stash も取られておらず、ツリーの移動も始まっていない場合です。git が stash したり、ブランチを切り替えたり、ファイルの移動を始めたりした後は、ZIP の上書きがその状態を埋もれさせてしまうため、更新は代わりに git のエラーを報告してステータス 1 で終了します。git の問題を修正してから `hermes update` を再実行してください。
- **Desktop のビルドには書き込み可能な `.git` が必要。** `hermes desktop` でチェックアウトから Hermes Desktop をビルドする場合、`hermes update` と同じチェックアウトのロック（`hermes update` もそれを必要とします）を取得します。これはチェックアウトの git ディレクトリに保持されます。そのディレクトリがあなたのユーザーで書き込み可能でない場合（例えば別のアカウントが所有するチェックアウト）、ビルドは更新と並行してビルドする代わりに `.../.git/hermes-update.lock is not writable` で拒否します。`.git` の所有者または権限を修正してください。macOS/Linux では、`sudo hermes update` によって読み取り専用のまま残されたロックファイルも引き続き使用できます。
- **再起動の記録が書き込めない。** `hermes update` は、チェックアウトを移動する前に、負っているゲートウェイの再起動をホストの状態ディレクトリ（`$HERMES_GATEWAY_LOCK_DIR`、なければ `$XDG_STATE_HOME/hermes/gateway-locks`）に記録します。そのディレクトリに書き込めない場合、記録は代わりに現在のプロファイルの Hermes ホームに保存されます。それを読むのはそのプロファイルだけなので、更新が進むのは他のプロファイルがないインストールの場合だけです。他のプロファイルが存在する場合、またはプロファイルの一覧を読み取れない場合、更新は何かを移動する前に拒否します。状態ディレクトリを書き込み可能にしてから再度実行してください。

```bash
hermes --version
```

[GitHub リリースページ](https://github.com/NousResearch/hermes-agent/releases) で最新リリースと比較してください。

### メッセージングプラットフォームからの更新

Telegram、Discord、Slack、WhatsApp、Teams から直接、次を送信して更新することもできます。

```
/update
```

これにより最新のコードを取得し、依存関係を更新し、実行中のゲートウェイを再起動します。再起動中、ボットは短時間オフラインになり（通常 5〜15 秒）、その後再開します。

### ソースの手動メンテナンスとロールバック

独立した開発用チェックアウトには、[ソースインストールのガイド](/docs/user-guide/switching-to-source) を使ってください。
Git のリビジョンを変更する前に、ローカルの作業をコミットするか、その他の方法で保全してください。
サービスが実行しているコードを置き換える前に、自分が所有するサービスを停止してください。

ソースのリビジョンを変更した後は、そのリビジョンの依存関係/ブートストラップの手順を実行してください。
PM が管理するチェックアウトでは、選択したソース環境から `python -m pm.cli install` を使います。
素の pip install は同等ではありません: マネージドなツールストアや PM のランタイムの選択を準備しないためです。

コードのチェックアウトだけではデータのロールバックにはなりません。新しいリリースは、古いコードが読めない形で
設定やデータベースを移行することがあります。古いリリースが以前のデータ形式を必要とする場合は、
更新前の一貫したバックアップを使ってください。復元を試みる前に、現在のデータを保全してください。

パッケージが所有するインストールでは、そのパッケージマネージャーのロールバックまたは再インストールの
手順を使います。署名されたアプリやイミュータブルなイメージの中で Git や pip を実行しないでください。

### Python 3.14 と古いインタープリター

Hermes は **Python 3.14** でのみ動作します。`pyproject.toml` は依然として
`requires-python = ">=3.11,<3.15"` を宣言していますが、すべてのランタイム依存関係には
`python_version >= '3.14'` のマーカーが付いています。範囲が広いのは 1 つの理由のためです:
venv が PM への移行より前（Python 3.11〜3.13）のソースインストールが、新しいコードを
チェックアウトしてもう一度 `hermes update` を実行できるようにするためです。その更新は
新しい完了プロセスに引き継がれ、PM が `pm/lock.json` からピン留めされた 3.14 の
インタープリターをプロビジョニングし、その上に依存関係の環境を構築し、ランチャーの向き先を
変更します。その後、古いインタープリターは使われなくなります。

`hermes update` の外で、これが意味すること:

- Python 3.11〜3.13 でビルドされた `pip install .`、`uv pip install .`、`pip install -e .`、または Homebrew/PyPI
  のパッケージは、`hermes-agent` を **依存関係なしで** インストールし、そのパッケージはインポートできません。これらのインストール方法は
  [サポートされていません](/docs/getting-started/platform-support#unsupported)。ソースインストーラーか
  パッケージ化されたビルドを使ってください。
- リポジトリの flake の外での Nix ビルドは、同じマーカーでゲートされた依存関係のセットを参照し、
  3.14 のインタープリターが必要です。
- まだ移行前の venv を指している `hermes` ランチャーは、古い venv への再インストールではなく、
  `hermes update`（またはチェックアウトからの `python -m pm.cli install`）で修復してください。

### イメージで管理されたインストール（Docker）: プロベナンスマーカー

公開されている Docker イメージには、ファイルシステムがイメージで管理されていることを権威的に示す小さな読み取り専用のマーカー（`/etc/hermes/image-provenance.json`）が組み込まれています。`hermes update`、`hermes update --check`、ダッシュボードの Update ボタンはいずれも、何かに触れる前にそれを参照します: イメージで管理されたインストールでは、きれいに拒否し（終了コード 2）、実際の更新コマンド（`docker pull nousresearch/hermes-agent:latest`）を表示し、フリートのツールが試行の発生を確認できるよう `refused` のレシートを書き込みます。ソースチェックアウトがコンテナにバインドマウントされている場合でもマーカーが優先されます — 拒否は、実行中のファイルシステムがどう見えるかではなく、それが *何であるか* に基づきます。破損したマーカーでも拒否します（フェイルクローズ）。Nix や apt で管理されたインストールは、既存の検出を使って同じゲートで拒否します。

### Nix ユーザー向けの注意

Nix はもはや明示的にサポートされるインストール方法ではありません（ベストエフォートのみ） — [Nix のセットアップ](/docs/getting-started/nix-setup) を参照してください。Nix flake 経由でインストールした場合、更新は Nix パッケージマネージャーを通じて管理されます。

```bash
# Update the flake input
nix flake update hermes-agent

# Or rebuild with the latest
nix profile upgrade hermes-agent
```

Nix のインストールはイミュータブルであり、ロールバックは Nix の世代システムによって処理されます。

```bash
nix profile rollback
```

詳細については [Nix のセットアップ](/docs/getting-started/nix-setup) を参照してください。

## アンインストール

```bash
hermes uninstall
```

ソースインストールの場合は、削除する前に `hermes uninstall --dry-run` を確認してください。
デフォルトの削除では、設定とユーザーデータを保持できます。`--full` はデータも
削除します。`--data` は、パッケージが所有するコードを削除せずにユーザーデータを削除します。
これらのモードは破壊的です。まずバックアップを作成してください。

MSIX/Store の場合は、Windows の Settings → Apps → Installed apps を使ってください。macOS の場合は、
Hermes を終了してそのアプリバンドルをゴミ箱に移動します。Docker、Nix、Termux は、それらを
インストールしたのと同じマネージャーを使います。それらのパッケージファイルは
ソースのアンインストーラーでは削除されません。データの削除はパッケージの削除とは別です。

:::tip 離れるのではなく、新しいマシンに移行する場合は?
インストールを削除する前に `hermes backup` を実行してください。完全なアーカイブには
認証情報が含まれますが、ダウンロードされたランタイム、依存関係の環境、キャッシュ、
ブラウザプロファイルは除外されます。ソースのデータを削除する前に、スキップされたファイルのレポートを確認してください。
`hermes profile export` は認証情報を含めずに 1 つのプロファイルをパックします。
[`hermes backup` vs `hermes profile export`](../reference/faq.md#hermes-backup-vs-hermes-profile-export) を参照してください。
:::

### 手動でのアンインストール

```bash
rm -f ~/.local/bin/hermes
rm -rf /path/to/hermes-agent
rm -rf ~/.hermes            # Optional — keep if you plan to reinstall
```

:::info
ゲートウェイをシステムサービスとしてインストールした場合は、まず停止して無効化してください。
```bash
hermes gateway stop
# Linux: systemctl --user disable hermes-gateway
# macOS: launchctl remove ai.hermes.gateway
```
:::
