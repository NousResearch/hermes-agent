# スケジュールタスク（Cron）

自然言語またはcron式でタスクを自動実行するようにスケジュールできます。Hermesはcron管理を、個別のschedule/list/removeツールではなく、アクションスタイルの操作を持つ単一の`cronjob_manage`ツールを通じて公開します。

## cronが今できること

cronジョブは次のことができます。

- ワンショットまたは繰り返しのタスクをスケジュールする
- ジョブの一時停止、再開、編集、トリガー、削除を行う
- ジョブのスケジュールには触れずに、すでに実行中の実行を停止する
- ジョブに0個、1個、または複数のスキルを紐づける
- 結果を発信元のチャット、ローカルファイル、または設定済みのプラットフォームターゲットに配信する
- 通常の静的ツールリストを持つ新規エージェントセッションで実行する
- **no-agentモード**で実行する — スケジュールに沿って動くスクリプトであり、その標準出力はそのまま配信され、LLMは一切関与しません（後述の[no-agentモード](#no-agent-mode-script-only-jobs)のセクションを参照）
- **外部イベント**で発火する — `cron_job`が設定されたwebhookルートは、次のスケジュールtickを待つ代わりに、何かが起きた瞬間（PRにフィードバックが付いた、サービスがアラートを投稿した）にジョブを発火させます。[イベントトリガー型のcronジョブ](../messaging/webhooks.md#event-triggered-cron-jobs)を参照してください。

これらすべては`cronjob_manage`ツールを通じてHermes自身からも利用できるため、平易な言葉で依頼するだけでジョブの作成、一時停止、編集、削除が可能です — CLIは不要です。

:::tip
**cronジョブはどのモデルで実行されるか？** 発火時の解決順序は次のとおりです: ジョブごとの固定 → `config.yaml`の`cron.model` → `hermes model`で設定したメインエージェントのモデル。

- **ジョブごとの固定** — 独自のモデルを持つジョブ。ダッシュボード、`hermes cron create/edit --model … --provider …`、または`~/.hermes/cron/jobs.json`の編集で特定のモデルに設定するか、`hermes cron create/edit --pin`で**現在のメインモデルに固定**します（エージェントの`cronjob_manage`ツールも`pinned=true`でこれを行えますが、あなたが依頼した場合に限ります）。`--unpin`（`pinned=false`）で固定を解除します。エージェントがジョブを*別の*モデルに向けることはできません — 推論の固定はユーザーが所有します。
- **`cron.model` / `cron.model_provider`** — cronフリート全体のデフォルト: 固定されていないすべてのジョブは、チャットのモデルとは独立にこのモデルで実行されます。一度設定すれば（`hermes config set cron.model <name>`）、`hermes model`や`/model`でチャットのモデルを切り替えてもcronフリートには影響しません。
- **メインエージェントのモデル** — 上記のどちらも設定されていない場合、ジョブは**発火した時点で**`hermes model` / `/model`に設定されているモデルで実行されます。メインモデルを変更すると、固定されていないすべてのジョブは次回の実行からそれに従います。

ジョブがどのプロバイダーに解決されても、そのプロバイダー固有のリクエスト設定（例: カスタムプロバイダー向けの`extra_body`/`extra_headers`などの`request_overrides`）は、インタラクティブなセッションと同様にスケジュール実行にも引き継がれます。

OAuthのリフレッシュが自動であるため、`hermes setup --portal`は無人実行にとって最も手間のかからない選択肢です。[Nous Portal](/docs/integrations/nous-portal)を参照してください。
:::

:::tip
**ジョブごとの推論の労力（reasoning effort）。** ジョブは、モデルの固定とは独立に、独自の思考レベルを固定できます: `none`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`、`ultra`のいずれかです。設定すると、そのジョブの実行についてグローバルの`agent.reasoning_effort`とモデルごとの`agent.reasoning_overrides`の両方を上書きします（`none`で思考を無効化）。`hermes cron create/edit --reasoning-effort high`で設定し、編集時に空文字列を渡すと固定がクリアされ、再び設定に従います。（モデルの設定はユーザーの判断に委ねるため、これは意図的にエージェントの`cronjob_manage`ツールには公開されていません。）モデルがサポートしないレベルは、リクエスト時にプロバイダーによって丸められるか省略されます — 上限が`high`のモデルで`xhigh`を固定すると`high`で実行されます。この固定は`no_agent`ジョブには効果がありません（調整するLLM呼び出しがないため）。グローバルのデフォルトに触れずに、重いスケジュール分析を`high`で、安価な繰り返しジョブを`minimal`で実行するのに使ってください。
:::

:::warning
cron実行中のセッションは、再帰的にさらにcronジョブを作成することはできません。Hermesは暴走するスケジューリングループを防ぐため、cron実行内ではcron管理ツールを無効化します。
:::

## 受け付けのリカバリー

エージェントを伴う実行は、出力と永続的な配信の引き渡しが記録されるまで、その発火のアイデンティティを保持します。
スケジューラは各tickで、所有者の再起動後も含め、未完了の受領記録を照合します。既知の
終端結果は、エージェントを再実行することなく配信キューに引き渡されます。重複した引き渡しや
記帳は元の発火のアイデンティティを使います。送信の要求後に中断された配信は不明のまま残り、
自動的にはリトライされません。

中断された実行や、見つからない準備済みの発火は、オペレーターのレビューのために一時停止されたままになります。
リカバリーがそれに対して別の受け付けを作ることは決してありません。一時停止されたジョブは、完了した結果が
回復された場合でも、自動的には再開されません。`hermes cron run`は、既知の同期的な
実行失敗に対して非ゼロで終了します。バックグラウンドでのディスパッチは、終端の成功/失敗の判定ではありません。

## スケジュールタスクの作成

### チャットで `/cron` を使う

```bash
/cron add "in 30m" "Remind me to check the build"
/cron add "every 2h" "Check server status"
/cron add "every 1h" "Summarize new feed items" --skill blogwatcher
/cron add "every 1h" "Use both skills and combine the result" --skill blogwatcher --skill maps
```

### スタンドアロンCLIから

```bash
hermes cron create "every 2h" "Check server status"
hermes cron create "every 1h" "Summarize new feed items" --skill blogwatcher
hermes cron create "every 1h" "Use both skills and combine the result" \
  --skill blogwatcher \
  --skill maps \
  --name "Skill combo"
```

### 自然な会話を通じて

通常どおりHermesに依頼します。

```text
Every morning at 9am, check Hacker News for AI news and send me a summary on Telegram.
```

Hermesは内部で統一された`cronjob_manage`ツールを使用します。

## ディスパッチ前の設定検証

スケジュール実行のためにエージェントの仕組みを構築する前に、スケジューラは
そのジョブの設定で実際に実行が成功し得るかを検証します。

- プロバイダーのAPIキーが解決できること（`fallback_providers`チェーンが設定されている場合、
  固定されていないジョブではスキップされます。フォールバック経路が欠けたプライマリキーを救える可能性があるためです。
  固定されたジョブはそのチェーンを使わないため、常にチェックされます）
- 紐づいたスキルの準備ができていること（必須の環境変数、
  コマンド、認証情報ファイルが欠けていないこと）
- 配信プラットフォームのターゲットが既知であり、ゲートウェイの認証情報が設定されていること
  （`local`/`origin`ターゲットはチェックされません）
- ジョブ自身の`enabled_toolsets`で指定されたすべてのMCPサーバーが、このプロファイルで
  少なくとも1つのツールに解決されたこと。このゲートウェイで以前に接続し、ネットワークの瞬断
  （ルーターの再起動、DNSの失敗）の後に再接続しているだけのサーバーは、ブロック**しません**: ジョブは
  解決できたツールで実行され、ゲートウェイのログにはどのサーバーがスキップされたかが記録されます（障害ごとに1回）。
  このプロファイルで一度も接続しなかったサーバー（URLや認証情報の誤り、またはマルチプレクサーのもとで
  別のプロファイルが所有するサーバー）や、失効した認証情報などの恒久的なエラーで停止しているサーバーは、
  実行をブロックします。

検証に失敗すると、ジョブの`last_status`は`blocked_config`になり、アラートが1回だけ
配信され（tickごとに繰り返されることはありません）、**LLM呼び出しは行われません**
— 設定の誤ったジョブがトークンを消費することは決してありません。次の正常な実行で
ブロック状態がクリアされるため、将来設定が壊れたときに再びアラートが出ます。

認証情報の欠落の判定には、スケジューラが読んだプロファイルと`HERMES_HOME`が示されます。例:
`provider credential missing: No Codex credentials stored … [profile
'default', HERMES_HOME /opt/data]`。「同じ」認証情報を使うインタラクティブなセッションが動作する場合は、
そのパスをシェルの`HERMES_HOME`と比較してください: シェルの環境なしで起動されたゲートウェイ
（Dockerの`HOME`と`HERMES_HOME`の違い、サービスユニット）や、多重化されたサテライトのプロファイルは、
シェルとは異なる`auth.json`や`.env`を読みます。

検証を無効にして以前の挙動（実行は進み、実行中に失敗する）に戻すには:

```yaml
cron:
  preflight: false
```

または: `hermes config set cron.preflight false`

## 固定されていないジョブを新しいグローバルデフォルトに移す

固定されていないジョブはメインエージェントのモデルに従うため、`hermes model`はcronフリートも一緒に移動させます。
ジョブを特定のモデルに*留めて*おきたい場合は:

```bash
hermes cron edit <job_id> --pin                                   # lock the current main model onto one job
hermes cron edit <job_id> --provider <provider> --model <model>   # pin an explicit model
hermes cron edit <job_id> --unpin                                 # follow the main model again
hermes config set cron.model <model>                              # every unpinned job, without touching chat
```

`hermes cron list`と`cronjob_manage`ツールは、ジョブごとに`pinned`を報告します。

## スキルを使ったcronジョブ

cronジョブは、プロンプトを実行する前に1つ以上のスキルをロードできます。各スキルは、チャットセッションで`/skill-name`から読み込む場合とまったく同じようにロードされ、`config.yaml`から解決された`metadata.hermes.config`の値を含む`[Skill config ...]`ブロックも含まれます。

### 単一スキル

```python
cronjob(
    action="create",
    skill="blogwatcher",
    prompt="Check the configured feeds and summarize anything new.",
    schedule="0 9 * * *",
    name="Morning feeds",
)
```

### 複数スキル

スキルは順番にロードされます。プロンプトは、それらのスキルの上に重ねられるタスク指示になります。

```python
cronjob(
    action="create",
    skills=["blogwatcher", "maps"],
    prompt="Look for new local events and interesting nearby places, then combine them into one short brief.",
    schedule="every 6h",
    name="Local brief",
)
```

これは、完全なスキルテキストをcronプロンプト自体に詰め込むことなく、スケジュールされたエージェントに再利用可能なワークフローを継承させたい場合に便利です。

## プロジェクトディレクトリ内でジョブを実行する

cronジョブはデフォルトで、いかなるリポジトリからも切り離されて実行されます — `AGENTS.md`、`CLAUDE.md`、`.cursorrules`はロードされず、ターミナル / ファイル / コード実行ツールはゲートウェイが起動した作業ディレクトリから動作します。これを変更するには、`--workdir`（CLI）または`workdir=`（ツール呼び出し）を渡します。

```bash
# Standalone CLI (schedule and prompt are positional)
hermes cron create "every 1d at 09:00" \
  "Audit open PRs, summarize CI health, and post to #eng" \
  --workdir /home/me/projects/acme
```

```python
# From a chat, via the cronjob tool
cronjob(
    action="create",
    schedule="every 1d at 09:00",
    workdir="/home/me/projects/acme",
    prompt="Audit open PRs, summarize CI health, and post to #eng",
)
```

`workdir`が設定されている場合は次のようになります。

- そのディレクトリの`AGENTS.md`、`CLAUDE.md`、`.cursorrules`がシステムプロンプトに注入されます（対話型CLIと同じ検出順序）
- `terminal`、`read_file`、`write_file`、`patch`、`search_files`、`execute_code`はすべて、そのディレクトリを作業ディレクトリとして使用します
- パスは存在する絶対ディレクトリでなければなりません — 相対パスや存在しないディレクトリは作成 / 更新時に拒否されます
- 編集時に`--workdir ""`（またはツール経由で`workdir=""`）を渡すと、これをクリアして以前の動作に戻せます

:::note 分離
各エージェント実行は、その`workdir`をその実行固有のタスクアイデンティティにバインドします。そのためworkdirを持つジョブは、プロセスグローバルなターミナルの状態を変更したり、並行する実行間でパスを漏らしたりすることなく、通常の並列プールを使います。cronの合計の並行数を制限したい場合は`cron.max_parallel_jobs`を設定してください。
:::

## ジョブごとのタイムゾーン

デフォルトでは、ジョブのcron式はプロファイルのタイムゾーン（`config.yaml`の`timezone:`）で解釈されます。ジョブは代わりに独自のタイムゾーンを固定できるため、1つのプロファイルで複数の市場に対応できます。

```bash
hermes cron create "0 9 * * 1-5" --timezone Asia/Hong_Kong "HK market open brief"
hermes cron create "0 9 * * 1-5" --timezone America/New_York "US market open brief"
```

- 式は固定されたタイムゾーンの**実時計**です: `0 9 * * *`はそのタイムゾーンの09:00に発火し、そのタイムゾーンのDSTの切り替えをまたいでも09:00のままです。
- 省略する（または編集時に`--timezone ""`を渡す）と、プロファイルのタイムゾーンを継承します。このフィールドのないジョブは以前とまったく同じように振る舞います。
- オフセットのないワンショットのタイムスタンプ（`2026-06-01T09:00:00`）もジョブのタイムゾーンで解釈されます。独自のオフセットを持つタイムスタンプはすでに特定の瞬間を表しています。
- タイムゾーンを変更すると`next_run_at`が即座に再計算されるため、次の発火は新しいタイムゾーンの実時計で行われます。
- `interval`ジョブは固定の期間を持ち実時計を持たないため、固定は効果がありません。
- ジョブのプロンプトに付く実行時刻の行（`[CURRENT RUN TIME: ...]`）は固定されたタイムゾーンで記述されるため、ニューヨークの09:00のジョブには、プロファイルのローカル時刻ではなく09:00 ESTと伝えられます。`hermes cron list`、`/cron list`、`cronjob(action="list")`は、スケジュールの横に固定されたタイムゾーンを表示します。

### 配布されるプロファイル内の固定ジョブとローカル時刻のジョブ {#pinned-and-local-time-jobs-in-a-shipped-profile}

[プロファイルディストリビューション](../profile-distributions.md)は、1つの`cron/jobs.json`に両方の種類のジョブを含められます。`timezone`を固定したジョブは、すべてのインストール先でそのタイムゾーンの実時計で発火します。固定していないジョブは、各ユーザー自身の`config.yaml`の`timezone:`に従います。ユーザーに自分のタイムゾーンを維持させたい場合は、配布する`config.yaml`に`timezone:`を含めないでください: `hermes profile update`はデフォルトでユーザーの`config.yaml`を保持します。

```json
{
  "jobs": [
    {"id": "premarket0001", "name": "pre-market", "prompt": "US pre-market update before the 09:30 NYSE open.",
     "schedule": "0 9 * * 1-5", "timezone": "America/New_York", "deliver": "origin"},
    {"id": "morningbrf01", "name": "morning-brief", "prompt": "My personal morning brief.",
     "schedule": "0 7 * * *", "deliver": "origin"}
  ]
}
```

このファイルでは、ロンドンのユーザーは14:00（英国が夏時間を終え、米国がまだ終えていない間の週は13:00）に、香港のユーザーは21:00または22:00に、ロサンゼルスのユーザーは06:00にプレマーケットの更新を受け取ります。3人とも、それぞれの現地時刻の07:00にモーニングブリーフを受け取ります。インストールと更新では、`timezone`がIANAのタイムゾーンでない配布ジョブを、そのジョブ名を示して拒否するため、タイプミスが黙って各ユーザーのローカル時刻になることはありません。作成元のプロファイルで`hermes cron create ... --timezone America/New_York`でジョブを書き、生成された`cron/jobs.json`をコミットするか、手で書いてください: `schedule`は`hermes cron create`が受け取るのと同じ文字列でよく、`next_run_at`とランタイムのフィールドはスケジューラが埋めます。更新はIDで照合されるため、配布するすべてのジョブに安定した`id`を与えてください。

## キャッチアップのウィンドウ

見逃したcronの発生は、キャッチアップのウィンドウ内でのみ遅れて実行されます: ジョブの周期の半分で、2分〜2時間にクランプされます。`--grace-minutes`でジョブごとに上書きできます（0〜1440）。

```bash
hermes cron edit market-open --grace-minutes 0    # never catch up: skip a missed occurrence
hermes cron edit market-open --grace-minutes 180  # run up to 3h late
```

`0`はキャッチアップしないことを意味し、`--grace-minutes ""`で計算されたウィンドウに戻ります。これはcron式にのみ適用されます — `once`と`interval`のスケジュールには、キャッチアップすべき見逃した実時計がありません。

## ジョブの編集

ジョブを変更するためだけに、削除して再作成する必要はありません。

:::tip ジョブの参照
下記（および[ライフサイクルアクション](#lifecycle-actions)）の`<job_id>`プレースホルダーには、ジョブの名前（大文字小文字を区別しない）も指定できます — 16進のIDは覚えていないが`morning-digest`は覚えている、という場合に便利です。正確なジョブIDは名前の一致より優先されます。参照がIDでなく、名前が複数のジョブに一致する場合、コマンドは拒否され、区別できるよう候補のIDが表示されます。
:::

### チャット

```bash
/cron edit <job_id> --schedule "every 4h"
/cron edit <job_id> --prompt "Use the revised task"
/cron edit <job_id> --skill blogwatcher --skill maps
/cron edit <job_id> --remove-skill blogwatcher
/cron edit <job_id> --clear-skills
```

### スタンドアロンCLI

```bash
hermes cron edit <job_id> --schedule "every 4h"
hermes cron edit <job_id> --prompt "Use the revised task"
hermes cron edit <job_id> --skill blogwatcher --skill maps
hermes cron edit <job_id> --add-skill maps
hermes cron edit <job_id> --remove-skill blogwatcher
hermes cron edit <job_id> --clear-skills
```

補足:

- `--skill`を繰り返すと、ジョブに紐づいたスキルリストが置き換えられます
- `--add-skill`は既存のリストを置き換えずに追加します
- `--remove-skill`は特定の紐づいたスキルを削除します
- `--clear-skills`は紐づいたスキルをすべて削除します

## ライフサイクルアクション {#lifecycle-actions}

cronジョブには、単なる作成/削除よりも充実したライフサイクルが備わっています。

### チャット

```bash
/cron list
/cron pause <job_id>
/cron resume <job_id>
/cron run <job_id>
/cron remove <job_id>
```

### スタンドアロンCLI

```bash
hermes cron list
hermes cron pause <job_id_or_name>
hermes cron resume <job_id_or_name>
hermes cron run <job_id_or_name>
hermes cron cancel <job_id_or_name>
hermes cron remove <job_id_or_name>
hermes cron edit <job_id_or_name> [...flags]
hermes cron status
hermes cron tick
```

各アクションの動作:

- `pause` — ジョブを残したままスケジューリングを停止する
- `resume` — ジョブを再有効化する。一時停止中に実行予定の枠が来た繰り返しジョブは、その枠を実行予定のまま保持するため、黙って次の発生に飛ぶのではなく、次のtickで1回のキャッチアップ実行を発火します（`cron.catch_up_missed: false`の場合はスキップをログに記録します）。それ以外の場合は、次回の将来の実行が計算されます
- `run` — 次のスケジューラtickでジョブをトリガーする。手動実行は追加の発火です: スケジュールされた実行は引き続き行われ、`repeat`のカウントは消費されないため、`in 30m`のリマインダーをテスト発火しても本来のものは残ります（枠がすでに実行予定になっている場合の実行は、そのスケジュールされた実行そのものです）
- `cancel` — ジョブの**現在の**実行を停止する（[実行中の実行を停止する](#stopping-a-run-in-flight)を参照）
- `remove` — 完全に削除する
- `edit` — スケジュール、プロンプト、配信などを変更する
- `tick` — スケジューラのパスを1回実行して終了する（システムのcrontabやその他の外部
  スケジューラ向け）。**ゲートウェイが実行中である必要があります:** エージェントのジョブはゲートウェイ内で実行され、
  tickがゲートウェイを起動することはありません。ゲートウェイが起動していない場合、エージェントのジョブは理由をログに記録して
  スキップされ（`hermes cron list`に表示されます）、`hermes gateway start`の後の次のtickで発火します。
  そのスケジュールが進められたり、ペナルティを受けたりすることはありません。`no_agent`のスクリプトジョブは、単独のtickからでも実行されます。

**名前による検索。** 変更を伴う動詞（`pause`、`resume`、`run`、`cancel`、`remove`、`edit`）とエージェントの`cronjob_manage`ツールは、16進のIDの代わりにジョブの**名前**（大文字小文字を区別しない）を受け付けるようになりました。エージェントとCLIはどちらも、正確なIDの一致があればそれを優先します。あいまいな名前の一致（同じ名前を共有する複数のジョブ）は、明示的に選べるよう候補IDの完全なリストとともに拒否されます。名前は一意ではないため、このガードは重要です — 2つのジョブが名前を共有している場合に、誤ったジョブを黙って変更してしまうことを防ぎます。

### すべてを一時停止する: `hermes pause`

`hermes pause [--reason ...]`はグローバルな緊急停止です（`hermes resume`で解除）。これが有効な間は、どの入り口から来ても、スケジュールされたcronの発火は開始されません: 組み込みのティッカーはディスパッチをスキップし、マネージドcron（ホスト型スケジューラ）の発火webhookは`Retry-After: 60`とともに`503`を返すため、スケジューラは再開後に発火を再配信します。また[ミスファイアのキャッチアップ](#misfire-catch-up)のスイープは、保留されていたものをすべて強制発火するのではなく、アイドルのままです。すでに実行中の実行が強制終了されることはなく、何も失われません: 実行予定の作業は、`hermes resume`の後の最初のtickまたはスイープでキャッチアップします。明示的な手動実行（`hermes cron run`、ダッシュボードのTriggerボタン）はオペレーターによる上書きであり、一時停止中でも実行されます。

### 実行中の実行を停止する: `hermes cron cancel` {#stopping-a-run-in-flight}

`pause`は将来の発火を抑制するだけです — すでに実行中の実行は、
終了するかタイムアウトに達するまで続きます。実行が詰まった場合（ネットワークI/Oでブロックされたスクリプト、
終わらないエージェントのターン）は、その実行だけを停止します。

```bash
hermes cron cancel <job_id_or_name>
hermes cron cancel <job_id_or_name> --reason "wedged on the staging API"
```

スケジュールには触れません: ジョブは有効なままで、次の発火は予定どおり行われます。
変わるのは現在の実行です。

- **スクリプトジョブ**（`--script`、[no-agentモード](#no-agent-mode-script-only-jobs)を含む）は、
  プロセスツリー全体が終了させられます — スクリプトのプロセスグループに`SIGTERM`を送り、猶予期間の後に
  `SIGKILL`へエスカレートし、バックグラウンドの孫プロセスも含みます。これはスクリプトのタイムアウトがすでに行う
  後始末と同じなので、ジョブの背後で新たに何かが実行されたまま残ることはありません。
- **エージェントジョブ**は、実行中のターンが次のチェックポイントで中断されます。

キャンセルは強制終了ではなく*要求*です: その実行の実行IDに対して記録され、
実行の次のキャンセルチェック（スクリプトなら1秒を大きく下回る）で取り込まれます。その後、実行は
理由付きの`cancelled`行を記録するため、`hermes cron runs <job_id>`には、説明のないタイムアウトや
単なる失敗ではなく、停止した理由が表示されます。キャンセルされた実行は失敗の通知を送らず、
ジョブの失敗の連続回数にも数えられません。同じ停止は`POST /api/cron/jobs/{id}/cancel`、
エージェントの`cronjob_manage`のアクション`cancel`、そしてDesktopでも利用できます: 実行中のジョブは
ヘッダーに**Stop**を表示します（実行が`cancelled`行を記録するまでは**Stopping…**と表示され、
その後*Run cancelled*のトーストで確認されます）。

**ジョブを削除すると、その実行中の実行も停止します。** `hermes cron remove`（およびダッシュボード/Desktopでの削除や
エージェントの`remove`アクション）は、実行中の実行をキャンセルし、理由
「job removed while running」とともに`cancelled`として記録します。誰も保持しない結果のためにトークンを
消費し続けさせることはありません。

何も実行されていないジョブをキャンセルするのは、その旨を伝える安全な何もしない操作であり、
実行がすでに終わった後に届いたキャンセルは何も変えません。キャンセルは、実行がすでに行った
副作用を元に戻すことはできません — 実行を停止するのであって、ロールバックするのではありません。

### 一時停止状態でジョブを作成する（安全なカナリア）

作成してから一時停止するというスケジューリングの競合なしに、カナリアを作成します。

```bash
hermes cron create "every 1h" "Post the digest" --paused --paused-reason "Awaiting review"
hermes cron resume <job_id>
```

`--paused`は、最初のロックされた書き込みで`enabled: false`、`state: paused`、`next_run_at: null`、
一時停止のタイムスタンプ、監査可能な理由を保存し、トリガーは登録しません。
理由を省略すると「Created paused; awaiting operator approval.」が保存されます。
`--paused`を省略すると、通常の有効な状態での作成になります。`--paused-reason`には
`--paused`が必要です。無効な値は永続化の前に拒否されます。

同じ`paused`のブール値と任意の`paused_reason`文字列は、
`cron.jobs.create_job`、cron管理ツールの`create`アクション、ゲートウェイの
`POST /api/jobs`、ダッシュボードの`POST /api/cron/jobs`でも受け付けられます。再開すると、次回の
将来の実行がスケジュールされます。一時停止が防ぐのは自動的な発火であり、オペレーターによる上書きではありません: 既存の
明示的な**Run now** / 強制実行の挙動は引き続き利用でき、ジョブを再開して実行できます。
これは、ジョブを実行できるオペレーターに対するセキュリティ境界ではありません。

## エージェントが管理するスケジューリング（cronジョブを管理するcronジョブ）

デフォルトでは、スケジューラ*によって*起動されたエージェントは`cronjob_manage`ツールを使えません —
スケジュールされたジョブが他のジョブを作成、編集、削除することはできません。`config.yaml`で
オプトインします。

```yaml
cron:
  allow_agent_scheduling: true   # default: false
```

有効にすると、スケジュールされたエージェントは、どのチャットセッションとも同じようにcronテーブルを
管理できます: スケジュールされた作業の中からフォローアップのワンショットをスケジュールしたり、自身の
頻度を調整したり、テーブル全体を照合する「cron司書」ジョブ（一覧を取得し、必要に応じて
更新/削除/作成）を実行したりできます。次の性質がこれを健全に保ちます。

- **1つのフラットな、ユーザーが所有するテーブル。** cron実行から作成されたジョブは、
  他のすべてのジョブと同じ`jobs.json`に特別な所有権なしで入ります — 自分で作成した場合と
  まったく同じように、一覧表示、編集、削除できます。
- **宙に浮いた配信なし。** cron実行は一時的なので、その中からの`deliver: origin`は
  **作成時に**、作成元のジョブ自身の具体的なターゲット（`platform:chat_id[:thread_id]`、
  または作成元のジョブがどこにも配信しない場合は`local`）に解決されます。スケジュールされたエージェントが
  作成したジョブが、もう存在しないセッションに出力を向けることは決してありません。明示的なターゲット
  （`local`、`all`、`telegram:<chat_id>`）はそのまま尊重されます。
- **ジョブは自身を削除しても報告できます。** 「Xを見張り、一度だけ知らせて、その後は止める」パターン —
  実行の中で`cronjob(action="remove", job_id=<its own id>)`を呼び出してから回答する
  繰り返しジョブ — は、その最終応答を配信し、実行を`completed`として記録します。その後ジョブの記録と
  その`cron/output/<job_id>/`ディレクトリはなくなり、最後の実行はそこには書き込まれません。
  実行の*外*から記録を削除した場合（別のプロセス、またはIDを再利用する置き換えのジョブ）は、
  従来どおり古い実行の出力が破棄されます。

実行のたびに新しいジョブを作るプロンプトよりも、既存のジョブを更新するプロンプト（まず一覧を取得し、IDで更新する）を
優先してください。

## 仕組み

**cronの実行はゲートウェイデーモンが処理します。** ゲートウェイは60秒ごとにスケジューラをtickさせ、実行予定のジョブを分離されたエージェントセッションで実行します。

```bash
hermes gateway install     # Install as a user service
sudo hermes gateway install --system   # Linux: boot-time system service for servers
hermes gateway             # Or run in foreground

hermes cron list
hermes cron status
```

`hermes cron status`は、スケジューラが生きているかどうか（ゲートウェイのプロセス、ティッカーのハートビート、最後に成功したtick）と、アクティブなジョブ全体で最も早くスケジュールされている実行を報告します。ジョブが異なるUTCオフセットを保存していても、実際の瞬間の順に並べられます。すでに15分以上過去になっている`next_run_at`が、今後の「Next run」として表示されることはありません: `cron status`は`⚠ Next run <time> is OVERDUE — passed 7h ago but the job has not fired`と表示し、`cron list`とチャット内の`/cron list`はその行に`Overdue:`のラベルを付け、ダッシュボードとDesktopのcronパネル（BotのRoutinesカードを含む）は`Overdue since`を表示します。またスケジューラがtickを止めている場合、（ゲートウェイがダウンしているときの）`status`とダッシュボードのCronページも、最後にtickした時刻を示します。これはスケジューラがtickを止めたことの兆候です — 次のtickで期限切れのジョブが拾われるようにゲートウェイを再起動する（`hermes gateway restart`）か、`hermes cron run <id>`ですぐに実行してください。

デフォルトプロファイルのマルチプレクサーが提供する名前付きプロファイルの場合、`hermes cron status`はそのスケジューラのホストを示し、名前付きプロファイル自身のハートビートの健全性を報告します。ハートビートが欠けているか古い場合は、`hermes --profile default gateway restart`を案内します。`cron list`と`cron create`も、そのハートビートが欠けているか古い場合に警告します。`cron status`はさらに、最後に成功したtickを確認し、tickのエラーを報告します。

#### cronストアに書き込めない（ディスクフル、読み取り専用マウント、権限）

cronストア（`~/.hermes/cron/`、またはプロファイル自身の`cron/`ディレクトリ）に書き込めない場合、たとえばディスクがいっぱい（`ENOSPC`）、マウントが読み取り専用（`EROFS`）、または権限が誤っている（`EACCES`）場合、スケジューラは実行を記録できないジョブを実行しません。これにより、回復後の二重発火を防ぎます。ティッカーは動き続けます。失敗が確定した書き込みの試行をやめ、約1分ごとにストアを再確認します。障害は4か所に表れます。

- `hermes cron status`はストア自体をプローブし、`⚠ Cron store is NOT writable — scheduled jobs are being skipped`を先頭に表示します。その下には、ストアのパス、OSのエラー、最後に成功した書き込み、発火していない実行予定の数が表示されます。`hermes cron list`は1行のバナーを表示します。
- `hermes doctor`は、ストアに書き込めない場合、またはそのファイルシステムの空きが100 MB未満の場合に警告します。
- ゲートウェイは、ストアが書き込めなくなったときに1回、1時間書き込み可能な状態が続いたときに1回、プロファイルのホームチャンネルに通知を投稿します（その1時間以内に再び失敗したストアはそれ以上何も投稿しないため、最後の通知は常にその状態と一致します）。どちらも`display.suppress_warning_notifications`を尊重し、プロファイルの`display.language`を使います。
- 監視では`hermes.cron.store.writable`（このゲートウェイが提供するいずれかのプロファイルのストアが書き込めない間は0、それ以外は1）と`hermes.cron.store.skipped_runs`（それらのストアの合計）がエクスポートされます。

修正するには、ストアがあるファイルシステムのディスク容量を空けるか、読み書き可能で再マウントするか、ゲートウェイのユーザーが書き込めるようにストアディレクトリの所有権と権限を修正してください。何かを再起動する必要はありません。書き込みが可能になった次のtickで、実行予定のまま残っていた各ジョブは、見逃したtickごとに1回ではなく、通常の[ミスファイアのキャッチアップ](#misfire-catch-up)のルールに従って**1回**発火します。障害中に実行予定になったワンショットは、期限切れになるのではなく1回発火します（ストアが書き込めない間にゲートウェイが再起動した場合を除く）。

### ゲートウェイスケジューラの動作

各tickでHermesは次のことを行います。

1. `~/.hermes/cron/jobs.json`からジョブをロードする
2. `next_run_at`を現在時刻と照合する
3. 実行予定の各ジョブに対して新規の`AIAgent`セッションを開始する
4. オプションで、その新規セッションに1つ以上の紐づいたスキルを注入する
5. プロンプトを完了まで実行する
6. 最終応答を配信する
7. 実行メタデータと次回スケジュール時刻を更新する

`~/.hermes/cron/.tick.lock`のファイルロックにより、重複するスケジューラtickが同じジョブバッチを二重実行することを防ぎます。

### systemd下での再起動に強いワーカー

ゲートウェイがsystemdのサービスとして動作している場合、実行予定の各ジョブは一時的なユーザースコープ（`systemd-run --user --scope`）で起動される外部のワーカープロセスに引き渡されるため、ジョブの途中でゲートウェイを再起動してもジョブは強制終了されません。そのスコープを作成するにはユーザーのsystemdセッションが必要です。それを持たないホスト（コンテナ、最小構成のLXC、lingerのないサービスユーザー）では提供できません。

デフォルトでは、cronはその場合**縮退**します: ジョブは同じ実行の引き渡しを伴う別の外部プロセスとして引き続き実行されますが、cgroupによる分離がないため、ジョブの間にゲートウェイが再起動するとジョブは強制終了されます（実行台帳がそれを記録します）。ゲートウェイのプロセスごとに1回警告がログに出力されます。代わりにフェイルクローズする — ジョブをスキップしてジョブの行にエラーを記録する — には、次を設定します。

```yaml
cron:
  require_restart_safe_scope: true
```

恒久的な修正は、ゲートウェイのユーザーにユーザーセッションを用意することです: `sudo loginctl enable-linger <gateway-user>`（システムレベルのインストールでは、ユニットに`XDG_RUNTIME_DIR` / `DBUS_SESSION_BUS_ADDRESS`も）を実行し、ゲートウェイを再起動します。Kanbanのワーカーは、このキーにかかわらず、管理されたゲートウェイのもとでは常にスコープを必要とします: ホストがスコープを作れない起動は、インフラストラクチャの失敗としてカードに記録されて後でリトライされ、カードの責任にされることはありません（[Kanbanのドキュメント](kanban.md#workers-and-systemd-cgroups)を参照）。

ワーカーは、ゲートウェイ自身のインタープリターで`python -m cron.scheduler`を実行するもので、`PYTHONPATH`にゲートウェイのチェックアウト（およびゲートウェイ自体が起動時に持っていたエントリ）が固定されているため、venvのeditableインストールのマッピング、ユニットの`WorkingDirectory`、ホストの`PYTHONSAFEPATH`に関係なく、ゲートウェイが実行しているのと同じHermesのツリーをインポートします。引き渡しの確認応答の前に死んだワーカーは、自身のstderrの末尾をジョブの最後のエラーと実行台帳に記録するため、単なる終了コードではなく、失敗したインポート（または原因となったもの）が示されます。

### 実行履歴 {#execution-history}

Hermesは、エグゼキューターやプロバイダーへのディスパッチの前に、要求された各cronの試行を
プロファイルローカルの`~/.hermes/cron/executions.db`に記録します。試行は
`claimed`、`running`、そして1つの不変の終端状態
（`completed`、`failed`、`unknown`）を経ます。再起動後 — および手動の
`hermes cron run` / `/cron run`の前ごとに。そのためスケジューラが動いていない単発の呼び出しでも
台帳が修復されます — Hermesが放棄された試行を`unknown`とするのは、
元のPIDとプロセス開始のフィンガープリントによって所有者が
いなくなったことが証明された場合、または生きている所有者が導出された
陳腐化の上限（`max(3 × HERMES_CRON_TIMEOUT, script timeout, 2 h)`）より長く**沈黙**している場合だけです: 実行の
モニターは、エージェントがまだツールを呼び出しているかストリーミングしている間、試行に`progress_at`を刻むため、
正常な数時間のジョブが実行途中で回収されることはありません。一方で
ロックでデッドロックしたワーカーは刻印を止め、上限を過ぎると解放されます。
不明な試行は監査記録であり、自動的に再実行されることはありません。

最近の試行は`hermes cron runs [job-id] --limit 20`（別名:
`history`）で調べられます。終端の履歴は上限付きで、アクティブな試行は決して刈り取られません。
台帳はクイックバックアップに含まれます。

スケジュールされた試行は、要求された時刻とは別に、その正確なスケジュール上の瞬間も記録します。
古い`jobs.json`のスナップショットが、保持された台帳で完了と記録されている発生を
再び有効にした場合、Hermesはそのリプレイをスキップし、
繰り返しジョブを再アンカーします。これは、スナップショットがディスパッチのスタンプより
古い場合や、元の実行が遅れて開始した場合でも機能します。明示的な手動実行は、
スケジュールされた発生のアイデンティティを消費しません。

これは副作用の厳密に1回の保証ではありません: アイデンティティのないレガシーの行、
刈り取られた履歴、利用できない台帳、中断された試行は、完了を
証明できません。台帳自体を古いバックアップに復元すると、その証拠も
失われます。外部の発火コールバックが識別するのは現在受け付けられているストアの
要求であり、コールバックに含まれない上流のスケジュール枠ではありません。

### 失敗が続いたときのレビューの促し

各ジョブは`failure_streak` — 連続して失敗した実行の数 — を追跡します（配信の
失敗は数えません）。エージェントに到達する前に失敗した実行 —
中途半端に適用された更新の後の不正なインポート、構築できないプロバイダークライアント —
も、エージェント自身が失敗した場合と同じように数えられ、アラートが出ます。
*繰り返し*ジョブの連続回数がしきい値に達すると、チャットに配信される失敗メッセージに
レビューの促しが加わり、ジョブがN回連続で失敗したことを伝え、
修正、一時停止（`hermes cron pause <job>`）、または削除を提案します。
成功した実行があれば連続回数はリセットされ、`hermes cron list`は失敗しているジョブの最後の実行とともに
連続回数を表示します。ワンショットのジョブが促しを出すことはありません。

```yaml
cron:
  failure_nudge_threshold: 3   # default; 0 disables the nudge
```

### モデルに到達できなかったときの自動再実行

モデル呼び出しが1回も行われる前に、一時的なネットワークやDNSのエラーで実行が失敗した
繰り返しジョブ — 典型的なのは、コンピューターがスリープから復帰した直後で、VPNやWi-Fiがまだ再接続中の
発火です — が、丸1周期を休むことはありません。スケジューラは
**5分、15分、30分**後に自動的に再実行し（Claude Coworkのスケジュールタスクの再実行に着想を得たもの）、その後は
通常のスケジュールに戻ります。API呼び出しはゼロだったため、再実行は
費用中立であり、副作用を重複させることもありません。再実行はジョブの`repeat`の制限にも
数えられません: 再実行される発生はすでに1回数えられているためです。

再実行が保留中の間は、途中の失敗通知は抑制されます — 再実行が成功すれば
本当の結果を受け取り、段階が尽きれば通常の失敗アラートを受け取ります。モデルに到達した
実行（成功でも失敗でも）は段階をリセットします。ワンショットのジョブは除外されます: そのディスパッチの計上は
最大回数方式であり、消費されたディスパッチが復活することはありません。リトライは、スケジュール自身の
次の発生の方が早い場合、それを越えて発火することはありません。

```yaml
cron:
  retry_unreachable: false   # default true; disables the automatic re-runs
```

### プロバイダーの利用ウィンドウが閉じている間ジョブを保留する

逆のケース: プロバイダーがどれだけ閉じたままでいるかを正確に伝えてくる場合です。
スケジューラがサブスクリプション型のプロバイダー（現在はOpenAI Codexの
利用プローブ）を解決し、プロバイダーが`retry after <N>s`のヒント（多くの場合何時間も）とともに
利用上限に達したと報告し、かつフォールバックチェーン全体が
利用できない場合、1時間未満の間隔のジョブをそのウィンドウ内で再発火させても、tickのたびに
確実に同じように失敗し — 毎回アラートが出ます。実行中にモデルAPIが返す429は
このようには保留されず、通常の頻度でリトライされます。

代わりに、スケジューラは**ジョブを駐機させます**: 1回の失敗アラートが、ウィンドウが
閉じていてジョブが保留されていることを伝えます。プロバイダーが、**間隔の広い**cronジョブの次の自然な発生より
十分前（少なくともスケジュール周期の半分前）に再開する場合、ブロックされたスケジュール上の発生は、その回復の
境界で1回リトライされます。2回目のクォータ失敗は自然なスケジュールを待ちます。間隔の密な
スケジュール、手動実行、intervalジョブは、自然な次の実行を維持します。
それ以外の場合、見逃した発生はまとめられ、
`next_run_at`はウィンドウ後の最初のスケジュール上の発生に移ります。駐機した
瞬間は`quota_hold_until`として保存され、それより前に発火やアラートが行われることはありません。
モデルに到達した実行は保留を解除します。ワンショットのジョブは保留されません。

### 失敗のインシデント: アラートは1回、クールダウンでリマインド、確認応答

*同じ*エラーで失敗し続ける繰り返しジョブは、実行のたびではなく**1回だけ**
アラートを出します。各失敗は永続的な**インシデント**として記録され、ジョブと
エラーテキストの正規化されたシグネチャ（大文字小文字、空白、`idle for 603s`のような
計測された時間は無視されます）をキーとし、実行履歴と同じプロファイルごとの
台帳データベースに保存されます。あるシグネチャの最初の失敗は
常に配信され、その後の繰り返しはインシデントが`alerted`である間は保留されます
（実行は引き続き記録されます — `hermes cron runs`と失敗の連続回数はそれを見ており、
保留されるのは通知だけです）。

```yaml
cron:
  failure_repeat_alert_hours: 6   # still broken after this long → one reminder ping,
                                  # then silent again; 0 = alert on every failing run
```

状況を変えるものは即座にアラートを出します: *異なる*エラーは
独自のインシデントを作ってすぐに通知し、成功した実行はシグネチャを再び有効にするため、
正常な実行の後の同じエラーは再びアラートを出します。インシデントの台帳を
読めない場合は、握りつぶすのではなく通知が配信されます。

```bash
hermes cron incidents                 # list incidents (newest activity first)
hermes cron incidents --state alerted # filter: detected | alerted | resolved | closed
hermes cron incidents ack <id>        # acknowledge — silence this signature for good
```

インシデントを確認応答すると、リマインダーを含め、その正確なシグネチャの失敗通知だけが
沈黙します。それ以外は何も変わりません: 実行履歴は引き続き
すべての失敗を記録し、失敗の連続回数は数え続け、ジョブが*異なる*エラーで
失敗し始めた瞬間に新しいインシデントが作られ、再びアラートが
出ます。

成功した実行は、そのジョブのすべての未解決のインシデントを`resolved`にするため、
一覧はジョブがこれまでに経験したすべての失敗ではなく、現在の健全性を反映します。
その後ジョブが*同じ*エラーで失敗すると、解決済みのインシデントは
`detected`として再び開かれ、再びアラートが出ます。確認応答された（`closed`）インシデントは
例外です: 成功してもそのままで、繰り返しても沈黙したままです。

インシデントのライフサイクル: `detected`（失敗が記録された）→ `alerted`（少なくとも1回の
失敗通知が配信に到達した。`alerted_at`は最新のもので、リマインダーの
クールダウンを開始する）→ `resolved`（その後ジョブが正常に実行された。繰り返すと再び開く）
または`closed`（確認応答された。そのシグネチャについては終端）。保存されるエラー
テキストは、書き込まれる前にシークレットが秘匿化され、切り詰められます。

### フリートの健全性チェック: `hermes cron doctor`

`hermes cron doctor`は、すべてのアクティブなジョブに対する読み取り専用の健全性チェックです。グループ化されたジョブごとの問題を表示し、過去の遅延やキャッチアップのディスパッチを含め、何らかの検出事項が残っている間は`1`で終了します（検出事項がなければ`0`）。

キャッチアップが成功しても遅延の警告はクリアされません。クリアされるのは次の定刻のディスパッチです。そのため`hermes cron doctor || alert`のようなウォッチドッグは、キャッチアップが成功しても、ホストが復帰した後のスケジュール間隔いっぱいアラートを出し続けることがあります。

```bash
hermes cron doctor
```

アクティブなジョブごとのチェック項目:

- 最後の実行が失敗した（`last_status`がokでない。記録されたエラー付き）
- 最後の配信が失敗した（出力は生成されたが、あなたに届かなかった）
- 最後のディスパッチが遅れた、または見逃したスケジュールの後にキャッチアップした（`last_dispatch`）。この警告は次の定刻の発火でクリアされます
- スケジュールされた発火がランナーに到達できなかった（`last_fire_error`）。記録されたタイムスタンプと短縮された理由付き。この警告は実行が成功するとクリアされます
- `next_run_at`が欠けている、または15分のティッカーの
  猶予ウィンドウを越えて過去に留まっている — 「ジョブが黙って発火していない」というシグナル（スケジューラの停止、
  ゲートウェイのダウン、または詰まった発火の要求）
- スクリプトが存在しない、ファイルではない、または`HERMES_HOME/scripts`の外に解決される
- スクリプトのない`no_agent`ジョブ
- 設定された`workdir`がもう存在しない

doctorはジョブや状態を変更することは決してなく、報告するだけです。フラグが立ったジョブを掘り下げるときは、
`hermes cron incidents`（永続的な失敗記録）と`hermes cron runs`
（試行の台帳）と組み合わせてください。

配信される出力は、すべての経路で出ていく際にシークレットが秘匿化されます: プラットフォームのメッセージ、
セッションのミラー（ペイロードと、その周りに挿入されるジョブ名）、`bot-chat`のターンです。認証情報の
形（ベンダーのプレフィックス付きAPIキー、トークン、`KEY=value`の代入）は、
`security.redact_secrets: false`であってもマスクされます — その設定が管理するのはあなた自身のログであり、マシンから
出ていくものではありません — また秘匿化処理が失敗した場合は、スキャンせずに送るのではなくペイロードが置き換えられます。
認証情報の名前を持つURLのクエリパラメータは除去されません（マジックリンクや署名付きURLは
正当なcronの出力です）。また、識別できる形を持たないユーザーが選んだシークレットは検出されません。
`cron/output/<job_id>/`配下の実行ドキュメントには、エージェントの応答が書かれたとおりに保存されます。

### 配信の失敗は別のステータス

実行と配信は別々に追跡されます。エージェントの実行が成功しても、
出力がターゲットに届かなかった場合（プラットフォームの5xx、レート制限、古いセッション、
アダプターが送信の確かな証拠を返さなかった）、ジョブは
`last_status: delivery_failed`を記録し — 単なる`ok`には決してなりません — 理由は
`last_delivery_error`に入ります。`hermes cron list`はそれを黄色で
`delivery_failed: <reason>`として表示し、`hermes cron doctor`は配信の
問題として報告し、手動の`cronjob run`は配信エラーとともに`success: false`を報告します。
配信の失敗はジョブの`failure_streak`には数えられません
（エージェントは自分の仕事をしたため）。次の完全に成功した実行でステータスは
`ok`に戻ります。

### Bot Chatへの配信（`bot-chat`）

`bot-chat`は、出力を**プロファイルの正規の「Bot Chat」セッションに実際のメッセージとして**配信します。受け手がチャンネルを読む人間である他のすべてのターゲットとは異なり、ここでの受け手はボット自身です: 出力を受信メッセージとして受け取り、対応が必要なことに対応し、そのチャットで応答します。スケジュールされた出力を単に投稿するのではなく*処理*させたい場合に使ってください。

- `bot-chat`（単独）は、ジョブ自身のプロファイルを対象にします。
- `bot-chat:<profile>`は、**同じマシン上**の別のプロファイルを対象にします。名前はジョブの作成時に`hermes profile list`と照合されます。他のゲートウェイやマシン上のプロファイルが対象になることは決してないため、マシン間で同名のプロファイルがあってもあいまいになりません。
- 各配信には、対象のボットのエージェントのターンが1回丸ごとかかります — スケジュールの頻度に注意してください。
- 他のターゲットと組み合わせられますが（`bot-chat,telegram`）、`all`に含まれることは決してありません。
- 正規のチャットがメールボックス対応のDesktop/TUIバックエンドで開かれている場合、ボットがアイドルでもビジーでも、配信は**即座に永続的にキューに入ります**。受信したターンを実行するのはその稼働中の所有者だけで、cronが競合するCLIの書き手を起動することはありません。まだBot Chatを持たないプロファイルには、最初の配信時に作成されます。対象のプロファイルのゲートウェイが実行されていない場合、実行は理由付きで`delivery_failed`として記録され（出力は`hermes cron runs`に残り、自動的に再配信されることはありません）、cronが独自のBot Chatのターンを開始することは決してありません。
- **キューに入ったことは完了ではありません。** cronは受領IDと`queued`/`claimed`のステータスを`last_delivery_queued`に記録し、配信結果は`queued`（配信済みでも失敗でもない）になります。成功したジョブは`delivery_queued`を表示します。他のターゲットでの本当のエラーは、引き続き配信の失敗として優先されます。ボットは後で完了するかもしれません。対象のプロファイルの`runtime/bot_live_delivery/<receipt-id>.json`にある永続的な受領記録が、ターン自体についての正となる情報です。エージェントジョブの場合、送信はゲートウェイの配信キューに乗り、ゲートウェイがそれをボットに引き渡すと、実行は`ok`（受け付けられたが、回答されたわけではない）に落ち着き、`last_delivery_queued`は受領記録を保持します。引き渡しが拒否された場合は`delivery_failed`に落ち着きます。スクリプトのみ（`no_agent`）のBot Chatへの配信は`delivery_queued`のままです: ボットのターンが後で完了しても、cronがその履歴を書き換えることはありません。
- 同じ実行を再確認すると、所有者がいなくなっていても、既存の受領記録を調べます。受け付けの後に別の書き手にフォールバックすることは決してありません。`failed`、`cancelled`、`ambiguous`の受領記録は自動的にはリプレイされません。意図的に新しい作業を始める前に、チャットと受領記録を確認してください。新しいcronの実行ごとに、異なる配信IDが割り当てられます。

### ルーティングの意図（`all`）

`all`を使うと、設定済みのすべてのメッセージングチャンネルに対して、名前で列挙することなく1つのcronジョブを送れます。これは**発火時に解決される**ため、Telegramを接続する前に作成されたジョブでも、`TELEGRAM_HOME_CHANNEL`を設定した後の次のtickでTelegramを拾います。

セマンティクス: `all`はホームチャンネルが設定されたすべてのプラットフォームに展開されます。0個でも問題ありません。その場合、ジョブは単に配信ターゲットを生成せず、上流で配信失敗として記録されます。

`all`は明示的なターゲットと組み合わせられます。`origin,all`は発信元のチャット*に加えて*接続済みの他のすべてのホームチャンネルに配信し、`(platform, chat_id, thread_id)`で重複を排除します。

### Telegramのcronトピック（`TELEGRAM_CRON_THREAD_ID`）

Telegramのトピックモードが有効な場合、ルートのDMはシステムのロビーとして予約されます — そこに送られた返信はロビーのリマインダーで退けられ、`reply_to_message_id`は破棄されるため、メインチャットに届いたcronのメッセージに返信することはできません。

代わりに、cronを専用のフォーラムトピックに向けます。

1. TelegramでボットとのDMを開き、たとえば`Cron`という名前のトピックを作成します。トピックのヘッダーを長押し → **Copy link**。末尾の整数がトピックの`message_thread_id`です。
2. `.env`に`TELEGRAM_CRON_THREAD_ID=<that id>`を設定します。

これはcronの配信にのみ適用されます。`TELEGRAM_HOME_CHANNEL_THREAD_ID`（再起動通知など、他の場所で使われるもの）は変わりません。明示的な`deliver="telegram:chat_id:thread_id"`ターゲットは、引き続き環境変数より優先されます。cronのメッセージへの返信は既存のトピックセッションに届くようになったため、直接対応できます。

### 応答のラッピング

デフォルトでは、配信されるcron出力は、受信者がスケジュールタスク由来であると分かるように、ヘッダーとフッターでラップされます。

```
Cronjob Response: Morning feeds
(job_id: <id>)
-------------

<agent output here>

To stop or manage this job, send me a new message (e.g. "stop reminder Morning feeds").
```

ラップされた配信に返信すると、エージェントは引用されたレポートを、参照用の過去の
スケジュール配信としてマークされた状態で受け取るため、返信で求めない限り、その行動項目が
新しいリクエストとして扱われることはありません。複数のメッセージに分割された長い配信は、最初の部分だけでなく
すべての部分にマークが付きます。ラップされない配信（`wrap_response: false`）にはマークがなく、
他のメッセージと同じように引用されます。

ラッパーなしで生のエージェント出力を配信するには、`cron.wrap_response`を`false`に設定します。

```yaml
# ~/.hermes/config.yaml
cron:
  wrap_response: false
```

### プッシュ通知（`cron.delivery.notify`）

cronの出力は進捗メッセージではなく*最終的な*配信であるため、デフォルトでは
プラットフォームの通知フラグを立てて送信されます — Telegramでは、アダプターの通知モードが`important`
（そうでなければ`disable_notification=true`で送信し、ユーザーは
沈黙したブリーフを「配信されなかった」と報告します）の場合でも、ブリーフがプッシュを発生させることを意味します。沈黙した配信に戻すには:

```yaml
# ~/.hermes/config.yaml
cron:
  delivery:
    notify: false   # default: true
```

このフラグはテキストの送信とメディアの添付の両方に適用されるため、実行が一方では
プッシュし、もう一方では沈黙することはありません。

### 配信の確認と`UNVERIFIED`状態

稼働中のアダプターによる配信が配信済みとしてログに記録されるのは、アダプターからの
確かな証拠がある場合だけです: フィルタによる破棄（`delivered: false`）ではない明示的な`success`と、
`message_id`または`raw_response`です。`success`を持つものの、どちらの証拠もない結果 —
Slack、Matrix、Mattermostのアダプターが返す形 — も引き続き受け付けられますが（失敗の証拠では
ないため）、その実行はジョブに`last_delivery_unverified`として記録され、
`hermes cron list`に表示されます:

```
⚠ Delivery UNVERIFIED: adapter acked slack:C0123456 without message_id/raw_response
```

また`hermes cron doctor`では`last delivery unverified (...)`として表示されます。このマーカーは、
証拠付きで配信した次の実行でクリアされます。空のペイロード（テキストも
メディアもない）がアダプターに渡されることは決してありません。それはフェイルクローズし、配信済みとしてログに記録されるのではなく、
`last_delivery_error`で報告されます。

### 継続可能なジョブ（cronの配信に返信する）

デフォルトでは、cronの配信は送りっぱなしです: メッセージは送信されますが、
チャットの会話履歴には残らないため、それに返信してもエージェントには
自分が何を言ったかの記録がありません。ジョブを**継続可能**にすると、配信されたブリーフは
返信できる会話になります — エージェントは「Task #2とは何ですか？」と尋ねる代わりに、
ブリーフをコンテキストに持ちます。

オプトインで、**デフォルトはオフ**です。設定でグローバルに有効にするか、`cronjob`
ツールの`attach_to_session`でジョブごとに有効にします（そのジョブについてはグローバル設定を上書きします）。

```yaml
# ~/.hermes/config.yaml
cron:
  mirror_delivery: false   # set true to make cron deliveries continuable
```

挙動は**スレッド優先**で、ジョブ自身の会話にスコープされます。

- **スレッド対応のプラットフォーム**（Telegramのトピック、Discord/Slack/Matrixのスレッド）: 各
  配信は専用のスレッドを開き、ブリーフはそのスレッドのセッションにシードされるため、
  スレッド内での返信は完全なコンテキストで継続します。繰り返し
  ジョブ（例: 毎日のブリーフ）は実行ごとに新しいスレッドを開き、各配信の
  フォローアップの議論を分離します。
- **DMのみのプラットフォーム**（WhatsApp、Signal、SMS）: スレッドが存在しないため、ブリーフは
  代わりに対象のDMセッション（発信元のDM、またはフォールバックや単独プラットフォーム指定のジョブではホームのDM）に
  ミラーされます — DM自体が継続のサーフェスです。

触れられるのはジョブの**自身の会話**だけです。

- ジョブが作成された**発信元のチャット**
- `deliver: origin`が発信元を捉えなかった場合（スクリプトで作成されたジョブ、または配信を
  受け取れないリクエスト/レスポンス型の`api_server`プラットフォーム上のセッションから作成されたジョブ）の
  **ホームチャンネルへのフォールバック** —
  ユーザーの主要な会話が発信元の代わりになります
- ジョブの**単一の明示的な`platform:chat`ターゲット**。ただしジョブ自体が
  `attach_to_session: true`でオプトインした場合に限ります — ジョブの作成者がそのターゲットを
  会話であると宣言します。グローバルの`mirror_delivery`フラグだけで、
  明示的に宛先指定されたチャットが継続可能になることは決してありません。

ブロードキャストの展開（`all`）が継続可能になることは決してありません。ユーザーが書いた単独の
プラットフォーム名（`deliver: slack`）は、そのプラットフォームのホームチャンネルを意図的に
宛先とし、上記のホームチャンネルへのフォールバックと同じルールに従います。
アップグレード後、`cron.mirror_delivery: true`の既存の`deliver: <platform>`ジョブは、
スレッド対応のプラットフォームで実行ごとに新しいスレッドを開くことがあります。この実行ごとのスレッドの挙動を
オプトアウトするには、ジョブで`attach_to_session: false`を設定してください。

ミラーはラベル付きのユーザーターン（`[Cron delivery: <task name>]`）として書き込まれるため、
すべてのモデルプロバイダーにわたって会話履歴の交互性が安全に保たれます。

#### フラットなチャンネル内での継続（Slack） {#flat-in-channel-continuation-slack}

上記のスレッド優先の挙動は、配信のたびに専用のスレッドを作ります。
継続可能なジョブを**チャンネルのタイムラインにフラットに** — スレッドなしで — 届けたい場合は、
Slackの**継続可能なサーフェス**を`in_channel`に設定します。

```yaml
# ~/.hermes/config.yaml
slack:
  cron_continuable_surface: in_channel   # default: thread
  reply_in_thread: false                 # required pairing (see below)
  require_mention: false                 # so a plain reply continues the job
```

`in_channel`モードでは、ブリーフは通常のトップレベルのチャンネル
メッセージとして配信され（スレッドは開かれません）、あなたの返信は
チャンネルの共有セッションを通じてジョブを継続します。3つの設定が連携します。

- **`cron_continuable_surface: in_channel`** — 配信時のスレッド作成をスキップします。
- **`reply_in_thread: false`**（必須） — ボットがあなたの返信にチャンネル内で*フラットに*
  回答し、ブリーフがシードされたのと同じチャンネル全体のセッションにそれを結び付けるようにします。
  これがないと継続は引き続き機能しますが、スレッド内に届きます（安全にスレッド形式の継続に
  フォールバックし、返信が破棄されることはありません — ゲートウェイは起動時に警告をログに出力するため、
  不一致に気づけます）。
- **`require_mention: false`**（またはチャンネルを`free_response_channels`に追加）
  — 通常のメッセージで返信できるようにします。そうしないと、ボットは返信のたびに
  `@`メンションしたときしか起きません。

継続は**チャンネル全体の**セッションなので、共有されます: チャンネル内の
他の会話 — および2つ目の継続可能なチャンネル内ジョブ — も同じ
進行中の会話に加わります。これは「チャンネルにフラットに」に本質的なもので、
`reply_in_thread: false`のユーザーがすでに受け入れているのと同じトレードオフです。各配信のフォローアップを
分離したい場合は、デフォルトの`thread`サーフェスを使ってください。

これは現在Slackの機能です。他のプラットフォームはキーを受け付けますが、`thread`サーフェスに
フォールバックします（継続の仕組みが異なるため）。選択は
プラットフォームごとで、各プラットフォームの設定の下で行います。これはゲートウェイ側の設定フラグです
— `/restart`で反映され、Slackアプリの再インストールは不要です。

:::note 1:1のDM
`cron_continuable_surface`は**チャンネル**の設定です — 1:1のDMには、
スレッドかタイムラインかを選ぶ区別がないため（DMはすでにフラットです）、このキーは
そこでは効果がありません。DMへのcron配信が継続可能かどうかを決めるのは、
別の既存のつまみ**`slack.dm_top_level_threads_as_sessions`**です。

- **`false`** — すべてのトップレベルのDMが1つの進行中のDMセッションを共有するため、継続可能な
  cronのブリーフとあなたの返信は**同じ**セッションに入り、ジョブはコンテキストの中で
  継続します。DMで継続可能なcronを使いたい場合はこちらです。
- **`true`**（デフォルト） — 各トップレベルのDMメッセージがそれぞれ独自のセッションになるため、
  配信されたブリーフへの返信は、ブリーフの記録を持たない*新しい*セッションを開始します。
  このモードでは継続は機能しません（cronでも、他のフラットな配信でも）。

したがって、1:1のDMに配信される継続可能なcronジョブでは、
`slack.dm_top_level_threads_as_sessions: false`を設定してください。`cron_continuable_surface`は
DMには不要です（無視されます）。
:::

### サイレント抑制

エージェントの最終応答に`[SILENT]`が含まれる場合、配信は完全に抑制されます。出力は監査用にローカル（`~/.hermes/cron/output/`内）に保存されますが、配信ターゲットへのメッセージは送信されません。

これは、問題があるときのみ報告すべき監視ジョブに便利です。

```text
Check if nginx is running. If everything is healthy, respond with only [SILENT].
Otherwise, report the issue.
```

失敗したジョブは`[SILENT]`マーカーに関わらず常に配信されます — サイレント化できるのは成功した実行だけです。静かな監視ジョブでは、報告することがないときは`[SILENT]`だけで返信するようエージェントに指示してください。

### 失敗した実行を宣言する

実行を失敗とするのは、ランタイムの失敗（例外、タイムアウト、到達できないモデル）だけです。エージェント自身は
ターンを終えたものの作業が完了しなかった場合 — たとえば委譲したサブエージェントや、実行したスクリプトが失敗した場合 —
エージェントは応答の**最初の行**に単独で`[CRON_FAILURE]`を置き、その後に説明を続けることで、
実行が失敗したと宣言できます。

```text
[CRON_FAILURE]
The nightly export subagent exited with "disk full"; no report was produced.
```

その場合、実行は失敗として記録され（`last_status`、失敗の連続回数、`hermes cron runs`、`hermes cron incidents`の
すべてに反映されます）、失敗の通知は他の失敗した実行と同様に配信されます。完全な応答は、トリアージのために
引き続き`~/.hermes/cron/output/`に保存されます。マーカーは厳格です: レポートの他の場所で`[CRON_FAILURE]`に
言及したり引用したりしても、実行は成功のままです。スクリプトのみ（`no_agent`）のジョブはこれを無視します — スクリプトは
非ゼロの終了コードで失敗を伝えます。

## スクリプトのタイムアウト

実行前スクリプト（`script`パラメータで紐づけたもの）には、デフォルトで3600秒（1時間）のタイムアウトがあります。これが制限するのは**スクリプトだけ**です — スキルベース / LLM駆動のジョブは別の非アクティブ予算で実行され、この値では上限設定されません。スクリプトに別の制限が必要な場合は、変更できます。

```yaml
# ~/.hermes/config.yaml
cron:
  script_timeout_seconds: 1800   # 30 minutes
```

または`HERMES_CRON_SCRIPT_TIMEOUT`環境変数を設定します。解決順序は、環境変数 → config.yaml → デフォルトの3600秒です。

cronは、実行後のセッションとエージェントのリソースのクリーンアップにも上限を設けます。これはLLMのターンが返った後に行われるため、非アクティブのタイムアウトとは別です。デフォルトはクリーンアップ操作ごとに10秒です。ストレージやクライアントのファイナライザーが戻らなくなった場合、スケジューラはエラーをログに出力し、ジョブの実行中ガードを解放して、そのジョブを永遠にスキップするのではなく後の実行がディスパッチされるようにします。

```yaml
# ~/.hermes/config.yaml
cron:
  cleanup_timeout_seconds: 10
```

`cleanup_timeout_seconds: 0`を設定するのは、レガシーの上限なしのクリーンアップの挙動に戻したい場合だけにしてください。

## メディア送信のタイムアウト

cronの配信に、稼働中のゲートウェイアダプターを通じて送信されるメディアの添付（生成されたPDF、TTSの音声、エクスポートされたレポート）が含まれる場合、各添付のアップロードにはタイムアウトの上限があります — デフォルトは300秒です。遅い上り回線での大きなファイルには、さらに必要な場合があります。

```yaml
# ~/.hermes/config.yaml
cron:
  media_send_timeout_seconds: 600   # 10 minutes per attachment
```

または`HERMES_CRON_MEDIA_SEND_TIMEOUT`環境変数を設定します。解決順序は、環境変数 → config.yaml → デフォルトの300秒です。その後、各添付のタイムアウトは、ファイルを128 KB/sでアップロードするのにかかる時間の1.5倍だけ延長されます（最大1時間）。プラットフォームがアップロードに応答するのは、ファイル全体が届いてからだからです。タイムアウトした添付は、ジョブの実行ステータスに部分的な配信失敗として記録されます（テキストは引き続き配信されます）。

## Bot Chatへの配信の完了

`bot-chat`の配信は、対象のプロファイルの稼働中のゲートウェイに受け付けられ、そこで完全なエージェントのターンとして実行されます。ジョブの実行ステータスは、対象の永続的な受領記録が確定するまで受け付けの受領記録（`delivery_outcome=queued`）を記録します。同じ実行のリトライは同じ受領記録を再利用し、再び受け付けることはありません。対象のプロファイルのゲートウェイが実行されていない場合、実行は`delivery_failed`として記録され、ローカルのフォールバックのターンは実行されません。

## スタンドアロン送信のタイムアウト

稼働中のゲートウェイアダプターが配信できない場合（またはゲートウェイが実行されていない場合）、ターゲットにはプラットフォームのスタンドアロンの送信機能で送信されます。その送信には実時間のタイムアウトの上限があります — デフォルトは60秒です — そのため、再接続中のトランスポートがジョブの実行（とその背後で待つ保留中の再起動のドレイン）を無期限に引き留めることはありません。

```yaml
# ~/.hermes/config.yaml
cron:
  standalone_send_timeout_seconds: 120
```

添付を含む配信には、そのタイムアウトに加えて、ファイルを128 KB/sでアップロードするのにかかる時間の1.5倍（最大1時間）が与えられるため、遅い回線上の大きなファイルが、まだアップロード中なのに失敗として報告されることはありません。テキストのみの送信は設定された値のままです。

タイムアウトした送信は`last_delivery_error`に`standalone send to <target> timed out after Ns`として記録されます。アダプターがすでにそれを受け付けていた場合、メッセージは届く可能性があります。

## no-agentモード（スクリプトのみのジョブ） {#no-agent-mode-script-only-jobs}

LLMの推論を必要としない繰り返しジョブ — 古典的なウォッチドッグ、ディスク/メモリのアラート、ハートビート、CIのpingなど — の場合、作成時に`no_agent=True`を渡します。スケジューラはスクリプトをスケジュールどおりに実行し、その標準出力を直接配信し、エージェントを完全にスキップします。

```bash
hermes cron create "every 5m" \
  --no-agent \
  --script memory-watchdog.sh \
  --deliver telegram \
  --name "memory-watchdog"
```

セマンティクス:

- スクリプトの標準出力（トリムされたもの）→ メッセージとしてそのまま配信されます。
- **空の標準出力 → サイレントtick**、配信なし。これがウォッチドッグのパターンです。「何か問題があるときだけ何かを言う」。
- 0以外の終了コードまたはタイムアウト → エラーアラートが配信されるため、壊れたウォッチドッグがサイレントに失敗することはありません。
- 最終行の`{"wakeAgent": false}` → サイレントtick（LLMジョブが使うのと同じゲート）。
- トークンなし、モデルなし、プロバイダーフォールバックなし — ジョブは推論レイヤーに一切触れません。

`.sh` / `.bash`ファイルは、利用可能であれば`PATH`上の`bash`の下で、そうでなければ`/bin/bash`の下で実行されます（WindowsのGit Bashで重要）。それ以外は現在のPythonインタプリタ（`sys.executable`）の下で実行されます。`script`は常に**ファイル**であり、コマンドラインではありません: `--script "echo hi"`は作成時に拒否されます（コマンドを`~/.hermes/scripts/hi.sh`に書いて`hi.sh`を渡してください）。スクリプトは`$HERMES_HOME/scripts/`の中に解決される必要があります — 相対名、絶対パス、`~`で始まるパスは、解決先がそのディレクトリ内に留まる場合に受け付けられ、そこから外れるパスは拒否されます。Pythonの`script`や`monitor_script`は、作成/編集時に`--interpreter ~/venvs/.../bin/python`を渡すことで、ユーザーが管理するvenv（Hermesのランタイムが持たないパッケージ用）を固定することもできます — [自分のPython環境を使う](../../guides/cron-script-only.md#using-your-own-python-environment)を参照してください。Hermesが管理するvenvはHermesの所有のままで、何かが自動的にインストールされたり復元されたりすることはありません。サブプロセスの環境はサニタイズされる（`_sanitize_subprocess_env`）ため、プロバイダーのAPI認証情報やその他のHermesが管理するシークレットがcronスクリプトに継承されることは**ありません**。

#### スクリプトに認証情報を与える {#giving-a-script-a-credential}

外部サービスに認証する必要があるスクリプト（APIトークン、サービスアカウントのキー）は、ターミナルや`execute_code`の子プロセスと同じ方法でそれを受け取ります — 所有するプロファイルの`config.yaml`で変数名を宣言し、そのプロファイルの`.env`（または外部の[シークレットソース](/docs/user-guide/secrets/)）で値を定義します。

```yaml
terminal:
  env_passthrough:
    - MY_SERVICE_TOKEN
```

変数は**所有するプロファイルの**値でスクリプトの環境に転送されます: マルチプロファイルのゲートウェイやDesktop/ダッシュボードのバックエンドが提供するプロファイルに属するジョブの場合、値はそのプロファイルのシークレットスコープを通じて解決され、起動プロファイルのプロセス環境から取られることはありません。またそのプロファイル自身の`.env`の認証情報が、別のプロファイルのスクリプトに届くことはありません。Hermesが管理するプロバイダーの認証情報（`OPENAI_API_KEY`、ゲートウェイのトークンなど）は宣言できません — サニタイザーがそれらを拒否します。単一プロファイルのインストールでは、スクリプトは従来どおり、ゲートウェイの`.env`がプロセス環境に入れたものを継承します。値ではなく、有無（`set`/`MISSING`）をログに出力してください: スクリプトの出力はそのまま配信されます。

### エージェントがこれらをセットアップしてくれる

`cronjob_manage`ツールのスキーマは`no_agent`をHermesに直接公開しているため、チャットでウォッチドッグを記述してエージェントに組み立ててもらえます。

```text
Ping me on Telegram if RAM is over 85%, every 5 minutes.
```

Hermesは`write_file`経由でチェックスクリプトを`~/.hermes/scripts/`に書き込み、次を呼び出します。

```python
cronjob(action="create", schedule="every 5m",
        script="memory-watchdog.sh", no_agent=True,
        deliver="telegram", name="memory-watchdog")
```

メッセージ内容がスクリプトによって完全に決定される場合（ウォッチドッグ、しきい値アラート、ハートビート）、`no_agent=True`を自動的に選択します。同じツールでエージェントはジョブの一時停止、再開、編集、削除も行えるため、誰もCLIに触れることなく、ライフサイクル全体がチャット駆動になります。

実例については[スクリプトのみのcronジョブガイド](../../guides/cron-script-only.md)を参照してください。

## `context_from` でジョブを連鎖させる

cronジョブは、過去の実行の記憶を持たない分離されたセッションで実行されます。しかし、あるジョブの出力がまさに次のジョブに必要なものである場合があります。`context_from`パラメータはその接続を自動的に配線します — ジョブBのプロンプトには、実行時にジョブAの最新の出力がコンテキストとして先頭に付加されます。

```python
# Job 1: Collect raw data
cronjob(
    action="create",
    prompt="Fetch the top 10 AI/ML stories from Hacker News. Save them to ~/.hermes/data/briefs/raw.md in markdown format with title, URL, and score.",
    schedule="0 7 * * *",
    name="AI News Collector",
)

# Job 2: Triage — receives Job 1's output as context
# Get Job 1's ID from: cronjob(action="list")
cronjob(
    action="create",
    prompt="Read ~/.hermes/data/briefs/raw.md. Score each story 1–10 for engagement potential and novelty. Output the top 5 to ~/.hermes/data/briefs/ranked.md.",
    schedule="30 7 * * *",
    context_from="<job1_id>",
    name="AI News Triage",
)

# Job 3: Ship — receives Job 2's output as context
cronjob(
    action="create",
    prompt="Read ~/.hermes/data/briefs/ranked.md. Write 3 tweet drafts (hook + body + hashtags). Deliver to telegram:7976161601.",
    schedule="0 8 * * *",
    context_from="<job2_id>",
    name="AI News Brief",
)
```

**仕組み:**

- ジョブ2が発火すると、Hermesは`~/.hermes/cron/output/{job1_id}/*.md`からジョブ1の最新の出力を読み取ります
- その出力はジョブ2のプロンプトに自動的に先頭付加されます
- ジョブ2は「このファイルを読め」とハードコードする必要はありません — その内容をコンテキストとして受け取ります
- 連鎖はどんな長さでも構いません: ジョブ1 → ジョブ2 → ジョブ3 → …

**`context_from` が受け付けるもの:**

| 形式 | 例 |
|--------|---------|
| 単一のジョブID（文字列） | `context_from="a1b2c3d4"` |
| 複数のジョブID（リスト） | `context_from=["job_a", "job_b"]` |

出力は列挙された順に連結されます。

**継続性: 前回の実行の出力を引き継ぐ**

`continuity=true`を設定すると、ジョブは各実行に*自身の*最新の出力を注入します。繰り返しジョブは通常、毎回記憶喪失の状態で実行を始めます — ニュースのスカウトは同じ記事を再び報告し、モニターは同じ状態について再びアラートを出します。継続性を有効にすると、ジョブは前回報告した内容を見た状態で目覚めるため、重複を排除して前回の続きから進められます。

```python
cronjob(
    action="create",
    prompt="Scan HN and arXiv for new agent-tooling papers. Report only items NOT already covered in your previous run's output.",
    schedule="every 6h",
    continuity=True,
    name="Agent Tooling Scout",
)
```

最初の実行には前回の出力がないため、プロンプトはそのまま実行されます。沈黙したモニターのtick（`no_change`）、空の出力、`wakeAgent=false`の監査記録は、コンテキストを選ぶ際にスキップされるため、静かな期間があっても最新の実質的な出力が保たれます。監査ファイルはディスク上に残ります。エラーのドキュメントは、次の実行に回復のためのコンテキストを与えるため引き続き対象になります。これは成功のみの履歴フィルタではありません。以降の実行では、前回の出力が継続性の枠組み（「すでに報告したことを繰り返さないこと」）とともに先頭に付加されます。上流のジョブと自由に組み合わせられ（`context_from=["<other_job_id>"]`と`continuity=true`）、更新で`continuity=false`にすると、他の`context_from`エントリを保ったままこれを無効にできます。内部的には、このフラグは`context_from`内の予約済みの`self`エントリとして保存されます。

CLIからは: `hermes cron create "every 6h" "Scan for news" --continuity`、既存のジョブで切り替えるには`hermes cron edit <job_id> --continuity` / `--no-continuity`。同じ切り替えは、ダッシュボードのcronエディターとデスクトップのBot Modeのルーティンのダイアログにもあります。

**使いどころ:**

- 多段パイプライン（収集 → フィルタ → 整形 → 配信）
- ステップNの作業がステップN−1の出力に依存する依存タスク
- 1つのジョブが他の複数のジョブの結果を集約するファンアウト/ファンインのパターン
- 自身の前回のレポートに対して重複排除すべき繰り返しのスカウト/モニター（`continuity=true`）

## プロバイダーのリカバリー {#provider-recovery}

プライマリのAPIキーがレート制限されている場合やプロバイダーがエラーを返した場合、cronエージェントは次のことができます。

- 同じプロバイダーについて、[認証情報プール](../configuration.md#credential-pool-strategies)内の**次の認証情報にローテーション**する。これは固定の有無にかかわらず、すべてのジョブに適用されます。
- `config.yaml`の`fallback_providers`（またはレガシーの`fallback_model`）から**代替プロバイダーにフォールバック**する — **固定されていないジョブのみ**。これは、実行開始前の認証情報の解決中の失敗と、実行途中のプロバイダーエラーの両方をカバーします。

独自の`provider`、`model`、`base_url`を持つジョブ（`--provider` / `--model`、`--pin`、ダッシュボード、または`jobs.json`で設定）は、グローバルのチェーンにフォールバックすることは決してありません。固定はジョブがどの経路で実行されるかを表しており、フォールバックのエントリは別のプロバイダーで、通常は別のモデルでもあるため、固定された経路が失敗すると実行は失敗し、失敗アラートがその旨を伝えます。これは[サブエージェントの委譲](./delegation.md)が固定された子に適用するのと同じルールです。ジョブでフォールバックを維持するには、固定しないでください: `cron.model` / `cron.model_provider`（またはメインモデル）に従い、他の固定されていないジョブと同じようにチェーンをたどります。

このルールの前は、プロバイダーが失敗した固定ジョブが、代わりに最初に機能する`fallback_providers`のエントリで、出力に1行の通知を付けて実行されることがありました。それに依存していた場合は、ジョブの固定を解除し（`hermes cron edit <job_id> --unpin`）、代わりに`cron.model`でモデルを設定してください。

したがって、1つのレート制限されたキーが、同じプロバイダーの別の認証情報を持つ実行を失敗させることはなく、チェーンが設定されていれば、固定されていないジョブは引き続きプロバイダーの障害を乗り越えます。

## 実行の失敗（`last_error`）

失敗したエージェントの実行は、簡潔な`last_error`を記録します。これはジョブの一覧や`/cron list`に表示され、
認証情報のパターンとURLの認証情報は秘匿化されます（以前に保存されたエラーを含む）。
これは`last_fire_error`（スケジューラの引き渡し）や`last_delivery_error`（配信）とは別のものです。
エージェント自身が失敗した場合、それらのフィールドは正しく空になり得ます。

接続の失敗については、アクティブなHermesホームの`cron/output/<job_id>/`配下にある実行ドキュメントを
調べてください。その`## Error`セクションには、認証情報のパターンとURLの認証情報が秘匿化された、
連鎖したトレースバックが含まれます。ファイルは既存のプライベートな出力ファイルの権限を使い、
トレースバックのローカル変数は取得されません。配信通知と`last_error`は、完全なトレースバックではなく
簡潔なエラーを保持します。共有する前に診断情報を確認してください: 秘匿化は、
任意のアプリケーションデータが機密でないことを保証するものではありません。

## 見逃したスケジュールの発火（`last_fire_error`）

ホスト型（マネージドcron）のデプロイでは、スケジュールされた発火は、プラットフォームのスケジューラからダッシュボードを経てゲートウェイの内部APIサーバーに届きます。最後の引き渡しが失敗した場合 — ゲートウェイのプロセスがダウンしている、またはそのAPIサーバーのリスナーが起動しなかった — 実行は始まらないため、実行記録も調べるべき`last_status`もありません。典型的な形: 手動でトリガーすると毎回動作するのに、自動では一度も発火しません。

これらの見逃しは、ジョブの記録に`last_fire_error`（タイムスタンプ + 理由）として刻まれ、次で表示されます。

- `cronjob_manage`ツール → `action: "list"` — `last_fire_error`フィールド
- `hermes cron list`: ジョブの下に赤い見逃し発火の警告
- `hermes cron doctor`: コマンドを`1`で終了させる、ジョブごとの見逃し発火の検出事項
- ダッシュボードのジョブビュー

この刻印は常に**現在の**自動発火の健全性を反映します: 新しい見逃しで上書きされ、次の成功した実行で自動的にクリアされます。これが表示されている場合、ジョブとそのスケジュールに問題はありません — 注意が必要なのは発火経路のゲートウェイ側です（最も一般的には、完全なプロファイル環境を読み込むよう、スーパーバイザーを通じてゲートウェイを再起動します: `hermes gateway restart`）。

### ローカルでの見逃した実行のポリシー

繰り返しジョブのスケジュール時刻が過ぎたときにゲートウェイがダウンしていた（または再起動中だった）場合、
スケジューラが戻ったときにジョブは**1回キャッチアップします**: 再起動の空白の中で見逃した枠はちょうど
1回発火し、再起動の前にすでに実行された枠が再び実行されることはなく、長い障害は
見逃した枠ごとに1回ではなく1回の実行にまとめられます。一時停止されたジョブがキャッチアップすることはありません。各キャッチアップは
`hermes cron list`に`⚠ late` / `⚠ catch-up after missed fire`として表示されます。

計画的なゲートウェイの停止の後のキャッチアップの負荷を避けるには、次を設定します。

```yaml
cron:
  catch_up_missed: false   # default: true
```

または`hermes config set cron.catch_up_missed false`を実行します。このオプトアウトでは、既存の猶予ウィンドウ
（周期の半分で、120秒〜2時間にクランプ）より遅れた繰り返しジョブは、今すぐ発火せずに
次の将来の発生に再アンカーされます。スキップは
ログに記録されます。猶予内のジョブと明示的な手動トリガーは引き続き通常どおり実行されます。
次の発生を計算できない場合は、既存の1回実行のフォールバックが維持されます。
これは再開時の挙動や、下記のホスト型プロバイダーのスイープを変更しません。

**ジョブごと。** ジョブは`catch_up`でデフォルトを上書きできます。

```bash
hermes cron create "0 7 * * 1-5" "Morning brief" --catch-up off   # a stale brief is useless: skip
hermes cron edit <job> --catch-up on                                # always run once on return
```

（`cronjob_manage`は`catch_up: true|false`を受け取ります。Desktopのジョブエディターにも同じ選択肢が
**Missed runs**として用意されています: *Use the default*、*Run once when back*、*Skip them*。）これがない場合、繰り返しジョブは
明示的な`--grace-minutes`を過ぎた見逃しをスキップし、それ以外は`cron.catch_up_missed`に従います。
ワンショットは120秒の猶予を維持します: それより長く見逃したリマインダーは
破棄されます。`--catch-up on`のワンショットは、代わりにスケジューラが戻ったときに
遅れて1回発火します。`--catch-up on`は`--grace-minutes`にも優先します: 猶予はいつ実行が見逃しとみなされるかを決め、
ジョブはそれでも1回実行されます。

**見逃した実行は可視化されます。** スケジューラが飛ばしたすべての枠は、実行台帳に1つの`missed ×N`
行として記録されます: スキップの場合は`missed ×3 (skipped, catch-up off; next run …)`、
3つの枠に対してキャッチアップした1回の実行の横には`missed ×2 (collapsed into one catch-up run)`です。
これらの行は`hermes cron runs <job>`とダッシュボード/Desktopの実行履歴に表示されます。

### ミスファイアのキャッチアップ {#misfire-catch-up}

外部のスケジューラプロバイダーが有効な場合（ホスト型デプロイでのマネージドcron）、ゲートウェイはキャッチアップのスイープも実行します: スケジュール時刻が過ぎたのに発火が届かず — かつ猶予ウィンドウも過ぎた — ジョブは要求されてローカルで実行されるため、発火の引き渡しの障害で失うのは丸1日ではなく数分で済みます。スイープは、通常の発火と同じストアの要求によって、遅れて届いたスケジューラのリトライと重複排除されます。

```yaml
cron:
  misfire_grace_minutes: 10   # wait this long for the scheduler's own retries
                              # before catching up locally; 0 disables catch-up
```

ローカル（組み込みのティッカー）のデプロイではこれは不要です — ティッカーはすでに次のtickで期限切れのジョブを拾います。

## スケジュール形式

エージェントの最終応答は、ジョブの`deliver:`ターゲットに自動的に配信されます — エージェントがもう自分でメッセージを送ることはないため、ユーザー向けの内容は単に最終応答に入れます。**追加の、または別の**ターゲットに配信するには、エージェントに送らせるのではなく、cronジョブに複数の`deliver:`ターゲットを列挙します（カンマ区切り。例: `deliver: "telegram,discord"`）。

### 相対遅延（ワンショット）

```text
in 30m  → Run once in 30 minutes
in 2h   → Run once in 2 hours
in 1d   → Run once in 1 day
```

### 間隔（繰り返し）

```text
30m          → Every 30 minutes (bare durations are recurring)
every 30m    → Every 30 minutes
every 2h     → Every 2 hours
every 1d     → Every day
every hour   → Every hour (bare unit = 1)
```

### 自然な曜日/時刻のスケジュール（繰り返し）

```text
every monday 9am         → Weekly, Mondays at 9:00 AM
every day at 9am         → Daily at 9:00 AM
weekdays at 9am          → Weekdays at 9:00 AM
weekends at 10am         → Saturdays and Sundays at 10:00 AM
daily at 7am             → Daily at 7:00 AM
monday, wednesday at 9am → Mondays and Wednesdays at 9:00 AM
```

時刻には`9am`、`9:30pm`、`14:00`、24時間制の時のみ（`at 7`）、`noon`、`midnight`を指定できます。これらの形式は内部的にcron式にコンパイルされます（デフォルトでインストールされる`croniter`パッケージが必要です）。

### cron式

```text
0 9 * * *       → Daily at 9:00 AM
0 9 * * 1-5     → Weekdays at 9:00 AM
0 9 * * MON-FRI → Weekdays at 9:00 AM (named weekdays/months accepted)
0 */6 * * *     → Every 6 hours
30 8 1 * *      → First of every month at 8:30 AM
0 0 * * 0       → Every Sunday at midnight
```

### ISOタイムスタンプ

```text
2026-03-15T09:00:00    → One-time at March 15, 2026 9:00 AM
```

## 繰り返しの動作

| スケジュールの種類 | デフォルトの繰り返し | 動作 |
|--------------|----------------|----------|
| ワンショット（`in 30m`、タイムスタンプ） | 1 | 1回実行 |
| 間隔（`every 2h`） | 無期限 | 削除されるまで実行 |
| cron式 | 無期限 | 削除されるまで実行 |

これは上書きできます。

```python
cronjob(
    action="create",
    prompt="...",
    schedule="every 2h",
    repeat=5,
)
```

## プログラムによるジョブ管理

エージェント向けのAPIは1つのツールです。

```python
cronjob(action="create", ...)
cronjob(action="list")
cronjob(action="update", job_id="...")
cronjob(action="pause", job_id="...")
cronjob(action="resume", job_id="...")
cronjob(action="run", job_id="...")
cronjob(action="remove", job_id="...")
```

`update`では、紐づいたスキルをすべて削除するために`skills=[]`を渡します。

### 手動実行は非同期

`cronjob(action="run")`はジョブを即座に**バックグラウンドで**発火させます（
`delegate_task`と同様）: ツール呼び出しはハンドルとともにすぐに返り、ジョブの
結果 — 成功/失敗、配信ターゲット、次のスケジュール実行 — は、実行が終わると
新しいメッセージとして会話に戻ってきます。出力の抜粋が含まれるのは、
`deliver: local`のジョブと、すべてのターゲットで配信が失敗した実行だけです:
チャットに配信したジョブはすでにそこに出力を投稿しているため、抜粋は
それを実行した会話（別のトピックかもしれません）にはコピーされません。
エージェント（とあなた）はその間も作業を続けられ、すでに実行中のジョブは
二重に発火するのではなく「already running」で拒否されます。

`action="run"`で`prompt`を渡して、一時的な実行ごとの
コンテキストを注入することもできます。

```python
cronjob(action="run", job_id="...", prompt="CONTEXT: focus on the EU region today")
```

コンテキストは、その1回の発火に限り、ジョブの保存済みプロンプトに`## Run Context`
ヘッダーの下で追加されます — ジョブの定義に永続化されることは決してなく、
保存済みのプロンプトと同じプロンプトインジェクションのスキャンを通ります。

デタッチされた結果を受け取れないランタイム（単発の`hermes -z`、CLIからの`hermes
cron run`、cronの子セッション、Kanbanのワーカー）は、自動的に
同期実行にフォールバックします。

## cronジョブが利用できるツールセット {#toolsets-available-to-cron-jobs}

cronは各ジョブを、チャットプラットフォームが紐づいていない新規エージェントセッションで実行します。デフォルトでは、cronエージェントは**`hermes tools`で`cron`プラットフォーム向けに設定したツールセット**を取得します — CLIのデフォルトでも、ありとあらゆるものでもありません。

```bash
hermes tools
# → pick the "cron" platform in the curses UI
# → toggle toolsets on/off just like you would for Telegram/Discord/etc.
```

ジョブごとのより厳密な制御は、`cronjob.create`の`enabled_toolsets`フィールド（または既存ジョブに対しては`cronjob.update`）で利用できます。

```text
cronjob(action="create", name="weekly-news-summary",
        schedule="every sunday 9am",
        enabled_toolsets=["web", "file"],      # just web + file, no terminal/browser/etc.
        prompt="Summarize this week's AI news: ...")
```

ジョブに`enabled_toolsets`が設定されている場合はそれが優先されます。そうでない場合は`hermes tools`のcronプラットフォーム設定が優先され、それもなければHermesは組み込みのデフォルトにフォールバックします。cronプラットフォームのツールセット設定がまったく読めない場合（たとえば`config.yaml`の`platform_toolsets`ブロックの形式が不正な場合）、すべてのツールで黙って実行するのではなく、エラーを記録して実行が失敗します — `hermes cron list` / `hermes cron doctor`を確認してください。これはコスト管理にとって重要です。`browser`、`delegation`を小さな「ニュース取得」ジョブごとに持ち込むと、すべてのLLM呼び出しでツールスキーマのプロンプトが肥大化します。

ジョブがログインしているサイトを操作する場合、ログインは実行前に済ませておく必要があります — スケジュールされたtickには、プロンプトに答える人がいません。そのセットアップについては[スケジュール実行と無人実行](./browser.md#scheduled-and-unattended-runs)を参照してください。

### エージェントを完全にスキップする: `wakeAgent`

cronジョブが事前チェックスクリプト（`script=`経由）を紐づけている場合、スクリプトは実行時にHermesがそもそもエージェントを起動すべきかどうかを判断できます。次の形式の最終標準出力行を出力します。

```text
{"wakeAgent": false}
```

…すると、cronはこのtickでのエージェント実行を完全にスキップします。状態が実際に変化したときだけLLMを起こせばよい高頻度のポーリング（1〜5分ごと）に便利です — そうしないと、中身のないエージェントターンに何度も課金されることになります。

```python
# pre-check script
import json, sys
latest = fetch_latest_issue_count()
prev = read_state("issue_count")
if latest == prev:
    print(json.dumps({"wakeAgent": False}))   # skip this tick
    sys.exit(0)
write_state("issue_count", latest)
print(json.dumps({"wakeAgent": True, "context": {"new_issues": latest - prev}}))
```

`wakeAgent`が省略された場合、デフォルトは`true`（通常どおりエージェントを起こす）です。

#### レシピ: 安価な実行前ゲート

`wakeAgent`ゲートを使うと、スケジュールされたジョブがそもそもLLMのトークンを使うべきかどうかを$0で判断できます。ほとんどのユースケースは3つのパターンでカバーできます。

**ファイル変更ゲート** — 監視しているファイルに、前回の成功したtick以降の新しい内容がある場合にのみ実行します。スケジューラは各ジョブの`last_run_at`を記録しているので、それをファイルのmtimeと比較します。

```bash
#!/usr/bin/env bash
# ~/.hermes/scripts/feed-changed.sh
FEED="$HOME/data/feed.json"
STATE="$HOME/.hermes/scripts/.feed-changed.last"
test -f "$FEED" || { echo '{"wakeAgent": false}'; exit 0; }
mtime=$(stat -c %Y "$FEED")
last=$(cat "$STATE" 2>/dev/null || echo 0)
if [ "$mtime" -le "$last" ]; then
  echo '{"wakeAgent": false}'
else
  echo "$mtime" > "$STATE"
  echo '{"wakeAgent": true}'
fi
```

```text
cronjob(action="create", name="process-feed",
        schedule="every 30m",
        script="feed-changed.sh",
        prompt="A new ~/data/feed.json has landed. Summarize what changed.")
```

**外部フラグゲート** — 他のプロセスが準備完了を通知した場合にのみ実行します（例: デプロイフックがファイルを置く、CIジョブが状態ストアに値を設定する）。

```bash
#!/usr/bin/env bash
# ~/.hermes/scripts/flag-ready.sh
if test -f ~/.hermes/cache/scratch/new-data-ready; then
  rm -f ~/.hermes/cache/scratch/new-data-ready
  echo '{"wakeAgent": true}'
else
  echo '{"wakeAgent": false}'
fi
```

```text
cronjob(action="create", name="nightly-analysis",
        schedule="0 9 * * *",
        script="flag-ready.sh",
        prompt="Run the nightly analysis over today's batch.")
```

**SQLカウントゲート** — 自分のデータベースに処理すべき新しい行がある場合にのみ実行します。スクリプトは`context`を通じてその件数をエージェントに渡すこともできるため、エージェントは再クエリせずにどれだけの量を扱うかを把握できます。

```python
#!/usr/bin/env python
# ~/.hermes/scripts/new-rows.py
import json, sqlite3
conn = sqlite3.connect("/home/me/data/app.db")
n = conn.execute(
    "SELECT COUNT(*) FROM messages WHERE ts > strftime('%s','now','-2 hours')"
).fetchone()[0]
if n < 1:
    print(json.dumps({"wakeAgent": False}))
else:
    print(json.dumps({"wakeAgent": True, "context": {"new_rows": n}}))
```

```text
cronjob(action="create", name="summarize-new-msgs",
        schedule="every 2h",
        script="new-rows.py",
        prompt="Summarize the new messages from the last 2 hours.")
```

同じパターンは、スクリプトからクエリできるあらゆるデータソース — Postgres、HTTP API、独自の状態ストア — で機能し、cronのサブシステムにSQLの評価器を組み込む必要はありません。

:::tip
Hermes自身の`~/.hermes/state.db`は、リリース間で変わる内部スキーマです。実行前ゲートからそれをクエリしないでください — 代わりに自分のデータベースやフィードを指定してください。
:::

謝辞: このレシピ集は、@iankar8による[#2654](https://github.com/NousResearch/hermes-agent/pull/2654)での探求がきっかけとなりました。そこではsql/file/commandのトリガーを並行する仕組みとして追加することが提案されました。`script` + `wakeAgent`ゲートがすでに3つのケースすべてを$0でカバーしているため、この作業はドキュメントとして実を結びました。

### ジョブの連鎖: `context_from`

cronジョブは、`context_from`に他の1つ以上のジョブの名前（またはID）を列挙することで、それらの最新の成功出力を取り込めます。

```text
cronjob(action="create", name="daily-digest",
        schedule="every day 7am",
        context_from=["ai-news-fetch", "github-prs-fetch"],
        prompt="Write the daily digest using the outputs above.")
```

参照されたジョブの最新の完了出力が、この実行のためのコンテキストとしてプロンプトの上に注入されます。各上流エントリは有効なジョブIDまたは名前でなければなりません（`cronjob action="list"`を参照）。注意: 連鎖は*最新の完了*出力を読み取ります — 同じtickで実行中の上流ジョブを待つことはありません。

## ジョブのストレージ

ジョブは`~/.hermes/cron/jobs.json`に保存されます。ジョブ実行の出力は`~/.hermes/cron/output/{job_id}/{timestamp}.md`に保存されます。

ジョブの定義はディスク上のプレーンなJSONです: `hermes update`、ゲートウェイの再起動、マシンの再起動を越えて残ります。再起動中に実行途中だったジョブは、実行台帳で`unknown`としてマークされます — 自動的にはリトライされませんが、ジョブの次のスケジュールtickは通常どおり発火します。詳細は[実行履歴](#execution-history)を参照してください。

:::tip
`jobs.json`を直接パッチするのではなく、`cronjob_manage`ツール、`hermes cron edit`、または`/cron`を通じてジョブを管理するようエージェントに依頼してください。[ファイル書き込みの安全性](../security.md#file-write-safety)がパスをブロックした場合（たとえば`HERMES_WRITE_SAFE_ROOT`が設定されている場合）、直接の編集は黙って失敗することがあり、何も保存されなかったことの正となるシグナルは[ファイル変更の検証器](../configuration.md#file-mutation-verifier)のフッターです。
:::

手作業の編集で`jobs.json`の形式が壊れた場合、スケジューラは停止するのではなく次の読み込みでそれを修復します: `jobs`リスト内のJSONオブジェクトでないエントリは削除され、非負の整数でない`repeat.completed`は有効なカウントにリセットされます（読めない場合は0）。各修復は警告としてログに記録されます（値の型のみで、内容は決して記録しません）。

ジョブは`model`と`provider`を`null`として保存することがあります。これらのフィールドが省略されている場合、Hermesは実行時にグローバル設定からそれらを解決します。これらはジョブごとのオーバーライドが設定されている場合にのみジョブレコードに現れます。

ジョブごとの`base_url`の上書きには、明示的な`provider`が必要です。保存されたキーを持つプロバイダー（名前付きのカスタムプロバイダーまたは組み込みのもの）の場合、上書きはそのプロバイダーの設定済みのエンドポイントと同じオリジン — 同じスキーム、ホスト、ポート — でなければなりません。別のスキーム、ポート、サブドメインは拒否されるため、保存されたキーは設定した場所にのみ送られます。単独の`provider: custom`は、保存されたキーを伴わない任意の`base_url`を受け付けます。保存されたキーがURLのホスト名に一致する場合（たとえば`api.deepseek.com`に対する`DEEPSEEK_API_KEY`）も同じルールが適用されます: `base_url`は、設定したエンドポイントまたは組み込みのプロバイダーのオリジンでなければなりません。

ストレージはアトミックなファイル書き込みを使用するため、書き込みが中断されても、部分的に書き込まれたジョブファイルが残ることはありません。

## 自己完結したプロンプトは依然として重要

:::warning Important
cronジョブは完全に新規のエージェントセッションで実行されます。プロンプトには、紐づいたスキルによってまだ提供されていない、エージェントが必要とするすべてを含める必要があります。
:::

**悪い例:** `"Check on that server issue"`

**良い例:** `"SSH into server 192.168.1.100 as user 'deploy', check if nginx is running with 'systemctl status nginx', and verify https://example.com returns HTTP 200."`

## セキュリティ

スケジュールタスクのプロンプトは、作成時と更新時にプロンプトインジェクションや認証情報の流出パターンがないかスキャンされます。不可視のUnicodeトリック、SSHバックドアの試み、明白なシークレット流出ペイロードを含むプロンプトはブロックされます。
