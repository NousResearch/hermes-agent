# サブエージェント委譲

`delegate_task` ツールは、独立したコンテキスト、継承されたツールアクセス、独自のターミナルセッションを持つ子AIAgentインスタンスを起動します。各子エージェントは新しい会話を取得し、独立して動作します。最終的な要約のみが親のコンテキストに入ります。

トップレベルのモデル呼び出しは自動的にバックグラウンドで実行されます。Hermesはすぐにハンドルを返すため会話を続けることができ、その後、結果を新しいメッセージとして投稿します。オーケストレーターのサブエージェントは、戻る前に結果を統合できるよう、自身のワーカーを待ちます。

## 完了の配信

メッセージングゲートウェイは、アダプターが実際にイベントをスケジュールするか、セッションのキューに挿入した後にのみ、バックグラウンドの完了を受領します。ハンドラーの欠落、セッションルートの不一致、キューの満杯の場合、完了は再試行のために保留のままになります。これらの受け入れ拒否は、永続的な配信試行の予算を消費しません。受け入れに成功すると、実行中のゲートウェイ内での重複配信は抑止されますが、それはモデルのターンや送信返信が完了したことの証明ではありません。クラッシュ/再起動時の配信は、既存のリプレイ期間の制限の範囲で、引き続き少なくとも1回（at least once）です。実際のトランスポートの失敗には、上限付きの再試行ポリシーがそのまま適用されます。

利用できないAPIサーバーのルートは、ルート欠落の警告を繰り返すことなく保留のままになります。不正な形式のメッセージングルートは引き続き診断を出力します。APIサーバーでは、非同期の委譲の完了は永続的なタイムラインの配信行を追加するだけです。次のモデルのターンはクライアントが担います。バックグラウンドプロセスの通知を `off` に設定しても、パターン監視のイベントは黙って処理され続けます。

## バックグラウンドプロセスの寿命

バックグラウンドのターミナルプロセスは、それを開始したエージェントに属します。委譲の後片付けの際に子を閉じると、以前のターンで開始された作業も含め、その子の残りのプロセスが終了されます。親や兄弟エージェントが所有するプロセスは停止されません。ターミナル環境を共有しても、プロセスの所有権は移りません。

子は、最終的な要約を返す前に、ビルド、テスト、その他の終了が見込まれるバックグラウンドコマンドを待つべきです。子の終了後も継続しなければならないCIウォッチャーやサーバーは、親のセッションで開始してください。プロセスIDを返しても、所有権が親に移るわけではありません。

## バックグラウンドの子からの承認

親のターンが終了した後にコマンドの承認を必要とするバックグラウンドの子は、引き続き親が開始されたチャットで尋ねます。メッセージングプラットフォームでは、承認カード（またはプレーンテキストの `/approve` プロンプト）がそこに表示され、`/approve`、`/deny`、またはカードのタップでその子のコマンドに応答します。親がまだ返信している間に子が出したカードは、親が終了した後も応答可能なままです。子を停止する（`/stop`）、セッションをリセットする（`/new`）、または子が終了すると、その開いているプロンプトは取り下げられます。

親のターンが終わった後にプロンプトを表示できるチャットがない場合（APIサーバーでの実行、Webhook、ローカルのビューアー）、子のコマンドは明示的な「no approval channel」の結果で拒否されます。保留中として報告されることはありません。

## 単一タスク

```python
delegate_task(
    goal="Debug why tests fail",
    context="Error: assertion in test_foo.py line 42"
)
```

## 並列バッチ

デフォルトでは最大10の同時サブエージェント（設定可能、ハードな上限なし）:

```python
delegate_task(tasks=[
    {"goal": "Research topic A", "context": "Focus on recent primary sources"},
    {"goal": "Research topic B", "context": "Compare the leading explanations"},
    {"goal": "Fix the build", "context": "Project root: /home/user/project"}
])
```

## 構造化出力（`output_schema`）

各タスクには、オプションで `output_schema` を付けることができます。これは子の最終回答が検証に合格しなければならないJSON Schemaオブジェクトです。子は出力契約としてスキーマを最初に受け取ります（「JSONの値のみを返すこと — 説明文もコードフェンスもなし」）。回答が戻ってくると親がそれを検証し、失敗した場合は検証エラーをそのまま含めた、上限付きの修正ターンを子に1回だけ送ります（スキーマは再度貼り付けられません）。タスクの結果には `schema_valid`（true/false）が付き、失敗した場合は `schema_errors` も付きます。

再試行後も契約を満たさなかった場合でも、子の作業は破棄**されません**: 結果は `status: completed` のままで、`summary` には子の生の最終テキスト、`schema_valid: false`、`schema_errors`、そしてテキストが未検証であることを示す `schema_note` が入ります。親は、1時間かかったかもしれないタスクを再実行するのではなく、生のテキストから必要なものを抽出します。それ以外は有効なJSON（オブジェクトまたは配列）の周りにある説明文やコードフェンスは、バリデーターで許容されます。

```python
delegate_task(
    tasks=[{
        "goal": "Check which of these three endpoints return 200",
        "context": "https://a.example, https://b.example, https://c.example",
        "output_schema": {
            "type": "object",
            "properties": {
                "healthy": {"type": "array", "items": {"type": "string"}},
                "failing": {"type": "array", "items": {"type": "string"}}
            },
            "required": ["healthy", "failing"]
        }
    }]
)
```

スキーマは寛容に保ってください: 実際に読むフィールドのみを必須にします。`output_schema` のないタスクには影響しません。

## サブエージェントのコンテキストの仕組み

:::warning 重要: サブエージェントは何も知らない
サブエージェントは**完全に新しい会話**で始まります。親の会話履歴、以前のツール呼び出し、委譲前に議論された内容について一切の知識を持ちません。サブエージェントの唯一のコンテキストは、親エージェントが `delegate_task` を呼び出すときに設定する `goal` と `context` フィールドから来ます。
:::

1つの例外: 親が解決済みのワークスペースディレクトリを持っている場合、すべてのサブエージェントのシステムプロンプトには、そのワークスペースの**プロジェクトコンテキストファイル**（`.hermes.md` > AGENTS.mdのチェーン > CLAUDE.md > `.cursorrules` — メインエージェントのシステムプロンプトと同じ検出、優先順位、サイズ上限。SOUL.mdは除外）が埋め込まれます。リポジトリで作業するサブエージェントは、それを再発見することなく、リポジトリ自身の規約の下で動作します。

`context` と `goal` は、サブエージェントの最初のユーザーメッセージとして、コンテキストを先にして届きます。そのシステムプロンプトにはタスク固有の内容が含まれないため、1つの親のサブエージェントは同一のプロンプトプレフィックスを送信し、共有するコンテキストも含めて互いのプロンプトキャッシュを読むことができます。その最初のメッセージは、コンテキスト圧縮を通じてもそのまま保持されます。

これは、親エージェントがサブエージェントに必要な**すべて**を呼び出し時に渡さなければならないことを意味します。

```python
# BAD - subagent has no idea what "the error" is
delegate_task(goal="Fix the error")

# GOOD - subagent has all context it needs
delegate_task(
    goal="Fix the TypeError in api/handlers.py",
    context="""The file api/handlers.py has a TypeError on line 47:
    'NoneType' object has no attribute 'get'.
    The function process_request() receives a dict from parse_body(),
    but parse_body() returns None when Content-Type is missing.
    The project is at /home/user/myproject and uses Python 3.11."""
)
```

サブエージェントの最初のメッセージは、あなたのコンテキストに続いて目標が置かれたものです。そのシステムプロンプトは、タスクを完了し、何をしたか、何を見つけたか、変更したファイル、遭遇した問題について構造化された要約を提供するよう指示します。

### サブエージェントへの画像の転送

タスクが本質的に視覚的な場合 — ユーザーが送ったスクリーンショット、デザインのモック、レンダリングされたチャート — テキストのコンテキストだけでは不十分です。各タスクはオプションの `images` リスト（最大8項目。ローカルファイルのパス、`http(s)` URL、または `data:image/...` URL）を受け付けます:

```python
delegate_task(tasks=[{
    "goal": "Compare the rendered dashboard against the design mock and list layout deviations",
    "context": "The app runs at http://localhost:3000; the repo is at /home/user/dash.",
    "images": ["/home/user/mocks/dashboard-v2.png",
               "https://cdn.example.com/current-render.png"],
}])
```

配信は、ユーザーが添付した画像と同じルーティング（`agent.image_input_mode`）に従います:

- **ビジョン対応の子モデル** — 画像は子の最初のターンでネイティブのマルチモーダルコンテンツとして届きます: ローカルファイルはdata URLとして埋め込まれ（他のすべてのファイル読み取りと同じ読み取りガードの対象）、リモートと `data:` のURLはそのまま渡されます。子は実際のピクセルを見ます。
- **ビジョン非対応の子モデル** — 目標に `[Image attached at: <path>]` というヒント行が付き、子は `vision_analyze` でそれらを確認するよう指示されます。

転送はベストエフォートです: 読み取れないパスはログ行を出してスキップされ、画像の処理で何らかの失敗があった場合はプレーンテキストの目標にフォールバックします — 起動が失敗することは決してありません。画像は子が*見る*必要があるもののためのものです。テキストファイルのパスは通常どおり `context` に入れてください。

## 実践的な例

### 並列リサーチ

複数のトピックを同時に調査し、要約を収集します。

```python
delegate_task(tasks=[
    {
        "goal": "Research the current state of WebAssembly in 2025",
        "context": "Focus on: browser support, non-browser runtimes, language support"
    },
    {
        "goal": "Research the current state of RISC-V adoption in 2025",
        "context": "Focus on: server chips, embedded systems, software ecosystem"
    },
    {
        "goal": "Research quantum computing progress in 2025",
        "context": "Focus on: error correction breakthroughs, practical applications, key players"
    }
])
```

### コードレビュー + 修正

レビューと修正のワークフローを新しいコンテキストに委譲します。

```python
delegate_task(
    goal="Review the authentication module for security issues and fix any found",
    context="""Project at /home/user/webapp.
    Auth module files: src/auth/login.py, src/auth/jwt.py, src/auth/middleware.py.
    The project uses Flask, PyJWT, and bcrypt.
    Focus on: SQL injection, JWT validation, password handling, session management.
    Fix any issues found and run the test suite (pytest tests/auth/)."""
)
```

### 複数ファイルのリファクタリング

親のコンテキストを溢れさせるような大規模なリファクタリングタスクを委譲します。

```python
delegate_task(
    goal="Refactor all Python files in src/ to replace print() with proper logging",
    context="""Project at /home/user/myproject.
    Use the 'logging' module with logger = logging.getLogger(__name__).
    Replace print() calls with appropriate log levels:
    - print(f"Error: ...") -> logger.error(...)
    - print(f"Warning: ...") -> logger.warning(...)
    - print(f"Debug: ...") -> logger.debug(...)
    - Other prints -> logger.info(...)
    Don't change print() in test files or CLI output.
    Run pytest after to verify nothing broke."""
)
```

## バッチモードの詳細

トップレベルのエージェントが `tasks` 配列を指定すると、Hermesはバックグラウンドのハンドルを1つ返し、サブエージェントを並列で実行します。デフォルトでは、すべてのタスクが終了した時点で、呼び出しは統合された**1つの**メッセージを返します。結果は親のターンの合間にのみ配信されます: 親は子に依存しない作業をすべて終えてから、待っている間にトランスクリプト、成果物、CIをポーリングするのではなく、ターンを終了すべきです。

### 個別の完了（オプトイン）

`delegation.independent_completions: true` を設定すると、結果は代わりに**完了単位ごと**に、それぞれが終了するたびに届くようになります。モデル向けの `group` フィールドとグループ分けのガイダンスは、このオプションが有効な場合にのみ提示されます。変更した後は、既存の会話のキャッシュ済みプレフィックスを変えることなくツールスキーマに設定が反映されるよう、新しいセッションを開始してください。`group` を含む古い呼び出しは引き続き受け付けられます。オプションがオフの場合、呼び出し全体がまとめて返されます。

個別の完了が有効な場合:

- スキーマはすべてのタスクで `group` を必須としてマークするため、モデルはフィールドを省略してタスクごとの配信に陥るのではなく、各呼び出しで配信の選択を明示します。
- すべてのタスクに同じ `group` 文字列を付けるのは、親がそれらすべてが完了したときにのみ応答する場合の選択です: 比較、統合、または1つの協調した判断です。グループは、そのすべてのタスクが終了した後に統合された**1つの**メッセージを返します。独立して実行可能なタスクであっても、その結果が同じ判断に役立つ場合は1つのグループに属します。
- タスクに独自の `group` を付けるのは、親がその結果が届き次第すぐに対応する場合のみです。そのような結果はそれぞれ単独で戻り、親のターンを1回消費します。
- 異なるグループは独立して報告され、1つの呼び出しを共有できます。`group` なしで届いたタスク（古いトランスクリプト、`required` を無視するモデル）も引き続き受け付けられ、以前と同様に単独で報告されます。

これがデフォルトでオフになっているのは、各単位がオーケストレーターにとって新しいターンになるためです: 15タスクの呼び出しは最大15回の起床になり、長いキャンペーンを断片化させていました。グループ分けが制御するのは**結果の配信であり、実行順序ではありません**: すべてのタスクは引き続き並列で実行されます。タスクBがその作業にタスクAの出力を必要とする場合は、まずAをディスパッチし、Aが戻った後にその出力を付けてBをディスパッチしてください。

```json
{"tasks": [
  {"goal": "Review PR #101 ..."},
  {"goal": "Review PR #102 ..."},
  {"goal": "Benchmark approach A ...", "group": "bench"},
  {"goal": "Benchmark approach B ...", "group": "bench"}
]}
```

ディスパッチのハンドルは各単位（`units[].delegation_id`、`group`、`task_indexes`）を列挙します。単位のIDは呼び出しのIDに `-1`、`-2`、… を付けたもので、1つの呼び出しのすべての単位は `delegation.max_concurrent_children` の1つのスロットを共有するため、グループ分けがキャパシティの計算を変えることはありません（ワーカープールは生きている単位の数まで拡大するため、満杯のプールの後ろで待たされる単位はありません）。オーケストレーターのサブエージェントは、結果を統合できるよう、現在のターンでバッチ全体を待ちます。

- **最大同時実行数:** デフォルトで10タスク（`delegation.max_concurrent_children` または `DELEGATION_MAX_CONCURRENT_CHILDREN` 環境変数で設定可能。下限は1、ハードな上限なし）。制限を超えるバッチは、静かに切り詰められるのではなく、ツールエラーを返します。
- **スレッドプール:** 設定された同時実行制限を最大ワーカー数として `ThreadPoolExecutor` を使用します
- **進捗表示:** CLIモードでは、ツリービューで各サブエージェントのツール呼び出しをリアルタイムに、タスクごとの完了行とともに表示します。ゲートウェイモードでは、進捗がバッチ化され、親の進捗コールバックに中継されます。CLIとTUIの完了通知は `Subagent Task Completed: Review changes` のようにタスクを先頭にしたタイトルを使い、複数タスクのグループはグループ名とタスク数を使います。成功しなかった、または不完全な作業には、それに対応するステータスラベルが付きます。これらの簡潔な通知は、親エージェントに配信される完全な結果を置き換えるものではありません。
- **結果の順序:** 単位内では、結果は完了順序に関係なく入力順に合わせてタスクインデックスでソートされます。`TASK i/N` のラベルは呼び出し全体でのインデックスです
- **キャンセル:** フォローアップのメッセージや現在のターンの停止（Ctrl+C、Esc、Desktop/TUIのStopボタン、ACPのキャンセル）では、トップレベルのバックグラウンドバッチはキャンセルされません。`/stop` コマンド（ゲートウェイまたはCLI）、または所有するセッションを閉じる/リセットすると、そのバックグラウンドの子とその下にあるすべての同期的な子孫が終了します。停止された各子は、`status="interrupted"` と部分的な出力を伴う完了として引き続き戻ります

オーケストレーターからの同期的な単一タスクの委譲は、スレッドプールのオーバーヘッドなしに直接実行されます。

### 永続的なバックグラウンドの完了

バックグラウンドの委譲が終了すると、Hermesはその完了イベントを、通常の新規ターンのキューに公開する前に、アクティブなプロファイルの `state.db` に保存します。完了後、配信前にHermesが再起動した場合、保留中のイベントが復元され、同じ所有権チェックを通じてルーティングされます。競合するコンシューマーは永続的なクレームを使用するため、合成ターンを正常に受け入れたコンシューマーのみが配信を確認します。失敗した試行は再試行のためにクレームを解放します。

これはクラッシュ後に子の実行を再開するものではありません。実行中に所有者のプロセスが消えた委譲は、外部への副作用が起きたかどうかをHermesが証明できないため、`unknown` として記録されます。保留中および配信済みの記録は上限付きで、プロファイルローカルです。

### 子のバックグラウンドプロセスの通知 {#child-background-process-notifications}

サブエージェントが開始したバックグラウンドプロセス（例: `notify_on_complete` を付けた `npm ci`）は、子より長く存続するものには永続的なコンシューマーが必要なため、技術的にはその完了とパターン監視の通知を**親**の会話にルーティングします。デフォルトでは、それらの通知は親のチャットで**抑制**されます — 成果物は子の統合された委譲結果であり、子の内部ビルドによる会話途中の「プロセス終了」の羅列はノイズだからです。抑制されたイベントは、プロセスのセッションIDとサブエージェントのタスクIDとともにデバッグレベルでログに記録されるため、診断は可能なままです。

委譲の結果自体が抑制されることはありません。子のプロセス通知の配信を復元するには（それぞれに「Started by subagent …」という帰属行が付きます）:

```yaml
delegation:
  surface_child_process_notifications: true   # default: false
```

### プロセスを親に引き渡す

サブエージェントのバックグラウンドプロセスは、**サブエージェントが終了すると強制終了**されるため、子が `notify=true` で開始したCIウォッチャーやビルドは誰にも報告しません。子の `terminal` の結果にはその旨が示され（`notify_on_complete: false` と `subagent_note`）、子は終了する前に3つの誠実な選択肢を持ちます:

- **wait** — `process_manage(action="wait", session_id=...)` で待ち、結果を自分で報告する。
- **kill** — `process_manage(action="kill", ...)`。
- **hand off** — `process_manage(action="handoff", session_id=..., data="<one sentence: what it is for>")`。ランタイムはレジストリのロックの下で所有権を親に移します（子ごとに最大3つ。子が所有する実行中のプロセスのみが受け付けられ、それ以外はツールエラーになります）。その後、親の完了通知が `Handed off to you by a subagent… Purpose: …` とともに親のチャットに届き、親は自身のプロセスと同様にpoll/log/killできます。

子がまだ実行中の間に終了したプロセスには引き渡しは不要です: 子がそれを読み（`poll`/`wait`/`log`）、報告します。子がそれを読まなかった場合、終了コードと出力の末尾が `unread_completions` として結果に添付され、親に表示されます。強制終了も引き渡しもされずにまだ実行中のものは、その結果（`orphaned_processes`）と親の委譲通知で終了済みとして名前が示されるため、「ウォッチャーは実行中」がもはや真ではないことを、親は子の文章からではなく、必ずランタイムから知ることになります。CIウォッチャーについては、依然としてより良いパターンがあります: 子は事実（PR番号、SHA）を返し、親が自身のウォッチャーを起動します。

## モデルのオーバーライド

`config.yaml` を介して、サブエージェント用に別のモデルを設定できます。単純なタスクをより安価/高速なモデルに委譲するのに便利です。

```yaml
# In ~/.hermes/config.yaml
delegation:
  model: "google/gemini-flash-2.0"    # Cheaper model for subagents
  provider: "openrouter"              # Optional: route subagents to a different provider
```

省略した場合、サブエージェントは親と同じモデルを使用します。

Desktopでは、同じキーを **Settings → Model → Subagents** で設定します（[Desktop](/docs/user-guide/desktop#subagent-models-and-limits)を参照）。このページは **Applies to** で選択したプロファイルを編集し、**Apply** をクリックした後に起動されたサブエージェントに影響します。メインのモデルや、すでに実行中の子が変更されることはありません。

### コスト戦略: フロンティアのプランナー、安価なワーカー

問題を明確に規定されたサブタスクに分解するにはフロンティアレベルの判断が必要ですが、明確な目標、完全なコンテキスト、出力契約がすでに揃ったサブタスクを実行するには、通常それは必要ありません。一方で、トークンが消費されるのは子の側です — サブエージェントの並列バッチは通常、実行全体のトークンの大部分を消費するため、コストが実際にかかるのはワーカーのモデルです。メインのセッションをフロンティアモデルのままにして `delegation.model` を安価なモデルに固定すると、重要なところで計画の品質を保ちつつ、量の多いところで支出を削減できます:

```yaml
# ~/.hermes/config.yaml
model:
  default: "your-frontier-model"     # parent (planner) stays on the frontier model
delegation:
  model: "your-inexpensive-model"    # all delegate_task children run on this
  provider: "openrouter"             # optional: route children to a different provider
```

解決順序: `delegation.base_url`（直接のエンドポイント）が優先され、次に `delegation.provider`（ランタイムのプロバイダーシステムで解決される完全な認証情報バンドル）、どちらも設定されていない場合、子は親のプロバイダーと認証情報を継承します。`delegation.model` はすべての場合に適用され、空の場合、子は親のモデルを継承します。`delegation.base_url` とともに `delegation.provider` を設定すると、明示的なエンドポイントは維持されつつ、そのプロバイダーのリクエストのオーバーライドと最大出力トークン数が子に引き継がれます。明示的な `delegation.request_overrides` の辞書はすべての分岐で尊重され、それらのランタイム由来の値の上にマージされます（下記の[設定](#configuration)を参照）。

この固定はグローバルであることに注意してください: デフォルトの戦略では `delegate_task` にタスクごとのモデルパラメータはないため、バッチ内のすべての子が設定された委譲モデルで実行されます。より強力なモデルを必要とする品質重視のサブタスクには、そのセッションでは `delegation.model` を未設定のままにするか、委譲戦略プラグイン（下記）を使うか、タスクごとのモデルのオーバーライドをサポートする[kanbanボード](kanban.md#per-task-model-override)にタスクを渡してください。

### 委譲戦略（`delegation.backend`） {#delegation-strategies-delegationbackend}

`delegation.backend` は、各タスクがどのようにサブエージェントになるかを選択します。`default`（デフォルト）は上記のすべてです。戦略プラグインを使うと、あなたが定義した選択肢の中から、モデルがタスクごとに選べるようになります:

- **サブエージェントごとのプロファイル**（`profile_routes`）: 各子は、あなたのHermesプロファイルの1つとして、そのプロファイルのモデル、認証情報、スキル、ペルソナで実行されます。
- **名前付きのモデルマップ**（`model_map`）: タイトル付きの選択肢（`fast`、`deep`、...）を、それぞれ説明とプロバイダー/モデルとともに列挙し、モデルがタスクごとに1つを選びます。

どちらも公式の `advanced-delegation` プラグインから提供され、このプラグインは `hermes delegation config`（モデルルートの作成、編集、削除、プロファイルの選択）と `/delegation` スラッシュコマンドも追加します。`model_map` または `profile_routes` が有効な間は、`delegation.model` / `delegation.provider` は無効になります: ルートが決定します。

各戦略の設定は `delegation.backends.<backend name>` 配下に置かれます:

```yaml
delegation:
  backend: model_map
  backends:
    model_map:
      options:
        - name: fast
          description: Cheap and quick; lookups, summaries, simple edits.
          provider: openrouter
          model: google/gemini-3-flash-preview
        - name: deep
          description: Slow and careful; hard debugging and design work.
          provider: anthropic
          model: claude-opus-5
          reasoning_effort: high
          service_tier: fast            # optional; refused at spawn if this route has no fast tier
      default: fast                     # optional: option for tasks that set none
    profile_routes:                     # read when backend: profile_routes
      profiles:
        - name: coder
          description: Writes and refactors code; runs tests.
```

モデルが目にするのは、あなたが設定した名前と説明だけであり、生のプロバイダー、モデル、キーのフィールドを見ることはありません。バックエンドでルーティングされたタスクの各結果には `route` が付きます: バックエンド、選択肢またはプロファイルの名前、そして子が実際に実行されたプロバイダー、モデル、reasoning effort、速度ティア（フォールバックプロバイダーが引き継いだ場合は `fallback_activated: true`）です。独自に書く場合: [委譲プロバイダープラグイン](/docs/developer-guide/delegation-provider-plugin)。

**失敗は明示的で、黙って切り替わることはありません。** 選択されたバックエンドが存在しない（プラグインが未インストールまたは無効）、または実行できないと報告した場合、`delegate_task` はバックエンドと修正方法を示すツールエラーを返し、サブエージェントは起動しません。子を黙ってデフォルトのルートで実行することは決してありません。バッチ内では、バックエンドがルーティングできないタスク（不明な選択肢、選択されたバックエンドが受け付けないパラメータ、存在しないプロファイル、ルートが提供しない `service_tier`、不明な `reasoning_effort`、認証情報の欠落）は単独で拒否されます: その結果のエントリには `status: "error"`、理由、`route.refused: true` が付き、他のタスクは実行されます。独自の `fallback_providers` を持たないモデルルートは `delegation.fallback_providers` を使用します。ルートで `fallback_providers: []` を指定すると、そのルートのフォールバックは無効になります。プロファイルルートは、そのプロファイル自身のフォールバックチェーンを使用します。

**元に戻す。** `/delegation default`（`advanced-delegation` プラグインによる）は `delegation.backend` を `config.yaml` に保存し、次のセッション（`/new`）から適用されます: 実行中のチャットは、開始時のバックエンドでルーティングを続けます。モデルが目にするタスクごとの選択肢（選択肢やプロファイルの名前）はキャッシュされたツールリストの一部であり、両者は一緒に切り替わるためです。`delegation.backend` を手で編集した場合も同じ動作になります。`/delegation <backend> --now` は、現在のチャットのツールも次のターンで再構築するため、そこから新しいバックエンドでルーティングし、それを提示します。その代償としてプロンプトキャッシュのミスが1回発生します（いずれにせよツールを再構築するコンテキスト圧縮でも、保存されたバックエンドが取り込まれます）。チャットのバックエンドが受け付けないパラメータを送ったタスクは、バックエンド、パラメータ、修正方法（`/delegation <backend> --now`、または `/new`）を示すメッセージとともに拒否されます。そのバックエンドのデフォルトのルートで実行されることは決してありません。プラグインがない場合は、`hermes config set delegation.backend default` でデフォルトに戻せます。

:::note プロファイルルートは認証情報を共有する
`delegation.backends.profile_routes` にプロファイルを列挙すると、このプロファイルのサブエージェントは、そのプロファイルの認証情報、認証情報プール、`SOUL.md`、ターミナルポリシーを使用できるようになります。そのキーとターミナルアクセスをこのプロファイルのエージェントに使わせてもよいプロファイルのみを列挙してください。
:::

## `/review` コマンド {#the-review-command}

`/review` は、会話がたった今生成した作業 — PR、diff、コード、ドキュメント、設計 — をレビューすることだけを目的とした、独立した完全な権限を持つバックグラウンドのサブエージェントを起動します。あらゆるサーフェスで動作します: CLI、TUI、Desktopアプリ、すべてのゲートウェイのメッセージングプラットフォーム。

```
/review                       # review whatever the last 10 messages presented
/review focus on security     # add extra instructions for the reviewer
```

何が起きるか:

1. 直近10件のユーザー/アシスタントのメッセージが、レビュアーの出発点となる証拠としてスナップショットされます（ツールの出力とシステムメッセージは除外されます）。ゲートウェイでは、エージェントが解放されている場合（`agent.agent_cache.idle_ttl_secs` のアイドル後。デフォルトは1時間）、それらはセッションに保存されたトランスクリプトから取得されるため、放置していたセッションでも、先にメッセージを送ることなく `/review` が動作します。
2. レビュアーのサブエージェントは、`delegate_task` と同じバックグラウンドの委譲レールでディスパッチされます — 通常のサブエージェントの完全なツールセット（terminal、web、files、browser...）が与えられるため、抜粋から判断するのではなく、実際にPRを開き、diffを読み、コードを実行します。
3. レビュアーはプライマリエージェントの作業コンテキストを継承します: プライマリエージェントがロードしていたスキル（起動時のプリロード、またはセッション中に `skill_view` で）はブリーフィングで名前が示され、それらをロードしてその規約に照らして作業を評価するよう指示されます。他のすべてのサブエージェントと同様に、そのシステムプロンプトにはワークスペースのプロジェクトコンテキストファイル（AGENTS.md / CLAUDE.md / .cursorrules）も拘束力のある規約として埋め込まれます。
4. 終了すると、その完全なレビューが、通常のバックグラウンドのサブエージェントの完了として同じセッションに戻ります — プライマリエージェントはそれを見て対応できます（指摘事項の修正、フォローアップのプッシュ、あなたへの返信）。

典型的な流れ: メインのエージェントがPRを開き、あなたが `/review` と入力すると、あなたが作業を続けている間に別の目がそれを調査します。レビューは、PRを作成したエージェント宛てにチャットに戻ってきます。

ディスパッチでは「Review started. Results will return here.」とだけ表示されます。ライブのサブエージェントビューアーでは、ワーカーは短縮された1行のラベルで **Review: your focus**（素の `/review` の場合は **Review recent work**）として識別されます。レビュアーは引き続きあなたの完全な指示を受け取ります。クラシックCLIでは、コンポーザーの上のドックに経過時間と最新のアクティビティが表示されます。**Ctrl+T**（または **F6**）で、モデル、トランスクリプト、ステアリング、停止の制御を備えたロスターが開きます。同じレビューのラベルが、TUIとDesktopのサブエージェントビューアーにも表示されます。

### レビューモデル {#review-model}

デフォルトでは、レビュアーはメインのモデルで実行されます。専用のレビューモデルを固定するには、`config.yaml` で `auxiliary.review` を設定します:

```yaml
auxiliary:
  review:
    provider: openrouter               # or nous, anthropic, a direct base_url, ...
    model: anthropic/claude-opus-4.6   # a strong reviewer model
```

認証情報は、`delegation.provider` の固定とまったく同じように解決されます（完全なランタイムプロバイダーのバンドル: base_url、APIキー、api_mode）。`provider: auto` で `model` が空の場合は「メインエージェントのモデルを継承する」を意味し、これがデフォルトです。

`/review` は意図的に `/refine` とは分けられています: `/refine` はメモリとスキルを更新するために会話をレビューし、`/review` は会話が生み出した*作業成果物*をレビューします。

## 継承されるツールアクセス

`delegate_task` は、モデル向けの `toolsets` パラメータを受け付けません。各サブエージェントは親の有効なツールセットを継承するため、モデルが親の持たない能力を子に与えることはできません。委譲する作業に追加の能力が必要な場合は、会話を開始する前に親のツールを設定してください。

親が持っている場合でも、特定のツールはサブエージェントに対してブロックされます:
- `delegate_task` — リーフサブエージェント（デフォルト）に対してブロックされます。`role="orchestrator"` の子に対しては保持され、`max_spawn_depth` で制限されます。以下の[深さ制限とネストされたオーケストレーション](#depth-limit-and-nested-orchestration)を参照してください。
- `clarify` — サブエージェントはユーザーと対話できません
- `memory` — 共有された永続メモリへの書き込みはできません
- `send_message` — クロスプラットフォームの副作用はありません
- `cronjob` — 親の名前でさらに作業をスケジュールすることはできません

どちらのロールも `execute_code`（プログラムによるツール呼び出し）を保持するため、子は機械的な作業をまとめて処理できます。

## 最大反復回数

各サブエージェントには、何回ツール呼び出しのターンを取れるかを制御する反復制限（デフォルト: 250）があります。この制限は `config.yaml` でグローバルに設定され、すべての子に適用されます。`delegate_task` の呼び出しごとのパラメータではありません:

```yaml
# In ~/.hermes/config.yaml
delegation:
  max_iterations: 60   # lower it for fleets of simple tasks, raise it for long investigations
```

予算を使い切った子は `exit_reason: max_iterations` と `truncated: true` とともに戻るため、親は予算による停止と完了したタスクを区別できます。

## 子のタイムアウト

デフォルトでは、サブエージェントに**実時間のタイムアウトはありません**。子が失敗するのは実際に行っていることによってのみです — APIエラー、ツールエラー、反復予算への到達 — 委譲レベルのストップウォッチによって失敗することは決してありません。以前のリリースにはハードな上限（300秒、後に600秒）があり、正当に忙しい子をタスクの途中で強制終了させ続けていました: 深いコードレビュー、大規模なリサーチのファンアウト、低速な推論モデルは、ずっと着実に進捗しながらも、日常的に10分以上を必要とします。

本当にスタックした子は、上限が設定されているかどうかにかかわらず、あらゆるランタイムで引き続き検出されます: ハートビートの鮮度モニターが、各子の進捗シグナル（API呼び出し、ツールの開始、アクティビティのタイムスタンプの更新）を監視します。進捗が完全に止まったまま古さのしきい値 — ターン間で450秒のアイドル、ツール内では1200秒 — を超えた子は割り込まれ、その待機は**放棄**されます: 親には `status: "timeout"` のエントリが渡され、そのエラーは `Subagent stopped making progress after N API call(s) — no activity for 450s (heartbeat stale threshold); the pending worker was abandoned.` となります。この待機の終了は、背後にゲートウェイの非アクティブ監視がないワンショットの実行（`hermes chat -Q`、Bot Chatのワンショット、cron）でも行われるため、固まった子がターンやそのセッションのリースを永遠に保持することはもうありません。進行中のモデルの待機は引き続き進捗として数えられます — サブエージェントはプロバイダーを待っている間もアクティビティの時計を更新するため、遅いローカル/長いプレフィルの補完がストールとして扱われることはありません。

それでも上限が必要な場合（例: 無人のcron駆動の委譲でのコスト管理）は、インストールごとにオプトインします:

```yaml
delegation:
  child_timeout_seconds: 0     # default: 0 = no timeout
  # child_timeout_seconds: 1800  # opt-in inactivity cap (floor 30s)
```

正の値が制限するのは**合計の実行時間ではなく非アクティブ時間**です: これは、子が放棄されるまでに*まったく*進捗のない状態（完了したAPI呼び出しなし、ツールの変化なし、アクティビティの時計の更新なし）でいられる最長の時間です。進捗の兆候があるたびにウィンドウがリセットされるため、数分かかる補完を待っている子 — 以前は完了した作業を失っていたケース — が時間がかかるという理由で強制終了されることは決してなく、一方で本当に動かなくなった子は引き続き捕捉されます（そして進行中のリクエストは、呼び出しごとの古さの監視によって独立して制限されます）。`0` または負の値で上限は無効になります。いずれの場合も、下記のハートビートの鮮度モニターは有効なままです。

アイドルウィンドウの約80%の時点で、子はステアチャネルを通じて1行の `[delegation budget warning]` を受け取ります（次の反復の境界で配信）。これはどれだけアイドル状態だったかを伝え、今すぐ要約を返すよう指示するため、遅いが回復可能な子は、コンテキストを失う代わりに作業をまとめることができます。警告はアイドルウィンドウごとに1回発生し、進捗が再開すると再び有効になります。

設定された上限または古さのしきい値が発動すると、子の結果にはエラーメッセージと並んで構造化されたタイムアウトのメタデータが付くため、親やフックはテキストをパースすることなく、ストップウォッチによる強制終了を他の失敗と区別できます: `timeout_seconds`（実際に待機を終わらせた制限 — より長く設定された上限より先に発動した場合は古さのしきい値、それ以外は上限）、`timed_out_after_seconds`（実際の実時間）、`last_event_age`（待機が終了したときに子が沈黙していた時間 — 遅いプロバイダーと暴走を見分ける手早い方法）、`timeout_phase`（子が最初のリクエストに到達しなかった場合は `before_first_llm_call`、それ以外は `after_llm_calls`）。タイムアウト以外のエラーでは、4つすべてが `null` になります。

## 失敗の可視性

失敗したサブエージェント — 再試行不可能なプロバイダーエラー（404/400）、タイムアウト、クラッシュ、または使える出力なし — が黙っていることは決してありません:

- **CLI**: 委譲ツリーに1行の理由が表示されます: `⚠️ Subagent failed — "your goal": HTTP 404: model not found (after 12s)`。バッチ実行では、タスクごとの `✗` の完了行に理由が付け加えられます。
- **ゲートウェイプラットフォーム**（Telegram、Discord、Slack、...）: そのプラットフォームで `tool_progress` がオフ**であっても**、同じ簡潔な行が独立したチャット通知として配信されます。
- **親エージェント**: ツール結果のエントリには `status: "failed"` と完全な `error` テキストが付くため、モデルは対応できます（再試行、再ルーティング、報告）。

エラーテキストは、最も情報量の多い1行（トレースバックの羅列ではなく、例外メッセージ）に絞られ、長さが制限されます。

:::tip ゼロ呼び出しタイムアウト時の診断ダンプ
ハードな上限が設定されている場合、サブエージェントが**ゼロ**回のAPI呼び出しでタイムアウトした場合（通常は、プロバイダーに到達不能、認証失敗、またはツールスキーマの拒否）、`delegate_task` は、サブエージェントの設定スナップショット、認証情報解決のトレース、初期のエラーメッセージ、そして（子自身のものだけでなく）**すべての**生きているスレッドのスタックトレースを含む構造化された診断を `~/.hermes/logs/subagent-timeout-<session>-<timestamp>.log` に書き込みます — ネストされたヘルパースレッドを待って止まっている子は、全体像がなければ遅いプロバイダーと区別がつかないためです。
:::

## バックグラウンドのサブエージェントのストール検出

バックグラウンドの委譲（`delegate_task(background=true)`）は、**進捗ベースのストールモニター**によって監視されます — デフォルトで有効、設定不要です。実時間のタイムアウトとは異なり、進捗している子には、どれだけ長く実行されていても決して手を出しません。

モニターは、切り離された各子の進捗シグナル — API呼び出し数、現在のツール、最終アクティビティのタイムスタンプ（**ストリーミングされるトークンごと**、ツールの遷移、API呼び出しの境界で更新されるため、長い応答をストリーミング中の子は常に生きているとみなされます）— をサンプリングします:

1. **進捗している子には決して手を出しません。** 進むシグナルがあれば時計がリセットされます。
2. 進捗が完全に止まったまま古さのしきい値（450秒のアイドル、ツール内では1200秒 — 正当に遅いターミナルコマンドやWebの取得にはより高い上限が与えられます）を超えた子は**割り込まれ**、120秒の猶予ウィンドウが与えられます。時間内に後処理を終えた子は、通常の完了パスを通じて部分的な結果を配信します。
3. 戻ってこない子は、終端の `stalled` 完了イベントで強制的に確定されるため、所有するセッションは沈黙する代わりに結果を受け取り、非同期のスロットは新しい作業のために解放されます。

`stalled` イベントには、同期パスのタイムアウトのフィールドを反映した構造化メタデータが付きます: `stalled_after_quiet_seconds`、`stall_threshold_seconds`、`stall_phase`（`idle` / `in_tool`）、`stall_grace_seconds`。

これにより、固まったバックグラウンドの子が、プロセスの再起動までセッションを死んだように見せていた長年の障害モードが解消されました。根本的な固まり（数日間のゲートウェイ稼働後に、子が最初のAPI呼び出しでハングする）も根本から修正されました: 委譲された子は現在、OpenAI形式のAPIリクエストを、ネストされたワーカースレッド — 固まりが起きていた層 — ではなく、自身の会話スレッド上でインラインで実行します。ストールモニターは、それ以外のあらゆるもののためのセーフティネットとして残っています。


## 実行中のサブエージェントの監視（`/agents`） {#monitoring-running-subagents-agents}

TUIには `/agents` オーバーレイ（エイリアス `/tasks`）が付属しており、再帰的な `delegate_task` のファンアウトを一級の監査面に変えます。

- 実行中および最近終了したサブエージェントのライブツリービュー（親ごとにグループ化）
- ブランチごとのコスト、トークン、変更ファイルの集計
- 強制終了と一時停止の制御 — 兄弟を割り込むことなく、特定のサブエージェントを途中でキャンセル
- 事後レビュー: 各サブエージェントがターンごとの履歴を、親に戻った後でもステップごとに確認できます

### コンポーザーの上のライブアクティビティ

クラシックCLI、TUI、Desktopは、コンポーザーの上にライブのサブエージェントを自動的に表示します。ライブの数、タスク名、経過時間、最新のアクティビティを見ながら書き続けることができます。ターミナルのドックは画面の高さに応じて表示行数を制限し、隠れている追加のワーカーの数を表示します。Desktopは最大3つのワーカーをプレビューします。

| サーフェス | 展開して確認する | 選択したワーカーを制御する |
|---|---|---|
| クラシックCLI | **Ctrl+T**（または **F6**）でフルスクリーンのライブロスターが開きます。矢印で選択、**Enter** でトランスクリプトの末尾を開き、**PgUp/PgDn** でスクロール | **s** で別のステアリング入力が開きます。**x**、続いて **y** で停止を要求 |
| TUI | **Ctrl+T** または `/agents` でフルハイトのツリーが開きます。**Enter/t** でライブのトランスクリプトの末尾を開き、**d** で詳細を開きます（アーカイブ/リプレイでは Enter で引き続き詳細が開きます） | **e** でステアリングが開きます。**x** で選択したワーカーを停止、**X** でそのサブツリーを停止 |
| Desktop | コンポーザーの上の **Subagents** を展開し、ワーカーを選択してそのアクティビティと詳細を確認 | **Steer** でガイダンスをキューに入れ、**Stop** でそのワーカーの割り込みを要求 |

ターミナルのモニターを閉じると、既存のコンポーザーの下書きに戻ります。ステアリングは独自の入力を使い、配信ではなく**キュー投入（queued）**を確認として返します: 子はチェックポイントでガイダンスを消費します。停止によって無関係な兄弟が割り込まれることはありません。

**バックグラウンドプロセスはドックを共有します。** エージェントが `terminal(background=true)` で開始したもの（ビルド、テスト実行、開発サーバー、CIのポーラー）は、起動した瞬間にサブエージェントの行の下の **Processes** ブロックに表示され — `⚙ <command> · 42s · last: <latest output line>` — 終了するとその場で `✔ exit 0` / `✘ exit 1` / `✘ killed` に切り替わり、約60秒後にドックから消えます（会話内の完了通知が永続的な記録です）。クラシックCLIのモニターでは、プロセスの行はエージェントの下に置かれます: **Enter** でプロセスのログの末尾が表示され、**x** でそのプロセスだけを停止します。プロセスをステアリングすることはできません。TUIの `/agents` オーバーレイは、起動ツリーの下に同じブロックを一覧表示します（`/stop` ですべてのバックグラウンドプロセスが終了します）。Desktopは同じプロセスをコンポーザーの上のタイルとして表示します。

クラシックCLIまたはTUIのコンポーザーで **Ctrl+R** を押すと、ドックを複数行のプレビューと1行の網掛けの要約行の間で切り替えられます。ターミナルがファンクションキーを転送する場合は、**F7** もオプションのエイリアスとして使えます。要約にはライブの数と展開/復元のヒントが残り、スペースがあればアクティビティも追加されます。入力と送信は引き続き可能で、モニターを開閉しても下書きと挿入位置は保持されます。これはローカルの表示上の選択であり、保存される設定変更ではありません。

ライブのトランスクリプトの末尾は、上限付きの直近の抜粋であり、無制限の会話ブラウザではありません。ライブのレジストリから外れた子はドックから消えます。終了した作業を確認する場所は、引き続き完了メッセージとTUI/Desktopの履歴ビューです。最新のアクティビティは観測であり、完了率の見積もりではありません。

クラシックCLIの `/agents` と `/tasks` コマンドは、引き続きテキストの要約を出力します。**Ctrl+T**（または **F6**）は、親が処理中であっても使える即時のインタラクティブなモニターです。[TUI — スラッシュコマンド](../tui.md#slash-commands)を参照してください。

クラシックCLIとすべてのゲートウェイプラットフォーム（Telegram、Discord、Slack、...）では、`/agents` は、実行中の各子から直接サンプリングされた**子ごとのライブアクティビティ付きのバックグラウンドの委譲**も一覧表示します:

```
Background delegations: 1 running
- deleg_ab12cd34 · running · research the delegation stall monitor
  - child 1: 4 api calls · in web_search · active 12s ago
  - child 2: 7 api calls · between turns · active 3s ago
```

ストールモニターがフラグを立てた委譲は `stalling · no progress 450s — interrupting` と表示され、長く静かだが健全な子にはその静かな時間が表示されるため、「遅い」と「スタックしている」を一目で見分けられます。

## 実行中のサブエージェントのステアリング

子を割り込むと、進行中の作業が捨てられてしまいます。多くの場合、単に方向を変えたいだけです。

### 親エージェントから（モデル向け）

親エージェントは、子を起動したのと同じ `delegate_task` ツールで、自身の実行中の子をオーケストレーションします — 別の制御ツールはありません:

```json
{"action": "list"}
{"action": "steer", "subagent_id": "sa-0-1a2b3c4d", "message": "focus on pricing instead"}
{"action": "stop",  "subagent_id": "sa-0-1a2b3c4d"}
```

- **`list`** は会話のライブの子を返します: `subagent_id`、目標、ステータス、`running_seconds`、`accepting_steer`、ライブのトランスクリプトのパス。IDは起動ディスパッチの応答でも `subagent_ids` として返されます。
- **`steer`** は、実行中の子を停止せずに、軌道修正をキューに入れます（配信のセマンティクスは下記）。
- **`stop`** は、次の反復の境界で子を早期に終了させます。部分的な結果は、通常の完了メッセージとして引き続き会話に戻ります。

制御アクションはターン内で同期的に実行され（バックグラウンド化されることはありません）、呼び出し元自身の起動ツリーにスコープされ — 会話が別のセッションの子を見たり制御したりすることは決してありません — ターンごとのサブエージェント起動上限を消費しないため、上限に達した後でも `stop` は機能し続けます。

**終了した子を続ける。** `{"action": "continue", "subagent_id": "sa-0-1a2b3c4d", "message": "now add tests for it"}` は、すでに結果を返した子にフォローアップを与えます。子は同じルート（モデル、プロバイダー、プロファイル）とツールセットで再構築され、その履歴は保存されたトランスクリプトから読み込まれ、`message` が次のターンになります。子は `subagent_id` とセッションを維持し（`--resume` と同様にトランスクリプトに追記されます）、独自の `delegation_id` を持つ新しいバックグラウンドの委譲として実行されるため、結果は通常の完了として届きます。まだ実行中の子は `steer` を案内して拒否されます。また、実行後に親が切り替えたために、継承したルートが別のプロバイダーやエンドポイントに解決されるようになった子も拒否されます。子を続けられるのは、所有する会話（またはその起動ツリーの祖先）のみです。子が開始したバックグラウンドプロセスはなくなっているため、新しいターミナルが与えられ、それは子が停止したディレクトリとworktreeで開始されます。continueは通常のディスパッチです: 閉じたチャット、`max_concurrent_children`、`max_spawn_depth`、起動の一時停止は、起動を拒否するのと同じ方法でそれを拒否します。ワンショットのセッションや管理されたワーカーのセッションでは提供されません。

**再起動やクラッシュの後でも再開可能。** すべての子は、プロファイルの `state.db` に永続的な記録も保持するため、プロセスがまだそれを覚えている間だけでなく、ゲートウェイの再起動、強制終了、PCのクラッシュの後でも `continue` が機能します。再起動後、子のルートは自身のルーティングリクエストから再解決され、同じプロバイダーとエンドポイントに到達しなければなりません。完了せず、あなたや親によって停止されたのでもない子（ゲートウェイのシャットダウン、クラッシュ、利用上限、プロバイダーの拒否）は*再開可能*です: その完了エントリには `resume_mode` が付き、上限による失敗には `failure_resets_at`（プランのウィンドウの場合は `usage_limit` も）が付くため、いつ続ければ成功するかが分かります。`resume_mode` は次のいずれかです:

| `resume_mode` | 典型的な原因 | 続けるために必要なこと |
|---|---|---|
| `AUTO_AT` | リセット時刻のある利用/レート制限、一時的なプロバイダーエラー | `failure_resets_at` まで待つ |
| `AUTO_ON_BOOT` | ゲートウェイのシャットダウン、クラッシュ、強制終了 | なし。副作用を再実行する前にgitの状態と最後のツールを確認する |
| `ON_FIX` | クレジット、認証、モデルへのアクセス、アカウントポリシー、リクエスト形式のエラー | 先に原因を修正する |
| `REPAIR_THEN_CONTINUE` | 会話が収まらなくなった、または画像/推論のパートが拒否された | 先にトランスクリプトの修復が必要 |
| `HANDOFF` | この会話に対するプロバイダーの安全性による拒否 | 別のモデル、または親が作業を引き継ぐ |

再開可能な子のworktree（停止したときにターミナルがあった場所と、子が作成したworktree）は、その記録が存在する間、起動時のworktreeの一掃から保護されます: `delegation.resumable_ttl_hours`（デフォルト48）、プロファイルごとに最大 `delegation.max_resumable`（デフォルト32）。上限を超えると、最も古いものから保護が外れます。保護が終わると、通常の一掃によってツリーは削除される前に `refs/hermes/archive/` にアーカイブされます。完了した子と、あなたが停止した子は保護されません。`delegation.auto_resume: true`（デフォルトは `false`。下記参照）でオプトインしない限り、何かが自動的に再開されることはありません。

### 自動再開（`delegation.auto_resume`、オプトイン）

`delegation.auto_resume: true` の場合、ゲートウェイは停止したバックグラウンドの子を、`action='continue'` と同じクレームと `continue` のパスを通じて、子自身の会話とworktreeで、実際の原因を示すメッセージ（「Your run was stopped by a provider limit; continue where you left off.」）とともに自ら続けます。ゲートウェイは、提供しているすべてのプロファイルを15秒ごとに、それぞれそのプロファイル自身の設定、認証情報、`state.db` の下でチェックします。

- **再開されるもの:** 上限のリセット時刻を過ぎた `AUTO_AT` の子と、ゲートウェイが復旧した後の `AUTO_ON_BOOT` の子（ゲートウェイのシャットダウン、クラッシュ、強制終了）。
- **決して再開されないもの:** `ON_FIX`、`REPAIR_THEN_CONTINUE`、`HANDOFF` の子（クレジット、認証、モデルが見つからない、拒否、決定論的なリクエストエラー）、あなたや親が停止した子、停止時に再開が約束されなかった子（`auto_resume` がオフの間に停止された、またはクラシックなローカルCLIのように、どのゲートウェイも提供していない親の下で停止された子: これらには手動の `continue` のヒントが表示されます）、期限切れの記録、`max_resumable` によってworktreeの保護が外された記録、ネストされた子（オーケストレーターのサブエージェント自身のワーカー。代わりにそのオーケストレーターが再開されます）。
- **待機中は沈黙。** 自動再開が約束された停止では、親に完了は送られません。`delegate_task(action='list')` では、子は `waiting_to_resume` として「waiting to resume at 14:05 (attempt 1 of 2); gives up at 19:40」のような注記とともに表示されます。一部の子だけが待機しているバッチでは、完了は待機中のものを同じステータスで列挙し、失敗した委譲のビューはそれらを失敗として数えません。
- **最後に1回だけ報告。** 親は子ごとに1回だけ知らされます: 再開された実行自身の結果、またはスケジューラーが諦めたときの1回の終端の失敗です。諦めるのは、2回の自動試行を使い切ったとき、子の最初の停止から `delegation.auto_resume_deadline_minutes`（デフォルト360）が経過したとき、上限のリセットがその期限より後になることが分かっているとき（その場合はすぐに諦めます）、または恒久的な理由が現れたとき（例えばworktreeの保護が外された）です。すでに再開を約束された子は、待機中に `auto_resume` がオフにされた場合や、その記録が先に `delegation.resumable_ttl_hours` に達した場合でも、1回の失敗を受け取ります。`auto_resume` がオフの間は、`/stop`、セッションの終了、`action='stop'` で引き続きキャンセルされます。失敗には、理由、子の最後の要約、トランスクリプトの末尾、そして手動で続ける方法（`delegate_task(action='continue', subagent_id=..., message=...)`）または再ディスパッチの方法が含まれます。最後の試行中のクラッシュは、汎用的な「outcome unknown」ではなく、同じ諦めとして報告されます。
- **明示的なキャンセルのみ。** 待機中の再開をキャンセルするのは次のものだけです（記録は `superseded`、`stop` の場合は `stopped` になります。TTLまでは引き続き手動で続けられます）:
  - 待機中の子に対する `delegate_task(action='stop', subagent_id=...)`: 決して再開されず、そのworktreeの保護は解除されます（トランスクリプトは残ります）。
  - 親がその子を自ら続けた。
  - 親の会話が停止された（`/stop`）、リセットされた（`/new`）、閉じられた、削除された、または結果を受け取るためにもう存在しない。
  親が開始する他の作業は、同じリポジトリでの新しいサブエージェントも含め、それをキャンセルしません。これらの判断は、再開が開始されつつある間も優先されます: スケジューラーは記録をクレームし、1つの `state.db` トランザクションでそれらを再チェックし、子が実行される直前にも再度チェックするため、その間に届いたstop、`/stop`、`/new` はそれをキャンセルします（その試行は数えられません）。すでに実行中の子は、他の子と同様に `delegate_task(action='stop')` で停止されます。
- **待機中の子の重複はなし。** 目標が、再開を待っている親の子の1つの目標と（前後の空白を無視して）完全に一致する起動は、その `subagent_id`、再開される時刻、そして2つの進め方（それを待つか、先に `delegate_task(action='stop', subagent_id=...)` を実行してから再ディスパッチする）を示すツールエラーで拒否されます。バッチ内では、そのタスクのみが拒否され、兄弟は実行されます。このガードは `auto_resume` がオフのときは無効で、その子が期限を過ぎたか試行回数を使い切った時点で、スケジューラーが諦めを配信する前であっても拒否をやめます。
- **確認されていない副作用。** 再開のメッセージは子に次のことを伝えます: 最後のツール呼び出しに記録された結果がなく、その呼び出しが実行されたかどうかを確認できない場合、それを繰り返してはならず、その呼び出しを示す `BLOCKED:` で始まる結果で終了しなければなりません。
  同じ上限で停止した親は、再開された子の結果によって単に起こされます（通常の無人での起床の制限が適用されます）。
- **上限付き:** 子ごとに最大2回の自動試行で、各試行が実行される前に数えられるため、再開のたびにゲートウェイがクラッシュする子は2回の起動の後に停止します。記録にはその理由が残ります。再び上限に当たった再開は、試行が数えられた状態で待機に戻ります。再開は、プロファイル自身の `delegation.max_concurrent_children`（そのプロファイルの実行中のバックグラウンド単位のみを数える）の範囲内にとどまり、委譲の起動が一時停止されている間は待機し、親の会話自身のモデルルート（その `/model` の選択、チャネルのオーバーライド、または起動ポリシー）で実行され、同じリセットを待っている子は、一度にすべてではなく、1パスにつきプロバイダーのエンドポイントごとに1つずつ（15秒間隔で）開始されます。
- **コスト:** 再開された子は誰も見ていないところでトークンを消費し、その結果によって開始される親のターンも同様です。無人での支出を望まない場合はオフのままにしてください。

### TUI / ゲートウェイから（セッション向け）

`tools/delegate_tool_registry.py` の `steer_subagent(subagent_id, text)` は、`interrupt_subagent()` の方向転換側の対となるものです: [`/steer`](../../reference/slash-commands.md) と同じ仕組みでライブの子にテキストをキューイングします — テキストは次の反復の境界で子の最後のツール結果に付け加えられ、進行中のツール呼び出しが中断されることはなく、子はそれを帯域外のユーザーメッセージとして見ます。プログラムによるホストは、`subagent.interrupt` の隣にあるセッションスコープの `subagent.steer` ゲートウェイRPCを通じてこれにアクセスします:

```json
{"method": "subagent.steer", "params": {"session_id": "owning-ui-session", "subagent_id": "sa-0-1a2b3c4d", "text": "focus on pricing instead"}}
```

サブエージェントのIDは `delegation.status`（または `list_active_subagents()`）から取得します — `subagent.interrupt` がそれを取得するのと同じ場所です。ゲートウェイは、その子を起動した正確なライブのUI/ゲートウェイのセッションからのみステアリングを受け付けます。欠落した、別の、曖昧な、または古い/再利用されたセッションIDは拒否されます。グローバルなサブエージェントIDを知っていることは権限になりません。プロセス内の直接の呼び出し元は、意図的にスコープなしのヘルパーの契約を保持しています。

**キュー投入は配信ではありませんが、偽の成功になることも決してありません。** `"queued"` の応答は、子の完了の境界より前にテキストが受け付けられたことを意味し、必ずしも子がそれを見たことを意味しません。受け付けと完了は同期されています: 子がまだテキストを消費できるか、その正確なテキストが `pending_steer` として結果に取り込まれるかのどちらかです。クローズ後の呼び出しは `"rejected"` を返します。子がステアを受け付けたものの、すでに最終回答を生成していた場合、親が受け取る完了エントリはそれを `missed_steer` として保持し、要約に注記が付け加えられます:

```
[steer did not land — the subagent finished before it could be delivered: focus on pricing instead]
```

そのため親（またはそれを操作するオペレーター）は、ステアリングされた子と古い指示で終了した子を区別でき、それが届いたと信じる代わりに、フォローアップとしてガイダンスを再発行できます。

## ライブのトランスクリプト

すべての `delegate_task` のディスパッチは、**タスクごとに追記専用の人間が読めるログ**も1つ作成するため、あなた（または親エージェント）は統合された要約を待つ代わりに、サブエージェントの作業をリアルタイムで見ることができます:

```
<hermes_home>/cache/delegation/live/<delegation_id>/task-<n>.log
```

ディスパッチの応答にはパスが `live_transcripts` として含まれ、ファイルはディスパッチ時に事前作成されるため、これはすぐに機能します:

```bash
tail -f ~/.hermes/cache/delegation/live/deleg_ab12cd34/task-0.log
```

各行にはタイムスタンプが付き、子のアシスタントのテキスト、思考の断片、ツール呼び出し（`-> tool_name({args})`）、ツールの結果、最終的なステータスのマーカーが表示されます。同じディレクトリにある `manifest.json` はバッチ（目標、タスク数、タスクごとのステータス）を記述します。ログは完了後も保持され — 要約と並ぶ完全な忠実度の運用記録としても機能します — 7日より古いディレクトリは、新しいディスパッチ時に自動的に削除されます。`cache/delegation` 配下にあるため、リモートのターミナルバックエンド（Docker/Modal/SSH）からも読むことができます。

## 深さ制限とネストされたオーケストレーション {#depth-limit-and-nested-orchestration}

デフォルトでは、委譲は**フラット**です。親（深さ0）が子（深さ1）を起動し、それらの子はそれ以上委譲できません。これにより、暴走する再帰的な委譲を防ぎます。

複数段階のワークフロー（リサーチ → 統合、またはサブ問題に対する並列オーケストレーション）のために、親は独自のワーカーを委譲*できる***オーケストレーター**子を起動できます。

```python
delegate_task(
    goal="Survey three code review approaches and recommend one",
    role="orchestrator",  # Allows this child to spawn its own workers
    context="...",
)
```

- `role="leaf"`（デフォルト）: 子はそれ以上委譲できません。フラット委譲の動作と同一です。
- `role="orchestrator"`: 子は `delegation` ツールセットを保持します。`delegation.max_spawn_depth`（デフォルト **1** = フラット。そのため `role="orchestrator"` はデフォルトでは何もしません）で制限されます。`max_spawn_depth` を2に上げると、オーケストレーター子がリーフの孫を起動できるようになります。3以上でより深いツリーになります。上限はありません — コストが実質的な制限です。
- `delegation.orchestrator_enabled: false`: `role` パラメータに関わらず、すべての子を `leaf` に強制するグローバルなキルスイッチです。

**コストの警告:** `max_spawn_depth: 3` と `max_concurrent_children: 3` の場合、ツリーは3×3×3 = 27の同時リーフエージェントに達する可能性があります。レベルが1つ増えるごとに支出が乗算されます。`max_spawn_depth` は意図的に上げてください。

**ワンショットの実行には別の上限があります。** `hermes chat -q` / `--oneshot` のセッションが起動できるサブエージェントは、合計で最大 `delegation.oneshot_max_children`（デフォルト `2`、`0` = 無制限）です。ワンショットの実行には結果を受け取る後続のターンがなく、ベンチマークの軌跡では、その起動のほとんどが並列の作業ではなく「自分の作業を独立してレビューする」ものでした — そのような子はそれぞれ、コールドなシステムプロンプトのコストを再び払い、リポジトリを読み直します。インタラクティブなセッションとゲートウェイのセッションには影響しません。ワンショットは `delegate_task` の呼び出し内で子を合流させるため、そのスキーマにはライブ制御のパラメータ（`action` のlist/steer/stop、`subagent_id`、`message`）が含まれません。

## 有限のチャット実行 {#finite-chat-runs}

チャットが回答して終了する場合（`-Q`、`chat --oneshot`、または非TTYのstdioでのクエリ）、`delegate_task` は子を待ち、同じターンでその結果を親に返します。バッチの子は、`delegation.max_concurrent_children` の範囲で引き続き並列に実行されます。親は、CLIが終了する前の最終応答でそれらの結果を使えます。

- **自動の合流:** オプトインやバックグラウンドモードのオーバーライドは必要ありません。インタラクティブなTTYのチャットはバックグラウンドの委譲を維持し、メッセージングのセッションは `delegation.gateway_mode` に従います（下記参照）。
- **入力ごとのポリシー:** CLIは、インタラクティブなセッションを再開する場合も含め、受け入れたプロンプトとともに有限の消費を記録します。そのセッションの作成ポリシー、兄弟のビューアー、デーモンの環境は変わりません。
- **既存のセーフガード:** 委譲の制限、タイムアウト、キャンセル、`approvals.single_query_mode`（`-q` のターン。`hermes -z` のターンは無人）は引き続き適用されます。合流によってコマンドが自動承認されたり、子の結果の成功が保証されたりすることはありません。結果を確認し、成果物を検証してください。管理された/安全なワーカーは、子の登録の契約が利用可能になるまで、引き続き子の委譲を拒否します。
- **別の制限:** `--run-budget` は引き続きゲートウェイのチャットではサポートされません。合流には必要ありません。`terminal.oneshot_completion_wait_seconds` は委譲のタイムアウトではありません。正規のターミナル通知は引き続きゲートウェイが所有します。

CLIを閉じると、ゲートウェイが所有するターンは終了されるのではなく切り離されます。子の実行は引き続きその所有者のプロセスローカルです: 所有者の再起動を生き延びなければならない作業には、永続的なスケジューラーを使ってください。

## 中間メッセージのないメッセージングチャット

メッセージングプラットフォームでは、バックグラウンドの委譲は親に1行のステータスを送ってターンを終えるよう指示します。そのプラットフォームで `display.interim_assistant_messages` がオフの場合、そのステータスがターンの最終回答になるため、チャットには「作業中」のメッセージが届き、その後に本当の回答が2つ目のメッセージとして届くことになります。`delegation.gateway_mode` がこれを制御します:

```yaml
delegation:
  gateway_mode: auto   # auto (default) | inline | background
```

- **`auto`:** 解決された `display.interim_assistant_messages`（グローバルの値、`display.platforms.<platform>` のオーバーライド、またはプラットフォームのデフォルト）がオフのメッセージングチャットは、ターン内で子を合流させます。親は `delegate_task` の呼び出しの中で待ち、そこで結果を受け取り、完成した1つの回答を送ります。中間メッセージがオンのチャット、APIサーバー、ローカルのセッション、Webhookはバックグラウンドの委譲を維持します。
- **`inline`:** すべてのゲートウェイのセッションがターン内で子を合流させます。
- **`background`**（エイリアス `async`）: すべてのゲートウェイのセッションがバックグラウンドの委譲を維持します。

インラインのセッションの `delegate_task` は、結果が呼び出しの中で返ることを示し、ライブ制御のパラメータ（`action` のlist/steer/stop、`subagent_id`、`message`）を含みません。ワンショットの実行と同じスキーマです。待っている間、入力中のインジケーターは表示されたままで、ターンは長いツール呼び出しと同じように振る舞います。`/stop` は子を停止し、デフォルトの `busy_input_mode: interrupt` の下ではフォローアップのメッセージでも停止します（各子は部分的な出力を伴う中断された結果を返します）。`queue` の下では、フォローアップはターンを待ちます。ネストされた委譲は変わりません。

`agent.gateway_notify_interval`（デフォルト180秒）を超えて実行されるインラインのターンには、引き続き定期的な「まだ作業中」の通知が送られます。これは `display.long_running_notifications` で別途制御され、Telegram、Slack、Discord、WhatsAppではデフォルトでオンです。ターンごとに1つのメッセージにするには、そのプラットフォームでこれも `off` に設定してください（`generic` は通知の文言を変えるだけです）:

```yaml
display:
  interim_assistant_messages: false
  platforms:
    telegram:
      long_running_notifications: false
```

このモードはセッションのツールスキーマの一部であり、会話とともに固定されます。`gateway_mode` や `interim_assistant_messages` の変更は、次のセッション（`/new`）から適用されます。実行中のチャットは、ゲートウェイの再起動、エージェントキャッシュの退避、コンテキストの圧縮、`/reload-mcp` をまたいでも、開始時のモードを維持します。スケジュールされたハートビートのターンは、自身についてのみ中間メッセージをミュートし、チャットのモードは変えません。1つの例外: Hermesの更新後の最初のターンは、新しいコードからセッションのツール定義を再構築するため、チャットはそのターンで現在の設定を採用します。

`tools.tool_search.defer` に `delegate_task` を列挙すると、そのセッションではインラインがオフになります: モデルは `tool_describe` を通じて通常の（バックグラウンドの）`delegate_task` のスキーマを読み込み、委譲はモデルが見るスキーマに従います。

## 寿命と耐久性

:::warning バックグラウンドの完了の永続性は、永続的な実行ではない
トップレベルのモデル向けの `delegate_task` 呼び出しは、セッションが後からの配信をサポートしている場合、自動的にバックグラウンドで実行されます。Hermesはすぐにハンドルを返し、子またはバッチが終了した後に結果が会話に戻ります。オーケストレーターのサブエージェントは、戻る前に結果を統合しなければならないため、現在のターンでワーカーを待ちます。ステートレスなリクエスト/レスポンスのエンドポイントは、切り離された結果を後から配信できない場合、同期実行にフォールバックします。

- 通常のフォローアップのメッセージではバックグラウンドの子はキャンセルされず、現在のターンを停止してもキャンセルされません: Ctrl+C、Esc、Desktop/TUIのStopボタン、ACPのキャンセルはターンを終わらせるだけです。`/stop` コマンド（ゲートウェイの `/stop` — ディスパッチしたターンが終わった後にセッションがアイドルの場合も — またはCLIの `/stop`）は、セッションの実行中のバックグラウンドの委譲を終了させ、所有するセッションを閉じる/リセットしても同じことが起きます。
- 明示的なセッションのクローズ/リセットは、そのセッションのバックグラウンドの子を割り込みます。CLIとTUIでは、セッションを所有するのはゲートウェイであり、クライアントはそれを表示するだけです: 最後のビューアーが終了するか `/new` を実行すると（TUIの再開による切り替えも含む）、ゲートウェイはそのセッションのバックグラウンドの子をただちに割り込み、ビューアーが再びセッションを開くまで、そのセッションの新しい子を拒否します。単なる切り離しでは何もキャンセルされません: Desktopを閉じる、接続が切れる、または別のビューアーがまだ接続している間に終了しても、作業は実行されたままです。バックグラウンドプロセス（`terminal(background=True)`）は、どちらの場合も実行され続けます。
- CLI、TUI、Desktop、Webのセッションに対するバックグラウンドの子の最終結果（中断されたものを含む）や `notify_on_complete` のプロセスの終了は、ビューアーが接続されているかどうかにかかわらず親のターンとして実行されるため、ノートPCがスリープしても、接続が切れても、タブが閉じられても、作業は続きます。閉じたチャット（終了、`/new`、またはTUIの再開やブランチの切り替え）への結果は、代わりにそのセッションに注記として書き込まれ、次のターン（例えば `hermes chat --resume` の後）がそれを読みます。パターン監視の通知、タスクごとの早期の失敗通知、手動のcron実行の結果（`cronjob(action='run')`）も、ビューアーが接続されていない間は注記になります。失敗した子（エラー、タイムアウト、プロバイダーの拒否、ストール監視が停止しなければならなかったスタックした子、または再起動後の不明な結果）を含む結果は、誰も見ていない間、親を連続して最大3回起こします: それ以上の失敗は、あなたが接続するかメッセージを送るまで注記として書き込まれるため、同じ失敗に再ディスパッチし続ける親がループすることはありません。成功した結果と `notify_on_complete` のプロセスの終了（終了コードにかかわらず）にはそのような制限はありません。同じモデルで繰り返される理由（安全フィルターによる拒否 `content_policy_blocked`、請求、認証、不明なモデル）で子が失敗した場合、結果は親に、変更せずに再ディスパッチしないよう伝えます: 別のモデルを使うか、それを報告してください。メッセージングのチャットにはビューアーがなく、変更はありません: その完了は引き続きターンを開始します。
- Hermesのプロセスの再起動では、実行中の子は再開**されません**。どの副作用が起きたかをHermesが証明できないため、その試行は `unknown` になります。
- 再起動前に完了したものの結果が配信されなかった子は復元され、所有するセッションの通常のチェックを通じてルーティングし直されます。
- 停止された子は構造化された結果（`status="interrupted"`、`exit_reason="interrupted"`）を返し、その `summary` は停止前に子が生成した最後のテキストです（割り込みのプレースホルダーは `error` に移ります）。停止は起動ツリーを再帰的に下っていき — オーケストレーターの子の同期的なワーカーが先に割り込まれ、その部分的な結果は子自身の中断された結果にまとめられます — 各バックグラウンド単位の結果は、通常の完了通知（`Subagent Task Interrupted: …`）としてすぐに会話に戻るため、子が予算を使い切るのを待つものは何もありません。

セッションのクローズやプロセスの再起動を生き延びなければならない**永続的な実行**には、次を使用してください。

- `cronjob`（action=`create`） — 別のエージェント実行をスケジュールします。親ターンの割り込みの影響を受けません。
- `terminal(background=True, notify_on_complete=True)` — エージェントが他のことをしている間も実行を続ける長時間実行のシェルコマンド。
:::

## 主要な特性

- 各サブエージェントは**独自のターミナルセッション**を取得します（親とは別）
- サブエージェントは親の有効なツールセットを継承します。モデルが呼び出しごとにそれらを選択したり広げたりすることはできません
- **ネストされた委譲はオプトイン** — `role="orchestrator"` の子のみがそれ以上委譲でき、それも `max_spawn_depth` がデフォルトの1（フラット）から上げられた場合のみです。`orchestrator_enabled: false` でグローバルに無効化できます。
- リーフサブエージェントは次を呼び出せ**ません**: `delegate_task`、`clarify`、`memory`、`send_message`、`cronjob`。オーケストレーターサブエージェントは `delegate_task` を保持しますが、他のブロックは維持されます。どちらのロールも `execute_code`（プログラムによるツール呼び出し）を保持するため、子は推論の反復を消費する代わりに機械的な作業をまとめて処理できます。
- **キャンセルは所有権に従う** — `/stop` または所有するセッションのクローズ/リセットで、そのバックグラウンドの子とその下の同期的な子孫が終了します。それぞれが部分的な出力を伴う中断された完了を返します
- 最終的な要約のみが親のコンテキストに入り、トークン使用量を効率的に保ちます
- サブエージェントは親の **APIキー、プロバイダー設定、認証情報プール**を継承します（レート制限時のキーローテーションを可能にします）

## worktreeの分離

デフォルトでは、サブエージェントは親の作業ディレクトリを共有します — リサーチや読み取り中心の作業には問題ありませんが、同じリポジトリを編集する並列の子は衝突する可能性があります。`delegation.worktree_isolation: true` を設定すると、各子にリポジトリの現在の `HEAD` から分岐した独自のgit worktreeが与えられます（Muse Codeの `--subagent-worktree-isolation` に着想を得たもの）:

```yaml
delegation:
  worktree_isolation: true   # default: false
```

分離がオンの場合:

- 各子は、独自のブランチ `hermes-subagent/subagent-<id>` 上の `<repo>/.worktrees/subagent-<id>` でターミナルを開始し、その目標メッセージはそこで作業してコミットするよう指示します。
- 親のチェックアウトには手が付けられません。子が互いの編集を壊すことはありません。
- 子が終了すると、その結果のエントリに `worktree` フィールドが追加され、`path`、`branch`、`commits`（ベースより先行しているもの）、`dirty` が報告されます。親は各ブランチをレビューまたはマージします（`git log <branch>`、`git merge <branch>`）。
- **コミットがなくツリーがクリーンなまま**残されたworktreeは**自動的に削除されます**（`pruned: true`）。作業を保持しているものはすべて残されます。
- 削除には証明が必要です。gitの検査プローブが失敗した場合 — または確定処理自体がエラーになった場合 — worktreeとブランチは残され、エントリには `inspection_failed: true` と `note` が付きます — その場合 `commits`/`dirty` は測定値ではなくデフォルト値なので、子が何も生成しなかったと決めつけずにworktreeを確認してください。

範囲: オプトイン、gitのみ、ローカルのターミナルバックエンドのみ。gitでないディレクトリ、docker/ssh/modalバックエンド、またはworktreeの作成が失敗した場合、この設定は黙って現在の共有ワークスペースの動作に縮退します — エラーになることはありません。

## delegate_task と execute_code の比較

| 要素 | delegate_task | execute_code |
|--------|--------------|-------------|
| **推論** | 完全なLLM推論ループ | 単なるPythonコードの実行 |
| **コンテキスト** | 新しい独立した会話 | 会話なし、スクリプトのみ |
| **ツールアクセス** | 推論を伴うすべての非ブロックツール | RPC経由の7ツール、推論なし |
| **並列性** | デフォルトで10の同時サブエージェント（設定可能） | 単一スクリプト |
| **適した用途** | 判断を要する複雑なタスク | 機械的な複数ステップのパイプライン |
| **トークンコスト** | 高い（完全なLLMループ） | 低い（stdoutのみ返される） |
| **ユーザー対話** | なし（サブエージェントは確認できない） | なし |

**経験則:** サブタスクが推論、判断、または複数ステップの問題解決を要する場合は `delegate_task` を使用してください。機械的なデータ処理やスクリプト化されたワークフローが必要な場合は `execute_code` を使用してください。

## 設定 {#configuration}

```yaml
# In ~/.hermes/config.yaml
delegation:
  max_iterations: 250                       # Max turns per child (default: 250)
  # max_concurrent_children: 10             # Parallel children per batch (default: 10)
  # independent_completions: false          # true = each task/group returns as it finishes (default: one message per call)
  # gateway_mode: auto                      # auto | inline | background (see Messaging chats without interim messages)
  # worktree_isolation: false               # Give each child its own git worktree (see Worktree Isolation above)
  # max_spawn_depth: 1                      # Tree depth (floor 1, no ceiling, default 1 = flat). Raise to 2 to allow orchestrator children to spawn leaves; 3+ for deeper trees.
  # orchestrator_enabled: true              # Disable to force all children to leaf role.
  # resumable_ttl_hours: 48                 # How long a stopped child stays continuable after a restart, worktree kept
  # max_resumable: 32                       # Resumable children per profile whose worktree is kept (oldest unpinned first)
  # auto_resume: false                      # Opt-in: the gateway resumes limit/restart-stopped children itself (spends tokens unattended)
  # auto_resume_deadline_minutes: 360       # Give up (one failure to the parent) this long after a child's first stop
  model: "google/gemini-3-flash-preview"             # Optional provider/model override
  provider: "openrouter"                             # Optional built-in provider
  api_mode: anthropic_messages                       # optional; auto-detected from base_url for anthropic_messages endpoints

# Or use a direct custom endpoint instead of provider:
delegation:
  model: "qwen2.5-coder"
  base_url: "http://localhost:1234/v1"
  api_key: "local-key"
  # api_mode: "anthropic_messages"  # Optional. Wire protocol override for base_url ("chat_completions", "codex_responses", or "anthropic_messages"). Empty = auto-detect from URL (e.g. /anthropic suffix). Set explicitly for endpoints the heuristic can't classify (Azure AI Foundry, MiniMax, Zhipu GLM, LiteLLM proxies, …).

# Send per-child request settings on every subagent API call — e.g. OpenRouter
# routing hints when delegating straight to openrouter.ai via base_url:
delegation:
  model: "deepseek/deepseek-v4-flash-0731"
  base_url: "https://openrouter.ai/api/v1"
  api_key: "sk-or-..."
  request_overrides:
    extra_body:
      provider:
        sort: throughput   # children route to the fastest OpenRouter provider
```

`base_url` がAnthropic互換のエンドポイント — 例えば `/anthropic` で終わるパス、Azure FoundryのClaudeルート、MiniMaxの `/anthropic` プロキシ — を指している場合、`api_mode` は `anthropic_messages` として自動検出されるため、何も設定しなくてもサブエージェントは正しいワイヤー形式を使います。自動検出の推測が間違っている場合（まれ）は、`api_mode` を明示的に設定してください。

サブエージェントは親と同じところで圧縮します: `compression.threshold` × ウィンドウ（デフォルトは0.50）、またはグローバルの `compression.threshold_tokens` の上限が設定されていてそれより低い場合はその値です。`delegation.compression_threshold_tokens`（デフォルト `0`、オフ）は、子の圧縮の*トリガー*にオプションの絶対的な上限を追加し、それと比率のしきい値の低い方として適用されます。リクエストのペイロードや親に影響することはありません。16000以上のトークン数で有効になります。`true` や `"200k"` は設定エラーで、警告が出て無視されます。これがデフォルトでオフになっているのは、1,393エージェントの実行のリプレイで、キャッシュのプレフィックスが無傷であれば200K〜400Kの上限のコストが互いに5%以内に収まり、また圧縮のたびに詳細を失う可能性があるためです。

`delegation.request_overrides` は、**3つすべての**解決の分岐 — 直接の `base_url`、名前付きの `provider`、純粋な継承 — で機能するため、常に効果を発揮します。トップレベルのキーはAPIのkwargs（例: `service_tier`）です。`extra_body` のサブ辞書は、リクエストの `extra_body` にマージされます。明示的な値は、ランタイム由来または親由来のオーバーライドの**上に**マージされます: 明示的なトップレベルのキーが優先され、`extra_body` は1階層だけディープマージされるため、プロバイダー独自のリクエストの性格（例: `thinking: {type: disabled}`）は、あなたのキーがそれを再定義しない限り維持されます。詳細は[設定 → 委譲](../configuration.md#delegation)を参照してください。

:::tip
エージェントは、タスクの複雑さに基づいて委譲を自動的に処理します。明示的に委譲を依頼する必要はありません。理にかなっている場合にエージェントが自動的に行います。
:::
