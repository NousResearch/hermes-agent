# 永続ゴール（`/goal`）

`/goal` は、ターンをまたいで存続する標準的な目標を Hermes に与えます。各ターンの後、軽量なジャッジモデルが、アシスタントの最後の応答によってゴールが満たされたかどうかをチェックします。満たされていなければ、Hermes は継続プロンプトを同じセッションに自動的にフィードバックし、作業を続けます — ゴールが達成されるか、あなたが一時停止/クリアするか、ターンの予算を使い切るまで。

これは **Ralph ループ**に対する私たちの解釈で、OpenAI の Eric Traut による [Codex CLI 0.128.0 の `/goal`](https://github.com/openai/codex) から直接着想を得ています。中心的なアイデア — ターンをまたいでゴールを生かし続け、達成するまで止めない — は彼らのものです。ここでの実装は独立しており、Hermes のアーキテクチャに合わせて適応されています。

## いつ使うか

`/goal` は、毎ターン再プロンプトせずに Hermes に自律的に反復してほしいタスクに使います:

- 「`src/` のすべての lint エラーを修正し、`ruff check` が通ることを確認して」
- 「機能 X をリポジトリ Y から、テストも含めて移植し、CI をグリーンにして」
- 「実行途中の圧縮でセッション ID がときどきずれる理由を調査し、レポートを書いて」
- 「EXIF の日付でファイルをリネームする小さな CLI を作り、photos/ フォルダで試して」

エージェントが 1 ターンで止まるタスクに `/goal` は必要ありません。*そうでなければ「続けて」を 3 回言わなければならない*ようなタスクこそ、これが真価を発揮する場面です。

## ゴールとカンバン: どちらを使うべきか

`/goal` と [カンバン](./kanban) はどちらも、再プロンプトなしで Hermes に作業を続けさせるため、一方がもう一方につながっていると考えたくなるかもしれません。しかしそうではありません — 境界ははっきりしています:

- **`/goal` は単一セッションです。** ループは、ジャッジが完了と言うまで *この* 会話に継続プロンプトをフィードバックします。ゴールを設定してもカンバンカードが作成されることはなく、別のプロファイルに作業を割り当てることも、ファンアウトすることもありません。暗黙的であれボードへのハンドオフは一切ありません。
- **カンバンは多数のタスクのボードです。** 各カードは、独自のセッションを持つ独自のワーカープロセスにディスパッチされます。カード、依存関係、担当者、ハンドオフはボード上に存在します — `/goal` の中ではありません。
- **重なりは意図的なもので、小さなものです。** `--goal` 付きで作成されたカンバンカードは、`/goal` と同じ Ralph スタイルの継続エンジンを実行します — ただし *その 1 枚のカードのワーカーセッション内で* です。借りているのはエンジンであって、ボードではありません。[ゴールモードのカード](./kanban#goal-mode-cards---goal) を参照してください。

| やりたいこと | 使うもの |
|---|---|
| このチャットで 1 つのタスクを完了するまで反復し続ける | `/goal <text>` |
| 依存関係、ハンドオフ、複数プロファイルを伴う多数の独立したタスク | [カンバン](./kanban) — `hermes kanban create …` |
| 受け入れ基準を満たすまで反復し続けるべき、ボード上の 1 枚のカード | `--goal` 付きのカンバンカード |

:::note
作業をボードに載せたい場合は、自分で載せてください（`hermes kanban create …`）— `/goal` がやってくれることはありません。逆もまた同様です: このチャットでゴールを一時停止、再開、クリアしても、カンバンカードが作成、クレーム、移動されることはありません。
:::

## クイックスタート

```
/goal Fix every failing test in tests/hermes_cli/ and make sure scripts/run_tests.sh passes for that directory
```

表示されるもの:

1. **ゴール受理** — `⊙ Goal set (20-turn budget): <your goal>`
2. **ターン 1 実行** — Hermes は、あなたがゴールを通常のメッセージとして送ったかのように作業を開始します。
3. **ジャッジ実行** — ターンの後、ジャッジモデルが `done`、`continue`、`blocked` のいずれかを判断します。
4. **必要ならループ発火** — `continue` の場合、`↻ Continuing toward goal (1/20): <judge's reason>` が表示され、Hermes が自動的に次のステップを実行します。
5. **終了** — 最終的に `✓ Goal achieved: <reason>` または `⏸ Goal paused — N/20 turns used` のいずれかが表示されます。

## コマンド

| コマンド | 機能 |
|---|---|
| `/goal <text>` | 標準ゴールを設定（または置換）します。最初のターンを即座に開始するので、別途メッセージを送る必要はありません。メッセージングプラットフォームでは、写真やファイルのキャプションとして送った `/goal` は、その添付ファイルを開始ターンに保持します。 |
| `/goal -- <text>` | 制御語で始まるゴールテキストを設定します（`/goal -- pause the nightly cron`）。`--` がないと、`resume`/`continue`/`unpause`/`pause`/`status`/`show`/`unwait` の後に単語が続く場合は制御コマンドが実行され、残りは無視されます。 |
| `/goal draft <text>` | 平易な言葉の目標から構造化された完了契約を起草し、それを設定します。[完了契約](#completion-contracts) を参照してください。 |
| `/goal show` | アクティブなゴールの完了契約を表示します。 |
| `/goal` または `/goal status` | 現在のゴール、そのステータス、使用ターン数を表示します。 |
| `/goal pause` | ゴールをクリアせずに自動継続ループを停止します。 |
| `/goal resume` | ループを再開します（ターンカウンターをゼロにリセット）。 |
| `/goal clear` | ゴールを完全に破棄します。 |
| `/goal wait <pid> [reason]` | ループをバックグラウンドプロセスに待機（パーク）させます — プロセスの実行中は毎ターンエージェントを再度つつくのをやめ、プロセスが終了すると自動的に再開します。 |
| `/goal unwait` | 待機バリアを破棄し、ループを即座に再開します。 |
| `/goal gate add <command>` | **品質ゲート** を追加します: ゴールが完了と判定される前にパスしなければならないシェルコマンドです。[品質ゲート](#quality-gates) を参照してください。 |
| `/goal gate` または `/goal gate list` | ゴールのゲートと、そのパス/失敗の状態を一覧表示します。 |
| `/goal gate remove <N>` | N 番目のゲート（1 始まり）を削除します。 |
| `/goal gate clear` | すべてのゲートを削除します。 |

クラシック CLI、TUI、Desktop、ダッシュボードチャット、メッセージングゲートウェイは、共有された 1 つの `/goal` コマンドハンドラーを使用します。これには draft/show、インライン契約、wait/unwait、品質ゲート、clear/stop/done エイリアスが含まれます。Desktop のゴール操作も同じハンドラーを使用します。ACP は現在 `/goal` を公開も実装もしていません。

`/goal draft <text>` はゴールの作成と最初のターンの開始の両方を行います。起草が利用できず Hermes が自由形式のゴールにフォールバックした場合も同様です。`draft` は単語全体で判定されるサブコマンドです: `/goal drafting docs` は、起草モデルを呼び出さずに `drafting docs` を文字どおりの目標として保持します。

メッセージングプラットフォームではアクセスルールが維持されます: `/goal gate add` には明示的に設定されたゲートウェイ管理者が必要です。ゲートの一覧表示、削除、クリアは復旧用に引き続き利用できます。レンダリングとターンのスケジューリングはサーフェスごとに異なりますが、コマンドの解析と永続化されるゴールの変更は共有されています。

## 完了契約 {#completion-contracts}

素の `/goal <text>` でも問題なく動作しますが、*曖昧な* ゴールは曖昧な判定を招きます — ジャッジは、あなたが求めると伝えたことしかチェックできません。Codex の `/goal` ガイダンスも同じ点を指摘しています: 永続的な目標は、**完了が何を意味するか、それをどう証明するか、何を壊してはいけないか、何が範囲内か、いつ止めるか** を明示したときに最もよく機能します。Hermes はこれを、既存のゴールループの上に重ねるオプションの **完了契約** として取り入れています。

契約には 5 つのフィールドがあり、すべてオプションです:

| フィールド | 意味 |
|---|---|
| `outcome` | 完了時に真でなければならない唯一の最終状態。 |
| `verification` | 成果を *証明する* 具体的なテスト / コマンド / 成果物。 |
| `constraints` | 変更したり退行させたりしてはいけないもの。 |
| `boundaries` | 範囲内のファイル、ディレクトリ、ツール、システム。 |
| `stop_when` | Hermes が停止して入力を求めるべき条件。 |

契約が設定されると、両方のプロンプトが変わります: **継続プロンプト** は検証対象を目標にし制約を尊重するようエージェントに指示し、**ジャッジプロンプト** は *検証基準が具体的な証拠（コマンドの結果、ファイルの抜粋、テスト出力）によって満たされた場合にのみ* `done` と判定します — 「完了したように見える」という緩い主張ではありません。これは、`/goal` の最も一般的な失敗モード（仕様が不十分な目標での早すぎる完了や終わりのない過剰継続）を直接引き締めます。

### 契約を設定する 2 つの方法

**1. Hermes に起草させる**（推奨 — Codex の「エージェントにゴールを起草させる」というヒントを取り入れたもの）:

```
/goal draft Migrate the auth service from session cookies to JWT
```

Hermes は `goal_judge` 補助モデルを介して 1 行の指示を完全な契約に展開し、それを設定して結果を表示するので、各フィールドを確認したり引き締めたりできます。補助モデルが利用できない場合は、単純な自由形式のゴールにフォールバックします — 起草がゴールの設定を妨げることは決してありません。

**2. `field: value` 行でインラインに書く**:

```
/goal Migrate auth to JWT
verify: pytest tests/auth passes
constraints: keep the /login response shape unchanged
boundaries: only touch services/auth and its tests
stop when: a DB schema migration is required
```

最初の非フィールド行がゴールの見出しになり、認識されるフィールドプレフィックス（`verify:`、`verified by:`、`constraints:`、`preserve:`、`boundaries:`、`scope:`、`stop when:`、`blocked:`、…）が契約を埋めます。たまたまコロンを含む普通のゴール（`Fix bug: the parser drops commas`）は崩されることは **ありません** — 既知のフィールドプレフィックスだけが抜き出されます。

アクティブな契約を確認するには `/goal show` を使います。契約はゴールとともに `SessionDB.state_meta` に永続化されるため、`/resume` 後も残ります。この機能以前の古いゴールは変更なし（契約なし）でロードされます。契約と `/subgoal` の基準は組み合わせられます: サブゴールは、ジャッジが満たす必要のある追加の基準として契約に組み込まれます。

## ゴールの途中で基準を追加する: `/subgoal`

ゴールがアクティブな間、`/subgoal <text>` を使ってループをリセットせずに追加の受け入れ基準を付け加えられます。呼び出しごとに、ゴールのサブゴールリストに番号付きの項目が 1 つ追加されます。次のターンでエージェントが目にする **継続プロンプト** には、元のゴールに加えて「Additional criteria the user added mid-loop」ブロックが含まれ、**ジャッジプロンプト** は判定がすべてのサブゴールを考慮しなければならないよう書き換えられます — 元の目標 **と** すべてのサブゴールが満たされるまで、ゴールは完了とマークされません。

| コマンド | 機能 |
|---|---|
| `/subgoal <text>` | アクティブなゴールに新しい基準を追加します。アクティブな `/goal` が必要です。 |
| `/subgoal`（引数なし） | 現在の番号付きサブゴールリストを表示します。 |
| `/subgoal remove <N>` | N 番目のサブゴール（1 始まり）を削除します。 |
| `/subgoal clear` | 元のゴールはそのままに、すべてのサブゴールを破棄します。 |

サブゴールはゴールとともに `SessionDB.state_meta` に永続化されるため、`/resume` 後も残ります。新しい `/goal <text>` を設定するとゴールが置き換えられ、サブゴールリストはクリアされます。`/goal clear` も同様です。

ループを開始した（「失敗しているテストを修正して」）後、途中で「さらに、今パッチを当てたバグの回帰テストも追加して」と思った場合に使います — `/subgoal add a regression test` は、実行中のループを壊すことなく成功基準を引き締めます。

## 品質ゲート {#quality-gates}

完了契約はジャッジをより厳格にしますが、ジャッジは依然として文章を読む LLM です。**品質ゲート** はより強力です: ゴールが完了できるようになる前に終了コード 0 で終わらなければならない、決定論的なシェルコマンドです。Prime-Agent の有界自律モード（`--autonomous-gate`）から着想を得ています。

```
/goal Fix the flaky session tests
/goal gate add scripts/run_tests.sh tests/hermes_cli/test_goals.py
```

各ターンでの仕組み:

1. **ゲートはジャッジの前に実行されます。** いずれかのゲートが失敗すると、ジャッジは *呼び出されません* — 赤いゲートは、ゴールが完了していないことの決定論的な証拠です。ゲートの終了コードと出力の末尾（最後の約 3 KB）が継続プロンプトになるため、エージェントは雰囲気ではなく実際の失敗に対して反復します。
2. **すべてのゲートがパス → 通常の判定。** その後、LLM ジャッジが以前とまったく同じように done/blocked/continue/wait を判断します。
3. **境界ごとに失敗したゲートを再実行します。** コマンドは毎回現在の入力に対して実行されます。古い結果が再利用されることはないため、入力を修正したばかりのゲートは次の境界でパスします。リトライ上限が、本当に行き詰まった赤いスイートを制限します。
4. **リトライには上限があります。** 各ゲートのデフォルトは 3 回のリトライと 5 分のタイムアウトです。ゲートがリトライを使い切ると、ゴールは（ターン予算と同様に）自動的に一時停止し、手動で修正するか、ゲートを削除するか、`/goal resume` するよう伝えるメッセージが表示されます。

ゲートはゴールとともに `SessionDB.state_meta` に永続化され（`/resume` とコンテキスト圧縮の後も残ります）、ゲートの管理（`/goal gate …`）はゲートウェイ上で実行途中でも安全です — ゲートはターンの境界でのみ実行されます。

ゲートと契約は組み合わせられます: 契約で *エージェントが何を目指すか* を形作り、ゲートで *「完了」を機械的にチェック可能* にします。両方が設定されている場合は、ゲートが先に実行されます。

## バックグラウンドプロセスでの待機: 自動、手動オーバーライドあり

一部のゴールは、数分かかり単独で実行される何かに左右されます — プッシュした PR の CI、長いビルド、テストマトリクス、デプロイ、レート制限のクールダウンなどです。何の助けもなければ、ゴールループは待っている間、毎ターンエージェントを「もう終わった？」という無駄な作業につつき続けてしまいます。

**これは自動的に処理されます。** 毎ターン、ジャッジにはゴールとエージェントの応答とともに、エージェント自身のライブなバックグラウンドプロセス（このセッションがスポーンした `terminal(background=true)` レジストリのエントリ — pid、セッション ID、コマンド、稼働時間、最近の出力、および `watch_patterns` / `notify_on_complete` トリガー。委任されたサブエージェントが開始したプロセスは表示されないため、ファンアウトした親がワーカーのポーラーで待機させられることはありません）が示されます。エージェントの進捗が本当にそのいずれかに左右されている場合、ジャッジは `continue` の代わりに **`wait`** 判定を返し、ループは **待機（パーク）** します: 待機条件が満たされるまで次のターンはスキップされ（ジャッジ呼び出しなし、継続なし、ターン消費なし）、その後、結果を手にして通常どおり再開します。pid/セッションでの待機は最大 30 分です。終了しないプロセス（ウォッチャー、忘れられたポーラー）がゴールを無期限に待機させることはできません。ジャッジは、バックオフ/クールダウンの待機のために **時間** ベース（`wait_for_seconds`）で待機させることもできます。待機中、`/goal status` には `⏳ Goal (parked …)` が表示されます。

ジャッジは、プロセス自身のシグナルから適切な種類の待機を選びます:

- **`wait_on_session <id>`** — プロセス *自身のトリガー* が発火したときに解除されます: プロセスが終了したとき、**または**（`watch_patterns` 付きで開始された場合）そのパターンがマッチしたときです。これは、**実行途中で** シグナルを出し、自分では終了しない可能性のある長寿命のウォッチャー / サーバー / ポーラー（例: `BUILD SUCCESSFUL` を出力した後も実行し続けるビルドプロセスや、`notify_on_complete` ウォッチャー）向けです。
- **`wait_on_pid <pid>`** — プロセスの終了時にのみ解除されます。
- **`wait_for_seconds <n>`** — 一定の遅延の後に解除されます。

これのために何かを入力する必要はありません — ループが渡すプロセスのコンテキストから、ジャッジが判断します。手動コマンドはオーバーライドとして存在します:

| コマンド | 機能 |
|---|---|
| `/goal wait <pid> [reason]` | その PID のプロセスが終了するまで、手動でループを待機させます。PID は Hermes ホスト上のライブなプロセスでなければなりません。リモートの PID や既に終了した PID は拒否されます（そのような PID を指定したジャッジの `wait_on_pid` は、待機せずに継続します）。 |
| `/goal unwait` | 待機バリア（ジャッジによるものでも手動設定でも）をクリアし、即座に再開します。 |

バリア（pid ベースまたは時間ベース）はゴールとともに `SessionDB.state_meta` に永続化されるため、`/resume` 後も残ります。`/goal pause`、`/goal resume`、`/goal clear` はいずれもバリアを破棄します。バリアの設定時に PID が既に死んでいる（または待機中に死んだ）場合や、時間の期限が過ぎた場合、バリアは次のチェックでクリアされます — 古いバリアがループを詰まらせることは決してありません。

典型的な流れ: エージェントが PR をプッシュし、`terminal(background=true, notify_on_complete=true)` で CI ウォッチャーを開始し、「CI を監視中」と報告します。ジャッジはウォッチャープロセスがまだ実行中であることを確認し、その pid で `wait` を返し、ループは静かになります — そして CI が終了した瞬間に再開し、実際の結果に照らしてゴールを判定します。

## 動作の詳細

### ジャッジ

各ターンの後、Hermes は補助モデルを次の内容で呼び出します:

- 標準ゴールのテキスト
- エージェントの最新の最終応答（テキストの最後の約 4 KB）
- 厳格な 1 行の JSON で応答するようジャッジに指示するシステムプロンプト: `{"verdict": "done" | "blocked" | "continue" | "wait", "reason": "<one-sentence rationale>"}`（wait 判定では `wait_on_session` / `wait_on_pid` / `wait_for_seconds` が追加されます。レガシーな `{"done": <bool>, "reason": "..."}` 形式も引き続き受け付けられます）

ジャッジは意図的に保守的です: 応答がゴールの完了を**明示的に**確認しているとき、最終成果物が明確に生成されているときにのみ、ゴールを `done` とマークします。エージェントが **達成不可能**（不可能、範囲外、ユーザーの入力が必要）と説明したゴールには、`done` ではなく `blocked` 判定が下されます: ゴールはジャッジの理由とともに **一時停止** する（`🚫 Goal judged unachievable — paused`）ため、予算を使い果たしたり、不可能なタスクが完了として通されたりする代わりに、`/goal <text>` で範囲を見直すか、`/goal resume` でオーバーライドできます。

### フェイルオープンのセマンティクス

ジャッジがエラーになった場合（ネットワークの瞬断、不正な形式の応答、補助クライアントの利用不可）、Hermes は判定を `continue` として扱います — 壊れたジャッジが進行を止めることは決してありません。**ターン予算**が真の最後の砦です。

### ターン予算

デフォルトは 20 継続ターン（`config.yaml` の `goals.max_turns`）です。予算に達すると、Hermes は自動的に一時停止し、どう進めるか正確に伝えます:

```
⏸ Goal paused — 20/20 turns used. Use /goal resume to keep going, or /goal clear to stop.
```

`/goal resume` はカウンターをゼロにリセットするので、測られたチャンク単位で続行できます。

### ユーザーメッセージは常に優先される

ゴールがアクティブな間にあなたが送る実際のメッセージは、継続ループより優先されます。CLI ではあなたのメッセージがキューに入った継続より前に `_pending_input` に着地し、ゲートウェイでは同じようにアダプターの FIFO を通ります。あなたのターンの後にジャッジが再び実行されます — そのため、あなたのメッセージがたまたまゴールを完了させると、ジャッジがそれを捉えて停止します。

### 実行途中の安全性（ゲートウェイ）

エージェントが既に実行中の間、`/goal status`、`/goal pause`、`/goal clear`、`/goal wait`、`/goal unwait` は安全に実行できます — これらは制御プレーンの状態だけに触れ、現在のターンを中断しません。実行途中で**新しい**ゴールを設定する（`/goal <new text>`）と、まず `/stop` するよう伝えるメッセージとともに拒否されます。これにより、古い継続が新しいものと競合できないようにします。

### 継続の返信はゴールのメッセージを引用しない（ゲートウェイ）

継続プロンプトはゴールを設定したメッセージへの返信ではないため、返信先を引用するプラットフォーム（Telegram）では、その進捗バブルと最終返信は元のメッセージを引用せずにチャット/トピックに投稿されます。返信として応答されるのは、あなた自身のメッセージだけです。

### 永続化

ゴールの状態は、`goal:<session_id>` をキーとして `SessionDB.state_meta` に存在します。つまり `/resume` は中断したところから正確に再開します — ゴールを設定し、ラップトップを閉じ、明日戻ってきて `/resume` すれば、ゴールはあなたが残したとおり（アクティブ、一時停止、または完了）にまだ立っています。

### プロンプトキャッシュ

継続プロンプトは履歴に追加される単純なユーザーロールのメッセージです。システムプロンプトを変更したり、ツールセットを入れ替えたり、Hermes のプロンプトキャッシュを無効化するような形で会話に触れたりは**しません**。20 ターンのゴールを実行しても、キャッシュ的には 20 ターンの通常会話と同じコストです。

## 設定

`~/.hermes/config.yaml` に追加します:

```yaml
goals:
  # Max continuation turns before Hermes auto-pauses and asks you to
  # /goal resume. Default 20. Lower this if you want tighter loops;
  # raise it for long-running refactors.
  max_turns: 20
```

### ジャッジモデルの選択

ジャッジは `goal_judge` 補助タスクを使います。デフォルトではメインモデルに解決されます（[補助モデル](../configuration.md#auxiliary-models)を参照）。コストを抑えるためにジャッジを安価で高速なモデルにルーティングしたい場合は、オーバーライドを追加します:

```yaml
auxiliary:
  goal_judge:
    provider: openrouter
    model: google/gemini-3-flash-preview
```

ジャッジの呼び出しは小さく（出力約 200 トークン）、ターンごとに 1 回実行されるだけなので、安価で高速なモデルが通常は適切な選択です。

## ジャッジが間違えるとき

完璧なジャッジはありません。注意すべき 2 つの失敗モード:

**偽陰性 — ゴールが実際には完了しているのにジャッジが continue と言う。** これはターン予算が捉えます。`⏸ Goal paused` が表示され、`/goal clear` するか、単に新しいメッセージを送れます。

**偽陽性 — 作業が残っているのにジャッジが done と言う。** `✓ Goal achieved` が表示されますが、あなたはそうでないと分かっています。フォローアップメッセージを送って続行するか、ゴールをより正確に設定し直してください: `/goal <more specific text>`。ジャッジのシステムプロンプトは意図的に保守的で、偽陽性が偽陰性より稀になるようにしています。

ジャッジの判定に納得できない場合、`↻ Continuing toward goal` または `✓ Goal achieved` の行にある理由テキストが、ジャッジが何を見たのかを正確に教えてくれます。それで通常、ゴールのテキストが曖昧だったのか、モデルの応答が曖昧だったのかを診断するのに十分です。

## 帰属

`/goal` は **Ralph ループ**パターンに対する Hermes の解釈です。ユーザー向けの設計 — ターンをまたいでゴールを生かし続け、達成するまで止めず、作成/一時停止/再開/クリアの制御を備える — は、OpenAI の Codex チームの Eric Traut によって [Codex CLI 0.128.0](https://github.com/openai/codex) で広められ出荷されました。私たちの実装は独立しています（中央の `CommandDef` レジストリ、`SessionDB.state_meta` 永続化、補助クライアントジャッジ、ゲートウェイ側のアダプター FIFO 継続）が、アイデアは彼らのものです。功績は功績に帰すべきです。
