# 永続メモリ

Hermes Agent は、セッションをまたいで保持される、上限付きで厳選されたメモリを持っています。これにより、あなたの好み、プロジェクト、環境、そして学習した事柄を記憶できます。

## 仕組み

エージェントのメモリは2つのファイルで構成されています。

| ファイル | 目的 | 文字数上限 |
|------|---------|------------|
| **MEMORY.md** | エージェント自身のメモ — 環境に関する事実、慣習、学習した事柄 | 2,200文字（約800トークン） |
| **USER.md** | ユーザープロファイル — あなたの好み、コミュニケーションスタイル、期待 | 1,375文字（約500トークン） |

どちらも `~/.hermes/memories/` に保存され、セッション開始時に固定されたスナップショットとしてシステムプロンプトに注入されます。エージェントは `memory` ツールを介して自身のメモリを管理します — エントリの追加、パッチ、削除が可能です。

:::caution 1つの Hermes ホームにつき1つのエージェント
2つのエージェントプロセスを同じ Hermes ホームディレクトリに向けないでください。メモリの書き込みは自動で行われ、セッション開始時にシステムプロンプトへ読み戻されるため、1つのホームを共有する2つの書き手は互いのエントリを積み重ね、どちらのエージェントも（そしてあなたも）書いていない状態を作り出してしまいます。メモリは設計上 [プロファイル](../profiles.md) ごとにスコープされています — 2つ目のエージェントには専用のプロファイルを与え、メモリの共有が必要な場合は代わりに [外部メモリプロバイダー](./memory-providers.md) を使用してください。
:::

:::info
文字数上限によってメモリを焦点の絞られた状態に保ちます。メモリは**自動的には圧縮されません**。書き込みが上限を超える場合、`memory` ツールはエントリを黙って捨てるのではなくエラーを返します。するとエージェント自身が余地を作ります — 再試行する前に、同じターンの中でエントリを統合または削除します（[メモリが満杯になったとき](#what-happens-when-memory-is-full) を参照）。なお、`patch` も上限の対象です。エントリを長くするパッチは上限を超える可能性があるため、収まるように新しいテキストを短くする（または別のエントリを削除する）必要があります。
:::

## メモリがシステムプロンプトにどう現れるか {#how-memory-appears-in-the-system-prompt}

すべてのセッションの開始時に、メモリのエントリがディスクから読み込まれ、固定されたブロックとしてシステムプロンプトにレンダリングされます。

```
══════════════════════════════════════════════
MEMORY (your personal notes) [67% — 1,474/2,200 chars]
══════════════════════════════════════════════
User's project is a Rust web service at ~/code/myapi using Axum + SQLx
§
This machine runs Ubuntu 22.04, has Docker and Podman installed
§
User prefers concise responses, dislikes verbose explanations
```

フォーマットには次の要素が含まれます。
- どのストア（MEMORY か USER PROFILE か）を示すヘッダー
- エージェントが容量を把握できるよう、使用率と文字数
- `§`（セクション記号）区切り文字で分割された個々のエントリ
- エントリは複数行にわたることができます

**固定スナップショットパターン:** システムプロンプトへの注入はセッション開始時に一度だけ取得され、セッションの途中で変化することはありません。これは意図的なものです — LLM のプレフィックスキャッシュを保持してパフォーマンスを維持するためです。エージェントがセッション中にメモリのエントリを追加・削除すると、その変更は即座にディスクに永続化されますが、次のセッションが開始するまではシステムプロンプトには現れません。ツールのレスポンスは常にライブの状態を表示します。

## メモリにはセッションの区切りが必要

メモリシステム全体は、セッションが**終わる**瞬間を中心に設計されています。`MEMORY.md` と `USER.md` が重要事項を次のセッションへ運び、古いコンテキストが失われた後は `session_search` がその隙間を埋めます。1つのセッションの中では、こうした仕組みが動く理由がありません — 重要なことはすべてまだライブのコンテキストにあるため、エージェントが `session_search` を参照することはほとんどなく、メモリのエントリも厳選するより圧縮することが中心になります。

これはメッセージングプラットフォーム（Telegram、Discord など）で重要になります。そこではチャットは意図的に、再起動、ゲートウェイのクラッシュ、マシンのリブートを越えて存続する [1つの連続したセッション](../sessions.md#session-continuity) になっています。夜間にマシンをシャットダウンしてもセッションは**終わりません** — 次のメッセージが、中断したところからそのまま再開します。一度もリセットしなければ、チャットは数週間にわたって1つのセッションとして続くことがあります。便利ではありますが、コストが膨らみ（どんどん長くなる履歴に対して圧縮が繰り返し実行されます）、*忘れる → メモリからリコールする → 過去のセッションを検索する* という学習ループがほとんど発動しなくなります。また、前述の固定スナップショットのため、新しいメモリエントリは実行中のセッションからは見えないままです。

**実践:** タスクの完了、話題の切り替え、1日の始まりといった自然な区切りで `/new` を実行してください。区切りのたびにメモリが効果を発揮します。エージェントは更新された `MEMORY.md`/`USER.md` のスナップショットを読み直し、安価で短いコンテキストから始め、本当に履歴が必要なときに `session_search` を使います。CLI ではほぼ自動的にそうなります（毎回の起動が新しいセッションです）が、ゲートウェイでは区切りを作るのはあなたです。

## トラブルシューティング: 「覚えておくよう伝えたのに、次のセッションで忘れていた」

最もよくある報告は次のようなものです。何かの場所（Obsidian の vault、プロジェクトディレクトリ、サーバー）をエージェントに伝えると「完了しました、覚えておきます」と答えるのに、新しいセッションでは何のことかわからない。以下を順番に確認してください — 最初の項目で大半のケースが説明できます。

1. **書き込みが実際に行われたか確認する。** メモリが永続化されるのは、モデルが *`memory` ツールを呼び出したとき* だけです。「メモリに追加しました」のような文は単なるテキストにすぎません。ファイルを開いてエントリを探してください。

   ```bash
   cat ~/.hermes/memories/MEMORY.md
   cat ~/.hermes/memories/USER.md
   ```

   事実がそこになければ、モデルは実行していない保存を主張したことになります。小規模なローカルモデル（おおよそ30B パラメータ未満）やツール呼び出しが弱いモデルはこれをよく起こします — ツール呼び出しなしに確認の返答だけを生成してしまうのです。明示的に依頼し（「`memory` ツールを使って vault のパス `/srv/vault` を保存して」）、エントリがファイルに書き込まれたことを確認してください。それでも繰り返し起こる場合、解決策は指示を増やすことではなく、セットアップ時により強力なモデルを使うことです。エントリが一度存在すれば、システムプロンプトに含まれて届くため、小さなモデルでも問題なく読めます。

2. **書き込みがステージングされていないか確認する。** `write_approval: true` の場合、対話型 CLI 以外からの書き込みはレビューのために保留され、承認されるまでファイルには届きません — `/memory pending` と `/memory approve all` を実行してください。[メモリ書き込みの制御](#controlling-memory-writes-write_approval) を参照してください。

3. **書き込んだのと同じメモリを読んでいるか確認する。** メモリは [プロファイル](../profiles.md) ごとです。`hermes -p work`（または `work chat` / `work gateway start`）は `~/.hermes/memories/` ではなく `~/.hermes/profiles/work/memories/` を読みます。デフォルトプロファイルの CLI セッションと、別のプロファイルの Telegram ボットはメモを共有しません。`hermes profile list` で存在するプロファイルを確認できます。

4. **メモリが有効になっているか確認する。** `memory.memory_enabled: false`（または `agent.disabled_toolsets` に `memory` を指定）にするとツール自体が削除されます — モデルが何と言おうと、何も保存できません。[設定](#configuration) を参照してください。

5. **スナップショットはセッション開始時に固定されることを思い出す。** 現在のセッションで保存された事実は *次の* セッションから見えるのであって、すでに実行中だった別のセッションからは見えません。書き込みの後に新しいセッション（`/new`、または新たな CLI の起動）を開始してください。

エージェントに記憶させることに**ならない**ものが2つあります。`.env` 内の変数（これらは認証情報や設定であり、メモリではありません）と、保存を依頼せずに会話の中でついでに触れた事実です。定期的なタスクを実行するたびにエージェントが必要とする場所については、メモリエントリより [スキル](./skills.md) のほうが適した置き場所であることが多いです — スキルは関連するときだけ読み込まれ、2,200文字の予算を奪い合うこともありません。

## メモリツールのアクション

エージェントは `memory` ツールを次のアクションで使用します。

- **add** — 新しいメモリエントリを追加する
- **patch** — 既存のエントリ内の1つの範囲を置換し、残りはそのまま保持する（`old_text` が対象範囲、`content` がその置換内容）
- **remove** — もはや関連性のないエントリを削除する（`old_text` による部分文字列マッチングを使用）

`read` アクションは存在しません — メモリの内容はセッション開始時に自動的にシステムプロンプトへ注入されます。エージェントは自身のメモリを会話コンテキストの一部として参照します。

すべてのツール呼び出しには、トップレベルの `target` が必要です。エージェントのメモには `"memory"`、ユーザープロファイルには `"user"` を指定します。バッチでは、すべての操作にその1つのターゲットが使われます。

```json
{"target": "user", "operations": [{"action": "add", "content": "User prefers metric units"}]}
```

ターゲットが欠落しているか null の場合、また操作内のターゲットがトップレベルのものと異なる場合は、書き込みや承認のステージングの前にエラーが返されます。ペイロードを修正して再試行してください。両方のストアを更新するには、呼び出しを分けてください。

### 部分文字列マッチング

`patch` と `remove` のアクションは、短く一意な部分文字列マッチングを使用します — エントリの全文は必要ありません。`old_text` パラメータは、ちょうど1つのエントリを特定する一意な部分文字列であれば十分です。

```python
# If memory contains "User prefers dark mode in all editors"
memory(action="patch", target="memory",
       old_text="dark mode in all editors",
       content="light mode in VS Code, dark mode in terminal")
# -> "User prefers light mode in VS Code, dark mode in terminal"
```

部分文字列が複数のエントリにマッチする場合は、より具体的なマッチを求めるエラーが返されます。

`patch` は、マッチしたエントリ内の `old_text` の範囲だけを置換し、それ以外はすべて保持します。その範囲はエントリ内に1回だけ出現する必要があります。複数回出現する場合、呼び出しは拒否され、エージェントは周辺のテキストを増やして再試行します。エントリからテキストを削除するには、そのテキストを含むより長い範囲をパッチしてください。エントリ全体を書き換えるには、エントリ全体を `old_text` として渡します（エントリ全体との完全一致は、部分文字列マッチより優先されます）。

`replace` アクションはありません。このアクションはマッチしたエントリ全体を上書きしていましたが、モデルはこれを検索と置換のように使っていたため、複数の事実を含むエントリの他の事実が消えてしまっていました。現在 `replace` を呼び出すと、`patch` を案内するエラーが返されます。この変更より前に承認待ちとしてステージングされた書き込みは、ステージングされたとおりに適用されます。

## 2つのターゲットの説明 {#two-targets-explained}

### `memory` — エージェント自身のメモ

エージェントが環境、ワークフロー、得られた教訓について記憶しておく必要のある情報のためのものです。

- 環境に関する事実（OS、ツール、プロジェクト構成）
- プロジェクトの慣習や設定
- 発見したツールの癖や回避策
- 完了したタスクの日誌エントリ
- 有効だったスキルやテクニック

### `user` — ユーザープロファイル

ユーザーの素性、好み、コミュニケーションスタイルに関する情報のためのものです。

- 名前、役割、タイムゾーン
- コミュニケーションの好み（簡潔か詳細か、フォーマットの好み）
- 嫌がること、避けるべき事柄
- ワークフローの習慣
- 技術的なスキルレベル

## 保存すべきもの vs 省くもの

### これらは保存する（積極的に）

エージェントは自動的に保存します — 依頼する必要はありません。次のような事柄を学習したときに保存します。

- **ユーザーの好み:** 「JavaScript より TypeScript が好き」→ `user` に保存
- **環境に関する事実:** 「このサーバーは Debian 12 と PostgreSQL 16 で動作している」→ `memory` に保存
- **訂正:** 「Docker コマンドに `sudo` を使わないで、ユーザーは docker グループに入っている」→ `memory` に保存
- **慣習:** 「プロジェクトはタブ、120文字の行幅、Google スタイルの docstring を使用」→ `memory` に保存
- **完了した作業:** 「2026-01-15 にデータベースを MySQL から PostgreSQL へ移行した」→ `memory` に保存
- **明示的なリクエスト:** 「私の API キーのローテーションは毎月行われることを覚えておいて」→ `memory` に保存

### これらは省く

- **些細・自明な情報:** 「ユーザーが Python について尋ねた」 — 役に立つには曖昧すぎる
- **簡単に再発見できる事実:** 「Python 3.12 は f-string のネストをサポートしている」 — Web 検索できる
- **生データのダンプ:** 大きなコードブロック、ログファイル、データテーブル — メモリには大きすぎる
- **セッション固有の一時情報:** 一時的なファイルパス、その場限りのデバッグコンテキスト
- **すでにコンテキストファイルにある情報:** SOUL.md や AGENTS.md の内容

## 容量管理 {#capacity-management}

メモリには、システムプロンプトを上限内に保つための厳格な文字数制限があります。

| ストア | 上限 | 一般的なエントリ数 |
|-------|-------|----------------|
| memory | 2,200文字 | 8〜15エントリ |
| user | 1,375文字 | 5〜10エントリ |

### メモリが満杯になったとき {#what-happens-when-memory-is-full}

上限を超えるエントリを追加しようとすると、ツールはエラーを返します。

```json
{
  "success": false,
  "error": "Memory at 2,100/2,200 chars; adding this entry (250 chars) would exceed the limit by 153 chars. Retry as ONE 'operations' batch that removes or shortens (patch) stale entries from current_entries below to free at least 153 chars AND adds this entry — the limit is checked only on the batch result.",
  "current_entries": ["..."],
  "usage": "2,100/2,200"
}
```

するとエージェントは、示された文字数以上を空ける操作（削除、または短くする `patch`）と新しいエントリの追加を含む、1つの `operations` バッチを再発行します。上限はバッチの最終結果に対してのみチェックされます。`old_text` がどのエントリにもマッチしない `patch`/`remove` も同じように失敗し、最も似ているエントリが `closest_entries` に含まれます。

**ベストプラクティス:** メモリが容量の80%を超えたら（システムプロンプトのヘッダーで確認できます）、新しいエントリを追加する前にエントリを統合してください。たとえば、3つの別々の「プロジェクトは X を使用」というエントリを、1つの包括的なプロジェクト説明エントリにまとめます。

### 良いメモリエントリの実例

**簡潔で情報密度の高いエントリが最も効果的です。**

```
# Good: Packs multiple related facts
User runs macOS 14 Sonoma, uses Homebrew, has Docker Desktop and Podman. Shell: zsh with oh-my-zsh. Editor: VS Code with Vim keybindings.

# Good: Specific, actionable convention
Project ~/code/api uses Go 1.22, sqlc for DB queries, chi router. Run tests with 'make test'. CI via GitHub Actions.

# Good: Lesson learned with context
The staging server (10.0.1.50) needs SSH port 2222, not 22. Key is at ~/.ssh/staging_ed25519.

# Bad: Too vague
User has a project.

# Bad: Too verbose
On January 5th, 2026, the user asked me to look at their project which is
located at ~/code/api. I discovered it uses Go version 1.22 and...
```

## 重複防止

メモリシステムは、完全に重複するエントリを自動的に拒否します。すでに存在する内容を追加しようとした場合、「重複は追加されませんでした」というメッセージとともに成功を返します。

## セキュリティスキャン

メモリのエントリはシステムプロンプトに注入されるため、受け入れられる前にインジェクションや情報持ち出しのパターンがスキャンされます。脅威パターン（プロンプトインジェクション、認証情報の持ち出し、SSH バックドア）にマッチする内容や、不可視の Unicode 文字を含む内容はブロックされます。

## セッション検索

MEMORY.md と USER.md を超えて、エージェントは `session_search` ツールを使って過去の会話を検索できます。

- すべての CLI およびメッセージングのセッションは、FTS5 全文検索を備えた SQLite（`~/.hermes/state.db`）に保存されます
- 検索クエリは DB から実際のメッセージを返します — LLM による要約も切り詰めもありません
- エージェントは、アクティブなメモリに含まれていなくても、数週間前に議論した事柄を見つけられます
- エージェントは、見つけたセッションの中を前後にスクロールすることもできます

```bash
hermes sessions list    # Browse past sessions
```

3つの呼び出し形式（discovery / scroll / browse）とレスポンス形式については、[セッション検索ツール](../sessions.md#session-search-tool) を参照してください。

### session_search vs memory

| 機能 | 永続メモリ | セッション検索 |
|---------|------------------|----------------|
| **容量** | 合計約1,300トークン | 無制限（全セッション） |
| **速度** | 即時（システムプロンプト内） | FTS5 クエリで約20ms、スクロールで約1ms |
| **コスト** | すべてのプロンプトでトークンコストが発生 | 無料 — LLM 呼び出しなし |
| **ユースケース** | 常に利用可能な重要な事実 | 特定の過去の会話を見つける |
| **管理** | エージェントが手動で厳選 | 自動 — 全セッションを保存 |
| **トークンコスト** | セッションごとに固定（約1,300トークン） | オンデマンド（必要なときに検索） |

**メモリ**は、常にコンテキストにあるべき重要な事実のためのものです。**セッション検索**は、「先週 X について議論したか？」といった、エージェントが過去の会話から具体的な内容をリコールする必要があるクエリのためのものです。

## 学習の軌跡（`/journey`） {#learning-journey-journey}

学習の軌跡（learning journey）は、Hermes が学習したすべてのもの — 保存されたスキルとメモリエントリ — を時系列に並べたタイムラインビューです（最も古いものが上、最も新しいものが下）。蓄積の過程を再生できる「コンステレーション」スクラバーも備えています。同じグラフデータが3つの画面を駆動します。

- **クラシック CLI / スタンドアロン** — `hermes journey`（エイリアス: `hermes learning`、`hermes memory-graph`）はターミナルにタイムラインをレンダリングします。フラグ: `--play` は蓄積の過程をアニメーション表示し（`--fps` で調整）、`--width`/`--height` はレンダリングサイズを上書きし、`--no-color` は色を無効にし、`--json` は生のグラフペイロードを出力します。
- **TUI** — `/journey`（エイリアス: `/learning`、`/memory-graph`）はタイムラインをオーバーレイとして開きます。
- **デスクトップアプリ** — `/journey` は Star Map / memory-graph パネルを開きます。同じノードをインタラクティブに可視化したものです。

スキルは、学習のシグナルを持った時点でタイムラインに表示されます。つまり、このプロファイルで作成された（`/learn` の結果、またはフォアグラウンドでの `skill_manage` による作成）、バックグラウンドレビューによって作成された、または少なくとも1回使用された場合です。同梱スキルや、一度も使われていない手書きのスキルはタイムラインに表示されません。

閲覧だけでなく、学習の軌跡は Hermes が学習した内容を**整理・修正**する場所でもあります。

| コマンド | 動作 |
|---------|--------------|
| `hermes journey list` | ノード ID を一覧表示します — スキル名と、メモリチャンクの `memory:<source>:<index>:<fingerprint>` ID です（表示されたとおりに正確に渡してください）。 |
| `hermes journey delete <node> [-y]` | ノードを削除します。スキルは**アーカイブ**され（復元可能）、メモリチャンクは削除されます。`-y` は確認をスキップします。 |
| `hermes journey edit <node>` | ノードの内容（スキルの `SKILL.md` またはメモリチャンク）を `$EDITOR` で開きます。 |

同じ `list` / `delete <id>` / `edit <id>` サブコマンドは、CLI のチャット内 `/journey` コマンドからも使えます。デスクトップのパネルでは、ノードに対して直接編集・削除を行えます。

## 設定 {#configuration}

```yaml
# In ~/.hermes/config.yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200   # ~800 tokens
  user_char_limit: 1375     # ~500 tokens
  write_approval: false     # false = write freely (default) | true = require approval
  prefetch_spill_enabled: false  # external recall stays intact unless explicitly enabled
```

`memory_enabled` と `user_profile_enabled` を**両方とも** `false` に設定すると、組み込みストアは完全にオフになります。`memory` ツールはスキーマから外され、そのガイダンスブロックもシステムプロンプトから外されるため、モデルが使えないツールについて知らされることはありません。`memory.provider` で設定した外部プロバイダー（Hindsight、Mem0、Honcho など）は影響を受けず、独自のツールを保持します — 組み込みファイルの *代わりに* サードパーティのメモリバックエンドを使いたい場合はこの設定を使ってください。`agent.disabled_toolsets` に `memory` を指定するのはより強力なスイッチで、外部プロバイダーのツールも非表示にします。

`memory_enabled: false` だけの場合（ユーザープロファイルはオンのまま）、ツールは残ります — プロファイルストアを支えるためです — が、システムプロンプトでは完全なメモリガイダンスが、プロファイル専用のより限定的なブロックに置き換わります。ツールスキーマは `user` ターゲットだけを提示し、無効化された `MEMORY.md` への直接またはステージングされた書き込みは拒否されます。逆の設定では `memory` だけが提示され、`USER.md` への書き込みが拒否されます。

### 外部リコールのサイズ

外部メモリプロバイダーは、デフォルトでプリフェッチしたコンテキストの全体を返します。上限は安全のための天井として `hooks.output_spill.max_chars` の10倍（最低100,000文字）で、それを超えるリコールは引き続きスピルされるため、暴走したプロバイダーがコンテキストウィンドウをあふれさせることはありません。
`memory.prefetch_spill_enabled: true` を設定すると、アクティブなプロファイルでは、サイズの大きすぎるリコールが先頭/末尾のプレビューとファイルパスに置き換えられるようになります。これにより再生されるコンテキストを減らせますが、関連度順に並んだ中間部分はモデルからすぐには見えなくなります。利用可能であれば、プロバイダー自身のリコール予算を優先してください。

このオプトインは、共有の `hooks.output_spill` のしきい値、プレビューの長さ、ディレクトリを使用します。`hooks.output_spill.enabled: false` の場合は引き続き無効になります。通常のプラグインフックは、メモリのオプトインとは独立して、デフォルトで引き続きスピルされます。設定はプロバイダーの登録時に取得されるため、変更後は Hermes を再起動してください。
設定の詳細については、[サイズの大きすぎるプリフェッチ結果](/docs/developer-guide/memory-provider-plugin#oversized-prefetch-results) を参照してください。

## メモリ書き込みの制御（`write_approval`） {#controlling-memory-writes-write_approval}

デフォルトでは、エージェントはメモリを自由に保存します — ターンの後に実行されるバックグラウンドの自己改善レビューからの保存も含みます。保存の前に承認したい場合は、`memory.write_approval: true` を設定してください。これはフォアグラウンドのターンとバックグラウンドレビューの**両方**に適用される、単純なオン/オフのゲートです。

| `write_approval` | 動作 |
|------------------|-----------|
| `false`（デフォルト） | 自由に書き込む — ゲートはオフ（ゲート導入前の動作）。 |
| `true` | 何かを保存する前に承認を求める。対話型 CLI では、フォアグラウンドの書き込みはインラインで確認を求めます（エントリは全文を読める程度に小さいため）。それ以外の場所 — メッセージングプラットフォーム、スクリプト、バックグラウンドの自己改善レビュー — では、書き込みは `/memory pending` でのレビューのために**ステージング**されます。 |

> メモリを（ゲートするだけでなく）完全にオフにするには、`memory_enabled: false` と `user_profile_enabled: false` の両方を設定してください。両方の組み込みストアが無効になると、組み込みの `memory` ツールは自動的に非表示になります。

ステージングされた書き込みは、CLI または任意のメッセージングプラットフォームからレビューできます。

```
/memory pending             # list staged memory writes (auto ones tagged [auto])
/memory approve <id>        # apply one (or 'all')
/memory reject <id>         # drop one (or 'all')
/memory approval on         # turn the gate on (or 'off') and persist it
```

これが「エージェントが私について誤った思い込みを保存した」への答えです。`write_approval: true` を設定すれば、すべての保存 — 特に頼んでもいないバックグラウンドの保存 — は、プロファイルに入る前にあなたの承認/拒否を待つようになります。

ステージングされた `patch` や `remove`（バックグラウンドレビューは、ゲートがオフでもこれらをステージングします）は対象となるエントリの全文を記録し、`/memory pending` にそれが表示されます。承認はまさにそのエントリに対して適用されます。書き込みがステージングされた後にエントリが変更されていた場合、書き込みは拒否され、あなたが却下できるよう保留のまま残ります。この固定（ピン留め）の仕組みが導入される前にステージングされた `replace`/`patch`/`remove` には検証可能なターゲットがないため、これも拒否されます。却下して変更を作り直してください。`/memory approve` は、上書きまたは削除したすべてのエントリの全文を一覧表示します。

## バックグラウンドレビューの通知（`display.memory_notifications`）

ターンの後、バックグラウンドの自己改善レビューが静かにメモリを保存したり、スキルを更新したりすることがあります。これは Hermes の同意を考慮した学習ループです。繰り返される訂正や永続的なワークフローの教訓は、コンパクトなメモリエントリや手続き的なスキルになり、`write_approval` によって、それらの書き込みが将来のセッションに影響する前にレビュー用にステージングできます。デフォルトでは、それが起きたことがわかるように、チャットに短い `💾 Memory updated` という行が表示されます。どの程度表示するかは次のように制御できます。

```yaml
display:
  memory_notifications: on    # off | on (default) | verbose
```

| 値 | 動作 |
|-------|-----------|
| `off` | チャット通知なし。レビューは引き続き実行され、書き込みも行われます — その行が表示されないだけです。 |
| `on`（デフォルト） | 汎用的な行。例: `💾 Memory updated`、`💾 Skill 'foo' patched`。 |
| `verbose` | 変更内容のコンパクトなプレビューを含みます。例: `💾 Memory ➕ User prefers terse replies`、またはスキルの `"old" → "new"` 差分の抜粋。 |

> これは**ゲートウェイ**のチャット通知のみを制御します。レビュー自体や、メモリ/スキルストアへの書き込みは、この設定の影響を受けません。プラットフォームごとに設定するには `display.platforms.<platform>.memory_notifications` を使ってください。

成功したスキルのバッチは、`on` と `verbose` のどちらのモードでも、適用された各操作を名前で示します。サポートファイルの書き込み/削除やスキルの削除も含みます。承認待ちのステージングされた書き込みや、ロールバックされたバッチは、完了した変更として報告されません。バッチの要約は、要求された書き込みが実行されたと仮定するのではなく、適用された結果を使います。

## より安価なモデルでレビューを実行する（`auxiliary.background_review`）

レビューはデフォルトで**メインのチャットモデル**で実行され、会話を再生します — 会話はすでにプロンプトキャッシュで温まっているため、安価なキャッシュ読み取りになります。メインモデルが高価な場合は、代わりにより安価なモデルでレビューを実行できます。

```yaml
auxiliary:
  background_review:
    provider: openrouter
    model: google/gemini-3-flash-preview   # auto (default) = main chat model
```

メインモデルとは**異なる**モデルを指定すると、レビューはそちらで実行され、コストが大幅に下がります（ベンチマークで約3〜5倍）。異なるモデルはいずれにせよメインモデルのプロンプトキャッシュを再利用できないため、フォークは完全なトランスクリプトの代わりに会話のコンパクトな**ダイジェスト**（直近のターンはそのまま + それより古いターンの要約）を自動的に再生し、新しいキャッシュへの書き込みを最小限に抑えます。取りこぼしはありません。テストでは、メモリの捕捉はメインモデルでのレビューと同一、スキルの捕捉もほぼ同一でした。

`auto` のままにする（またはメインモデルを設定する）と何も変わりません — レビューは引き続きメインモデルで、温まったキャッシュによる完全な再生で実行されます。

### 同一モデルでのレビューの推論 {#same-model-review-reasoning}

親と同じモデルを使うレビューは、**常に親の推論努力（reasoning effort）を継承します**。`auxiliary.background_review.reasoning_effort` を設定しても、ルートが `auto` であっても親のプロバイダー/モデルを明示的に選択していても、これは上書きされません。

推論設定、システムプロンプト、会話の完全なスナップショット、ツール定義は、レビューが親のプロンプトキャッシュのプレフィックスを再利用できるよう、フォーク生成時に親とバイト単位で同一に保たれます。レビューの思考レベルだけを変更すると、この同一性が崩れてしまいます。同一モデルのレビューには、推論努力を独立して設定するスイッチはありません。

メインの会話の推論努力を変えずにレビューの作業量を減らすには、`memory.nudge_interval` / `skills.creation_nudge_interval` を調整するか、後述のように自動レビューを無効にするか、レビューを別のモデルにルーティングしてください。別モデルへのルートはダイジェストを使い、親の温まったプレフィックスを共有しません。そのルートでは `auxiliary.background_review.reasoning_effort` が実際に尊重されます（未設定 = ルーティング先プロバイダーのデフォルト）。キーが設定されているのにレビューがメインモデルのままの場合は、一度だけ警告が表示されます。これらの頻度やルーティングの制御によって、同一モデルの推論が切り離されることはありません。

### 自動レビューの無効化（`enabled`）

レビューのフォークは、負荷の高いホストでは総トークンのかなりの割合を消費することがあります。運用者は、ナッジ間隔をゼロにすることなくこれを無効にできます。

```yaml
auxiliary:
  background_review:
    enabled: true              # false = skip automatic post-turn forks
```

`enabled: false` の場合、ターン後の自動フォークは生成されません。手動の `/refine` は、フォーカステキストの有無にかかわらず引き続き機能します。

### レビューコストの上限設定（`max_input_tokens`）

レビューループは、プロバイダーへのリクエストのたびに会話を再生するため、1回のレビューでツールの反復にわたって入力トークンが何倍にも膨らむことがあります。`max_input_tokens` は1回のレビューで再生される入力トークンの合計に上限を設け、ループはそれを超える前に停止します。`<= 0` は無制限を意味します。

```yaml
auxiliary:
  background_review:
    max_input_tokens: 48000  # <= 0 = unlimited
```

キーが未設定の場合、予算はレビューモデルの解決済みコンテキストウィンドウから導出されます。ウィンドウの75%で、上限は600,000トークンです — そのため、固定のクラウド規模のデフォルトではまったく効かないような小さなローカルモデルでも上限として機能します（65,536トークンのモデルなら49,152）。ウィンドウを解決できない場合は、控えめな120,000トークンのフォールバックが適用されます。なお、このキーは `auxiliary:` の下に置きます。トップレベルの `background_review:` ブロックは読み込まれません。

フォークの使用量は `task='background_review'` として `session_model_usage` に永続化され、完了の行が `agent.log` に書き込まれます（`Background review complete: thread=bg-review calls=… in=… out=… result=…`）。

### 範囲を限定した追加レビューツールの許可（`extra_tools`）

バックグラウンドレビューは、デフォルトでメモリ、スキル管理、読み取り専用のファイルツールを使用できます。プロファイルが無人のレビューでも安全な別のツールを提供している場合は、名前を指定してオプトインできます。

```yaml
auxiliary:
  background_review:
    extra_tools:
      - propose_shared_memory
```

ツールはすでに親エージェントで利用可能になっている必要があります。この設定は、レビューフォークのランタイムのホワイトリストにそれを追加するだけです。任意のツールを有効にするものではなく、ここに列挙されていないツールは引き続き拒否されます。リストは狭く保ち、外部への変更や破壊的な変更を直接適用するのではなく、人間のレビュー用に提案をステージングするツールを優先してください。デフォルトは空のリストです。

### ローカルモデル: レビューは GPU のアイドルを待つ（`defer`）

クラウドプロバイダーでは、レビューは数秒で完了し、あなたが次に行うことと並行して実行されます。レビューのランタイムが**管理対象のローカル llama-server**（Settings → Local models）の場合、同じフォークがあなたの次のプロンプトに必要な GPU を占有し — 大きなモデルでは数分間 — 新しいプロンプトを送るとそれがキャンセルされ、学習内容が破棄されてしまいます。そのため、管理対象のローカルランタイムでは、レビューは**デフォルトで延期**されます。ターン終了時にキューに入れられ、マシンが短い安定期間だけ静かになったら実行されます。レビュー自体は何も変わりません — 同じモデル、同じ完全トランスクリプトの再生、同じ書き込み — 実行のタイミングが移動するだけです。

```yaml
auxiliary:
  background_review:
    defer: auto            # auto (default) | never
    defer_max_age_s: 1800  # run a queued review anyway after this long
```

| 値 | 動作 |
|-------|-----------|
| `auto`（デフォルト） | ランタイムが管理対象のローカルサーバーに解決されるレビューはキューに入れられ、アイドル時に実行されます。それ以外のランタイム（クラウド、外部サーバー）は従来どおり即座に生成されます。 |
| `never` | どこでも従来の動作: 管理対象のローカル GPU であっても、ターン終了時に即座に生成します。 |

キューに入ったレビューはセッションごとにまとめられます（新しいターンのスナップショットが古いものを置き換えます — レビューは会話全体を再生するため、何も失われません）。新しいプロンプトによって中断されたレビューは破棄されずに再びキューに入れられ、`defer_max_age_s` より長く待ったレビューは、マシンがアイドルにならなくても実行されます。明示的な `/refine` は常に即座に実行されます。キューはメモリ内にあるため、アプリ終了時にまだ保留中のレビューは破棄されます。これは実行中のフォークの場合と同じです。

## スキル書き込みの制御（`skills.write_approval`）

スキルも同じオン/オフのゲートを使いますが、`SKILL.md` はチャットの吹き出しで読むには大きすぎるため、レビューの UX が異なります。

```yaml
skills:
  write_approval: false     # false = write freely (default) | true = require approval
```

`write_approval: true` の場合、スキルの書き込み（create / edit / patch / write_file / delete）は発生元にかかわらず常に**ステージング**されます。1行の要旨はインラインでレビューできますが、完全な差分は別の場所で確認します。

```
/skills pending             # list staged skill writes + a one-line gist each
/skills diff <id>           # full unified diff (best viewed in CLI or dashboard)
/skills approve <id>        # apply it (or 'all')
/skills reject <id>         # drop it (or 'all')
/skills approval on         # turn the gate on (or 'off') and persist it
```

メッセージングプラットフォームでは、要旨とメタデータからスキルを承認するか、変更全体を読みたい場合は CLI / ダッシュボードで `/skills diff` を開くか、`~/.hermes/pending/skills/<id>.json` にあるステージングされたファイルを開いてください。詳細は [エージェントのスキル書き込みのゲート](./skills.md#gating-agent-skill-writes-skillswrite_approval) を参照してください。


## 外部メモリプロバイダー

MEMORY.md と USER.md を超えた、より深く永続的なメモリのために、Hermes は2つの外部メモリプロバイダープラグイン — RetainDB と ByteRover — を同梱しています。さらに Honcho、Hindsight、Supermemory、Mem0、OpenViking、Holographic などは、`hermes plugins install <name>` で [プラグインカタログ](plugins.md) から利用できます。

外部プロバイダーは組み込みメモリと**並行して**動作し（組み込みメモリを置き換えることは決してありません）、ナレッジグラフ、セマンティック検索、自動的な事実抽出、セッションをまたいだユーザーモデリングといった機能を追加します。

```bash
hermes memory setup      # pick a provider and configure it
hermes memory status     # check what's active
```

各プロバイダーの詳細、セットアップ手順、比較については、[メモリプロバイダー](./memory-providers.md)ガイドを参照してください。
