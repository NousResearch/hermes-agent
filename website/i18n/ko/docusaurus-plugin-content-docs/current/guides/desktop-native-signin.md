# 데스크톱 네이티브 로그인 (RFC 8252)

Hermes Desktop 앱이 **게이트된 게이트웨이**(OAuth 공급자 뒤에 있는 호스팅 또는 자체 호스팅 대시보드)에 연결할 때는 두 가지 방법으로 로그인할 수 있습니다.

1. **네이티브 로그인 (RFC 8252)** — 앱이 **실제 시스템 브라우저**를 열고, 이미 신뢰하는 브라우저에서 승인하면 앱이 OS 키체인에 저장하는 토큰을 받습니다. **임베디드 웹뷰와 브라우저 세션 쿠키가 없습니다.** 게이트웨이가 지원하는 경우 항상 이것이 기본값입니다.
2. **임베디드 로그인 (기존 방식의 대체 수단)** — 앱이 작은 인앱 브라우저 창을 열고 게이트웨이의 세션 쿠키를 캡처합니다. 게이트웨이가 네이티브 로그인을 알리지 않는 이전 빌드일 때 자동으로 사용됩니다.

둘 중 하나를 직접 선택할 필요는 없습니다. 앱이 게이트웨이가 지원하는 기능을 감지하고 가장 적합한 방법을 선택합니다. 이 페이지에서는 어떤 일이 일어나며 그 이유가 무엇인지 설명합니다.

## 네이티브 로그인인 이유

OAuth를 위해 네이티브 앱 안에 브라우저를 임베드하면 잘 알려진 단점이 있습니다. 로그인 페이지가 기존 브라우저 세션을 볼 수 없어서 자격 증명을 다시 입력하고 MFA를 다시 수행해야 하며, 비밀번호 관리자와 패스키가 작동하지 않는 경우가 많고, 앱이 비공개 웹뷰에서 세션 쿠키를 읽는 데 의존합니다. RFC 8252("네이티브 앱을 위한 OAuth 2.0")는 이 모든 문제를 피하는 업계 모범 사례입니다. **시스템 브라우저에서 인증을 수행하고 앱에 자체 토큰을 전달하는 방식**입니다.

Hermes에서 네이티브 로그인은 다음을 의미합니다.

- **임베디드 웹뷰가 없습니다.** 인증은 Safari / Chrome / Firefox / Edge 중 어떤 브라우저를 사용하든 해당 브라우저에서 수행되며, 로그인 정보·확장 프로그램·패스키가 그대로 유지됩니다.
- **세션 쿠키가 없습니다.** 앱은 OAuth **액세스 토큰**(단기)과 **리프레시 토큰**을 보유하며, 이 토큰은 OS 키체인(Electron `safeStorage`)을 통해 저장 시 암호화됩니다. REST 호출과 WebSocket 티켓은 쿠키 저장소가 아니라 `Authorization: Bearer` 헤더로 인증됩니다.

## 작동 방식

```
Desktop app                Gateway (/auth/native/*)          Nous Portal (IDP)
   │ 1. open loopback 127.0.0.1:<random port>
   │ 2. system browser ─►  /auth/native/authorize
   │    (PKCE challenge)    (starts the normal PKCE login) ─► /oauth/authorize
   │                        ◄──── code ──── /auth/callback ◄──┘
   │                        3. mint one-time gateway code
   │ ◄─ 302 127.0.0.1/cb?code=… ─┘
   │ 4. POST /auth/native/token (code + PKCE verifier)
   │ ◄─ 5. { access_token, refresh_token, expires_at } ───────┘
   │ 6. store in OS keychain; use Bearer for REST + WS tickets
```

게이트웨이는 이 흐름을 **중개**합니다. 즉, *데스크톱 앱에 대해서는* 인증 서버이고 업스트림 ID 공급자(Nous Portal)에 대해서는 OAuth 클라이언트입니다. 업스트림 `client_id`와 허용된 리디렉션 URI가 게이트웨이 자체 오리진에 연결되어 있으므로 이것이 필요합니다. 데스크톱 앱은 Portal의 직접 클라이언트가 될 수 없습니다. 데스크톱은 자체 PKCE 쌍, 자체 루프백 리디렉션, 자체 소유 토큰이라는 완전한 RFC 8252 경험을 그대로 얻습니다.

**PKCE (RFC 7636)**는 루프백 홉을 보호합니다. 일회성 게이트웨이 코드는 앱에서 절대 벗어나지 않는 코드 검증자가 없으면 쓸모가 없습니다. 코드는 한 번만 사용할 수 있고 수명이 짧습니다.

## 기능 감지 및 대체 수단

데스크톱은 게이트웨이의 공개 `/api/status` 엔드포인트를 읽습니다. 이 엔드포인트는 `auth_flows` 배열을 제공합니다.

| `auth_flows` 값 | 의미 |
|--------------------|---------|
| `["cookie", "native_pkce"]` | 게이트웨이가 네이티브 로그인을 지원함 → 앱이 이를 사용 |
| `["cookie"]` | 게이트웨이가 기존 흐름만 지원함 → 앱이 임베디드 웹뷰를 사용 |
| *(필드 없음)* | 이전 게이트웨이 → 앱이 임베디드 웹뷰를 사용 |

네이티브 로그인이 광고되었지만 로컬 이유로 실패하는 경우(예: 보안 도구가 루프백 리스너를 차단하거나 브라우저 탭을 닫은 경우)에도 앱은 **자동으로 임베디드 흐름으로 대체**되므로 계속 로그인할 수 있습니다.

## 토큰 수명 주기

- **액세스 토큰**: 수명이 짧습니다(수분). 모든 REST 호출과 WebSocket 티켓 발급 시 `Authorization: Bearer`로 전송됩니다.
- **리프레시 토큰**: 수명이 더 길고 순환됩니다. 액세스 토큰이 만료될 때가 가까워지면 앱은 `/auth/native/refresh`를 호출해 두 토큰을 모두 순환한 다음 키체인을 업데이트합니다.
- **최종 만료**: 리프레시 토큰이 만료·폐기되었거나 재사용이 감지되어 무효화되면 앱은 저장된 토큰을 삭제하고 새 로그인을 요청합니다.
- **로그아웃**: 네이티브 토큰(키체인)과 해당 게이트웨이의 기존 세션 쿠키를 모두 삭제합니다.

## 게이트웨이 운영자를 위한 안내

대화형 세션 공급자가 등록된 모든 게이트된 게이트웨이에서는 네이티브 로그인을 자동으로 사용할 수 있습니다. 구성이 필요하지 않습니다. `/auth/native/*` 경로와 `auth_flows` 광고는 대시보드 인증 하위 시스템의 일부입니다. OAuth 공급자(예: 기본 제공 **Nous** 공급자)는 업스트림 IDP 리디렉션을 중개하고, 비밀번호 공급자(예: 기본 제공 **basic-auth** 플러그인)는 시스템 브라우저를 게이트웨이의 `/login` 자격 증명 양식으로 이동시킵니다. 따라서 임베디드 데스크톱 웹뷰에서는 제공할 수 없는 OS 비밀번호 관리자(macOS Passwords 등)의 양식 자동 완성이 가능합니다. 토큰 전용 자격 증명(예: drain)은 대화형 로그인이 아니므로 `native_pkce`를 광고하지 않습니다.

관련 엔드포인트(모두 공개되며, 기존 `/auth/*` OAuth 경로와 동일하게 사전 인증 부트스트랩에 사용됨)는 다음과 같습니다.

- `GET /auth/native/authorize` — 중개된 PKCE 로그인 시작
- `POST /auth/native/token` — 루프백 코드와 검증자를 토큰으로 교환
- `POST /auth/native/refresh` — 앱의 리프레시 토큰으로 토큰 순환
