# 반복 루프 (`/loop`)

`/loop`는 **현재 세션 안에서** 프롬프트(또는 슬래시 명령)를 일정한 주기로 다시 실행합니다. 깨어날 때마다 실제 에이전트 턴이 진행됩니다. Hermes는 최신 CI 결과, 현재 큐 깊이, 지금의 파일 상태처럼 현재 상태를 새로 읽고 작업을 수행해 결과를 보고한 다음 다음 틱까지 조용히 대기합니다.

이는 **Claude Code의 `/loop`**(여기서도 작동하는 `/proactive` 별칭 포함)를 Hermes식으로 구현한 것입니다. [`/goal`](./goals.md)이 “이 목표를 달성할 때까지 계속 작업하라”는 판정자 주도 방식이라면, `/loop`는 “무언가 중단하라고 할 때까지 N분마다(또는 적절한 때마다) 다시 수행하라”는 타이머 주도 방식입니다.

## 언제 사용할까요?

- **외부 상태 폴링.** “배포 / CI 실행 / 큐를 지켜보다가 바뀌면 알려줘.” 대표적인 사용 사례입니다.
- **성공할 때까지 반복.** “테스트를 실행하고, 실패한 부분을 수정하고, 통과할 때까지 반복해.”
- **작업 세션 중 모니터링.** 같은 대화에서 다른 일을 하는 동안 오류율이나 오래 걸리는 작업의 진행 상황을 지켜봅니다.
- **주기적인 정리 작업.** 긴 세션 동안 N분마다 린트 실행이나 상태 요약을 다시 수행합니다.

작업이 **무인으로** 실행되어야 한다면(밤새, 실제 일정에 따라, 터미널을 다시 시작해도 유지되도록) 대신 [cron 작업](./cron.md)을 사용하세요. `/loop`는 세션 내부에 존재하고, cron은 모든 세션 외부에 존재합니다. 작업이 완료되는 조건이 있는 단일 목표라면 [`/goal`](./goals.md)이 대체로 더 적합합니다.

## 빠른 시작

```
/loop 5m check the deploy status and tell me if it's live yet
```

다음과 같은 결과를 볼 수 있습니다.

1. **루프 수락됨** — `↻ Loop set (every 5m): check the deploy status…`
2. **5분 후 첫 번째 깨우기** — 세션이 유휴 상태인 동안 Hermes가 깨우기 요청을 주입하고 현재 상태를 기준으로 일반 턴을 실행합니다.
3. **반복** — 중단 조건이 발생하거나 사용자가 중단할 때까지 5분마다 반복합니다.

슬래시 명령도 똑같이 쉽게 반복할 수 있습니다.

```
/loop 10m /recap
```

## 두 가지 주기 모드

**고정 간격 — 사용자가 시계를 설정합니다.** 간격(`30s`, `5m`, `2h`, `1h30m`)을 지정하면 루프가 해당 일정에 따라 실행됩니다. 감시 대상이 자체 일정에 따라 변할 때 사용하세요.

```
/loop 2m poll the build at ci.example.com/job/42 and ping me the moment it finishes
```

**자율 조정 — Hermes가 시계를 설정합니다.** 간격을 생략하면 루프가 스스로 주기를 조정합니다. 기본적으로 최소값(기본 1분)에서 시작하고, 에이전트의 답변이 계속 동일하면 2분, 4분, 8분처럼 지수적으로 늘려 최대값(기본 15분)까지 늦춥니다. 답변이 직전 답변과 달라지는 순간 주기는 최소값으로 돌아갑니다. 변경 감지는 로컬 다이제스트 비교(타임스탬프는 무시)이므로 유휴 대기에는 추가 비용이 들지 않습니다.

```
/loop keep an eye on the migration and summarize progress
```

간단한 기준은 다음과 같습니다. **외부 시계가 작업을 주도하면 고정 간격을, 작업이 리듬을 주도하면 자율 조정을 사용하세요.**

## 중단 조건

다음 중 하나가 발생하면 루프가 종료됩니다.

| 조건 | 방법 |
|---|---|
| 에이전트가 완료되었다고 판단 | 깨우기 프롬프트가 작업이 끝났거나 더 이상 의미가 없을 때 에이전트가 자신의 답변을 `LOOP_COMPLETE` 한 줄로 끝내도록 안내합니다. |
| 실행 횟수 제한 | `--times N` — N회 깨운 후 중단합니다. |
| 근거 기반 조건 | `--until <condition>` — 각 깨우기 후 `/goal`을 작동시키는 것과 동일한 보조 판정자가 조건에 비추어 답변을 확인합니다(실패 시 열린 상태로 처리: 판정자가 고장 나도 루프가 멈추지 않습니다). |
| 사용자 | `/loop stop`(또는 루프를 유지하려면 `/loop pause`) |
| 안전 예산 | `loops.max_ticks`(기본값 100)가 루프를 일시 중지해 무인 세션이 토큰을 영원히 소모하지 않도록 합니다. `0` = 무제한입니다. |

예시:

```
/loop 2m poll CI --times 30
/loop 5m watch the queue --until queue depth reaches zero
```

## 명령

| 명령 | 동작 |
|---|---|
| `/loop [interval] <prompt> [--times N] [--until <cond>]` | 이 세션에서 루프를 시작합니다(또는 기존 루프를 교체합니다). |
| `/loop` 또는 `/loop status` | 주기, 실행된 틱 수, 다음 깨우기까지의 시간을 표시합니다. |
| `/loop pause` | 루프를 잃지 않고 실행을 중지합니다. |
| `/loop resume` | 다시 시작합니다. |
| `/loop stop` | 루프를 종료합니다. |
| `/proactive …` | `/loop`의 별칭입니다(Claude Code 호환성). |

CLI, TUI(`hermes --tui`), 웹 대시보드 채팅, 데스크톱 앱, 모든 게이트웨이 플랫폼(Telegram, Discord, Slack, WhatsApp 등)에서 작동합니다. 메시징 플랫폼에서는 사용자의 메시지 사이에도 게이트웨이가 깨우기를 실행합니다. 루프는 채팅 세션에 속하며, 결과는 일반 답변으로 도착합니다.

## `/goal`과 함께 사용하기

두 기능 모두 유휴 경계에서 합성 턴을 주입하므로 한 가지 규칙을 따릅니다. **활성 목표가 세션을 소유합니다.** `/goal`이 실제로 작업을 주도하는 동안(판정자가 “계속”이라고 하는 동안) 루프 깨우기는 연기됩니다. 목표가 끝나거나 일시 중지되거나 대기 장벽(`/goal wait` 또는 판정자의 자동 WAIT 판정)에 걸리면 루프는 유휴 시간을 사용해 즉시 재개됩니다. 대기 중인 목표와 `/loop`를 함께 사용하는 것은 자연스러운 조합입니다. 목표가 큰 비동기 작업을 기다리는 동안 루프는 다른 작업에 대한 심박을 유지합니다.

실제 사용자 메시지는 언제나 둘보다 우선합니다. 깨우기는 세션이 유휴 상태이고 사용자의 대기 중인 요청이 없을 때만 실행됩니다.

## 동작 세부 사항

- **깨우기는 일반 사용자 역할 턴입니다.** 시스템 프롬프트 변경도, 도구 세트 교체도 없으므로 프롬프트 캐싱이 유지됩니다.
- **`/resume`과 압축 후에도 유지됩니다.** 루프 상태는 세션별로 유지되며 `/goal`과 마찬가지로 컨텍스트 압축 경계를 넘어 이전됩니다.
- **세션당 루프 하나입니다.** 새 `/loop`를 설정하면 이전 루프를 교체합니다. 여러 루프를 실행하려면 여러 세션을 사용하세요(여러 일정에는 cron을 사용하세요).
- **깨우기 턴을 중단하면(Ctrl+C) 루프가 일시 중지됩니다.** `/loop resume`으로 복구할 수 있으므로 취소가 실제 취소로 작동합니다.
- **토큰 비용은 주기에 따라 증가합니다.** 모든 틱은 전체 에이전트 턴입니다. 상태가 실제로 변하는 빈도에 맞춰 간격을 정하고, 유휴 대기에는 자율 조정을 우선하세요.

## 구성

```yaml
# ~/.hermes/config.yaml
loops:
  min_interval_seconds: 30       # floor for fixed intervals
  max_ticks: 100                 # backstop budget (0 = unlimited)
  self_paced_floor_seconds: 60   # self-paced starting cadence
  self_paced_ceiling_seconds: 900  # self-paced max backoff
```

`--until` 판정자는 `goal_judge` 보조 작업을 통해 실행되므로 `auxiliary.goal_judge.*` 재정의(제공자, 모델, max_tokens)는 루프 조건에도 적용됩니다.

## `/loop`와 `/goal`, cron 비교

| | `/loop` | `/goal` | cron |
|---|---|---|---|
| **트리거** | 타이머(또는 자율 조정) | 각 턴 후 판정자 판정 | 모든 세션 외부의 일정 |
| **존재 위치** | 현재 세션 | 현재 세션 | 실행마다 자체 세션 |
| **종료 조건** | 중단 조건 / 제한 / 사용자 | 목표 달성 / 예산 / 사용자 | 작업을 제거할 때 |
| **적합한 용도** | 폴링, 모니터링, 주기적 재실행 | 하나의 목표, 달성할 때까지 반복 | 무인 장기 일정 |
