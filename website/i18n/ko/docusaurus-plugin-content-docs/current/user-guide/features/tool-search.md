# 도구 검색

세션에 많은 MCP 서버나 코어가 아닌 플러그인 도구가 연결되어 있으면, 실제 사용자의 요청과 관련된 도구가 몇 개뿐인 경우에도 해당 도구의 JSON 스키마가 매 턴 컨텍스트 창의 상당 부분을 차지할 수 있습니다.

**도구 검색**은 이 문제를 해결하기 위해 Hermes가 선택적으로 제공하는 점진적 공개 계층입니다. 활성화하면 MCP 및 플러그인 도구가 모델에 표시되는 도구 배열에서 세 개의 브리지 도구로 대체되고, 모델은 필요할 때 각 도구의 스키마를 로드합니다.

:::info 기본 제공 Hermes 도구는 지연되지 않음
Hermes의 핵심 기능 집합을 구성하는 도구(`terminal`, `read_file`, `write_file`, `patch`, `search_files`, `todo`, `memory`, `browser_*`, `web_search`, `web_extract`, `clarify`, `execute_code`, `delegate_task`, `session_search` 및 나머지 `_HERMES_CORE_TOOLS`)는 *항상* 직접 로드됩니다. 지연 공개 대상은 MCP 도구와 코어가 아닌 플러그인 도구뿐입니다.
:::

## 작동 방식

한 턴에 도구 검색이 활성화되면 모델은 지연된 도구 대신 다음 세 가지 새 도구를 봅니다.

```
tool_search(query, limit?)     — search the deferred-tool catalog
tool_describe(name)            — load the full schema for one tool
tool_call(name, arguments)     — invoke a deferred tool
```

일반적인 상호작용은 다음과 같습니다.

```
Model: tool_search("create a github issue")
  → { matches: [{ name: "mcp_github_create_issue", ... }, ...] }
Model: tool_describe("mcp_github_create_issue")
  → { parameters: { type: "object", properties: { ... } } }
Model: tool_call("mcp_github_create_issue", { title: "...", body: "..." })
  → { ok: true, issue_number: 42 }
```

모델이 `tool_call`을 호출하면 Hermes는 **브리지를 해제하고** 모델이 해당 도구를 직접 호출한 것처럼 내부 도구를 정확히 디스패치합니다. 사전 도구 호출 훅, 가드레일, 승인 프롬프트, 사후 도구 호출 훅은 모두 `tool_call`이 아니라 실제 도구 이름을 기준으로 실행됩니다. CLI와 게이트웨이의 활동 피드도 브리지를 해제하므로 브리지 대신 내부 도구가 표시됩니다.

## 언제 활성화되나요?

도구 검색은 **계층형 공개**를 사용합니다. 지연할 수 있는(MCP/플러그인) 도구가 하나라도 있으면 브리지가 활성화됩니다. 카탈로그 크기에 따라 달라지는 것은 카탈로그 중 얼마나 많은 부분을 계속 표시할지이지, 스키마를 지연할지 여부가 아닙니다.

| 계층 | 조건 | 모델에 표시되는 내용 |
| --- | --- | --- |
| **0** | MCP/플러그인 도구 없음 | 모든 도구를 즉시 로드하고 브리지를 사용하지 않음. 그대로 통과. |
| **1** | 지연된 카탈로그의 목록이 예산에 들어감 | 브리지 + 지연된 모든 도구의 스킬 스타일 매니페스트(이름 + 짧은 설명, 예산을 초과하면 이름만 표시). 축소는 **서버별**로 적용됩니다. 작은 서버(Linear)와 함께 하나의 큰 서버(Cloudflare)가 연결되어 있으면 작은 서버는 도구별 목록을 유지하고 큰 서버만 요약 한 줄로 축소됩니다. |
| **2** | 모든 서버에서 이름만 표시해도 도구별 목록이 예산을 초과함(예: Cloudflare의 평면 API 표면만으로도 이름이 약 32K 토큰인 약 3,300개 도구) | 브리지와 서버별 한 줄 요약(서버 이름 + 도구 수)만 표시하여 모델이 어느 도메인에 접근할 수 있는지 알 수 있게 함. 개별 도구는 `tool_search`를 통해서만 검색 가능. |

목록 예산은 `min(threshold_pct% of context, listing_max_tokens)`입니다. 도구 배열을 구성할 때마다 결정을 다시 평가하므로, 세션 중간에 MCP 서버를 추가하거나 제거하면 다음 구성부터 세션이 계층 사이에서 이동합니다.

## 설정

```yaml
tools:
  tool_search:
    enabled: auto       # auto (default), on, or off
    threshold_pct: 5    # listing budget as a percentage of context
    search_default_limit: 5
    max_search_limit: 20
    listing: auto       # embed a grouped name+description catalog manifest
    listing_max_tokens: 4000
```

| 키 | 기본값 | 의미 |
| --- | --- | --- |
| `enabled` | `auto` | 지연 가능한 도구가 하나 이상 있으면 `auto`/`on`이 활성화되고, `off`는 완전히 비활성화되어 모든 도구를 즉시 로드합니다. |
| `threshold_pct` | `5` | 활성 모델의 컨텍스트 길이에 대한 목록 예산의 비율. 범위는 0~100입니다. |
| `search_default_limit` | `5` | 모델이 `limit` 없이 `tool_search`를 호출할 때 반환되는 결과 수. |
| `max_search_limit` | `20` | 모델이 `limit`으로 요청할 수 있는 하드 상한. 범위는 1~50입니다. |
| `listing` | `auto` | 지연된 모든 도구의 매니페스트(이름 + 설명의 첫 문장, 60자 이하, MCP 서버별 그룹화)를 `tool_search` 브리지 설명에 포함합니다. `auto`는 예산에 들어갈 때 포함하며(이후 이름만 표시, 다시 계층 2 서버 요약으로 대체), `on`/`off`는 각각 강제 적용합니다. |
| `listing_max_tokens` | `4000` | 컨텍스트 크기와 관계없이 포함된 목록에 적용되는 절대 상한. 범위는 200~60000입니다. 큰 카탈로그는 이름만 표시하거나 서버별 요약으로 축소되며, 전체 스키마는 검색을 통해 계속 사용할 수 있습니다. |

### 목록이 존재하는 이유

목록이 없으면 지연된 기능은 **보이지 않습니다**. 실제 벤치마킹에서 모델은 표시되는 코어 도구로 대체하거나(지연된 GitHub 도구를 검색하는 대신 터미널에서 `gh` 실행), `tool_search`를 호출하지 않고 기능이 없다고 선언했습니다. 목록은 도구에 스킬 패턴을 적용합니다. 전체 매개변수 스키마는 지연된 상태로 유지하면서도 모든 기능을 항상 이름으로 검색할 수 있습니다. 모델이 목록에서 정확한 도구 이름을 보면 `tool_search`를 건너뛰고 바로 `tool_describe`로 이동하여 왕복 한 번을 줄일 수 있습니다.

기존의 불리언 형태로 전환할 수도 있습니다.

```yaml
tools:
  tool_search: true   # equivalent to {enabled: auto}
```

## 사용하지 말아야 할 때

도구 검색은 고정된 턴당 토큰 비용(세 브리지 도구 스키마와 카탈로그 목록)과 차가운 도구에서 최소 한 번의 추가 왕복(describe → call)을 지불하는 대신 지연된 스키마에서 비용을 절약합니다. 계층 1에서는 목록에 모든 기능이 표시되므로 검색 왕복이 대개 사라지고 모델은 곧바로 `tool_describe`로 이동합니다. 실제 벤치마킹에서는 목록 모드가 즉시 로드와 동일한 작업 성공률을 보이면서도 브리지만 사용하는 방식보다 비용이 적었습니다.

작은 도구 집합에 예전의 항상 즉시 로드 동작을 원한다면 `enabled: off`로 설정합니다.

## 사라지지 않는 트레이드오프

이는 프롬프트 캐시 무결성 불변식에서 비롯됩니다. 구현에만 해당하는 것이 아니라 모든 점진적 공개 설계에 내재한 특성입니다.

- **차가운 도구에서 왕복 한 번 추가.** 모델이 처음으로 지연된 도구를 필요로 할 때 도구를 찾고 스키마를 로드하기 위해 모델 호출을 한두 번 추가로 사용합니다. 정적 부분에서 토큰을 절약하는 효과는 실제로 존재하지만, 그 일부는 런타임에 다시 지불합니다.
- **지연된 스키마에는 캐시 이점 없음.** 로드된 `tool_describe` 결과는 대화 기록에 들어가므로(다음 턴부터 캐시되기는 함) 시스템 프롬프트 캐시 접두사의 이점은 전혀 얻지 못합니다.
- **모델 품질 의존성.** 도구 검색은 모델이 원하는 도구에 대해 합리적인 검색어를 작성할 수 있다고 가정합니다. 작은 모델은 이를 덜 잘 수행합니다. 도구 검색을 사용했을 때와 사용하지 않았을 때 Opus 4에서 49% → 74%로 향상된 공개 Anthropic 수치는 가능성을 보여주지만, 동시에 약 26포인트의 정확도가 여전히 검색 실패임을 보여줍니다.
- **도구 집합 편집은 캐시 무효화.** 세션 중간에 도구를 추가하거나 제거하면 브리지 도구 설명(지연된 도구 수를 포함함)과 카탈로그가 변경되므로 프롬프트 캐시가 무효화됩니다. 이는 모든 도구 집합 편집과 동일한 트레이드오프입니다.

## 구현 세부 사항

- **검색:** 토큰화된 도구 이름 + 설명 + 매개변수 이름에 BM25를 적용합니다. BM25가 양의 점수인 결과를 반환하지 않으면 도구 이름의 리터럴 부분 문자열 일치로 대체합니다. 이는 모든 도구 이름에 `github`가 포함된 카탈로그에서 `"github"`를 검색하는 경우처럼 IDF가 0이 되는 특수한 상황에서도 보호 기능을 제공합니다.
- **카탈로그는 턴 간 상태를 유지하지 않음.** 매 구성마다 현재 도구 정의 목록에서 다시 빌드하며 세션 키가 있는 `Map`을 사용하지 않습니다. 이렇게 하면 저장된 카탈로그가 실제 도구 레지스트리와 동기화되지 않는 종류의 버그를 피할 수 있습니다.
- **카탈로그는 세션의 도구 집합으로 범위가 제한됨.** `tool_search`, `tool_describe`, `tool_call`은 세션에 실제로 부여된 도구만 보고 호출합니다. 도구 집합의 일부로 제한된 서브에이전트, kanban 워커 또는 게이트웨이 세션은 브리지를 사용하여 해당 범위 밖의 도구를 검색하거나 호출할 수 없습니다. 지연된 카탈로그는 전체 프로세스 레지스트리가 아니라 세션 자체의 활성화/비활성화된 도구 집합 중 지연 가능한 부분입니다.
- **JS 샌드박스 없음.** Hermes는 더 단순한 "구조화된 도구" 모드(검색 / 설명 / 호출을 일반 함수로 사용)를 사용합니다. 다른 구현에서 제공하는 JS 샌드박스의 "코드 모드"는 표면적이 크므로 사용하지 않습니다.
