# 코드 단순화 — 병렬 검토 및 정리

4명의 집중 검토자가 병렬로 최근 코드 변경 사항을 검토하고, 결과를 종합한 다음 적용할 가치가 있는 수정 사항을 반영합니다.

**이 작업은 버그 찾기가 아니라 정리 작업입니다.** 이미 동작하는 코드의 품질을 개선하여 중복을 제거하고, 불필요한 복잡성을 평탄화하고, 낭비를 줄이며, 임시방편 수정을 더 근본적으로 개선합니다. 여기서 정확성 버그를 찾아다니지 마세요. 그 역할은 `requesting-code-review`에 있습니다.

**핵심 원칙:** 하나의 광범위한 검토자보다 네 명의 좁은 범위 검토자가 낫습니다. 각 검토자는 네 가지를 모두 보느라 주의를 분산하지 않고 재사용성, 품질, 효율성, 추상화 수준이라는 단일 문제 유형을 깊이 탐색합니다. 검토자들은 동시에 실행되므로 네 번의 검토가 아니라 한 번의 검토에 해당하는 지연 시간만 부담합니다.

## 사용 시점

다음과 같이 말할 때 이 스킬을 실행합니다.

- "simplify" / "simplify my changes" / "simplify these changes"
- "review my code" / "review my recent changes" / "clean up my changes"
- "/simplify" (Claude Code 사용 습관을 이어가는 경우)

사용자가 추가할 수 있는 선택적 수식어도 존중합니다.

- **초점:** "simplify focus on efficiency" → 효율성 검토자만 실행하거나(또는 결과 종합에서 효율성 검토에 더 큰 비중을 둡니다). 인식되는 초점은 `reuse`, `quality` (`simplification`도 허용), `efficiency`, `altitude`입니다.
- **시험 실행:** "simplify but don't change anything" / "just report" → 네 검토자를 실행하고 결과를 제시하되 아무것도 적용하지 않습니다. 적용하기 전에 사용자에게 묻습니다.
- **범위:** "simplify the last commit" / "simplify staged" / "simplify src/foo.py" → 요청에 따라 변경 사항의 원본 범위를 좁힙니다(1단계 참조).

매번 편집 후 자동으로 실행하거나 관련 없는 작업의 끝에 덧붙이지 마세요. 이 작업은 네 하위 에이전트에 해당하는 토큰을 사용하므로 사용자가 명시적으로 요청했을 때만 실행합니다.

## 과정

### 1단계: 변경 사항 식별

사용자가 요청한 방식에 따라 검토할 diff를 수집합니다. 기본 순서는 다음과 같습니다.

```bash
# 1. Default: uncommitted working-tree changes (tracked files)
git diff

# 2. If that's empty, include staged changes
git diff HEAD

# 3. Scoped variants the user may request:
git diff --staged                 # "staged changes"
git diff HEAD~1                    # "the last commit"
git diff main...HEAD              # "this branch" / "my PR"
git diff -- src/foo.py            # specific file(s)
```

`git diff`와 `git diff HEAD`가 모두 비어 있고 Git 저장소나 변경 사항도 없다면, 사용자가 명시적으로 지정했거나 이 세션에서 최근 생성/편집된 파일로 대체합니다. 검토할 코드 변경 사항을 정말로 찾을 수 없다면 그렇게 말하고 중단합니다. 단순화할 것이 없습니다.

전체 diff 텍스트를 수집합니다. 크기도 기록합니다. 매우 크다면(예: 변경된 줄이 2,000줄 초과) 네 하위 에이전트가 모두 전체 diff를 전달받으므로 토큰 비용이 커진다고 사용자에게 알리고, 범위를 줄일지(디렉터리별 또는 커밋별) 제안합니다.

### 2단계: 네 검토자를 병렬로 실행

`delegate_task` **배치 모드**를 사용합니다. 네 작업을 모두 하나의 `tasks` 배열에 전달하여 동시에 실행합니다. 네 갈래 분기가 적절하며 기본 설치의 `delegation.max_concurrent_children` 제한 내에 있습니다.

**위임을 사용할 수 없나요?** 이 컨텍스트에서 `delegate_task`를 호출할 수 없거나(리프 하위 에이전트, 위임 비활성화, 예산 소진) 네 검토 관점을 생략하거나 줄이지 마세요. 이 컨텍스트에서 네 검토 관점을 차례대로 직접 수행합니다. 그런 다음 최종 요약에서 이것이 병렬 분기가 아닌 단일 패스 인라인 검토였음을 명확히 밝혀 실제로 어떤 검토가 실행되었는지 사용자가 알 수 있게 합니다.

네 검토자 모두에게 전체 diff(일부가 아님)와 절대 저장소 경로를 전달하여 더 넓은 코드베이스를 검색할 수 있게 합니다. 각 검토자는 `terminal`, `file`, `search` 도구 모음(따라서 `git`, `read_file`, `search_files`/grep 사용 가능)을 받습니다.

모든 검토자에게 다음을 지시합니다.

- diff만 보고 추론하지 말고 기존 코드베이스에서 근거를 검색합니다.
- **체스터턴의 울타리 원칙을 적용합니다.** 제거를 지적하기 전에 해당 줄의 `git blame`을 실행하여 존재 이유를 파악합니다. 원래 목적을 판단할 수 없다면 추측하지 말고 `confidence: low`로 표시합니다.
- 구체적인 비용, 확신도, 위험을 포함한 구조화된 결과로 보고합니다.
  ```
  file:line → problem → cost (what's duplicated/wasted/harder to maintain) → suggested fix | confidence: high/medium/low | risk: SAFE/CAREFUL/RISKY
  ```
  - **SAFE** = 동작에 영향을 주지 않는 것이 입증됨(사용하지 않는 import, 주석 처리된 코드, 그대로 전달하는 래퍼). 자동 적용합니다.
  - **CAREFUL** = 의미를 바꾸지 않고 개선함(지역 변수 이름 변경, 중첩 삼항 연산자 평탄화, 헬퍼 추출). 테스트로 검증하며 적용합니다.
  - **RISKY** = 동작을 바꾸거나 공개 계약을 깨뜨릴 수 있음(N+1 재구성, 공개 API 이름 변경, 메모리 수명 변경). 사람의 검토를 위해 표시하고 자동 적용하지 않습니다.
- 사소한 지적과 스타일만 바꾸는 변경은 건너뜁니다. 코드에 실질적인 개선을 가져오는 항목만 지적합니다.

사용자가 초점에서 제외한 항목은 제거하고 다음 네 가지 목표를 전달합니다.

**검토자 1 — 코드 재사용**
> 이 diff에서 코드가 코드베이스에 이미 있는 기능을 중복 구현하는지 검토합니다. 유틸리티 모듈, 공유 헬퍼, 인접 파일을 검색(`search_files` / grep 사용)하여 새 코드가 직접 재구현하는 대신 호출할 수 있는 기존 함수, 상수, 패턴을 찾습니다. 기존 함수를 중복하는 새 함수, 기존 유틸리티가 이미 처리하는 로직을 직접 작성한 코드(수동 문자열/경로 조작, 사용자 정의 환경 변수 확인, 임시 타입 가드, 재구현한 파싱)를 지적합니다. 각 항목에 사용할 기존 요소와 위치를 명시합니다.

**검토자 2 — 코드 품질**
> 이 diff의 품질 문제를 검토합니다. 불필요한 상태(기존 상태와 중복되거나 기존 상태에서 파생할 수 있는 값, 없어도 되는 캐시), 매개변수 확장(함수를 재구성해야 하는데 새 매개변수만 덧붙임), 변형을 가한 복사-붙여넣기 블록(공유 추상화를 사용해야 하는 유사 블록), 누수되는 추상화(내부 구현을 노출하거나 기존 캡슐화 경계를 깨뜨림), 문자열로 표현한 타입(상수/열거형/레지스트리가 이미 있는데 원시 문자열 사용 — 지적하기 전에 정식 레지스트리를 확인), 깊이 중첩된 조건문(삼항 연산자 연쇄, 3단계 이상의 if/else 피라미드 — 가드 절, 조기 반환 또는 조회 테이블로 평탄화), AI가 생성한 군더더기(명백한 코드를 다시 설명하는 추가 주석, 예: `// increment counter`와 그 아래 `count++`; 이미 검증된 입력에 대한 불필요한 방어적 null 확인; 타입 시스템을 우회하는 `as any` 캐스팅; 파일의 나머지 부분과 일관되지 않은 패턴)를 살핍니다. 각 항목에 구체적인 리팩터링을 제시합니다.

**검토자 3 — 효율성**
> 이 diff의 효율성 문제를 검토합니다. 불필요한 작업(중복 계산, 반복적인 파일 읽기, 중복 API 호출, N+1 접근 패턴), 놓친 동시성(독립적인 작업을 순차적으로 실행), 핫패스 비대화(시작 시 또는 요청마다 무겁거나 차단하는 작업), TOCTOU 안티패턴(작업 전에 존재 여부를 확인하고 오류를 처리하는 대신 작업을 수행한 뒤 오류를 처리해야 함), 메모리 문제(제한 없는 증가, 누락된 정리, 리스너/핸들 누수, 전체 바깥 스코프를 캡처하는 클로저로 만든 장수 콜백 또는 객체 — 객체가 존재하는 동안 캡처한 모든 것이 유지되므로 작은 클래스나 필요한 것만 복사하는 명시적 필드 구조체를 선호), 지나치게 광범위한 읽기(일부분이면 충분한데 파일 전체를 로드), 조용한 실패(빈 catch 블록, 무시된 오류 반환, `except: pass`, 처리 없이 사용하는 `.catch(() => {})`, 오류 전파 누락 — 이런 방식은 버그를 숨기므로 최소한 삼키기 전에 로그를 남겨야 함)를 찾습니다. 각 항목에 구체적인 수정 방법과 더 빠르거나 안전해지는 이유를 제시합니다.

**검토자 4 — 추상화 수준**
> 이 diff의 변경 사항이 잘못된 깊이에서 구현되었는지 검토합니다. 공유 인프라 위에 임시방편을 쌓고 인프라 자체를 수정하지 않은 변경이 해당합니다. 너무 얕은 수정의 징후는 다음과 같습니다. 한 호출자를 처리하기 위해 일반 코드 경로에 특수 사례를 추가함(예: `if (caller == X)` 분기, 타입 확인, 매직 값 우회로), 호출 지점에서 증상을 수정했지만 같은 결함이 있는 형제 호출 지점은 그대로 둠, 이전 임시방편 위에 또 다른 우회책을 쌓음, 실제로 수정해야 하는 대상을 건드리지 않기 위해 래퍼를 추가함, 잘못된 기본값을 수정하는 대신 설정이나 플래그를 도입해 우회함. 각 항목에 대해 변경 사항이 피하고 있는 기반 메커니즘을 식별하고 더 깊은 수정 방법을 설명합니다 — 공유 경로를 일반화하거나, 근본 기본값을 수정하거나, 버그 유형 전체를 수정합니다. 더 깊은 수정이 별도 작업으로 분리할 만큼 큰 경우에는 솔직하게 밝힙니다. 주변 코드와 `git blame`을 먼저 읽습니다. 임시방편처럼 보이는 것이 의도적인 경계일 수도 있습니다(호환성 shim, 단계적 마이그레이션, vendored 코드 격리). 그런 경우에는 지적하지 않습니다.

### 3단계: 종합 및 적용

네 검토자가 모두 결과를 반환할 때까지 기다립니다(배치 모드는 결과를 함께 반환합니다).

1. 검토 결과를 하나의 목록으로 합치고 중복을 제거합니다. 두 항목이 같은 줄이나 같은 기반 메커니즘을 대상으로 한다면 하나로 합칩니다.
2. 잘못된 양성 결과를 버립니다. 가장 많은 맥락을 가진 것은 사용자이므로 검토자의 제안에 반드시 반박할 필요는 없고, 약하거나 잘못된 제안은 조용히 제외하면 됩니다.
3. 충돌을 해결합니다. 검토자들은 의견이 다를 수 있습니다(검토자 1: "기존 유틸리티 X를 사용하라"; 검토자 3: "X는 느리므로 인라인하라"). 기본 우선순위는 **정확성 > 사용자가 명시한 초점 > 가독성/재사용성 > 미세한 성능**입니다. 경로가 실제로 핫패스가 아닌 한 명확성을 해치는 성능 수정을 적용하지 않습니다. 서로 배타적이지만 모두 타당한 제안이라면 코드 변경이 더 적은 쪽을 선택하고 대안을 기록합니다.
4. 위험 등급 순서로 적용합니다.
   - **SAFE 우선**(자동 적용): 사용하지 않는 import, 주석 처리된 코드, 그대로 전달하는 래퍼, 불필요한 타입 단언. 이후 테스트를 실행합니다.
   - **CAREFUL 다음**(검증하며 적용, 파일별로 한 번에 하나씩): 지역 변수 이름 변경, 삼항 연산자 평탄화, 헬퍼 추출, 중복 통합. 각 파일 후 테스트를 실행합니다. 깨지는 항목은 되돌립니다.
   - **RISKY 마지막**(검토를 위해 표시하고 자동 적용하지 않음): N+1 재구성, 공개 API 변경, 동시성 수정, 오류 처리 변경. 위험 설명과 테스트 커버리지 상태를 함께 제시합니다. 추상화 수준 관련 결과는 대개 이 등급입니다. 수정을 더 깊게 하려면 공유 인프라를 건드려야 하므로, 더 깊은 수정과 그것을 지금 수행할지 후속 작업으로 할지를 사용자에게 제시합니다.
   시험 실행을 선택한 경우 세 등급을 모두 제시하고 아무것도 적용하지 않습니다.
5. 문제가 발생하지 않았는지 확인합니다. 변경된 파일에 대한 프로젝트의 대상 테스트(전체 테스트가 아님)를 실행하고, 저장소에서 사용하는 린터/타입 검사도 다시 실행합니다. 수정 사항으로 테스트가 깨지면 해당 수정만 되돌리고 보고합니다.
6. 변경 사항을 요약합니다. 검토자 범주와 위험 등급별로 적용한 수정 사항을 짧게 나열하고, 의도적으로 건너뛴 결과와 그 이유를 함께 적습니다. 위임 없이 인라인으로 실행했다면 이 사실도 여기에 밝힙니다.
## 주의할 점

- **4개보다 넓게 분산하지 마세요.** 검토자가 많아지면 비용과 조율해야 할 상충되는 제안만 늘어날 뿐, 커버리지가 좋아지지는 않습니다. 네 가지 범주면 전체 영역을 다룰 수 있습니다.
- **각 검토자에게 전체 diff를 제공하세요.** diff를 나누면 설계의 허점이 가려집니다. 파일 간 중복과 N+1 문제는 전체 diff를 봐야만 드러납니다.
- **검토자는 추측하지 말고 검색해야 합니다.** 기존 유틸리티를 재사용하라는 지적에 해당 유틸리티를 가리키는 포인터가 없다면(“아마 이런 헬퍼가 있을 겁니다” 같은 식이라면) 잡음에 불과합니다. `file:line` 근거를 요구하고, 근거가 없는 지적은 제외하세요.
- **Apply ≠ rewrite.** 이것은 사용자가 최근에 변경한 내용을 정리하는 작업이지, 모듈 전체를 리팩터링할 수 있는 면허가 아닙니다. 수정 범위는 diff가 건드린 부분과, 문제를 해결하는 데 필요한 최소한의 주변 변경으로 제한하세요. 더 깊은 수정이 필요한 경우가 예외입니다. 올바른 수정이 diff보다 더 깊은 곳에 있다면 **지적만 하세요** — 정리 작업 중에 공유 메커니즘을 일방적으로 재구축하지 마세요.
- **버그 찾기로 방향을 바꾸지 마세요.** 검토자가 실제 정확성 버그를 발견하면 눈에 띄게 보고하되, 수정 사항에 섞지 말고 별도의 “발견된 버그” 항목으로 기록하세요. 정확성 검토는 검증 기준이 다른 별도의 단계입니다.
- **프로젝트 규칙을 존중하세요.** 저장소에 AGENTS.md / CLAUDE.md / HERMES.md 또는 린터 설정이 있다면 검토자 프롬프트에 반영하여 제안이 프로젝트의 스타일과 충돌하지 않도록 하세요.
- **큰 diff는 컨텍스트를 소진시킵니다.** diff가 너무 크다면 위임 전에 범위를 줄이세요. 검토자 네 명에게 각각 5000줄짜리 diff를 전달하면 비용이 크고 내용이 잘릴 수 있습니다.
- **오래된 코드 도구를 과신하지 마세요.** `knip`, `ts-prune`, `depcheck`는 동적으로 사용되는 export(문자열 기반 import나 리플렉션 등)도 사용되지 않는 것으로 표시합니다. 심볼 이름을 항상 검색한 뒤 삭제하세요. 도구 보고서가 깨끗하다는 것만으로는 충분한 근거가 되지 않습니다.
- **공개 계약을 확인하지 않은 채 이름을 바꾸지 마세요.** export 이름, API 경로, DB 컬럼 이름, 설정 키는 계약입니다. 이름이 좋지 않더라도 변경하면 소비자가 깨집니다. 공개 계약 변경은 RISKY로 표시하고, 자동으로 이름을 바꾸지 마세요.
- **“불필요한” 오류 처리를 제거하지 마세요.** 빈 catch 블록이나 무시된 오류는 해당 맥락에서 의도된 것이거나 무해한 오류일 수 있습니다. 지적만 하고 제거하지 마세요. 최종 결정은 사람이 내리도록 하세요.
- **모든 특수 사례가 임시방편은 아닙니다.** 벤더 코드 주변의 호환성 shim, 단계적 마이그레이션, 격리 계층은 고도 위반처럼 보일 수 있지만 의도적인 설계일 수 있습니다. 문제를 제기하기 전에 `git blame`과 주변 주석으로 의도를 확인하세요. 의도가 불분명하면 신뢰도를 낮게 표시하세요.

## 관련 항목

설치 환경에 `subagent-driven-development` 스킬이 있다면 구현 중 병렬 검토를 작업별로 다루므로 상호 보완적으로 사용할 수 있습니다. 이 스킬은 사후 정리를 위한 독립적인 단계입니다. 커밋 전 보안/품질 게이트에는 `$code-review`를 사용하세요. 이는 버그를 찾는 별도의 검토 단계입니다.
