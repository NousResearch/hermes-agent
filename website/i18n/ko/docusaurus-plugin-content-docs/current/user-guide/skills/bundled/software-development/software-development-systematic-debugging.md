# 체계적 디버깅

## 개요

무작위로 수정하면 시간이 낭비되고 새로운 버그가 생깁니다. 빠른 패치는 근본적인 문제를 가립니다.

**핵심 원칙:** 수정하기 전에 항상 근본 원인을 찾으세요. 증상만 고치는 것은 실패입니다.

**이 프로세스의 문구를 위반하는 것은 디버깅의 취지를 위반하는 것입니다.**

## 철칙

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

Phase 1을 완료하지 않았다면 수정안을 제안할 수 없습니다.

## 피드백 루프 규칙

피드백 루프가 곧 디버깅 작업입니다. 이론을 세우기 위해 코드를 읽기 전에, 사용자가 겪은 정확한 증상에서 실패하고 버그가 수정되면 성공하는 **긴밀한** 명령을 만들거나 찾아내세요. 긴밀한 루프는 빠르고 결정적이며 에이전트가 실행할 수 있고, 단순히 "충돌하지 않는가"가 아니라 이 버그를 잡을 만큼 구체적이어야 합니다.

깨끗한 재현이 어렵다면 루프를 만드는 데 불균형적으로 많은 노력을 들이세요. 빨간색이 될 수 있는 루프 없이 추측하는 것이 이 스킬이 막고자 하는 실패 모드입니다.

## 사용 시점

다음과 같은 **모든** 기술적 문제에 사용하세요:
- 테스트 실패
- 프로덕션 버그
- 예상치 못한 동작
- 성능 문제
- 빌드 실패
- 통합 문제

**다음과 같은 경우에는 특히 사용하세요:**
- 시간 압박을 받을 때 (긴급 상황에서는 추측하고 싶은 마음이 커집니다)
- "빠른 수정 하나만" 하면 될 것처럼 보일 때
- 이미 여러 번 수정을 시도했을 때
- 이전 수정이 작동하지 않았을 때
- 문제를 완전히 이해하지 못했을 때

**다음과 같은 경우에도 건너뛰지 마세요:**
- 문제가 단순해 보일 때 (단순한 버그에도 근본 원인은 있습니다)
- 서두르고 있을 때 (서두르면 반드시 재작업하게 됩니다)
- 누군가 지금 당장 고치기를 원할 때 (체계적으로 접근하는 것이 무작정 시도하는 것보다 빠릅니다)

## 네 가지 Phase

다음 Phase로 진행하기 전에 각 Phase를 반드시 완료해야 합니다.

## Phase 1: 근본 원인 조사

**어떤 수정이든 시도하기 전에:**

### 1. 오류 메시지를 주의 깊게 읽기

- 오류나 경고를 건너뛰지 마세요
- 오류와 경고에는 정확한 해결책이 들어 있는 경우가 많습니다
- 스택 트레이스를 끝까지 읽으세요
- 줄 번호, 파일 경로, 오류 코드를 기록하세요

**작업:** 관련 소스 파일에 `read_file`을 사용하세요. 코드베이스에서 오류 문자열을 찾으려면 `search_files`를 사용하세요.

### 2. 긴밀한 피드백 루프 만들기

- 사용자의 정확한 증상을 한 번의 명령으로 재현할 수 있나요?
- 이 버그에서는 명령이 실패하고, 버그가 수정된 뒤에만 통과하나요?
- 반복해서 실행할 수 있을 만큼 빠른가요?
- 결정적인가요? 불안정한 버그라면 재현율을 충분히 높여 디버깅할 수 있나요?
- 재현할 수 없다면 → 더 많은 데이터를 수집하고 추측하지 마세요.

**루프를 구성하는 방법 — 대략 다음 순서로 시도하세요:**

1. 버그에 도달하는 접점의 **실패하는 테스트**: 단위, 통합 또는 엔드투엔드
2. 실행 중인 개발 서버에 대한 **HTTP 스크립트 / curl**
3. 픽스처 입력을 사용한 **CLI 호출** — stdout/stderr를 예상 결과와 비교
4. DOM, 콘솔 또는 네트워크를 검증하는 **헤드리스 브라우저 스크립트** (Playwright/Puppeteer)
5. **캡처된 트레이스 재생**: HAR, 요청 페이로드, 이벤트 로그, 큐 메시지 또는 웹훅 본문
6. 실패하는 경로를 호출하는 시스템의 가장 작은 유용한 부분을 부팅하는 **일회성 하네스**
7. 넓은 입력 공간에서 간헐적으로 잘못된 출력이 나오는 경우의 **속성 / 퍼즈 루프**
8. 버그가 알려진 두 상태 사이에서 나타났을 때 사용할 수 있는 `git bisect run`용 **이분 탐색 하네스**
9. 이전 버전과 새 버전, 두 설정, 두 제공자 또는 두 데이터셋을 비교하는 **차등 루프**
10. 최후의 수단으로만 사용하는 **휴먼 인 더 루프 스크립트**: 사람의 단계를 스크립트로 만들고 결과를 캡처하여 루프를 구조화된 상태로 유지

**루프가 생긴 뒤에는 루프를 더 긴밀하게 만드세요:**

- 더 빠르게 만들기: 설정을 캐시하고, 범위를 좁히고, 관련 없는 초기화를 건너뛰세요.
- 신호를 더 선명하게 만들기: 일반적인 성공이 아니라 정확한 증상을 검증하세요.
- 더 결정적으로 만들기: 시간을 고정하고, 난수를 시드하고, 파일 시스템을 격리하고, 네트워크를 고정하세요.

비결정적 버그의 즉각적인 목표는 완벽함이 아니라 더 높은 재현율입니다. 트리거를 100번 실행하고, 병렬화하고, 부하를 추가하고, 타이밍 창을 좁히거나, sleep을 주입하세요. 50% 플래키는 디버깅할 수 있지만 1% 플래키는 대개 디버깅하기 어렵습니다.

**작업:** `terminal` 도구를 사용해 긴밀한 루프를 실행하세요:

```bash
# Run a specific failing test
pytest tests/test_module.py::test_name -v

# Or run a scripted repro
python scripts/repro_bug.py

# Or run a high-repetition flaky repro
for i in {1..100}; do pytest tests/test_flake.py::test_name -q || break; done
```

### 3. 최근 변경 사항 확인

- 이 문제를 일으킬 수 있는 변경 사항은 무엇인가요?
- Git diff, 최근 커밋
- 새로운 의존성, 설정 변경

**작업:**

```bash
# Recent commits
git log --oneline -10

# Uncommitted changes
git diff

# Changes in specific file
git log -p --follow src/problematic_file.py | head -100
```

### 4. 여러 컴포넌트로 이루어진 시스템에서 증거 수집

**시스템에 여러 컴포넌트가 있는 경우 (API → 서비스 → 데이터베이스, CI → 빌드 → 배포):**

**수정안을 제안하기 전에 진단용 계측을 추가하세요:**

각 컴포넌트 경계마다:
- 컴포넌트에 들어오는 데이터를 로깅하세요
- 컴포넌트에서 나가는 데이터를 로깅하세요
- 환경/설정 전파를 검증하세요
- 각 계층의 상태를 확인하세요

한 번 실행하여 **어디서** 문제가 발생하는지를 보여주는 증거를 수집하세요.
그런 다음 증거를 분석하여 실패하는 컴포넌트를 식별하세요.
그런 다음 해당 컴포넌트를 조사하세요.

### 5. 데이터 흐름 추적

**호출 스택 깊은 곳에서 오류가 발생하는 경우:**

- 잘못된 값은 어디서 시작되나요?
- 이 함수를 잘못된 값과 함께 호출한 것은 무엇인가요?
- 출처를 찾을 때까지 상류로 계속 추적하세요
- 증상이 아니라 출처에서 수정하세요

**작업:** 참조를 추적하려면 `search_files`를 사용하세요:

```python
# Find where the function is called
search_files("function_name(", path="src/", file_glob="*.py")

# Find where the variable is set
search_files("variable_name\\s*=", path="src/", file_glob="*.py")
```

### Phase 1 완료 체크리스트

- [ ] 오류 메시지를 완전히 읽고 이해함
- [ ] 긴밀한 루프 명령이 존재하며 적어도 한 번 실행함
- [ ] 루프가 빨간색이 될 수 있음: 가까운 다른 실패가 아니라 사용자의 정확한 증상을 검증함
- [ ] 루프가 결정적이거나, 플래키 버그의 재현율이 디버깅하기에 충분히 높음
- [ ] 최근 변경 사항을 식별하고 검토함
- [ ] 증거를 수집함 (로그, 상태, 데이터 흐름)
- [ ] 문제를 특정 컴포넌트/코드로 격리함
- [ ] 근본 원인 가설을 진술하고 검증할 수 있음

**중단:** 왜 이런 문제가 발생하는지 이해하기 전에는 Phase 2로 진행하지 마세요.

## Phase 2: 패턴 분석

**수정하기 전에 패턴을 찾으세요:**

### 0. 재현 최소화

루프가 빨간색이 되면 여전히 빨간색을 유지하는 가장 작은 시나리오로 재현을 줄이세요. 입력, 호출자, 설정, 데이터 및 단계를 **한 번에 하나씩** 제거하고, 제거할 때마다 루프를 다시 실행하세요. 실패에 결정적인 요소만 남기세요.

남아 있는 요소를 하나라도 제거하면 루프가 초록색이 되는 시점에 완료된 것입니다. 최소 재현은 가설 공간을 좁히며, 가장 깔끔한 회귀 테스트가 되는 경우가 많습니다.

### 1. 작동하는 예시 찾기

- 같은 코드베이스에서 유사하게 작동하는 코드를 찾으세요
- 고장 난 것과 유사하면서 작동하는 것은 무엇인가요?

**작업:** 비교 가능한 패턴을 찾으려면 `search_files`를 사용하세요:

```python
search_files("similar_pattern", path="src/", file_glob="*.py")
```

### 2. 참조와 비교

- 패턴을 구현하는 경우 참조 구현을 **완전히** 읽으세요
- 훑어보지 마세요 — 모든 줄을 읽으세요
- 적용하기 전에 패턴을 완전히 이해하세요

### 3. 차이점 식별

- 작동하는 것과 고장 난 것의 차이는 무엇인가요?
- 아무리 작아도 모든 차이를 나열하세요
- "그건 중요하지 않을 거야"라고 가정하지 마세요

### 4. 의존성 이해

- 이것에 필요한 다른 컴포넌트는 무엇인가요?
- 어떤 설정, 구성, 환경이 필요한가요?
- 어떤 가정을 전제로 하나요?

## Phase 3: 가설 수립 및 테스트

**과학적 방법:**

### 1. 순위를 매긴 반증 가능한 가설 수립

- 단일 가설을 테스트하기 전에 그럴듯한 가설을 3~5개 생성하세요.
- 가능성이 높고 반증 비용이 낮은 순서로 순위를 매기세요.
- 각 가설이 내놓는 예측을 명시하세요: "X가 원인이라면 Y를 변경하거나 관찰했을 때 Z가 발생해야 합니다."
- 검증 가능한 예측을 내놓지 못하는 가설은 버리거나 구체화하세요.

사용자가 함께 있다면 테스트하기 전에 순위가 매겨진 목록을 보여 주세요. 사용자는 도메인 지식으로 순위를 즉시 재조정할 수 있습니다. 사용자가 자리를 비웠다면 순위를 정해 진행하세요.

### 2. 최소한으로 테스트

- 가장 높은 순위의 가설을 가능한 가장 작은 탐색으로 테스트하세요.
- 한 번에 하나의 변수만 변경하세요.
- 여러 가지를 한 번에 수정하지 마세요.
- 가능하다면 디버거/REPL 검사를 우선하세요. 중단점 하나가 로그 열 개보다 낫습니다.
- 로그를 추가한다면 `[DEBUG-a4f2]`와 같은 고유 접두사로 모든 임시 줄에 태그를 지정하여 한 번의 검색으로 정리할 수 있게 하세요.

### 3. 계속하기 전에 검증

- 작동했나요? → Phase 4
- 작동하지 않았나요? → **새로운** 가설 수립
- 그 위에 더 많은 수정을 추가하지 마세요

### 4. 모를 때

- "X를 이해하지 못하겠습니다"라고 말하세요
- 아는 척하지 마세요
- 사용자에게 도움을 요청하세요
- 더 조사하세요

## Phase 4: 구현

**증상이 아니라 근본 원인을 수정하세요:**

### 1. 실패하는 테스트 케이스 만들기

- 가능한 가장 단순한 재현
- 가능하다면 자동화된 테스트
- 수정하기 전에 **반드시** 존재해야 함
- `test-driven-development` 스킬을 사용하세요

### 2. 단일 수정 구현

- 식별한 근본 원인을 해결하세요
- 한 번에 **하나**만 변경하세요
- "이왕 하는 김에" 개선하지 마세요
- 리팩터링을 묶어서 하지 마세요

### 3. 수정 검증

```bash
# Run the specific regression test
pytest tests/test_module.py::test_regression -v

# Run full suite — no regressions
pytest tests/ -q
```

### 4. 수정이 작동하지 않는다면 — 세 번 규칙

- **중단하세요.**
- 횟수를 세세요: 몇 번 수정을 시도했나요?
- 3회 미만이면: Phase 1로 돌아가 새로운 정보로 다시 분석하세요
- **3회 이상이면: 아키텍처에 의문을 제기하세요 (아래 5단계).**
- 아키텍처 논의 없이 수정 #4를 시도하지 마세요

### 5. 3회 이상의 수정이 실패했다면: 아키텍처에 의문 제기

**아키텍처 문제를 나타내는 패턴:**
- 각 수정에서 서로 다른 위치의 새로운 공유 상태/결합이 드러남
- 수정을 구현하려면 "대규모 리팩터링"이 필요함
- 각 수정이 다른 곳에서 새로운 증상을 만듦

**중단하고 기본 전제에 의문을 제기하세요:**
- 이 패턴은 근본적으로 타당한가요?
- 우리는 "순전히 관성 때문에 고집스럽게 유지"하고 있는 건가요?
- 증상을 계속 고치는 대신 아키텍처를 리팩터링해야 하나요?

더 많은 수정을 시도하기 전에 사용자와 논의하세요.

이는 실패한 가설이 **아닙니다** — 잘못된 아키텍처입니다.

## 흔한 합리화

| 핑계 | 현실 |
|-------|---------|
| "문제가 단순하니 절차는 필요 없어" | 단순한 문제에도 근본 원인은 있습니다. 절차는 단순한 버그를 해결할 때 오히려 빠릅니다. |
| "긴급하니 절차를 따를 시간이 없어" | 체계적인 디버깅은 무작정 추측하고 시행착오를 반복하는 것보다 훨씬 빠릅니다. |
| "일단 이것부터 시도하고 나중에 조사하자" | 첫 번째 수정이 이후의 방식과 기준을 정합니다. 처음부터 제대로 하세요. |
| "수정이 제대로 작동하는지 확인한 다음 테스트를 작성하자" | 테스트하지 않은 수정은 오래 유지되지 않습니다. 먼저 테스트를 작성하면 문제를 입증할 수 있습니다. |
| "여러 가지를 한꺼번에 수정하면 시간을 절약할 수 있어" | 무엇이 효과가 있었는지 분리해서 확인할 수 없습니다. |
| "참고 자료가 너무 기니 패턴만 보고 적용하자" | 불완전한 이해는 버그를 보장합니다. 끝까지 읽으세요. |
| "문제가 뭔지 알겠으니 바로 수정하자" | 증상을 보는 것과 근본 원인을 이해하는 것은 다릅니다. |
| 2번 이상 실패한 뒤에도 "한 번만 더 수정해 보자" | 3번 이상 실패했다면 아키텍처에 문제가 있다는 뜻입니다. 패턴을 의심하고 다시 수정하지 마세요. |

## 빠른 참조

|-------|---------------|------------------|
| **1. 근본 원인** | 오류 읽기, 재현, 변경 사항 확인, 증거 수집, 데이터 흐름 추적 | 무엇이 문제이고 왜 발생했는지 이해 |

| **4. 구현** | 회귀 테스트 작성, 근본 원인 수정, 검증 | 버그 해결, 모든 테스트 통과 |

## Hermes Agent 통합

### 조사 도구

1단계에서 다음 Hermes 도구를 사용하세요.

- **`search_files`** — 오류 문자열을 찾고, 함수 호출을 추적하며, 패턴을 찾습니다.
- **`read_file`** — 정확한 분석을 위해 소스 코드를 줄 번호와 함께 읽습니다.
- **`terminal`** — 테스트를 실행하고, Git 기록을 확인하며, 버그를 재현합니다.
- **`web_search`/`web_extract`** — 오류 메시지와 라이브러리 문서를 조사합니다.

### `delegate_task` 사용

여러 구성 요소에 걸친 복잡한 디버깅의 경우, 조사 하위 에이전트를 파견하세요.

```python
delegate_task(
    goal="Investigate why [specific test/behavior] fails",
    context="""
    Follow systematic-debugging skill:
    1. Read the error message carefully
    2. Reproduce the issue
    3. Trace the data flow to find root cause
    4. Report findings — do NOT fix yet

    Error: [paste full error]
    File: [path to failing code]
    Test command: [exact command]
    """,
    toolsets=['terminal', 'file']
)
```

### `test-driven-development` 사용

버그를 수정할 때:
1. 버그를 재현하는 테스트를 작성합니다(RED).
2. 체계적으로 디버깅하여 근본 원인을 찾습니다.
3. 근본 원인을 수정합니다(GREEN).
4. 테스트로 수정 사항을 입증하고 회귀를 방지합니다.

## 실제 영향
