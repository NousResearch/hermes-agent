# 1-3-1 커뮤니케이션 규칙

여러 접근 방식이 가능하고 사용자에게 명확한 추천이 필요할 때 사용하는 구조화된 의사결정 형식입니다. 간결한 문제 정의, 장단점이 있는 세 가지 선택지, 추천 경로를 위한 실행 가능한 계획을 만듭니다.

## 사용 시점

- 사용자가 명시적으로 "1-3-1" 응답을 요청한 경우
- 기술적 결정에 대해 "선택지를 알려줘" 또는 "어떤 선택이 있나요?"라고 말한 경우
- 의미 있는 트레이드오프가 있는 여러 실행 가능한 접근 방식이 있는 작업(아키텍처, 도구, 마이그레이션 전략)
- 팀이나 이해관계자에게 전달할 수 있는 제안이 필요한 경우

답이 하나뿐인 간단한 질문, 디버깅 세션, 또는 사용자가 이미 접근 방식을 결정한 작업에는 사용하지 마세요.

## 절차

1. **문제**(한 문장)
   - 핵심 결정이나 원하는 결과를 간결한 한 문장으로 말합니다.
   - 방법이 아니라 *무엇*에 집중합니다 — 구현 세부 사항, 도구 이름 또는 특정 기술은 포함하지 않습니다.
   - 짧게 유지합니다. "그리고"가 필요하다면 두 가지 문제를 설명하고 있는 것입니다.

2. **선택지**(정확히 세 가지)
   - A, B, C로 표시한 서로 다르고 실행 가능한 세 가지 접근 방식을 제시합니다.
   - 각 선택지에는 간단한 설명, 장점 및 단점이 있어야 합니다.
   - 선택지는 같은 접근 방식의 사소한 변형이 아니라 실제로 다른 전략을 나타내야 합니다.

3. **추천**(하나의 선택지)
   - 사용자의 맥락과 우선순위에 근거해 추천하는 선택지와 그 이유를 밝힙니다.
   - 직접적으로 말합니다 — 이는 애매한 답이 아니라 전문가로서의 판단입니다.

4. **완료 정의**
   - 추천 선택지의 구체적인 성공 기준을 나열합니다.
   - 모호한 바람이 아니라 구체적이고 검증 가능한 결과여야 합니다.
   - 사용자가 다른 선택지를 고르면 이 부분을 그 선택지에 맞게 수정합니다.

5. **구현 계획**
   - 추천 선택지를 실행하기 위한 구체적인 단계를 제시합니다.
   - 해당되는 경우 구체적인 명령, 도구 또는 작업을 포함합니다.
   - 사용자가 다른 선택지를 고르면 이 부분을 그 선택지에 맞게 수정합니다.

## 검증

- 응답에 문제가 정확히 한 문장으로 작성되어 있습니다.
- 응답에 장단점이 포함된 선택지(A, B, C)가 정확히 세 개 있습니다.
- 추천 항목 하나가 있으며 이유와 함께 하나의 선택지를 고릅니다.
- 완료 정의와 구현 계획이 추천 선택지와 일치합니다.
- 사용자가 다른 선택지를 고르면 추천, 완료 정의 및 구현 계획이 그에 맞게 업데이트됩니다.

## 예시

사용자: "API 클라이언트에 재시도 로직을 추가하는 1-3-1을 작성해줘."

에이전트:

**문제:** 외부 서비스에 대한 API 호출이 부하 상황에서 간헐적으로 실패하므로 우아한 재시도 처리가 필요합니다.

**선택지:**

- **선택지 A: 공유 유틸리티에 지터를 포함한 지수 백오프를 적용합니다.**
  장점: 단순하고 잘 알려진 패턴이며 모든 호출자가 하나의 구현을 공유합니다.
  단점: 서킷 브레이커가 없고 호출자는 재시도 중에도 계속 대기합니다.

- **선택지 B: 각 엔드포인트 호출에 데코레이터로 재시도 라이브러리(tenacity)를 적용합니다.**
  장점: 엔드포인트별로 구성할 수 있고 서킷 브레이커와 속도 제한을 기본 지원합니다.
  단점: 종속성이 추가되고 데코레이터 패턴이 제어 흐름을 가릴 수 있습니다.

- **선택지 C: 데드 레터 처리를 포함한 큐 기반 비동기 재시도입니다.**
  장점: 비차단 방식이며 실패한 호출을 추적하고 재생할 수 있고 확장성이 좋습니다.
  단점: 복잡성이 크게 증가하고 큐 백엔드가 필요하며 저용량 서비스에는 과도합니다.

**추천:** 선택지 A입니다. 호출량이 큐 인프라를 정당화할 정도가 아니며, 지수 백오프와 지터를 적용한 공유 유틸리티가 새로운 종속성 없이 실패 상황을 깔끔하게 처리합니다.

**완료 정의:**
- `api_retry()` 유틸리티가 일시적인 HTTP 오류(429, 502, 503, 504)를 처리합니다.
- 지수 백오프와 지터를 사용해 최대 3번 재시도합니다.
- 모든 외부 API 호출이 재시도 유틸리티를 거칩니다.
- 엔드포인트와 시도 횟수와 함께 각 재시도 시도를 기록합니다.
- 재시도 소진, 즉시 성공, 일시적 실패 후 성공하는 시나리오를 테스트합니다.

**구현 계획:**
1. 구성 가능한 최대 재시도 횟수, 기본 지연 시간 및 재시도 가능한 상태 코드를 포함한 `utils/api_retry.py`를 만듭니다.
2. 폭주를 방지하기 위해 `random.uniform(0, base_delay)`를 사용해 지터를 추가합니다.
3. `api_client.py`의 기존 API 호출을 재시도 유틸리티로 감쌉니다.
4. 각 재시도 시나리오에 대해 HTTP 응답을 모킹하는 단위 테스트를 추가합니다.
5. 오류가 발생하는 엔드포인트 모의 객체를 대상으로 간단한 부하 테스트를 실행해 부하 상황에서 검증합니다.
