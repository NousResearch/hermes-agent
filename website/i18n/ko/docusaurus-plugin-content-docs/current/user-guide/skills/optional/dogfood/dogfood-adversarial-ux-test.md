# 적대적 UX 테스트

제품을 최악의 사용자 관점에서 연기하세요. 기술을 싫어하고, 여러분의 소프트웨어를 원하지 않으며, 불평할 이유를 모두 찾아내는 사람입니다. 그런 다음 피드백을 실용성 계층으로 걸러내 실제 UX 문제와 "나는 컴퓨터가 싫어"라는 잡음을 분리합니다.

자동화된 "엄마 테스트"라고 생각하면 됩니다. 다만 화가 나 있습니다.

## 이 방법이 효과적인 이유

대부분의 QA는 버그를 찾습니다. 이 방법은 **마찰**을 찾습니다. 기술적으로 올바르게 작동하는 앱도 실제 사람에게는 여전히 사용하기 어려울 수 있습니다. 적대적 페르소나는 다음을 포착합니다.

- 개발자에게는 말이 되지만 사용자에게는 혼란스러운 용어
- 기본 작업을 완료하기까지 필요한 단계가 너무 많음
- 온보딩 또는 "아하 순간"의 부재
- 접근성 문제(글꼴 크기, 대비, 클릭 영역)
- 콜드 스타트 문제(빈 상태, 데모 콘텐츠 없음)
- 전환을 망치는 유료 벽/가입 마찰

이 작업을 단순한 재미가 아닌 유용한 것으로 만드는 것은 **실용성 필터**(3단계)입니다. 이 필터가 없다면 할아버지가 PDF 사용법을 이해하지 못한다는 이유로 모든 화면에 "이 페이지 인쇄" 버튼을 추가하게 될 것입니다.

## 사용 방법

에이전트에게 다음과 같이 말하세요.

```
"Run an adversarial UX test on [URL]"
"Be a grumpy [persona type] and test [app name]"
"Do an asshole user test on my staging site"
```

페르소나를 직접 제공하거나, 제품의 대상 사용자에 맞춰 에이전트가 생성하도록 할 수 있습니다.

## 1단계: 페르소나 정의

페르소나가 제공되지 않았다면 다음 질문에 답해 페르소나를 생성하세요.

1. **이 제품에서 가장 어려운 사용자는 누구인가?** (50세 이상, 비기술 직군, 수십 년 동안 "옛날 방식"으로 일해 온 사람)
2. **기술에 얼마나 익숙한가?** (낮을수록 좋음 — WhatsApp만 사용하고, 종이 수첩을 쓰며, 아내가 이메일을 설정해 줌)
3. **이 사람이 반드시 해내야 하는 한 가지는 무엇인가?** (기능 목록이 아니라 핵심 작업)
4. **무엇 때문에 포기할까?** (클릭이 너무 많음, 전문 용어, 느림, 혼란스러움)
5. **답답할 때 어떻게 말하는가?** (직설적임, 욕설을 섞음, 무시하는 말투, 한숨을 쉼)

### 좋은 페르소나 예시
> **"Big Mick" McAllister** — 58세의 S&C 코치. WhatsApp만 사용한다. 그의 "스프레드시트"는 종이 수첩이다. "10초 안에 알아내지 못하면 수첩으로 돌아갈 거야." 선수 25명의 세션 결과를 기록해야 한다. 작은 글씨, 전문 용어, 비밀번호를 싫어한다.

### 나쁜 페르소나 예시
> "앱을 좋아하지 않는 사용자" — 너무 모호하고, 제약 조건도 말투도 없다.

페르소나는 20분 동안 캐릭터를 유지할 수 있을 만큼 **구체적이어야** 합니다.

## 2단계: 개망나니 사용자가 되기(페르소나로 탐색하기)

1. 앱의 맥락과 URL을 파악할 수 있는 프로젝트 문서를 읽습니다.
2. **페르소나를 완전히 체화합니다** — 그 사람의 답답함, 제약, 목표를 느낍니다.
3. 브라우저 도구를 사용해 앱으로 이동합니다.
4. 페르소나의 **실제 작업을 시도합니다**(기능 둘러보기가 아님).
   - 방문 목적을 달성할 수 있는가?
   - 이를 완료하려면 클릭/화면 전환이 몇 번 필요한가?
   - 무엇이 혼란스러운가?
   - 무엇이 화나게 하는가?
   - 어디에서 길을 잃는가?
   - 무엇 때문에 포기하고 예전 방식으로 돌아가겠는가?

5. 다음 마찰 범주를 테스트합니다.
   - **첫인상** — 랜딩 페이지를 지나 계속 사용하려고 할까?
   - **핵심 워크플로** — 가장 자주 해야 하는 한 가지 작업
   - **오류 복구** — 무언가를 잘못했을 때 어떻게 되는가?
   - **가독성** — 글자 크기, 대비, 정보 밀도
   - **속도** — 현재 방식보다 빠르게 느껴지는가?
   - **용어** — 이해하지 못할 전문 용어가 있는가?
   - **탐색** — 돌아가는 길을 찾을 수 있는가? 현재 위치를 알고 있는가?

6. 모든 문제 지점의 스크린샷을 찍습니다.
7. 모든 페이지에서 브라우저 콘솔의 JS 오류를 확인합니다.

## 3단계: 불평하기(캐릭터로 피드백 작성)

**페르소나의 목소리로** 피드백을 작성합니다. 그 사람의 말투와 답답함을 담으세요. 이는 버그 리포트가 아닙니다. 실제 사람이 감정을 쏟아내는 글입니다.

```
[PERSONA NAME]'s Review of [PRODUCT]

Overall: [Would they keep using it? Yes/No/Maybe with conditions]

THE GOOD (grudging admission):
- [things even they have to admit work]

THE BAD (legitimate UX issues):
- [real problems that would stop them from using the product]

THE UGLY (showstoppers):
- [things that would make them uninstall/cancel immediately]

SPECIFIC COMPLAINTS:
1. [Page/feature]: "[quote in persona voice]" — [what happened, expected]
2. ...

VERDICT: "[one-line persona quote summarizing their experience]"
```

## 4단계: 실용성 필터(중요 — 건너뛰지 마세요)

페르소나에서 **벗어나세요**. 제품 담당자의 관점에서 각 불만을 평가합니다.

- **RED: 실제 UX 버그** — 심술궂은 사용자뿐 아니라 누구나 겪을 문제입니다. 수정하세요.
- **YELLOW: 타당하지만 우선순위 낮음** — 실제 문제지만 극단적인 사용자에게만 해당합니다. 기록하세요.
- **WHITE: 페르소나 잡음** — 제품 문제가 아니라 "나는 컴퓨터가 싫어"라는 반응입니다. 무시하세요.
- **GREEN: 기능 요청** — 불만 속에 숨은 좋은 아이디어입니다. 검토하세요.

### 필터 기준

1. 유능하지만 바쁜 35세 사용자도 같은 불만을 가질까요? → RED
2. 진정한 접근성 문제인가요(글꼴 크기, 대비, 클릭 영역)? → RED
3. "종이처럼 작동했으면 좋겠다"는 디지털 방식에 대한 저항인가요? → WHITE
4. 페르소나가 우연히 발견한 실제 워크플로 비효율인가요? → YELLOW 또는 RED
5. 이를 수정하면 괜찮다고 느끼는 80%의 사용자에게 복잡성이 더해질까요? → WHITE
6. 불만이 온보딩에서 빠진 순간을 드러내나요? → GREEN

**이 필터는 필수입니다.** 원시적인 페르소나 불만을 티켓으로 등록하지 마세요.

## 5단계: 티켓 생성

**RED** 및 **GREEN** 항목만 다음과 같이 처리합니다.

- 명확하고 실행 가능한 제목
- 페르소나의 그대로의 인용(재미있고 기억에 남도록)
- 그 아래에 있는 실제 UX 문제(객관적으로)
- 제안하는 수정 방법(실행 가능하게)
- 태그/라벨: "ux-review"

**YELLOW** 항목은 모든 메모를 담은 하나의 종합 티켓으로 작성합니다.

세션당 티켓은 **최대 10개**입니다. 가장 심각한 문제에 집중하세요.

**WHITE** 항목은 보고서에만 표시합니다. 티켓은 만들지 않습니다.

## 6단계: 보고서

다음을 전달합니다.

1. 페르소나의 불평(3단계) — 재미있고 생생하게
2. 필터링된 평가(4단계) — 실용적이고 실행 가능하게
3. 생성된 티켓(5단계) — 링크 포함
4. 핵심 문제의 스크린샷

## 팁

- **세션마다 페르소나는 하나만 사용하세요.** 관점을 섞지 마세요.
- **2~3단계에서는 캐릭터를 유지하세요.** 4단계에서만 캐릭터를 벗어나세요.
- **먼저 핵심 워크플로를 테스트하세요.** 설정 페이지에 정신을 빼앗기지 마세요.
- **빈 상태는 보물입니다.** 신규 사용자 경험에서 마찰이 가장 잘 드러납니다.
- **최고의 발견은 페르소나가 다른 작업을 하다가 우연히 발견한 RED 항목입니다.**
- 페르소나가 불평을 하나도 하지 않는다면 기술에 너무 익숙한 페르소나입니다. 더 나이가 많고, 인내심이 부족하며, 기존 방식을 더 고수하는 사람으로 바꾸세요.
- 데모, 출시 전 또는 기능 묶음을 배포한 후에 실행하세요.
- **가능하면 신규 사용자로 가입하세요.** 미리 데이터가 채워진 관리자 계정을 사용하지 마세요. 대부분의 마찰은 콜드 스타트 경험에서 드러납니다.
- **WHITE 항목이 하나도 없는 것은 실패가 아니라 신호입니다.** 실용성 필터가 잡음을 찾지 못했다면 제품에 심술궂은 페르소나만의 문제가 아닌 실제 UX 문제가 있다는 뜻입니다.
- 테스트 후 프로젝트 문서에서 알려진 문제를 확인하세요. 페르소나가 이미 알려진 문제 목록에 있는 버그를 찾았다면 이는 가장 심각한 발견입니다. 팀이 알고도 사용자의 고통을 체감하지 못했다는 뜻이기 때문입니다.
- **구독/유료 벽 테스트는 중요합니다.** 활성 계정뿐 아니라 만료된 계정으로도 테스트하세요. 결제할 수 없을 때 어떤 일이 일어나는지 살펴보면 제품이 사용자를 존중하는지, 데이터를 인질로 잡는지 알 수 있습니다.
- **페르소나의 한 가지 작업을 완료하는 데 필요한 클릭 수를 세세요.** 5회를 넘으면 페르소나의 기술 수준과 관계없이 거의 항상 RED 발견 사항입니다.

## 업계별 페르소나 예시

다음은 시작점일 뿐입니다. 특정 제품에 맞게 조정하세요.

| 제품 유형 | 페르소나 | 나이 | 핵심 특징 |
|-------------|---------|-----|-----------|
| CRM | 양로원 원장 | 68 | 현재 CRM은 서류 캐비닛 |
| 사진 SaaS | 시골 웨딩 사진작가 | 62 | 전화로 고객을 예약하고 종이에 청구서를 작성 |
| AI/ML 도구 | 백화점 바이어 | 55 | 기술 스타트업 3곳의 실패를 겪음 |
| 피트니스 앱 | 구식 헬스장 코치 | 58 | 종이 수첩, 굵은 손가락, 나쁜 시력 |
| 회계 | 가족 운영 빵집 주인 | 64 | 영수증을 상자에 모아 두며 구독을 싫어함 |
| 전자상거래 | 시장 노점 상인 | 60 | 현금만 사용하며 스마트폰은 전화용 |
| 의료 | 선임 일반의 | 63 | 메모를 받아쓰고 간호사가 컴퓨터를 담당 |
| 교육 | 베테랑 교사 | 57 | 칠판 수업과 워크시트는 링 바인더에 보관 |

## 규칙

- 2~3단계에서는 캐릭터를 유지하세요.
- 진심으로 무례하되 공정하게 행동하세요. 만들어낸 문제가 아니라 실제 문제를 찾으세요.
- 실용성 필터(4단계)는 **필수입니다**.
- 모든 불만에 스크린샷이 필요합니다.
- 세션당 티켓은 최대 10개입니다.
- 로컬 개발 환경이 아니라 스테이징/배포된 앱에서 테스트하세요.
- 한 명의 페르소나, 한 세션, 한 보고서를 사용하세요.
